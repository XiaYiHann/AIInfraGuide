> 原文：[Aegaeon: Effective GPU Pooling for Concurrent LLM Serving on the Market](https://dl.acm.org/doi/10.1145/3731569.3764815)（Yuxing Xiang, Xue Li, Kun Qian 等，SOSP 2025,16 页；本文访问日期 2026-08-15）

模型市场（如 Hugging Face、阿里云 Model Studio）上有成千上万个模型，但**绝大多数请求集中在少数热门模型上，长尾模型调用稀疏得可怜**：论文观测到超过 90% 的模型属于低频长尾，而17.7% 的 GPU 只服务了 1.35% 的请求（平均每 GPU 每秒不到 0.2 个请求，§1,Fig.1a）。给每个模型单独预留 GPU 是巨大的浪费；而现有的多模型共享方案（GPU 复用与 serverless）每张卡最多只能放 2-3 个模型。Aegaeon 的答案是 token 级自动扩缩容（token-level auto-scaling）：不等一个请求完全结束才换模型，而是在每个 token 的粒度上决定“哪个模型继续跑、哪个模型换下去”，配合抢占式调度与把扩缩容开销削减 97% 的工程优化（组件复用、显式内存管理、细粒度 KV cache 同步，§5）。效果：相对 ServerlessLLM/MuxServe 支撑 2-2.5× 更高的请求到达率或 1.5-9× 更高的 goodput，一张 GPU 同时服务最多 7 个模型（§7.2）；生产部署把模型服务的 GPU 从 1192 台降到 213 台（82% 节省）（§7.5）。本文先建立“长尾市场负载”的直觉，再拆“为什么请求级扩缩容不行”的定理证明、token 级调度与三项工程优化，最后核对评测与生产数字。

## 0. 读前 3 分钟：两组直觉

**第一组：模型市场是“头部爆挤、长尾冷清”的幂律分布。** 少数热门模型（DeepSeek、Llama、Qwen）请求源源不断，偶尔还来一波突发；而绝大多数模型一天没几个请求。给每个模型都预留 GPU = 大量 GPU 空转；把 GPU 池化共享 = 要频繁换模型进显存，换模型很慢（加载权重、初始化引擎、搬 KV cache）。问题就变成：换得够快吗？什么时候换？

**第二组：换模型的最小粒度决定了你能省多少。** 请求级方案：一个请求来了 → 加载它的模型 → 算完整个请求 → 换下一个模型。请求还没结束，模型就不能换——而 LLM 请求可能持续几十秒。如果“算一个 token 的时间”内就能完成换模型，那每个 token 之间都可以决定换不换——这就是 token 级扩缩容：在满足 SLO 的前提下，把“正在跑的模型”抢占换下，让“新请求的模型”上来。粒度越细，GPU 空闲越少。

## 1. 问题：模型市场的长尾与热点并存

**数据（§1,Fig.1）**：

- **长尾**：超过 90% 的模型调用稀疏；17.7% 的 GPU 只服务 1.35% 的请求（每 GPU 平均 <0.2 req/s）；
- **热点**：热门模型会突发（Fig.1b），按峰值预留 GPU 同样浪费；
- **优化空间**：若所有请求都来自同一模型，典型单 GPU 可达每秒数个请求——论文估算现有部署有 超过 10× 的优化空间（§1）。

**现有方案的局限（§1）**：静态复用（MuxServe 那类时间/空间共享）受显存容量硬限制——80GB GPU 只能放 2 个 14B FP16 模型，每卡最多 2-3 个模型；serverless auto-scaling（ServerlessLLM 等）从 CPU 内存/SSD 加载模型，突破了显存限制，但在请求粒度上扩缩容——下一节证明这被活跃模型数卡死。

## 2. 为什么请求级扩缩容被卡死：活跃模型数定理

**核心概念**：活跃模型 = 至少有一个正在服务的请求的模型。请求级扩缩容下，GPU 数量必须 ≥ 活跃模型数（每个活跃模型至少要占一块 GPU 的完整时间片），否则新请求要等“正在服务的模型跑完”才有位置（head-of-line blocking，队头阻塞）。

**定理（§3.1,Theorem 3.1,证明在 Appendix A.1）**：每个模型的请求到达服从泊松过程（速率 λ），平均服务时间 T，则 M 个模型中活跃模型数的期望：

$$E[m] = M \cdot (1 - e^{-\lambda T})$$

逐项解释：$e^{-\lambda T}$ 是“过去 T 时间内没有请求到达”的概率（泊松过程）；$1 - e^{-\lambda T}$ 是“至少有一个请求在服务”的概率；乘以 M 就是期望的活跃模型数。**关键**：T 是 LLM 请求的服务时间——几十秒量级——所以即使 λ 很小，$1 - e^{-\lambda T}$ 也明显大于 0。

**数字例子（§1）**：总到达率只有 3.7 req/s 时（M=100 模型均分，λ=0.037），期望活跃模型数 = 100 × (1-e^{-0.037×T})。按论文报告的 46.55 个活跃模型反推（T≈17.4s 量级），请求级方案需要 ≥47 块 GPU 的容量，每 GPU 服务模型数 = 100/46.55 < 3——这就是“请求级扩缩容每卡最多 3 个模型”的理论根源。论文 Fig.2 对比：请求级（a）模型 A 一直占着 GPU 直到请求结束，新模型 B 的请求排队等；token 级（b）A 的 token 间隙里 B 就能上来。

**直觉总结**：请求越长（T 越大），同一时刻“活着”的模型越多，请求级方案越没用。 LLM 请求恰恰很长——这是 LLM 时代特有的问题。

## 3. 核心机制：token 级调度

**要解决什么（Challenge #1,§1,§4）**：在 token 粒度做扩缩容决策，需要同时考虑“每个 token 的执行时间”与“换模型的开销”，还要满足不同的每 token SLO——最优解实时不可解，纯启发式又难兼顾。

**Aegaeon 的两阶段调度（§1,§4）**：prefill 与 decode 分阶段调度（沿用 PD 解耦，站内 [splitwise-notes](/AIInfraGuide/papers/splitwise-notes)）：

- **prefill 阶段——分组 FCFS（grouped first-come-first-serve）**：目标是压 TTFT（首 token 延迟）。同组模型按先来先服务排队，减少换模型次数；
- **decode 阶段——加权轮转（weighted round robin）**：目标是压 TBT 违规数（时间戳间延迟）。在多个活跃模型之间按权重轮流分配时间片，让每个模型的 token 都能在 SLO 内产出。

**抢占式扩缩容（§1,Fig.2b）**：调度器在 token 间隙“预判”下一个需要上来的模型并提前换入（preemptive scaling）：主动把活跃模型换下（KV cache 换出到 CPU 统一缓存），把等待中的模型换上来（权重从模型缓存加载）。这要求换模型足够快——下一节的三项工程优化就是为了让“换模型”从几十秒降到亚秒。

## 4. 工程攻坚：把扩缩容开销砍掉 97%

**未优化的初始化有多慢（§5.1）**：引擎初始化（调度器、profiling、KV cache 分配决策）可能花数秒；加载 LLaMA-13B 权重经 PCIe 4.0 实测约 4.6 秒（实际带宽仅 2.83 GB/s，远低于理论 32 GB/s）；KV cache 的 CPU 内存页锁定初始化又要几秒。合计：一个 13B 模型未优化的扩缩容最多 26.9 秒——这显然没法做 token 级调度。

**优化一：组件复用（§5.1,Fig.8a）**：引擎与 worker 每实例只初始化一次，把除“模型权重 + KV cache”外的所有组件（tokenizer、profiling 结果、调度器）缓存复用；KV cache 用预分配内存池（配合优化二），省掉页锁定。效果：去掉超过 80% 的扩缩容延迟（T₀ → T₁）。

**优化二：显式内存管理（§5.2,Fig.9）**：

- **自管理 VRAM 缓冲**：启动时一次性向张量库申请所有权重 + KV cache 所需显存（留约 10% 给激活等中间结果），用 bump allocation（指针递增分配、复位即释放）——绕开 PyTorch 缓存分配器的碎片与垃圾回收（gc.collect 可能耗时数秒）；
- **快速模型加载**：共享主机内存里的 Model Cache（论文示例 640GB）缓存权重原始张量；每 GPU 配专用页锁定 Stage Buffer,多线程分块流水化拷贝——模型在缓存中时加载 1 秒以内;还可按 token 级调度在独立 CUDA stream 上预取下一个模型（显存够时直接分配在运行模型之后，换入时一次廉价片上拷贝）；
- **统一 KV cache（slab 分配）**：不同模型 KV cache 形状不同（Table 1:Qwen-7B 每 token 512KB、LLaMA-13B 800KB、Qwen-72B 2560KB），按形状分 slab 池分配，碎片率控制在 20% 以下（§7.3,Fig.16）。

**优化三：细粒度 KV 同步（§5.3,Fig.10,Table 2）**：KV cache 换入/换出用独立 CUDA stream 异步执行，用 CUDA event 做细粒度同步（cudaEventRecord/Query/StreamWaitEvent + IPC 跨实例共享）。三条数据依赖规则（❶推理需要 KV 在 GPU；❷新传输要等源块上次传输完成；❸目标块不能被正在进行的传输占用）用 move lists（活跃传输块清单）从关键路径上移除规则❸。效果：总扩缩容延迟从 T₀ 降到 T₃,减少高达 97%,实测亚秒级（§5.3,§7.3,Fig.15）。

## 5. 评测：7 个模型/卡与 82% 节省

**实验设置（§7.1）**：2 节点 16 块 H800 80GB（NVLink、2TB DDR5、192 核 Xeon）；模型以 6B-14B 为主（市场主流）；ShareGPT 及输入/输出加倍的变体；SLO：TTFT 10s、TBT 100ms（也测更严的 2s/20ms）。基线：ServerlessLLM（+ 带 oracle 的 SJF 变体 ServerlessLLM+）、MuxServe。

**端到端（§7.2,Fig.11-13）**：

- **RPS=0.1**：Aegaeon 支撑 2× 更高 goodput;最多 70 个模型、10 个 decode 实例 = 7 个模型/卡;ServerlessLLM 因跨模型排队 SLO 崩；
- **RPS=0.5**：2.5× 更高请求率（队头阻塞在高负载下更严重）；
- **替代数据集**：输出更长时最高 2.5× goodput;
- **更严 SLO**（0.5×/0.3×/0.2×）：前两档 Aegaeon 仍多支持 50%/12.5% 的模型；最严档（2s/20ms）与静态复用 MuxServe 打平——SLO 越严，可池化空间越小;
- **有效性拆解（§7.3,Fig.14-16）**：约 50% 场景扩缩容近即时（预取命中），其余亚秒；每请求 KV 同步开销 <1 秒；碎片 <20%;
- **敏感性（§7.4,Fig.17）**：4×A10 低端节点与 72B 大模型（TP4,8×H800）同样有效。

**生产部署（§7.5,Fig.18）**：阿里云 Model Studio beta 部署——213 台 H20 GPU 服务 28 个 1.8-7B 模型（TP=1）+ 19 个 32-72B 模型（TP=4），到达率 0.01-1.13 req/s（均值 0.037）；这些模型原本用 1192 台 H20 GPU——82% 资源节省;GPU 利用率从平均 13.3%-33.9% 提升到 48.1%（70 小时观测，无 SLO 违规）。

## 6. 与已有系统的关系

- **与 Orca/vLLM（[orca-notes](/AIInfraGuide/papers/orca-notes)）**：Orca 解决“同模型多请求”的批处理；Aegaeon 解决“多模型共享 GPU”的编排——Aegaeon 直接用 vLLM 做模型执行后端（§6），在其之上加调度与扩缩容；
- **与 Splitwise/Mooncake（[splitwise-notes](/AIInfraGuide/papers/splitwise-notes)）**：PD 解耦是 Aegaeon 的前提之一（prefill/decode 分实例，§4）；Mooncake 的“缓存池”思路与 Aegaeon 的“模型/缓存加载”同源，但目标不同（单模型长上下文 vs 多模型市场）；
- **与 PagedAttention（[pagedattention-notes](/AIInfraGuide/papers/pagedattention-notes)）**：分页解决“单模型内 KV cache 的碎片与共享”；Aegaeon 的 slab 分配解决“跨模型不同 KV 形状的碎片”——层递关系：分页管块内，slab 管跨形状；
- **与 ServerlessLLM**：同为 serverless 路线，Aegaeon 的差异在粒度（token vs 请求）与抢占（主动换下 vs 等请求结束）。

## 🕰️ 原文时代 vs 当前工程

Aegaeon 论文（SOSP 2025-10）本身就是“正在进行中的生产系统”（§7.5:beta 部署 3 个月以上）。2026 年 8 月复核（来源标注如下）：

- **论文自述**：部署已覆盖 Model Studio 的混合并行配置（TP1/TP4 多套 Aegaeon 实例，§7.5）；作者称有计划扩展到更多实例与更大集群——截至访问日期，后续公开数据未见（「待核实」）,读者应以论文 §7.5 为基线；
- **代码状态**：论文未提供官方开源仓库（§6 仅描述实现），「待核实」；
- **同主题进展**：多模型 GPU 池化是 2025-2026 年的活跃方向（BlitzScale、ParaServe 等 serverless 加载优化持续出现，论文 §8 引用了 2025 年的相关工作），Aegaeon 的“token 级抢占”定位仍是独树一帜的。

**结论边界**：论文的“7 个模型/卡”与“82% 节省”都是在特定负载画像（稀疏长尾 + 突发热点、6B-72B 模型混合）下测得的；对“请求密集均匀”的传统负载（如单一大模型高并发），池化收益本来就小（论文 Fig.13c 最严 SLO 下与 MuxServe 打平也说明边界）。SLO 越严、负载越密集，这套方案的相对优势越小——这是选型时最重要的边界。

## 7. 常见误读与错误做法

- **误读 1：“Aegaeon 是又一种模型复用（multiplexing）方案。”** 错。静态复用受显存限制（每卡 2-3 个模型，§1）；Aegaeon 是抢占式 auto-scaling,通过快速换模型突破显存限制（每卡 7 个）。两者机制不同，论文还把 MuxServe 当基线对比（§7.1）。
- **误读 2：“扩缩容快 = 只优化权重加载。”** 错。论文实测未优化初始化 26.9 秒里，权重加载只是一部分——引擎初始化、KV cache 页锁定、profiling 都很贵（§5.1）；三项优化（组件复用/显存管理/KV 同步）缺一不可，97% 的削减是三者的合力。
- **误读 3：“82% GPU 节省可以平移到任何多模型集群。”** 错。这是 Model Studio 特定负载（到达率均值 0.037 req/s 的稀疏流量，§7.5）下的结果；负载越密集，可池化空间越小（论文自己指出 §7.2/7.4 的边界）。
- **错误做法 1（选型）**：给“强 SLO + 密集负载”场景硬上 token 级抢占。论文 Fig.13c 显示最严 SLO（2s TTFT/20ms TBT）下 Aegaeon 与静态复用打平——静态复用在该场景仍有位置（§7.2 原文：无扩缩容成本）。
- **错误做法 2（复现）**：用预取模型时就以为换模型零成本。预取只在显存充足时有效（论文 §5.2：显存不够就禁用，如 A10 场景 Fig.17）；不预取时换模型仍有亚秒级开销，KV 同步仍要按规则 ❶❷❸ 处理数据竞争。

## 📝 总结

1. **模型市场的长尾让“每模型预留 GPU”浪费巨大**（17.7% GPU 服务 1.35% 请求）；请求级 auto-scaling 被活跃模型数定理卡死（$E[m] = M(1-e^{-\lambda T})$,请求越长越糟，每卡 <3 模型）。
2. **token 级抢占是破局点**：prefill 分组 FCFS + decode 加权轮转 + 主动换模型；而让“换模型”可行的是三项工程——组件复用（去 80%）、显式内存管理（自管理缓冲 + 模型缓存 + slab 统一 KV）、细粒度 KV 同步（CUDA event + move lists），合计削减 97% 开销到亚秒。
3. **实测与生产**：每卡 7 模型、2-2.5× 请求率/1.5-9× goodput、1192→213 GPU（82% 节省）、利用率 13.3-33.9% → 48.1%——但收益依赖稀疏负载，强 SLO 密集场景仍是静态复用的主场。
