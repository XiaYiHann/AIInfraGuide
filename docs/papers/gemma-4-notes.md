## 1. Gemma 是谁:开源家族的定位

**Google DeepMind 为什么同时维护两条模型线?** 一条是闭源的 Gemini 旗舰——追求上限,不开放权重;另一条就是 Gemma(拉丁语"宝石"),2024 年 2 月首发的**开源轻量家族**,主打"小规模、可自部署、Apache 2.0 许可",服务端侧设备、自托管和研究社区。Gemma 4 报告在开篇就把定位说得直白:模型套件"built to serve a variety of on-device hardware"(为各类端侧硬件而建),并强调开放生态("empowering developers and researchers everywhere")。

家族谱系(报告引用的前作):

| 代际 | 发布时间 | 特点 |
|---|---|---|
| Gemma 1 | 2024 | 文本为主,2B/7B |
| Gemma 2 | 2024-06 | 实用尺寸下的质量提升 |
| Gemma 3 | 2025-03 | 引入多模态与长上下文 |
| Gemma 3n | 2025 | 逐层嵌入(PLE)、端侧优化 |
| **Gemma 4** | **2026-07** | 原生多模态 + thinking 模式 + 长上下文 + 效率四件套 |

**这一代要解决的问题是什么?** 报告引言归纳为三件事的叠加:**强多模态理解、强推理、高计算效率**,而它们都要装进 2.3B–31B 这种"小"体量里。上一代 Gemma 3 27B 在多模态和推理上已经有了基础,但 Gemma 4 的目标是把"会看图听音、会先思考再回答、能读 256K 上下文、量化后能上手机"四件事塞进同一组模型——这就是本报告所有设计决策的出发点。

## 2. 模型家族:密集与 MoE 两条线、五个档位

**先看全局:这一代一共五个模型,走两条技术路线。**

- **稠密路线(Dense)**:E2B、E4B、12B、31B——每个 token 都经过全部参数。
- **MoE 路线**:26B-A4B——总参数 26B,但每个 token 只激活 3.8B。

> 打个比方:稠密模型像一家全员参与的公司,每个项目(每个 token)都把全体员工叫上,人多但每次都全员出勤;MoE 像项目制外包——公司档案库里躺着 26B 人的简历(总参数),但每个项目只抽调 3.8B 的团队进场(激活参数),干活快,可档案库本身还得整个带着。所以 MoE 的代价是**权重占用的存储/显存一分不少**,换来的是**单 token 的计算量大幅下降**。

表格数据来自报告 Table 1、§2 与 HF 官方模型卡(两处口径有细微出入,见 💡 提示):

| 模型 | 架构 | 有效/总参数 | 层数 | 滑窗大小 | 上下文 | 视觉编码器 | 音频编码器 | 量化后权重 | 来源口径 |
|---|---|---|---|---|---|---|---|---|---|
| E2B | 稠密 | 2.3B / 5B(逐层嵌入) | 35 | 512 | 128K | 150M ViT | 305M | 0.8GB(mobile 量化) | 报告 Table 1/3 + HF 模型卡 |
| E4B | 稠密 | 4.5B / 8B(逐层嵌入) | 42 | 512 | 128K | 150M ViT | 305M | 2.3GB(mobile 量化) | 同上 |
| 12B | 稠密、无编码器 | 11.95B | 48 | 1024 | 256K | 无(35M 投影) | 无(直投) | 7.65GB(Q4_0) | 同上 |
| 26B-A4B | MoE | 26B / 3.8B 激活 | 30 | 1024 | 256K | 550M ViT | 无 | 16.2GB / 2.8GB(Q4_0) | 同上 |
| 31B | 稠密 | 30.7B | 60 | 1024 | 256K | 550M ViT | 无 | 19.2GB(Q4_0) | 同上 |

📌 **关键点**:这代家族不是"一个架构缩放五份",而是**两套参数哲学并存**——E2B/E4B 用逐层嵌入压缩"有效参数",12B 用无编码器统一多模态,26B-A4B 用 MoE 换吞吐,31B 用最传统的稠密大模型打质量上限。选型时先想清楚你的瓶颈是显存、吞吐还是质量。

**两个必须补的定义:**

- **有效参数 vs 总参数(Per-Layer Embeddings,PLE)**:E2B/E4B 的每个解码器层都有自己的小嵌入表(embedding table),只做查表、不参与矩阵乘,所以"总参数"虚高(5B/8B),真正干活的是"有效参数"(2.3B/4.5B)。打个比方:每层楼都放一本自己的员工花名册,查人快,但楼多了花名册总量不小——参数总量大,推理时真正参与计算的却少。这个设计继承自 Gemma 3n。
- **激活参数(Active Parameters)**:MoE 模型里,每个 token 经路由器(router)只唤醒一部分专家。26B-A4B 的专家配置是 **8 个激活 / 128 个总专家 + 1 个共享专家**(HF 模型卡披露),"4B"指激活量。A4B 的"A"就是 Active。

💡 **提示**:报告 Table 1 把 26B-A4B 总参数记为 26B(其中主干 einsums 24.5B 总 / 2.8B 激活),HF 模型卡写 25.2B——两者相差约 0.8B,是"总参数"的口径差异(是否计入嵌入层等),不是错误。报告里用 "einsums" 一词指代主干 Transformer 的矩阵乘法参数,这是参数账本的内部口径。

## 3. 架构设计:为长上下文和显存而生的四个决定

**骨架很常规**:decoder-only Transformer,pre-norm + post-norm 双 RMSNorm(均方根归一化),外加 QKNorm(查询-键归一化)。真正值得读的是四个为"长上下文 + 省显存"做的设计决定。

### 3.1 局部滑窗 + 全局注意力混合

**问题是:全注意力(每个 token 看全部历史)在长上下文下,计算和 KV Cache 都随序列长度线性膨胀,小模型扛不住。怎么办?**

**答案:大部分层只看"最近一段",少数层看全部。** 报告采用局部滑窗注意力(local sliding window attention)与全局注意力(global attention)按比例交错:局部层只能看到自己往前 512 或 1024 个 token 的窗口(见家族表),全局层看整个序列;比例是 **5:1(除 E2B 为 4:1)**,且最后一层保证是全局层(HF 模型卡),让模型永远保有"全视野出口"。

> 这像开会:大部分讨论小组只跟邻座交流(局部层),但每个环节都留一个"全场广播"席位(全局层),保证任何信息最终都能传到全场。

### 3.2 pp-RoPE:部分旋转位置编码

**位置编码怎么省 KV Cache?** 报告在全局注意力层用 **pp-RoPE,参数 p=0.25**,局部层用普通 RoPE;全局层频率设为 1M(百万级波长,支撑长距离位置信息),局部层 10k。报告称仅此一项"有效减少全局 KV Cache 37.5%"(§2),而引言把 37.5% 归因于 pp-RoPE + KV 共享 + 键值复用三项合计("reduce the global KV cache footprint by up to 37.5%")——两处表述的归因口径不完全一致,这里以引言口径为准:三项叠加,最多省 37.5%。

**pp-RoPE 是什么?** 它出自 Barbero et al.(ICLR 2025,《Round and Round We Go!》):作者解剖 Gemma 7B 后发现,RoPE 的高频分量被模型用来构造"位置注意力头",低频分量被当作"语义通道";于是提出 p-RoPE——**砍掉最低频的一批旋转维度(占比 p),让这些维度不再参与旋转**。p=0.25 即只保留 75% 维度的旋转。Gemma 4 是首个把这个想法大规模用进全局注意力层的开源旗舰家族。

### 3.3 键值复用与 KV Cache 共享

**KV Cache 还能怎么省?** 两个手段(12B/26B-A4B/31B 生效):

- **values = keys(键当值用)**:全局注意力层直接复用 key 作为 value,省掉一半 value 的存储和计算。报告明确说 **E2B/E4B 不用这个技巧**——小模型没有这个容量余量,这是"代价"意识:省显存有损自由度。
- **KV Cache 共享(KV sharing)**:E2B/E4B 则采用共享比例 **20/35 与 18/42**(即部分层的 KV Cache 互相共用),同样压缩缓存总量。

### 3.4 MTP Drafter:为投机解码准备的草稿头

**投机解码(Speculative Decoding)需要一个小模型先"打草稿",但额外部署一个草稿模型又费存储,怎么办?** 报告的方案是 MTP(多 token 预测)Drafter 头:**一个小型 Transformer 块直接挂在主模型最后一层激活上**(4 层:3 局部 + 1 全局注意力),cross-attend 主模型的 KV Cache,用独立的小嵌入表逐个预测未来 token。好处是**不需要单独的草稿模型、不需要 MTP 预填充、草稿长度任意**。对 E2B/E4B,草稿头最后的词表投影从 $d \times 262{,}000$ 压到 $d \times 4{,}096$(对 token 聚类做 top-k),输出维度缩到约 1/64,"在保持相近接受率的前提下"省掉该投影矩阵约 98% 的计算量。

### 3.5 KV Cache 账本

**这些优化省下的到底是多少?** 报告 Table 3 给了 32k 上下文下的显存账本(来源:报告 Table 3):

| 模型 | bf16 权重 | 量化后权重 | + int8 KV Cache(32k) | 来源口径 |
|---|---|---|---|---|
| E2B | 4.6 GB | 0.8 GB(mobile 量化) | +0.05 GB | 报告 Table 3 |
| E4B | 9.0 GB | 2.3 GB(mobile 量化) | +0.14 GB | 同上 |
| 12B | 24.0 GB | 7.65 GB(Q4_0) | +0.28 GB | 同上 |
| 26B-A4B | 52.0 / 7.6 GB | 16.2 / 2.8 GB(Q4_0) | +0.28 GB | 同上 |
| 31B | 64.0 GB | 19.2 GB(Q4_0) | +1.10 GB | 同上 |

📌 **关键点**:31B 在 32k 上下文时,int8 KV Cache 只有 1.10GB——混合注意力 + pp-RoPE + 键值复用把长上下文的显存增长压到了"可接受"档位;而 E2B 全套(权重 + KV)不到 1GB,这就是"上手机"的底气。⚠️ 注意:表里 KV 是 32k 上下文的口径,256K 时会按比例放大(31B 层数多、每层 KV 大,长上下文仍是它最吃显存的地方)。

## 4. 原生多模态:编码器路线与无编码器路线

**"原生多模态"指什么?** 不是外挂一个视觉问答插件,而是从预训练起,文本、图像、音频就走同一条 Transformer 主干。这一代有两个方案:**小模型用"编码器 + 投影"的经典路线,12B 走全新的"无编码器"路线**。

### 4.1 视觉:两代 ViT 编码器 + 可变分辨率

E2B/E4B 带 **150M** 的 ViT(Vision Transformer)视觉编码器,26B-A4B/31B 带 **550M**;patch size 16。两个细节值得记:

- **非因果 + 轴向 2D-RoPE**:视觉编码器里的注意力不做因果掩码(图像没有"过去/未来"),位置用轴向 2D-RoPE(分别编码行、列)叠加 2D 绝对位置嵌入——让模型知道"这个 patch 在图片的哪个坐标"。
- **可变分辨率预算**:一张图转成多少视觉 token 是**可配置的**,支持 70 / 140 / 280 / 560 / 1120 五档(HF 模型卡建议:低档给分类、视频抽帧,高档给 OCR、文档解析)。报告给了保长宽比的缩放算法(Algorithm 1),核心是三步:先按目标 token 预算反推缩放因子 → 把宽高向下取整到 pooled patch 尺寸的整数倍 → 双三次插值缩放。翻译成伪代码(报告 Algorithm 1 的转述):

```python
# 输入:图像 I(H×W×C),patch 尺寸 p,最大 token 数 N_max,池化核 k
m = k * p                    # 池化后的 patch 尺寸(如 3×16 = 48px)
T = N_max * m * m            # 目标像素预算
f = sqrt(T / (H * W))        # 理想缩放因子:让像素总数 ≈ 预算
H_target = floor(H * f / m) * m   # 向下取整到 m 的整数倍(保长宽比)
W_target = floor(W * f / m) * m
I_resized = BicubicResize(I, H_target, W_target)
```

💡 **提示**:这个算法的目的是"**保长宽比 + 精确卡预算**"——不做粗暴的居中裁剪,高图、宽图都不会被压变形,同时保证视觉 token 数不超预算,推理显存可预测。

### 4.2 音频:305M 的 USM 编码器(E2B/E4B/12B)

音频编码器基于 Google 的 **USM(Universal Speech Model)**:2 层下采样卷积 + 12 层 Conformer(卷积增强的 Transformer),输入是 40ms 一帧的 Mel 滤波器组特征,**不做向量量化(VQ),直接把连续表示喂给 LLM**,预训练期间编码器权重冻结。相比 Gemma 3n 的 680M,**参数减少 55%(到 305M)**,且量化后磁盘占用从 390MB 降到 87MB(见第 5 节)。

### 4.3 12B 无编码器路线:取消翻译官

**为什么可以不要编码器?** 传统路线里,视觉编码器把图像"翻译"成 LLM 能懂的 token 序列,音频编码器把声音"翻译"成特征——两个翻译官各占几百 M 参数,还制造内存碎片(多个模型组件的生命周期不同)。12B 的思路是:**取消翻译官,让原始素材直接进会场**。

> 打个比方:以前开多语种会议要配两个翻译官(编码器),翻译官贵、还各有各的毛病;12B 的做法是直接让与会者用各自语言发言,由主持人(LLM 主干)自己消化——省了翻译官,也省了"翻译质量"这个不可控环节。

具体实现(报告 §2.3,全部为报告数字):

- **图像**:输入 **48×48×3 的 RGB patch**,用**一个 35M 参数的大矩阵乘法(matmul)**替代 550M 的 ViT;空间位置靠**2D 坐标位置嵌入**直接加到 patch 表示上,最后过一层 LayerNorm。
- **音频**:16kHz 采样率下每 **40ms** 切成一块,得到 **640 维**向量,直接投影进 LLM 嵌入空间;音频是时间序列,天然有序,**不需要位置编码**。
- 整条链路只剩一个模型,报告称可缓解**内存碎片**,且整个模型可以**单次端到端微调**(HF 模型卡:all modalities flow straight into a single decoder-only transformer)。

**这条路划算吗?** 用数据说话:12B 无音频编码器,在 FLEURS ASR 英语 WER 0.063、CoVoST 德→英 41.9、俄→英 50.5(报告 Table 8),报告原话是"without a dedicated audio encoder, competitive audio-text performance"(没有专用音频编码器也能拿到有竞争力的音文表现)。视觉上 12B 比带 550M 编码器的 31B 低一档(如 MMMU Pro 69.1 vs 76.9),但这里混入了参数量差异,不能直接归因于"无编码器"——报告的对比口径是"模型整体",不是消融实验。⚠️ 报告没有给出"同参数量下有/无编码器"的对照,严格说这条路线与经典路线的净差,报告未完整回答。

### 4.4 与站内 VLM 知识的衔接

站内 [8.4 多模态推理 VLM](/AIInfraGuide/inference/模块四-推理优化/第8章-生产级服务特性/84-多模态推理vlm)讲过:VLM 推理的成本大头是视觉 token 撑爆 KV Cache、以及编码器与 LLM 的调度耦合。Gemma 4 的两条路线正好是对这两个问题的回应——**token 预算档位(70–1120)就是"视觉成本旋钮",无编码器路线则把多模态服务简化成单模型部署**。

## 5. 训练:数据、算力与效率设计

### 5.1 数据与分词器

- **预训练数据**:大规模多领域混合,含网页文本、代码、图像、音频(E2B/E4B/12B 含音频),**截止日期 2025 年 1 月**;覆盖 140+ 语言(模型卡:开箱 35+ 语言,预训练 140+)。过滤管线做三件事:基准去污(decontamination)、降低有害/不安全内容风险、降低"背诵"(recitation)风险。
- **分词器**:与 Gemini 2.5 同款 SentencePiece,词表 **262k**,拆分数字、保留空白、byte-level 编码。全家共享同一个分词器,只靠控制 token 区分预训练/指令微调格式。

### 5.2 算力与弹性

报告 Table 2 给出训练基础设施(来源:报告 Table 2):

| 模型 | TPU 型号 | 芯片数 | 数据分片 | 序列分片 | 副本数 |
|---|---|---|---|---|---|
| E2B | v6e | 4,096 | 16 | 8 | 32 |
| E4B | v6e | 6,144 | 16 | 16 | 24 |
| 12B | **v4** | 12,288 | 16 | 16 | 48 |
| 26B-A4B | v6e | 6,144 | 16 | 16 | 24 |
| 31B | v6e | 10,240 | 16 | 16 | 40 |

值得注意的工程细节:

- **Slice-Granularity Elasticity**:大规模训练中某片 TPU 故障时,不必整体停摆——用更少的"slice"继续训练,把中断延迟从**几分钟压到几秒**。这是从 Gemini 2.5 继承的故障弹性技术。
- 优化器状态用 **ZeRO-3** 分片(站内 [ZeRO 系列](/AIInfraGuide/distributed/模块三-分布式训练/第5章-zero系列)同源技术);跨 pod 用 Pathways 做数据副本归约;编译栈为 JAX 单控制器 + GSPMD 分区器 + MegaScale XLA 编译器。

⚠️ **报告未公开的内容**:全文没有出现 "distill" 一词——**与 Gemini 旗舰的蒸馏关系,报告只字未提**,只写"沿用与 Gemma 3 类似的预训练配方"。Gemma 2 时代 Google 公开过"蒸馏自 Gemini 2.0"的做法,但**不要因此推断 Gemma 4 也蒸馏了 Gemini**——报告没有说,这就是"未公开"。

### 5.3 后训练:thinking 模式与数据策略

- **Thinking 模式**:模型先输出一段推理轨迹(reasoning trace)再给最终答案,报告称在数学、代码等推理密集任务上显著提升。激活方式很朴素:system 提示里加 `<|think|>` 控制 token 即开启;推理轨迹包在 `<|channel>thought…<channel|>` 里,函数调用用 `<|tool>declaration` / `<|tool_call>call` 标记。**它是个开关——不想要推理开销可以关掉**(HF 模型卡:E2B/E4B 关闭后不再吐 thought 块,其他模型会输出空 thought 块)。
- **数据过滤**:过滤个人信息、有毒输出、错误自我身份识别、重复样本;特意加入鼓励**上下文归因(in-context attribution)、对冲性表述(hedging)与拒答**的数据子集,报告称这在不掉其他指标的前提下改善了事实性。

### 5.4 量化感知训练(QAT)

**量化通常掉点,怎么让掉点最小?** 答案是让模型"在训练时就习惯低精度"——量化感知训练(QAT)。报告给两种格式:

- **mobile 量化**:逐通道低比特权重(int2/int4 混合)+ int8 激活,面向端侧;
- **Q4_0**:块级量化(即 llama.cpp 生态的 Q4_0),面向通用推理引擎。

配套两个细节:每个 block 加一个**标量缩放**把激活范围钳制进 fp16 稳定区间;编码器也做 QAT——150M 图像编码器 W8A8(权重激活各 8bit)后,前向显存从 400MB 降到 200MB(2 倍),端侧延迟相对 Gemma 3n **降 44%**;音频编码器权重按层簇混合 {2,4,8}bit,磁盘占用从 390MB 降到 **87MB(-78%)**(以上均为报告数字)。

## 7. 部署视角:小参数多模态的端侧与低成本路线

**这一代的部署故事,就是"一个模型五档配置,从手机铺到服务器"。** 结合报告 Table 3 与 HF 模型卡,部署选型可以这样看:

| 场景 | 推荐模型 | 权重占用 | 理由 | 来源口径 |
|---|---|---|---|---|
| 手机 / 端侧 | E2B(mobile 量化) | 0.8GB(+KV 0.05GB@32k) | 全套不到 1GB,原生音频+图像 | 报告 Table 3 |
| 笔记本电脑 | E4B | 2.3GB | 端侧延迟比 3n 降 44%(150M 编码器 W8A8) | 报告 §2.5 |
| 消费级 GPU | 12B(Q4_0) | 7.65GB | 无编码器、单模型部署、256K 上下文 | 报告 Table 3 |
| 高吞吐服务 | 26B-A4B(Q4_0) | 16.2GB(权重)+ 2.8GB(激活相关) | 激活仅 3.8B,推理"几乎与 4B 模型一样快"(HF 卡原话) | 报告 + HF 卡 |
| 质量优先 | 31B(Q4_0) | 19.2GB | Arena 1451,开源稠密第一 | 报告 Table 3/4 |

**部署侧的三个"成本旋钮"**(全部有官方依据):

1. **视觉 token 预算**:70 → 1120 五档,低档省算力、高档保细节(HF 模型卡:OCR/文档解析用高档,分类/视频抽帧用低档)。
2. **Thinking 开关**:`<|think|>` 控制,关掉省推理时长——**质量与延迟的权衡第一次以"一个 token"的形式暴露给部署者**。
3. **MTP Drafter**:主模型自带投机解码草稿头,不需要另部署草稿模型,解码加速的收益直接可拿。

**代价清单(权衡视角)**:MoE 省了单 token 算力,但 26B 的权重显存/存储一分不少(bf16 下 52GB,小卡装不下,还得量化);量化省了内存和带宽,但 QAT 是训练期投入,且 int2/int4 混合量化对算子的端侧支持有要求;无编码器省了组件,但 12B 的视觉上限比 550M 编码器路线低(报告数字:MMMU Pro 69.1 vs 31B 76.9)。**没有免费午餐,选型先问瓶颈是显存、吞吐还是质量。**

⚠️ **别忘了模态限制**(HF 模型卡):音频只支持 E2B/E4B/12B,且**单段最长 30 秒**;视频按帧处理,**最长 60 秒、约 1 帧/秒**;31B 和 26B-A4B 没有音频输入。多模态不等于全模态。

## 8. 局限与意义

### 报告没有说的(忠实性清单)

- **蒸馏细节未公开**:全文无 "distill",与 Gemini 的关系(是否蒸馏、蒸馏哪些能力)报告未披露。
- **训练数据规模未公开**:报告没给预训练 token 数、各模态数据配比——只有"大规模多领域混合"这种描述。
- **部分架构配置未公开**:head 维度、专家路由细节、pp-RoPE 的 37.5% 推导过程、KV 共享的具体层间方案,报告均未展开。
- **消融不完整**:无编码器 vs 编码器路线的同参数对照没有给出;37.5% 的归因在两处表述不一致(§3.2 已指出)。
- **自报口径**:所有基准为厂商自报,Elo 为 2026-06-19 快照;安全评测是"无过滤条件下"的自报结果。

### 模型自己承认的边界

- 安全章节承认:模型可能反映训练数据中的社会文化偏见;可能生成虚假/误导信息;需要开发者持续监控与本地隐私合规。安全测试的改进(报告称所有安全类别相对 Gemma 3/3n 大幅改进、无理由拒答保持低位)是在**关闭安全过滤器**的条件下测的"模型内在能力",不代表部署态安全。
- 从数据看:专家级难题(HLE ≤19.5)、小模型长程图推理(GraphWalks E2B 4.1)、E2B 的长上下文检索(50.5)仍是明确洼地。

### 意义:三句话

1. **开源小模型的"全能化"**:2.3B 有效参数同时拿到多模态 + 推理 + 128K 上下文,量化后 0.8GB——"小"不再意味着"残废"。
2. **31B 稠密登顶开源**:证明"参数量不是唯一变量",架构与训练配方的效率红利可以抵消 50 倍的规模差(1451 vs 1456 Elo)。
3. **无编码器路线被大规模验证**:12B 证明"取消翻译官"可行且性能有竞争力,这可能改变下一代多模态模型的标准架构——更少组件、更少碎片、整模型可微调。

## 📝 总结

1. **家族布局**:五个模型两条路线——稠密(E2B/E4B/12B/31B)与 MoE(26B-A4B),参数 2.3B 有效到 31B,上下文 128K/256K 两档,全部 Apache 2.0 开源(报告 §1/§2)。
2. **效率四件套**:滑窗+全局混合注意力(5:1)、pp-RoPE(p=0.25)+ 键值复用 + KV 共享(全局 KV Cache 最多省 37.5%)、MTP Drafter(投机解码,词表投影从 262k 维压到 4k 维)、QAT 量化(E2B 量化后 0.8GB)。
3. **多模态两条路**:150M/550M ViT + 305M USM 音频编码器(经典路线)vs 12B 无编码器(35M 视觉投影 + 640 维音频直投),12B 用数据证明无编码器可行。
4. **评测口径**:全部自报、默认 thinking;31B Arena Elo 1451 开源稠密第一,E2B 以少 10 倍参数追平 Gemma 3 27B;HLE ≤19.5 提示推理仍有上限。
5. **未公开事项**:蒸馏关系、数据规模、部分架构细节——读报告时与"已公开数字"分开对待。
6. **部署含义**:从 0.8GB 手机模型到 19.2GB 高质量稠密,三个成本旋钮(视觉 token 预算 / thinking 开关 / MTP)让"多模态 + 推理"第一次有了可预期的成本曲线。
