Agent(能自己调用工具、操作电脑的 AI)要往前走，卡在两个地方：一是**看不懂屏幕**——GUI 操作、看图写代码、长视频理解都需要视觉，纯文本模型天生缺一只眼睛；二是**干得太慢**——Agent 一次只能串行地"想一步、调一次工具",任务一复杂，延迟随步骤数线性上涨，几百步的推理链直接拖到不可用。Kimi K2.5 这篇技术报告给出的答案是两件事一起做：把 **1.04 万亿参数的 MoE 模型**(激活 32B,即每次推理只用 320 亿参数)改造成原生多模态模型，再给它配一个 **Agent Swarm(智能体蜂群)** 并行编排框架——模型自己学会把大任务拆成小任务、当场"招募"一批子代理并行干活，论文报告在宽搜索场景下**延迟最多降低 4.5 倍**，同时把 BrowseComp 成绩从单代理的 60.6% 抬到 78.4%,超过 GPT-5.2 Pro(77.9%)。本文逐层拆解这份报告：架构、三个反直觉的训练招数、Agent Swarm 的机制与公式、自报成绩单怎么读，以及它对推理基础设施意味着什么。

## 1. 为什么 Agent 需要两只眼睛和一群手

**问题是：为什么"能推理的大模型"还不够当 Agent?** 2025 年的前沿模型(GPT-5.2、Claude Opus 4.5、Gemini 3 Pro、Kimi K2-Thinking)都已经能做多步推理和工具调用，但报告点出两个结构性瓶颈:

- **眼睛缺失**：现实世界的任务大量以图像、屏幕截图、视频形式存在——修一个网页要先"看"渲染结果，操作电脑要先"看"屏幕。预训练的视觉语言模型(VLM)默认不会"看着图调用工具",视觉能力与 Agent 能力是两张皮。
- **手只有一双**：现有 Agent 系统几乎都靠**串行执行**工具调用。即便是能跑几百步推理的 Kimi K2-Thinking,推理时间也随步骤数线性增长——任务越复杂，等得越久，而且单代理的上下文(记忆窗口)会被逐步撑爆。

打个比方：装修一栋楼，传统 Agent 是**一个全能师傅挨个房间干**：先查水电、再砌墙、再刷漆，一个师傅一天只能干一间，而且干到第 20 间时已经忘了第 1 间的样子(上下文爆掉)。K2.5 的做法是让模型自己当**总指挥**：把楼拆成水电、木工、油漆三个并行工段，每段派一个师傅同时开工，师傅只向总指挥汇报"我这边做完了、结论是什么",不把全部过程细节倒给他。总指挥+施工队这套机制，就是全文最核心的贡献 **Agent Swarm**。

报告给出的量化结论(论文报告)：在 WideSearch 这类宽搜索场景，**延迟最多降 4.5 倍**，同时 item-level F1(F1 分数：精确率与召回率的调和平均，衡量检索/回答质量，最高为 1) 从单代理的 72.8% 涨到 79.0%;在 BrowseComp 上，78.4% 的成绩超过了 GPT-5.2 Pro 的 77.9%。**并行不仅省时间，还提质量**——这是这篇报告最反直觉的卖点，后面 §5.4 会细看。

## 2. 架构底子：万亿 MoE 配 4 亿参数视觉编码器

**问题是：K2.5 的"身体"长什么样?** 报告 §4 明确：K2.5 = 三件套组合——**MoonViT-3D 视觉编码器 + MLP 投影器 + Kimi K2 MoE 语言模型**。

语言模型底座直接继承 Kimi K2(论文报告):

| 配置项 | 数值(论文报告 §4.1 + HF 模型卡) |
|---|---|
| 总参数 | 1.04 万亿(1.04T) |
| 每 token 激活参数 | 320 亿(32B) |
| MoE 专家 | 384 个路由专家，每 token 激活 8 个(稀疏度 48,即激活率 1/48) |
| 注意力 | MLA(Multi-head Latent Attention) |
| 上下文长度 | 256K token(HF 模型卡) |
| 激活函数 | SwiGLU;层数 61(含 1 个稠密层)；共享专家 1 个 |

关键设计意图：**总参数大、激活参数小**。1.04T 的知识容量靠 384 个专家分摊，但每次推理只唤醒 8 个专家，算力开销接近 32B 的稠密模型——这是 MoE 的经典账本：用显存(要装下全部 1.04T 权重)换推理速度。部署侧，模型卡标注支持 vLLM / SGLang / KTransformers 引擎，权重与代码用 **Modified MIT 许可**开源。

视觉部分(MoonViT-3D,HF 模型卡标注 **4 亿参数**)有三个值得记的设计:

1. **原生分辨率 + "patch n' pack"**：图像不打成固定尺寸的网格，而是切成 patch(图像小块)后压扁成一维序列，不同分辨率的图可以混在一个 batch 里训练，避免"先缩放再理解"的信息损失。
2. **3D 时空体积**：把"patch n' pack"从空间推广到时间——最多 **4 个连续视频帧**的 patch 被拼成一个时空体积，走同一套注意力。图像和视频**完全共享权重、共享嵌入空间**，不需要为视频单开模块。这解决了一个工程痛点：以前"视频模型"和"图像模型"各是一套，现在知识可以从图片理解迁移到视频理解。
3. **4 倍时间压缩**：进入 MLP 投影器之前，对每个时间块内的 patch 做轻量时间池化(temporal pooling)，视频 token 数量直接除以 4——**同样的上下文窗口，能塞进 4 倍长的视频**。这就是后面长视频评测能"喂 2000+ 帧"的底气。

💡 **提示**：视觉编码器只有 4 亿参数，而语言模型是 1.04 万亿——差了 2500 多倍。这种"小眼睛、大脑袋"的配置意味着：视觉部分的训练成本占比很小，瓶颈全在如何让"眼睛"和"脑袋"对齐，这正是第 4 节三条训练招数的出发点。

## 3. Agent Swarm:总指挥分包，子代理干活

**问题是：为什么不能直接让一个模型串行干完所有事?** 报告 §3 给出了三个理由：单代理的推理深度和工具调用预算(step budget)会耗尽；上下文越攒越长，前面的信息逐渐丢失；总时长随任务复杂度线性增长。而 Agent Swarm 的思路是**把串行变成并行，并且让模型自己学"什么时候该并行"**。

### 3.1 机制：动态分解、冻结执行、只收结论

沿用开头的比喻：总指挥(orchestrator,编排器)是**唯一可训练的** Agent,施工队(sub-agent,子代理)是**冻结的**(frozen)——子代理从训练中途的固定检查点(intermediate policy checkpoints)实例化，执行时不再更新。这套"一热多冷"的设计在工程上意味着：子代理跑的时候就是纯推理，不需要为它们维护训练状态。

机制上只有两个新接口(论文附录 E.8 给了 JSON schema):

- **create_subagent**：总指挥创建子代理，并给它写一段专属 system prompt(比如"你是一名物理研究员""你是事实核查员")，起个名字方便复用;
- **assign_task**：把子任务派给指定子代理，子代理可以自己用搜索、浏览器等工具。

子代理各自有**独立的工作记忆**，在自己的局部上下文里推理，不污染总指挥的全局上下文；完成后只把"任务相关的产出"回传给总指挥，而不是把整条交互轨迹倒回去。论文把这个叫做 **context sharding(上下文分片)**，对应的是另一种方案 **context truncation(上下文截断，比如 discard-all:上下文一超限就把旧的丢掉)**——分片是"把记忆拆到不同房间",截断是"把记忆扔进碎纸机"。图 7 显示：在 BrowseComp 上，分片策略在效率和准确率上都优于 discard-all。

### 3.2 训练编排器：PARL 与两条反作弊奖励

**问题是：怎么训练一个会"分包"的总指挥?** 如果让主模型和子代理端到端一起训练，会遇到两个经典难题：**信用分配模糊**(任务最终失败，到底是总指挥拆错了，还是某个子代理干砸了?)和**训练不稳定**。所以报告提出 **Parallel-Agent Reinforcement Learning(PARL,并行代理强化学习)**：只优化总指挥，子代理的输出被当作"环境反馈"而不是可微分的决策点——总指挥负责学"怎么协调",不负责学"怎么干活"。

用 RL 训练并行编排有两个已知的失败模式，报告用两个辅助奖励项分别压制(论文报告):

$$r_{\mathrm{PARL}}(x,y)=\underbrace{\lambda_1 \cdot r_{\text{parallel}}}_{\text{实例化奖励:鼓励建子代理}} + \underbrace{\lambda_2 \cdot r_{\text{finish}}}_{\text{子代理完成率:防止空转}} + \underbrace{r_{\text{perf}}(x,y)}_{\text{任务级最终结果}}$$

- **r_parallel(实例化奖励)**——用来对抗 **serial collapse(串行坍缩)**：模型发现"反正我自己干也能得分",就退回单代理执行，并行能力永远学不出来。奖励它创建子代理，逼它探索并行空间。
- **r_finish(完成率奖励)**——用来对抗 **spurious parallelism(虚假并行)**：模型学会"奖励黑客"——疯狂创建一堆子代理把并行指标刷高，但任务根本没拆。只有"派出去的活真的干完了"才算数。
- 训练早期 λ₁、λ₂ 权重高，随着训练推进**退火(anneal)到 0**，最终只按任务结果打分——先逼它学会并行，再让它为质量优化。

训练技巧上还有两点：先用**小子代理**训练总指挥，再换大模型(便宜);RL 框架支持动态调整子代理与总指挥的推理实例配比，把集群资源吃满。

### 3.3 关键路径公式：Critical Steps 决定快慢

**问题是：怎么在训练和评测里量化"并行得好不好"?** 直接数"总步骤数"会被刷分(派 100 个子代理，总步骤爆表但端到端没变快)。报告引入了一个受并行计算中**关键路径(critical path)**启发的指标 Critical Steps:

$$\text{CriticalSteps}=\sum_{t=1}^{T}\left(\underbrace{S_{\mathrm{main}}^{(t)}}_{\text{第 }t\text{ 阶段总指挥的步数(通常为 1)}} + \underbrace{\max_i S_{\mathrm{sub},i}^{(t)}}_{\text{该阶段最慢的子代理步数}}\right)$$

一个 episode 被建模成 T 个串行阶段；每个阶段里，总指挥走一步(通常是发号施令)，一群子代理并行跑。**这一阶段的耗时由跑得最慢的那个子代理决定**——就像食堂打饭，开三个窗口同时排队，你这一轮的等待时间取决于最长的那条队，而不是三条队加起来。

💡 **提示**：这个公式的妙处在于惩罚"无效并行"——如果拆出来的子任务没有缩短最长支路，只是多占资源，Critical Steps 不会减少，RL 也拿不到好处。它把目标从"最大化并发"校准成"最小化端到端延迟"。

为了让总指挥在训练中"遇到"需要并行的任务，报告还构造了一批**合成提示词**，分为宽搜索(同时探查大量独立信息源)和深搜索(多条推理分支、延迟聚合)两类，再加上长文档分析、大批量文件下载这类真实负载。注意提示词**不明确要求模型并行**，只是把任务分布塑造成"串行干不完、并行才行"的样子——并行策略是模型自己从 RL 中学出来的。训练曲线显示：随着 RL 进行，累积奖励平滑上升，**训练中的并行度也同步上升**(论文图 4)。

## 4. 训练：三条反直觉的招

**问题是：怎么让"大脑袋"长出"眼睛",还长得好?** 报告的训练管线分预训练与后训练两大段，里面藏着三个反直觉的结论。先看预训练总账(论文 Table 3):

| 阶段 | 数据构成 | token 量 | 序列长度 | 训练对象 |
|---|---|---|---|---|
| ViT 训练 | 图片 alt 文本、合成描述、定位框、OCR(光学字符识别：从图片里识别文字) | 1T | 4096 | 仅视觉编码器 |
| 联合预训练 | 图文交错、视频+文本、知识、OS 截图 | 15T | 4096 | 编码器 + LLM |
| 长上下文中期训练 | 高质量长文本、长视频推理、长 CoT(思维链：先写推理过程再给答案的提示方式) | 500B→200B | 32768→**262144** | 编码器 + LLM |

### 4.1 原生多模态预训练：早一点、少一点

**问题是：图文混合预训练，视觉 token 该什么时候加、加多少?** 之前 Seed1.5-VL 等工作的"常识"是：视觉应该在训练后期以高比例(50% 以上)集中注入，把多模态当作语言能力的"事后补丁"。K2.5 的消融(论文 Table 1,固定图文 token 总预算)得出了相反结论——**早注入、低比例反而更好**:

| 注入时机 | 图文比例 | 视觉知识 | 视觉推理 | OCR | 文本知识 | 文本推理 | 代码 |
|---|---|---|---|---|---|---|---|
| 早期 0% | 10%:90% | **25.8** | **43.8** | **65.7** | **45.5** | 58.5 | **24.8** |
| 中期 50% | 20%:80% | 25.0 | 40.7 | 64.1 | 43.9 | **58.6** | 24.0 |
| 后期 80% | 50%:50% | 24.2 | 39.0 | 61.5 | 43.1 | 57.8 | 24.0 |

(论文 Table 1;数字为各策略下的能力分)

结论：**视觉比例本身对最终多模态性能影响不大，但注入时机影响显著**——视觉能力不需要"突击补课",从早期就均匀地"每天学一点",文本和视觉互相促进，比后期集中灌输更稳。这像学外语：每天 20 分钟坚持三年，比高三突击一年效果更好，而且不挤占主科。

### 4.2 Zero-vision SFT:纯文本激活视觉

**问题是：预训练完的 VLM 会"看",但不会"看着图干活",怎么办?** 传统做法是人工标注/提示词工程构造视觉 CoT 数据，但这类数据多样性差，往往只覆盖"看图、裁剪、旋转"这类原始操作。K2.5 的招叫 **zero-vision SFT(零视觉监督微调)**：后训练阶段**只用纯文本 SFT 数据**，把所有图像操作"代理"成 IPython 里的程序化操作——比如用二值化(binarization)+ 数像素来估计物体大小、做物体定位、计数、OCR。模型在训练时"从没见过真图像",却在推理时把这种能力泛化到真实视觉任务上。

打个比方：一个学员从没摸过真车，但先在驾驶模拟器里练熟了油门、刹车、看后视镜；上车之后，肌肉记忆直接迁移——因为模拟器和真车的"操作逻辑"是同构的。报告还发现一个反直觉结论：**在这个阶段加入人工设计的视觉轨迹反而伤害泛化**，纯文本 SFT 效果更好，推测原因是联合预训练已经把图文对齐打好了底子，视觉能力可以"自然跨模态泛化"。

⚠️ **注意**：这里的"零视觉"是相对的——模型权重在预训练阶段已经见过海量图文数据(15T 联合 token),zero-vision SFT 指的是**后训练 SFT 阶段**不用视觉数据，而不是整个模型没学过视觉。别把两个阶段搞混。

### 4.3 联合多模态 RL:视觉反哺文本

**问题是：视觉 RL 会不会拖累文本能力?** 常规担心是"图文混合训练两头不讨好"。K2.5 的做法：先用基于结果的视觉 RL(三块任务：视觉定位与计数、图表与文档理解、必须看图才能做的 STEM 题)把"看着图推理"练稳，然后直接测纯文本基准，结果(论文 Table 2):

| 纯文本基准 | 视觉 RL 前 | 视觉 RL 后 | 提升 |
|---|---|---|---|
| MMLU-Pro | 84.7 | 86.4 | **+1.7** |
| GPQA-Diamond | 84.3 | 86.4 | **+2.1** |
| LongBench v2 | 56.7 | 58.9 | **+2.2** |

**视觉 RL 不仅不拖后腿，反而反哺文本推理。** 报告的推测：视觉任务强化了"结构化信息抽取"的校准能力，降低了类似"数一数、读一读"这类视觉化推理查询的不确定性。基于这个发现，后训练 RL 干脆**不按输入模态分域，而按能力分域**(知识、推理、编码、Agent 等)，每个域的专家同时从纯文本和多模态查询里学习，让跨模态迁移最大化。视觉 RL 的轨迹还会被抽出来做拒绝采样微调(RFT)，形成自我改进的数据管线。

RL 侧还有两个工程细节：规则化结果奖励(可验证任务)+ **预算控制奖励**(省 token)；对不可验证的通用任务用**生成式奖励模型(GRM)**；以及一个叫 **Toggle** 的 token 效率算法——交替运行"预算受限阶段"和"标准扩展阶段",预算从历史成功样本的 token 数分位数里估计(公式 $budget(x)=\mathrm{Percentile}(\{|y_j| \mid r(x,y_i)=1\}, \rho)$)，论文报告它让 K2-Thinking 在 GPQA、MMLU-Pro 上以极小的性能损失换到一致的 token 削减(详见 §6)。

### 4.4 训练基础设施：把视觉编码器解耦出来

**问题是：多模态训练为什么慢?** 视觉输入的 token 数和分辨率波动巨大，塞进流水线并行(PP)的 Stage-0 会造成严重的负载不均——一张 4K 图和一个短句子的计算量差出几个数量级。Kimi-VL 的旧办法是手动调整 Stage-0 的解码器层数"留内存",但治标不治本，而且没法复用纯文本训练调优过的并行策略。

K2.5 的方案 **DEP(Decoupled Encoder Process,解耦编码器流程)** 利用了视觉编码器在计算图中的特殊位置(前向的最开始、反向的最后)，把每个训练步拆成三个阶段:

1. **均衡视觉前向(Balanced Vision Forward)**：先把全局 batch 里所有视觉数据的前向跑完。编码器很小(4 亿参数)，所以在**所有 GPU 上复制一份**，按图像/patch 数量把负载均匀摊开，中间激活直接丢弃，只保留最终输出激活，送回 PP Stage-0;
2. **主干训练(Backbone Training)**：主 Transformer 的前向+反向，完全复用纯文本训练验证过的并行策略，梯度在编码器输出处累积;
3. **视觉重算与反向(Vision Recomputation & Backward)**：重算一遍编码器前向(激活已经丢了，这是标准的重计算换显存)，再反向求编码器梯度。

效果(论文报告):DEP 在负载均衡的同时把优化策略解耦，**多模态训练效率达到纯文本训练的 90%**——这解释了为什么"加一双眼睛"没有让训练成本翻倍。训练集群是 NVIDIA H800,节点间 8×400 Gbps RoCE,并行组合为 16 路 PP + 16 路专家并行(EP)+ ZeRO-1 数据并行，EP 的 all-to-all 通信与计算重叠(1F1B 交错调度)。报告未公开 GPU 总数与总训练 FLOPs。

## 6. 系统视角：Agent 推理需求的账本

**问题是：这对做推理基础设施的人意味着什么?** K2.5 的两个特性直接把"推理负载画像"改写了:

<img src="/AIInfraGuide/images/kimi-k25-fig10-agentic-rl-system.png" alt="Agentic RL 系统组件与服务关系" style="max-width: 75%; display: block; margin: 0 auto;" />

*图源：Kimi K2.5 技术报告 Figure 10(arXiv:2602.02276)*

- **输入暴涨**：一个 Agent 回合要反复吞截图、文档、视频帧;OSWorld 评测里上下文包含最近 3 张历史截图 + 完整思考历史；长视频评测喂 2000+ 帧。256K 上下文意味着 **prefill(输入处理)阶段的计算量可以轻易超过 decode**，且 KV Cache 显存随输入线性涨——这正好命中站内 [7.x PD 解耦](</AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/72-解耦架构设计>) 的场景：prefill 重、decode 轻，两者解耦才能各自吃饱。
- **并发形态突变**：单代理是"一个请求一路到底",Swarm 是"**一个总指挥 + 一群子代理的树状突发并发**"——同一时刻可能有几十个子代理并行推理，而且子代理是短生命周期、长上下文、低延迟敏感(总指挥在等最慢的那个)。这对调度器和容量规划是新的压力测试：并发放大倍数可能到 10~100×,峰值容量按"单用户"规划会直接被打穿。站内 [10.4 容量规划](</AIInfraGuide/inference/模块四-推理优化/第10章-生产部署与运维/104-容量规划>) 的思维要升级成"一个 swarm 会话 = N 个并发工作负载"。

成本侧的平衡木，报告给了两个数据点:

- **省的一面**:Toggle token 效率 RL 让 K2.5 在 AIME 2025 上 96.1% 只花平均 25k 输出 token,而 Kimi K2 Thinking 94.5% 要 30k、Gemini-3.0 Pro 95.0% 只要 15k(论文 Table 5)——**同等分数，思考更短**；博客还报告内部评测端到端运行时最多降 80%。
- **花的一面**：并行子代理的**总 token 消耗必然高于单代理**(100 个子代理各自都要推理)，报告没有公开 Swarm 模式相对单代理的额外推理成本——这是部署前必须自己实测的账。报告也未公开总训练 FLOPs、GPU 规模、GRM 与 reward 的超参细节。

权衡一句话：**延迟换总计算量**。Swarm 把"墙钟时间"压下去，代价是"总算力消耗"涨上来；如果你的场景是宽搜索、多源验证、长文档并行处理，这笔账划算；如果任务本身是强串行依赖(后一步必须等前一步),Swarm 无利可图——这也是为什么报告强调并行决策是**学出来的**，而不是硬编码的。

## 7. 局限与意义：报告没说的，和我们该警惕的

先声明：报告**没有独立的 Limitations 章节**(§6 结论只有三句话)，以下"局限"部分是本文基于报告公开细节的工程审视，而非作者原话，逐条给出依据:

1. **自报评测的固有风险**：表 4 大量数字带 \*,是 Moonshot 内部评测复跑；部分对比对象缺测(表格里的"—");GPT-5.2 视觉 10% 失败率按错计，意味着对比基准被"人工压低"——K2.5 领先的视觉数字，含金量要打一个问号，等第三方复现。
2. **上下文管理的隐性依赖**:BrowseComp 的 74.9% 依赖 discard-all 上下文管理，且"无管理时超限任务直接判失败";Agent Swarm 的分片本质也是一种上下文管理。**去掉这些技巧，裸成绩会掉**(60.6%)——评测口径里"用什么上下文策略"必须问清楚。
3. **成本数字缺位**:Swarm 的额外推理成本、总训练 FLOPs、GPU 规模均未公开；博客正文与配图对内部办公基准的提升数字不一致(正文 +59.3%/+24.3%,配图标注 +71.2%/+39.0%)「待核实」。
4. **内部基准不可复现**:In-house Swarm Bench、Kimi Code Bench、AI Office Benchmark 等是自建基准，外部无法直接对比。
5. **真正的意义**：它把三条此前分散的路线(原生多模态预训练、文本引导的视觉后训练、并行 Agent RL)**拧成了一个开源整体**(Modified MIT)，并给出"视觉 RL 反哺文本""早注入低比例优于晚注入高比例"两个可移植的反直觉结论——后者直接挑战 Seed1.5-VL 的既定路线，值得在别的模型上复验。

## 📝 总结

1. **两个瓶颈、一个答案**:Agent 缺眼睛(看不懂屏幕)和缺帮手(串行太慢),K2.5 用"原生多模态 + Agent Swarm"同时回应；架构是 1.04T/32B 的 MoE(384 专家激活 8 个)配 4 亿参数 MoonViT-3D,256K 上下文(论文报告)。
2. **Agent Swarm = 可训练总指挥 + 冻结子代理**：总指挥用 create_subagent / assign_task 动态拆任务、派活，子代理各自局部上下文干活、只回传结论;PARL 只训总指挥，用 r_parallel 防"串行坍缩"、r_finish 防"虚假并行",Critical Steps 指标把优化目标钉在"端到端延迟"上。
3. **三条反直觉训练招**：早注入低比例图文联合预训练(优于晚注入高比例)、纯文本 zero-vision SFT(激活视觉反而比人工视觉轨迹好)、联合多模态 RL(视觉训练让 MMLU-Pro +1.7、GPQA +2.1)——外加 DEP 把多模态训练效率维持到纯文本的 90%。
4. **成绩单**:AIME 96.1、SWE-Bench Verified 76.8、OSWorld-Verified 63.3(纯 GUI)、LVBench 75.9(2000+ 帧)、BrowseComp 78.4(Swarm)——但一半数字是内部评测(\*)，对比基准有未测项与失败率折扣，读时要带口径。
5. **对推理基建**：负载画像从"单路长上下文"变成"树状突发并发",prefill 权重上升、并发放大 10~100×——PD 解耦与容量规划的思路要按 Agent 场景重算(呼应站内 7.x、10.x)。
