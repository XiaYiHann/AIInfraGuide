12.3 已经把 GRPO（Group Relative Policy Optimization，组相对策略优化）和 DAPO（Decoupled Clip and Dynamic Sampling Policy Optimization，解耦裁剪与动态采样策略优化）接到 RLVR（Reinforcement Learning with Verifiable Rewards，基于可验证奖励的强化学习）上：模型不再需要人逐条比较回答，checker（程序化检查器）可以直接把最终答案变成 reward（奖励分数）。但题目本身仍由人准备。Absolute Zero 把问题再往前推一步：让模型自己提出任务、自己用环境验证任务、再自己解决任务。论文中的 Absolute Zero Reasoner（AZR）以没有人工题库的方式训练，Qwen2.5-7B-Coder 底座在表 1 的综合平均分达到 50.4，高于先前对比模型 48.6，差值为 1.8 个百分点；这不是“只换了一个奖励函数”，而是把学习任务分布也交给了 proposer（出题角色）和环境。

### 0.1 你先需要哪些词？

| 术语 | 第一次见到时的白话定义 |
|---|---|
| **LLM** | Large Language Model，大语言模型；它根据前文逐步生成后文。 |
| **SFT** | Supervised Fine-Tuning，监督微调；给模型看“题目—示范推理—答案”，让它模仿示范。 |
| **RL** | Reinforcement Learning，强化学习；模型试着行动，环境返回分数，训练让高分行动更容易出现。 |
| **RLHF** | Reinforcement Learning from Human Feedback，基于人类反馈的强化学习；人类偏好先被变成训练信号，再用于更新模型。 |
| **RLVR** | Reinforcement Learning with Verifiable Rewards；奖励不是人凭感觉打分，而是由答案、程序执行或格式规则自动判定。 |
| **CoT** | Chain of Thought，思维链；模型在最终答案前生成的一串中间推理文字。本文只把它当作模型可自行生成的中间过程，不把它当作人工标签。 |
| **token** | 词元；模型处理文本时使用的最小片段，可能是一个字、一个词或一个标点。 |
| **batch** | 批次；一次并行处理的一组样本。 |
| **CPU** | Central Processing Unit，中央处理器；本文主要指执行 checker 和 Python 程序的主机侧计算资源。 |
| **GPU** | Graphics Processing Unit，图形处理器；本文主要指负责模型 rollout、反向传播和参数更新的加速器。 |
| **policy** | 策略；这里记作 $\pi_\theta$，表示模型在给定输入时生成不同文本的概率分布。 |
| **reward** | 奖励；环境对一次回答给出的数值分数，分数越高表示越符合当前检查规则。 |
| **checker** | 程序化检查器；它把“答案是否正确”写成可执行规则，例如运行代码后比较输出，或精确匹配一个字符串。 |
| **verifier** | 验证器；与 checker 同义，强调它负责把候选答案和程序执行结果对照。 |
| **self-play** | 自博弈；模型不只解决外部题目，还和自己产生的任务交互。这里不是两个模型下棋，而是同一个策略轮流承担 proposer 和 solver。 |
| **proposer** | 出题角色；生成任务 $\tau$，目标是提出既有效又能推动学习的题。 |
| **solver** | 解题角色；接收经过验证的题目，生成答案。 |
| **rollout** | 一次采样轨迹；从输入开始生成完整回答，并记录 checker 返回的结果。一次 rollout 不是一个训练轮次。 |
| **triplet** | 三元组；AZR 用 $(p,i,o)$ 表示程序 $p$、输入 $i$ 和输出 $o$，并要求 $o=p(i)$。 |
| **buffer** | 任务缓冲区；保存已经通过环境检查的历史 triplet，供下一轮 proposer 参考。 |
| **baseline** | 基线；用来表示“通常水平”的参考分数，优势就是当前 reward 减去这个参考。 |
| **DPO** | Direct Preference Optimization，直接偏好优化；把离线偏好对直接变成策略概率比较目标。 |
| **GRPO** | Group Relative Policy Optimization；同一道题采样一组回答，用组内相对分数估计更新方向，通常不额外训练一个 critic（价值模型）。 |
| **DAPO** | Decoupled Clip and Dynamic Sampling Policy Optimization；在 GRPO 路线上拆开裁剪和采样控制的后训练算法。它是 12.3 的主线，不是本文 AZR 的算法名。 |
| **PPO** | Proximal Policy Optimization；通过限制策略更新步长来稳定强化学习的策略优化算法。论文配置表里出现“PPO Epochs”，但 AZR 的主算法名称是 TRR++。 |
| **REINFORCE++** | 一类策略梯度更新方法；用奖励减去基线得到优势，再把高优势回答的概率推高。 |
| **TRR++** | Task-Relative REINFORCE++，任务相对 REINFORCE++；AZR 为每种任务类型和角色分别计算基线。 |
| **PRM800K** | Process Reward Model 800K，过程奖励模型数据集；它用步骤级标注检查中间推理，而不是只检查最后答案。 |
| **KL** | Kullback–Leibler divergence，衡量两个概率分布差异的方向性距离；在 RL 训练里常用来限制新策略不要离参考策略太远。 |
| **OOD** | Out-of-Distribution，分布外；评测题目不属于训练时直接看到的题目分布。 |

### 0.2 SFT 和 RLVR 到底把什么交给了模型？

先用一张最小数据表把差异钉住：

| 训练方式 | 人需要准备什么 | 模型自己生成什么 | 奖励或目标 |
|---|---|---|---|
| SFT | 题目 $x$、人工或更强模型写的推理 $c^{\star}$、答案 $y^{\star}$ | 几乎不需要探索，主要模仿 $c^{\star},y^{\star}$ | 最大化示范文本的概率 |
| RLVR | 题目 $x$、可验证答案 $y^{\star}$ | 自己生成推理 $c$ 和答案 $y$ | checker 根据 $y$ 与 $y^{\star}$ 返回 $r(y,y^{\star})$ |
| Absolute Zero | 不提供人工题库；论文用最简单的 seed triplet 启动缓冲区 | 先生成任务，再生成答案 | 环境验证任务和答案，并把两个阶段都用于 RL |

论文 §2.1 给出的 SFT 目标是：

$$
\mathcal{L}_{\mathrm{SFT}}(\theta)
= -\mathbb{E}_{(x,c^{\star},y^{\star})\sim\mathcal{D}}
\left[\log \pi_\theta(c^{\star},y^{\star}\mid x)\right].
$$

这个式子只做一件事：提高专家示范 $(c^{\star},y^{\star})$ 在题目 $x$ 下的概率。$\mathcal{D}$ 是示范数据集，$\pi_\theta$ 是正在训练的模型。

RLVR 把人工推理轨迹拿掉，但保留题目和正确答案：

$$
J_{\mathrm{RLVR}}(\theta)
=\mathbb{E}_{(x,y^{\star})\sim\mathcal{D},\;(c,y)\sim\pi_\theta(\cdot\mid x)}
\left[r(y,y^{\star})\right].
$$

读这个式子只需要沿着一条样本走：模型看到 $x$，自己生成中间推理 $c$ 和最终答案 $y$，checker 再计算 $r$。例如 4 道题的结果是 $[1,1,0,1]$，这一个小 batch 的平均奖励就是 $(1+1+0+1)/4=0.75$。**模型可以自己想过程，但题目 $x$ 和金标准 $y^{\star}$ 仍然要有人准备。**

> 💡 **回顾：12.3 的 reward 是什么**
>
> reward 是一条回答经过验证后得到的分数，不是“模型觉得自己答得不错”的自评。GRPO 会对同一道题采样多条回答，用组内相对 reward 形成优势；DAPO 再调整裁剪和采样机制。Absolute Zero 保留“由环境给可验证 reward”这一核心，却把题目也交给 proposer 生成。本文在这里重新写出最小目标函数，是为了让后文的自生成任务不依赖读者记忆上一节公式。

## 1. 问题：可验证奖励为什么还不够

### 1.1 RLVR 谱系：奖励从人类偏好走向可验证结果

为什么 RLVR 比逐条人工标注便宜？**因为一次写好的规则可以重复执行，而不是每个候选答案都请一个人重新判断。**数学最终答案可以做精确匹配，代码可以运行测试，符号推理可以检查等价关系，格式任务可以检查字段和括号。对同一条规则，1000 个候选答案都走同一条 checker 路径，标注速度和一致性不再由人工阅读速度决定。

这里的“无偏”需要加限定。**相对于“不同标注员有不同偏好”，确定性 checker 会减少主观方差；但 checker 仍可能把错误目标写成正确目标。**例如一个只比较字符串的数学 checker 可能拒绝数值等价的写法，所以“可验证”不等于“目标天然正确”。

沿着后训练历史看，变化大致是三步：

1. **SFT 先教会模型模仿**：人或更强模型提供完整推理轨迹，数据里有“应该怎么想”。代价是专家轨迹昂贵，而且覆盖范围受人工产能限制。
2. **RLVR 再把过程交给模型**：DeepSeekMath 先用 GRPO 这类组相对策略更新推进数学强化学习，DeepSeek-R1 等 zero-style 路线再直接在底座模型上使用数学、代码任务的结果验证来奖励最终答案，不再要求人工标注每一步 CoT。但题目和答案仍是人整理的。
3. **过程奖励补充中间检查**：`Let's Verify Step by Step` 提出的 PRM800K 是一个过程奖励数据集，用 80 万级别的步骤级标注帮助判断推理中间步骤。它把监督信号推进到“过程是否正确”，但数据本身仍来自人工标注。

Qwen2.5-Math 技术报告则展示了数学专用模型如何结合合成数据、验证器和强化学习构建更强的数学能力。它说明“可验证奖励”可以扩大训练规模，却没有消除题目生产这件事。Absolute Zero 的新问题是：**如果结果能被环境检查，题目能不能也由模型自己提出？**

### 1.2 12.3 留下的尖锐问题：题目是谁出的？

上一节的 GRPO/DAPO 已经把“回答好不好”从人工偏好改成了可验证结果，但训练循环仍然从一个固定题库取 $x$：

```text
固定题目 x
    ↓
当前 policy 采样多条回答
    ↓
checker 给每条回答 reward
    ↓
GRPO / DAPO 更新 policy
```

这条链减少了人逐条批改答案的工作，却没有减少人设计题目、答案和验证器的工作。题库越大，覆盖越广，但整理、去重、验证和维护也越贵。

Absolute Zero 的回答不是“把人工题库压缩成更小的文件”，而是把任务分布变成训练中的一个角色：模型先提出 $\tau$，环境把它转换为可验证的题目 $(x,y^{\star})$，模型再解题。这样，后训练数据从“人类偏好”走向“可验证奖励”，再走向“零数据自博弈”。

## 2. 核心思想：让模型自己提出可学习的题

### 2.1 自博弈不是两个模型互殴，而是两个角色共用一套参数

打个比方：一个学生同时扮演“出题老师”和“答题学生”。出题老师不能只出一道一眼就会的题，也不能出一道连自己都无法检查的题；最有价值的是“偶尔答对、偶尔答错”的题，因为这类题最能暴露当前能力边界。Absolute Zero 把这个对应关系写成 proposer、solver 和环境三部分：

- proposer 负责提出任务，像出题老师；
- solver 负责回答任务，像答题学生；
- 环境负责执行程序、生成正确结果和检查答案，像一把不带主观意见的尺子。

论文中的 $\pi_\theta$ 是同一个大语言模型参数，训练时分成两个使用方式：$\pi_\theta^{\mathrm{propose}}$ 生成任务，$\pi_\theta^{\mathrm{solve}}$ 解决任务。它们不是两套独立权重，而是同一策略在不同提示和不同阶段的两个角色。

### 2.2 一轮 Absolute Zero 需要经过哪些状态？

论文 Eq. 3 可以压缩成下面这个目标：

$$
\mathcal{J}(\theta)
=\mathbb{E}\left[
\underbrace{\lambda r^{\mathrm{propose}}_e(\tau,\pi_\theta)}_{\text{任务是否值得学习}}
+
\underbrace{r^{\mathrm{solve}}_e(y,y^{\star})}_{\text{答案是否正确}}
\right],
$$

其中采样关系是：

$$
\tau\sim\pi_\theta^{\mathrm{propose}}(\cdot\mid z),
\qquad
(x,y^{\star})\sim f_e(\cdot\mid\tau),
\qquad
y\sim\pi_\theta^{\mathrm{solve}}(\cdot\mid x).
$$

前一个式子回答“奖励由哪两块组成”：一块奖励出题质量，一块奖励解题正确性。后一个式子回答“数据怎样流动”：模型从条件 $z$ 生成任务 $\tau$，环境函数 $f_e$ 把任务变成带金标准的 $(x,y^{\star})$，solver 再生成 $y$。$\lambda\ge 0$ 控制探索新题和解决当前题之间的权衡。

用一个数值样本走一遍：假设某个任务的 proposer reward 是 $0.625$，solver 正好答对，所以 solver reward 是 $1$；若暂取 $\lambda=1$，这一条样本的合成目标贡献就是 $0.625+1=1.625$。这只是解释 Eq. 3 的思想实验，论文训练时还要经过角色、格式和 task type 的分组归一化。

这张图讲的是一条闭环：**任务生成、任务验证、答案验证和策略更新在同一轮训练里相互连接。**最关键的箭头不是“solver 得到一个 0/1 分”，而是“proposer 的任务也会被评估，历史有效任务还会回到下一轮作为参考”。

### 2.3 Absolute Zero 与普通 RLVR 的边界

| 问题 | 普通 RLVR | Absolute Zero |
|---|---|---|
| 题目从哪里来 | 人工或程序预先准备 | proposer 在线生成 |
| 正确答案从哪里来 | 数据集中的 $y^{\star}$ | 环境执行任务后得到 |
| 模型生成什么 | 主要生成推理和答案 | 先生成任务，再生成答案 |
| checker 做什么 | 判定答案是否正确 | 先验证任务有效，再验证答案 |
| 数据形态 | 固定 $\mathcal{D}$ | 在线增长的任务 buffer |

因此，“zero data”不是“训练时没有任何输入”，而是**没有人工整理的题目—答案数据集**。论文仍然需要一个可执行环境，并在启动阶段使用最简单的 identity function triplet 作为 seed。把这两个概念混为一谈，会误以为 Absolute Zero 不需要任何规则或初始化。

## 3. Absolute Zero Reasoner：把 checker 变成环境

### 3.1 为什么论文选择代码 triplet？

AZR 的具体实现把每个代码任务写成三元组：

$$
(p,i,o),\qquad o=p(i)。
$$

$p$ 是程序，$i$ 是输入，$o$ 是程序运行后的输出。这个表示法的好处是，正确答案不需要另一位专家写出来：只要在受控环境里运行 $p(i)$，就能得到 $o$。代码既能表达字符串处理、动态规划等复杂逻辑，又能让 checker 直接执行。

论文 §3.2 把三元组的三个位置轮流遮住，得到三种推理模式：

| 模式 | 给 solver 的输入 | solver 要预测 | checker 怎样验 |
|---|---|---|---|
| **Deduction，演绎** | 程序 $p$、输入 $i$ | 输出 $o$ | 比较预测输出与 Python 执行得到的 $o^{\star}$ |
| **Abduction，溯因** | 程序 $p$、输出 $o$ | 一个可能的输入 $i$ | 运行 $p(i_\pi)$，检查是否得到目标输出；不要求输入文本与原输入完全相同 |
| **Induction，归纳** | 一半输入—输出样例和提示 $m$ | 程序 $p$ | 在隐藏输入上运行预测程序，要求全部输出正确 |

这里的“溯因”尤其适合解释为什么 checker 不能只做字符串相等：同一个程序可能有多个输入都会产生同一个输出，只要预测输入经过程序后得到目标输出，就应当判对。归纳任务则用隐藏测试抑制“只记住几个样例”的投机写法。

### 3.2 一条候选任务怎样被环境放行？

proposer 生成的代码不能直接进入训练。论文 §3.3.3 依次做三层过滤：

1. **程序完整性**：用 Python 执行 $p(i)$，不能报错，而且必须返回结果。
2. **程序安全性**：过滤可能影响执行环境的模块，例如 `os.sys`、`sys`、`shutil`、`subprocess` 等；论文 Figure 10 给出禁用列表。
3. **确定性**：同一个输入重复执行，输出必须稳定。论文将合法程序限制在确定性程序集合 $\mathcal{P}_{\mathrm{deterministic}}$ 中，并在实验里独立运行 $j=2$ 次做近似检查。

最小的确定性判断可以写成：

$$
 p^{(1)}(i)=p^{(2)}(i)。
$$

例如第一次返回 `6`、第二次返回 `6`，通过确定性检查；第一次返回 `6`、第二次返回 `7`，任务直接丢弃。论文明确说，随机程序可能覆盖更大的行为范围，但当前版本为了让验证可靠而没有纳入。

### 3.3 任务 buffer 如何把“过去经验”喂回 proposer？

论文 Algorithm 1 的主干可以改写成下面的非逐字伪代码：

```python
# 非逐字伪代码：对应论文 Algorithm 1
D_ded, D_abd, D_ind = init_seed_buffers(base_model)

for step in range(T):
    for _ in range(B):
        # 1. proposer 参考 K 个历史 triplet，生成新任务
        task_type = sample(["deduction", "abduction", "induction"])
        proposal = proposer(task_type, sample_references(D, K))

        # 2. 环境执行、过滤，失败的 proposal 不进入 solver batch
        task = validate_and_construct(proposal)
        if task is valid:
            D[task_type].append(task)

    # 3. 从三个 buffer 准备待解决的任务
    problems = sample_solver_tasks(D, B)
    answers = solver(problems)

    # 4. 环境计算 proposer / solver reward
    rewards = verify_and_score(problems, answers)

    # 5. 按 task type × role 计算优势，再更新同一个 policy
    policy_update_with_TRR_plus_plus(rewards)
```

论文实验里，参考样例数是 $K=6$，seed batch factor 是 $S=4$。如果 proposer 没有生成足够多的合法题，算法会从已有 buffer 里抽取已经验证过的任务补齐 solver batch；这保证了一个坏的 proposal 不会把整轮训练变成空 batch。

这里还有一个容易被“零数据”掩盖的事实：论文 Figure 5 的启动 seed 是最简单的 identity function triplet。它不是人工题库，后续 buffer 会由模型生成的有效 triplet 继续扩张；论文同时指出，底座模型也可能在没有 seed program 时启动循环。**零数据的核心是没有人工整理的学习题目，而不是没有 checker、没有代码执行器或没有初始化策略。**

## 4. 奖励账本：正确性、可学习性与格式

### 4.1 solver reward 为什么是 0/1？

对 solver，论文 Eq. 5 只关心最终答案是否通过环境验证：

$$
 r_{\mathrm{solve}}=\mathbb{I}_{(y=y^{\star})}。
$$

$\mathbb{I}$ 是指示函数：条件成立就取 1，不成立就取 0。对代码任务，“$y=y^{\star}$”不是简单的文本相等，而是根据任务类型做 Python value equality（值相等）检查。例如集合顺序不同但内容相同，可以按值相等处理；溯因任务还可以接受不同输入，只要执行后得到同一个目标输出。

这就是 RLVR 的核心直觉：**不是模型写得像不像参考答案，而是它的结果能不能被规则验证。**

### 4.2 proposer reward 为什么偏爱“半会不全会”的题？

如果只奖励“题目有效”，模型很容易提出简单但没有学习价值的题。Absolute Zero 因此让 solver 对每个候选题做 $G$ 次非零温度采样，估计它的成功率：

$$
\bar r_{\mathrm{solve}}
=\frac{1}{G}\sum_{i=1}^{G}r_{\mathrm{solve}}^{(i)}。
$$

然后使用论文 Eq. 4：

$$
 r_{\mathrm{propose}}=
 \begin{cases}
 0, & \bar r_{\mathrm{solve}}=0,\\
 1-\bar r_{\mathrm{solve}}, & \text{否则}。
 \end{cases}
$$

前一个式子把 $G$ 个 rollout 的 0/1 结果平均起来；后一个式子把任务难度变成 proposer 的学习性分数。为什么全错也不给高分？因为 solver 完全不会时，题目只产生“无法学习”的失败；为什么全对也不给高分？因为题目太简单，几乎没有新的边界信息。

用论文配置里的 $G=8$ 走一遍：

| 8 次 solver rollout 的结果 | $\bar r_{\mathrm{solve}}$ | $r_{\mathrm{propose}}$ | 解释 |
|---|---:|---:|---|
| 0 次答对 | $0/8=0$ | 0 | 可能不可学或 checker 造成了无效题 |
| 3 次答对 | $3/8=0.375$ | $1-0.375=0.625$ | 有一定难度，也留下学习信号 |
| 4 次答对 | $4/8=0.5$ | $0.5$ | 论文公式下的中等难度 |
| 8 次答对 | $8/8=1$ | $0$ | 太容易，新增信息少 |

这个奖励设计把 proposer 和 solver 变成一种“弱对抗、总体合作”的关系：proposer 想出难题，但题目完全不可解也拿不到 proposer reward；solver 想答对题，又需要 proposer 不断给出自己尚未完全掌握的题。

### 4.3 论文到底加了什么“正则”？

这里必须把三件事分开，不能把所有稳定手段都叫 KL 正则：

1. **格式感知惩罚**：论文 Eq. 6 把返回值写成分段奖励。正确格式且角色目标完成时，取对应的 $r_{\mathrm{role}}$；格式正确但答案错误时取 $-0.5$；格式错误时取 $-1$。proposer 还必须生成合法 triplet 并通过过滤，单纯包上 `<think>` 和 `<answer>` 标签不算合格。
2. **KL 惩罚没有启用**：论文 Table 3 明确写 `KL Loss = False`、`KL Reward = False`。因此不能因为熟悉 PPO 或 GRPO，就默认给 AZR 加一个 reference policy 的 KL 项；那会改变论文实验设置。
3. **熵系数是 0.001**：Table 3 报告 `Entropy Coefficient = 0.001`，它是鼓励策略保留一定采样探索的训练配置。论文没有在正文给出一个完整的总损失展开式，本文不把这个配置反写成新的论文定理。

落成一句话：**AZR 的关键稳定来源是任务难度奖励、格式惩罚、分组优势归一化和环境验证；不是一个默认开启的 KL 锚点。**

## 5. 最小例子：方程 checker 怎样给出 0 或 1

论文的 AZR 具体使用 Python 程序 triplet。为了让 checker 的 0/1 语义更直观，下面用一个数学任务做教学化缩小版；它不是论文实验里的原始提示词，也不改变论文的代码环境设定。

### 5.1 从 proposer 到金标准

proposer 生成任务：

```text
解方程 x² - 5x + 6 = 0。
请按 a,b 输出两个根，顺序不限，不要输出额外文字。
```

环境先做一次简单的解析：

$$
x^2-5x+6=(x-2)(x-3)，
$$

所以金标准集合是 $\{2,3\}$。这一步对应论文里的 `ValidateAndConstruct`：在代码版本中，环境不是手算因式分解，而是执行 proposer 给出的确定性程序，得到 $o=p(i)$。

### 5.2 checker 怎样判答案？

下面是一个最小 checker，代码是教学示意，不是论文源码：

```python
# 教学示意：返回“格式状态”和 solver 的 0/1 reward

def check_roots(text):
    try:
        a, b = (int(part.strip()) for part in text.split(","))
    except (TypeError, ValueError):
        return "format_error", None

    reward = int(sorted((a, b)) == [2, 3])
    return "well_formatted", reward

assert check_roots("2,3") == ("well_formatted", 1)
assert check_roots("3,2") == ("well_formatted", 1)
assert check_roots("2,4") == ("well_formatted", 0)
```

逐条走查：

| solver 输出 $y$ | 格式 | 数学检查 | $r_{\mathrm{solve}}$ | 按论文 Eq. 6 的 solver reward |
|---|---|---|---:|---:|
| `2,3` | 正确 | 两个根都对 | 1 | 1 |
| `3,2` | 正确 | 排序后仍是 `[2,3]` | 1 | 1 |
| `2,4` | 正确 | 有一个根错误 | 0 | -0.5 |
| `x=2,3` | 错误 | 尚未进入数学检查 | — | -1 |

这张表把两个层次分开了：`rsolve` 是论文 Eq. 5 的正确性信号，只取 0/1；Eq. 6 的复合 reward 还会惩罚“格式正确但答案错”和“格式本身错”。

### 5.3 任务难度怎样回到 proposer？

假设同一个方程题让 solver 采样 8 次，结果是 `[1,0,0,1,0,0,0,1]`。那么：

$$
\bar r_{\mathrm{solve}}=\frac{3}{8}=0.375，
\qquad
r_{\mathrm{propose}}=1-0.375=0.625。
$$

于是这道题对 proposer 比“8 次全对”的题更有价值。注意这个数值是对奖励公式的纸笔走查，不是论文报告的某个具体题目分数。

读完这一节，你应该能回答：如果 checker 把 `3,2` 误判为错误，问题是在 solver 还是 checker？答案是 checker 的目标定义太窄；RLVR 可以减少人工批改，却不能替你保证规则与真实目标一致。

## 6. 训练算法：任务相对更新不是 GRPO

### 6.1 先看一轮在线训练

论文 Algorithm 1 的实际训练顺序可以压缩为 5 步：

1. **从 buffer 取参考**：按 deduction、abduction、induction 三种 task type 选择任务类型，并抽取 $K=6$ 个历史样例作为提示。
2. **propose**：当前 policy 生成程序、输入或输入集合与描述。
3. **validate**：Python 执行程序，做完整性、安全性和确定性检查；失败 proposal 丢弃，有效 triplet 写回 buffer。
4. **solve and verify**：从 buffer 准备题目，solver 生成答案，环境按任务类型计算 $r_{\mathrm{solve}}$，同时用 8 次采样估计 $r_{\mathrm{propose}}$。
5. **joint update**：把 proposer 和 solver 的 reward 放进 TRR++，更新同一个 policy；下一轮继续从增长后的 buffer 出题。

这里的 online rollout（在线采样轨迹）指样本由当前正在更新的 policy 生成，而不是提前冻结的一张题库。Absolute Zero 的“在线”有两层：题目在线生成，答案也在线生成。

### 6.2 TRR++ 做了什么归一化？

论文没有把 AZR 叫作 GRPO 变体。它使用的是 Task-Relative REINFORCE++（TRR++）：为 3 种任务和 2 个角色分别维护奖励均值与标准差，一共 6 个任务类型 × 角色组合。

论文 Eq. 8 是：

$$
A^{\mathrm{norm}}_{\mathrm{task,role}}
=\frac{r-\mu_{\mathrm{task,role}}}{\sigma_{\mathrm{task,role}}},
\quad
\mathrm{task}\in\{\mathrm{ind},\mathrm{ded},\mathrm{abd}\},
\quad
\mathrm{role}\in\{\mathrm{propose},\mathrm{solve}\}。
$$

$r$ 是某条 rollout 的 reward，$\mu$ 和 $\sigma$ 只在同一个任务类型 × 角色桶中计算。这样，“一个 induction proposer 的 0.6 分”和“一个 deduction solver 的 0.6 分”不会被不加区分地混成同一把尺子。

给一个最小数字例子：某个 deduction-solve 桶的 4 条结果是 `[0,1,1,0]`，均值为 $0.5$；若用总体标准差 $0.5$ 做教学化计算，则优势为 `[-1,+1,+1,-1]`。正优势回答被推高，负优势回答被压低。

论文对 TRR++ 的解释是：它介于 GRPO 的“按问题分组”与 REINFORCE++ 的“全局基线”之间。**相似点是都用相对 reward 降低方差，差异是 AZR 的分组轴多了一层 task type 和 role。**

### 6.3 论文训练配置给了哪些工程线索？

| 配置 | 论文值 | 工程含义 |
|---|---:|---|
| 训练 batch | $64\times6$ | 论文按 2 个角色 × 3 种任务组织 batch；按字面相乘是 384 个位置 |
| 学习率 | $1\mathrm{e}{-6}$ | 固定学习率，不是动态调度结论 |
| 优化器 | AdamW（带权重衰减的 Adam 优化器） | 论文 Table 3 的实现配置 |
| 总步数 | 500 | 论文主实验的训练长度 |
| $K$ references | 6 | proposer 每次参考的历史 triplet 数 |
| 估计任务准确率的样本数 | 8 | 每个候选任务用 8 次 solver rollout 估计难度 |
| KL Loss / KL Reward | False / False | 没有启用 KL 惩罚 |
| 熵系数 | 0.001 | 保留一定采样探索 |
| PPO Epochs / N Rollouts | 1 / 1 | 框架配置项；不改变主算法名称 TRR++ |
| 硬件和耗时 | A800 GPU 集群，每个实验约 3–5 天 | 论文报告的实验成本，不是本文实测 |

这里有一个工程上容易误读的点：表里出现 `PPO Epochs`，不代表 AZR 使用 PPO 作为论文主算法。作者在算法栏写的是 TRR++，并且明确报告 KL loss 和 KL reward 都关闭。配置字段名称可能来自训练框架，不能替代论文的算法定义。

## 7. 实验：零数据换来了什么

### 7.1 先把评测口径摆清楚

论文 Table 1 把结果分成三类：代码基准、数学基准和两个平均值。这里的 benchmark（基准）是固定的一组评测题，不等于训练题目。

- **代码基准**：HumanEval+、MBPP+ 和 LiveCodeBench v1–5，测试代码生成与执行正确性。
- **数学基准**：AIME 2024、AIME 2025、AMC 2023、MATH500、Minerva、OlympiadBench；它们都是用于数学推理的公开题集或评测集合。
- **CAvg**：三个代码基准的平均分；**MAvg**：六个数学基准的平均分；**AVG**：两者再平均，论文使用
  $$\mathrm{AVG}=\frac{\mathrm{CAvg}+\mathrm{MAvg}}{2}。$$

例如 AZR-Coder-7B 的 CAvg 是 61.6，MAvg 是 39.1，所以 $(61.6+39.1)/2=50.35$，四舍五入得到表中的 50.4。论文所有基准结果都使用 greedy decoding（贪心解码，即每一步选择当前概率最高的 token）以便比较。

### 7.2 Qwen2.5-7B 底座的总账

“7B”表示约 70 亿参数的模型规模。论文主实验分别使用普通 Qwen2.5-7B 和 Qwen2.5-7B-Coder，后者是代码能力更强的底座。

| 模型 | 训练数据口径 | CAvg | MAvg | AVG | 来源口径 |
|---|---|---:|---:|---:|---|
| Qwen2.5-7B | 底座 | 52.0 | 27.5 | 39.8 | 论文 Table 1 |

## 8. ⚠️ 失败模式与边界

### 8.1 任务生成器会塌缩到“自己最容易解的题”

这是自博弈最直接的风险：如果 proposer 只追求自己能稳定拿分，就会不断生成简单题，训练看起来很顺，能力边界却没有移动。论文的 Eq. 4 用“中等成功率”缓解这个问题，但它不是严格的多样性保证。

论文 Appendix D.2 给了一个具体失败尝试：组合程序本来想提高难度，但模型常常退化成直接返回 `g(x)`，也就是 $f(g(x))=g(x)$，没有真正增加挑战。Appendix D.3 还报告了 recency-based sampling（按新近程度采样）可能导致 collapse（塌缩），最终实验采用更简单的 uniform sampling（均匀采样）。

### 8.2 checker 能覆盖的世界很小

AZR 当前 checker 的强项是“可以安全执行、结果稳定的 Python 程序”。论文因此限制程序为确定性的，并明确把随机程序留给未来工作。开放式写作、价值判断、科学假设和真实世界实验没有天然的 `p(i)=o` 检查器；如果硬套字符串相等，只会得到一个脆弱目标。

这也是“可验证奖励更便宜但不等于无偏”的工程边界：**规则写得越窄，奖励越稳定；规则写得越宽，验证成本和漏洞风险越高。**论文讨论了形式数学、互联网、世界模拟器和真实世界环境等后续方向，但这些不是当前 AZR 实验已经证明的能力。

### 8.3 探索多样性仍然需要额外设计

AZR 用 $K=6$ 个历史 triplet 作为参考，并在提示词中要求生成与参考不同的任务。论文 Table 2 的消融显示，去掉动态参考后，数学平均分下降 5 个百分点，代码平均分下降 1 个百分点；不训练 proposer、只训练 solver 时，综合平均下降 1.4 个百分点。这说明任务来源和 proposer 学习确实影响结果。

作者还尝试过代码编辑距离、答案 surprise 等 diversity reward，但没有观察到显著性能差异，并把更强的探索奖励留作未来方向。因此，本文的工程推断是：**不要把“buffer 会增长”误当成“覆盖范围一定会增长”；必须监控任务去重率、程序复杂度、输出分布和失败率。**

### 8.4 “零人工题库”不等于“无需人监督”

论文在 Llama3.1-8B 实验中观察到安全相关的思维链，称为 “uh-oh moment”。论文结论明确指出，自我改进组件仍需要安全监督。代码执行器也需要隔离、超时、资源限制和敏感模块过滤；这些是工程安全边界，不会因为 proposer 是模型自己就自动消失。

## 9. 工程账本：从人工题库到在线生成

### 9.1 Absolute Zero 多付了哪些成本？

把一次训练步的主要成本拆开：

$$
C_{\mathrm{AZR}}
\approx
C_{\mathrm{propose}}
+C_{\mathrm{validate}}
+C_{G\text{-solve}}
+C_{\mathrm{solve}}
+C_{\mathrm{RL\ update}}。
$$

- $C_{\mathrm{propose}}$：模型生成程序、输入、描述和格式包裹的成本。
- $C_{\mathrm{validate}}$：CPU 侧执行程序、检查安全性，并按论文设置重复执行 $j=2$ 次检查确定性。
- $C_{G\text{-solve}}$：为估计 proposer 的可学习性，对每个候选题做 $G=8$ 次 solver rollout。
- $C_{\mathrm{solve}}$：正式 solver batch 的回答和验证。
- $C_{\mathrm{RL\ update}}$：把六个任务类型 × 角色桶的优势送进 TRR++，完成反向传播和参数更新。

上式不是论文给出的 wall-clock（真实耗时）公式，而是工程账本。论文只报告了配置和 A800 集群上每个实验约 3–5 天；没有在 Table 1 中给出“每条人工题的标注成本”和“每次 CPU checker 的单独耗时”，所以本文不虚构二者的比例。

### 9.2 与 12.3 的账本对比

| 账本项 | 12.3 的 GRPO/DAPO | Absolute Zero / AZR |
|---|---|---|
| 题目 | 人工或程序预先准备的固定题目 | policy 在线提出 $\tau$，buffer 持续增长 |
| 答案验证 | checker 对 rollout 答案给 reward | checker 先验证 proposal，再验证 solver 答案 |
| GPU rollout | 当前 policy 对固定题目采样 | proposer、solver 和 $G=8$ 可学习性估计都要采样 |
| CPU 工作 | 主要是已有 verifier 的判定 | 程序执行、安全过滤、确定性重复运行 |
| 训练更新 | GRPO/DAPO 的组内相对优势与裁剪 | TRR++ 的 6 个任务类型 × 角色基线 |
| 牺牲 | 付人工题库和覆盖维护成本 | 付在线生成、验证、缓存和探索监控成本 |
| 换取 | 训练循环更简单、任务边界可预先控制 | 减少人工题目依赖，任务分布可以随模型经验扩张 |

落成一句话的工程规则：**如果你的任务已有可靠题库和 checker，先用 12.3 的固定题目 RLVR；只有当题目生产成为真正瓶颈，并且你能提供安全、确定、可执行的环境时，才值得付 Absolute Zero 的在线生成账。**

## 10. ⚠️ 看起来合理但会错的理解

### 10.1 “只要 reward 是 0/1，就是 GRPO”

❌ 错误理解：AZR 的 solver reward 是 0/1，所以它就是 GRPO。

✅ 正确理解：0/1 描述的是 verifier 的结果，不决定策略优化算法。AZR 主算法是 TRR++；论文只说它在基线结构上介于 GRPO 的按问题分组和 REINFORCE++ 的全局基线之间。

### 10.2 “没有人工数据，所以不需要 checker”

❌ 错误理解：模型自己出题，模型自己说对，就能继续训练。

✅ 正确理解：没有外部 checker，proposer 和 solver 会共享同一个错误标准，奖励会变成自我确认。Absolute Zero 的“zero”恰恰依赖环境提供外部可验证反馈；题目可以自己出，正确性不能只靠自己宣布。

### 10.3 “把 solver reward 做大，就能自动得到更难的题”

❌ 错误理解：只最大化 solver 的正确率，任务自然会越来越难。

✅ 正确理解：只看 solver 正确率会偏向简单题。论文额外用 proposer learnability reward，让全错和全对的题都得到 0，让中等成功率的题获得更高分。

### 10.4 “论文配置里有 PPO Epochs，所以应该加 KL”

❌ 错误理解：只要训练框架字段出现 PPO，就把 PPO 的 KL 参考项打开。

✅ 正确理解：论文 Table 3 明确关闭 KL Loss 和 KL Reward，主算法栏写的是 TRR++。复现实验时应先按论文设置；要改成带 KL 的版本，应把它当作新消融，而不是原方法的默认实现。

## 11. 延伸：RLVR 是从 R1 到 Absolute Zero 的桥梁

DeepSeek-R1 证明了“固定的人类题目 + 可验证结果”可以成为推理能力的强化学习桥梁；Absolute Zero 沿着同一条 RLVR 轨道继续前移，让模型连学习题目也在线提出。换句话说，RLVR 连接了 R1 的零式后训练和 Absolute Zero 的零数据自博弈，但它不自动保证开放世界任务也可验证。

## 📝 总结

1. **问题**：12.3 的 GRPO/DAPO 已经让 checker 替代人工逐条评答案，但题目和答案仍需人工题库；Absolute Zero 追问“题目能不能也自己出”。
2. **机制**：同一个 policy 分成 proposer 和 solver 两个角色，环境把 proposer 的任务转换成有效 $(x,y^{\star})$，再验证 solver 的 $y$。
3. **奖励**：solver 使用 $r_{\mathrm{solve}}=\mathbb{I}(y=y^{\star})$；proposer 用 $G=8$ 次成功率构造中等难度奖励，并叠加格式惩罚。
4. **算法**：AZR 用 Task-Relative REINFORCE++（TRR++），按 3 种任务 × 2 个角色得到 6 个优势基线；它不是论文命名的 GRPO 变体，也没有启用 KL reward/loss。
5. **结果**：Qwen2.5-7B-Coder 上，AZR 在无人工整理题目的口径下达到 CAvg 61.6、MAvg 39.1、AVG 50.4；论文报告比先前最好综合分高 1.8 个百分点，但 MATH500 增量标记存在表内算术冲突。
6. **边界**：任务生成可能塌缩，checker 只能覆盖可执行且可验证的任务，探索多样性和安全监督仍然需要工程设计。
