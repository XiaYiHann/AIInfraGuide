## 1. 为什么 FA2 在 Hopper 上不够好

### 1.1 问题是什么：35% 利用率意味着什么

先算一笔账。H100 SXM5 的 FP16 Tensor Core 峰值是 **989 TFLOPS**，35% 利用率意味着 FA2 前向实际只跑出约 **350 TFLOPS**。同一块卡上，cuBLAS/CUTLASS 的 GEMM 能干到 80-90%。同样是“以矩阵乘为主体”的算子，差距为什么这么大？

FA3 论文给了一个很直接的解释：**FA2 的算法建立在“简化同步模型”之上，没有显式利用异步和低精度**。具体到代码层面，有三层原因：

| 📊 层面 | FA2 的做法 | Hopper 现实 |
|---------|-----------|-------------|
| 指令 | 仍以 Ampere 时代的 `mma.sync` 为主 | `mma.sync` 只能达到 Hopper Tensor Core 峰值吞吐的约 2/3 |
| 访存 | 同步加载 + 显式等待数据就绪 | Hopper 有 TMA 硬件可以异步批量搬运，几乎不占线程 |
| 精度 | FP16/BF16 | FP8 Tensor Core 吞吐是 FP16 的 2 倍（1979 TFLOPS） |

也就是说：FA2 是在用上一代硬件的编程模型，跑新一代硬件。算法没错，但**硬件红利一点没吃到**。

### 1.2 Hopper 到底多了什么

先把 FA3 要用到的四样新东西认全（都是 Hopper 引入或强化的）：

- **WGMMA（Warpgroup MMA）**：第 4 代 Tensor Core 的新矩阵乘指令。和 Ampere 的 `mma.sync`（单个 warp、32 线程粒度、同步执行）不同，WGMMA 以 **warpgroup（4 个连续 warp，128 线程）** 为粒度发起。它**异步执行**：指令发出去后 Tensor Core 自己算，线程可以继续干别的。Operand A 可以来自寄存器或共享内存，Operand B 只能来自共享内存。
- **TMA（Tensor Memory Accelerator）**：一个专门负责“全局内存 ↔ 共享内存”批量搬运的硬件单元。你只需把搬运描述（源地址、形状、步长）写进一张描述符，TMA 硬件就独立完成整块搬运。它**不消耗线程的指令发射和寄存器**，搬完通过 mbarrier 通知。
- **异步执行模型**：上面两个异步单元 + mbarrier（内存屏障）同步原语，让“搬数据”和“算数据”可以真正并行。
- **FP8 低精度**：E4M3（4 位指数、3 位尾数）格式，Tensor Core 吞吐翻倍（1979 TFLOPS），数据字节减半。

打个比方：FA2 的后厨里，一个厨师既要自己洗菜、切菜、备料，又要炒菜——洗菜时锅空着，炒菜时菜还没到。Hopper 给你配了**配菜员（TMA）和一条传送带**：配菜员只管把料切好放上传送带，厨师只管炒——两边同时干活，谁也别等谁。FA3 的 Warp Specialization 就是把“配菜”和“炒菜”这两件事分给不同的 warp 去干。

📌 **关键点**：FA2 没吃到红利不是它的错，而是它诞生时（2023 年中）Hopper 的编程范式还没普及。FA3 的贡献本质上是**把 Attention 重新设计成适配异步硬件的软件流水线**。

## 2. 核心设计一：Warp Specialization 分工

### 2.1 问题是什么：为什么不能让一个 warp 既搬数据又算

传统 kernel 里，每个 warp 都要自己发加载指令、等数据回来、再发计算指令。加载延迟（几百个周期）暴露在关键路径上，warp 只能靠“切出去让别的 warp 顶上”来掩盖——这就是 Occupancy 的玩法（见 2.3 节）。但 FA3 要的是：**数据搬运和矩阵乘同时在硬件层面跑**，而不是靠切换线程来“假装并行”。

Hopper 给了两个异步单元（TMA 搬数据、Tensor Core 算矩阵），但它们是不同硬件，**一个 warp 的指令流没法同时驱动两套单元**——指令是一条条发射的。怎么办？

**答案是把线程本身也分工**：让一部分 warp 专职发搬运指令（生产者），另一部分专职发计算指令（消费者），中间用共享内存 + mbarrier 交接。

### 2.2 设计：producer / consumer 两个 warpgroup

FA3 前向把一个 CTA（线程块）里的线程分成两类角色：

```
CTA（线程块）= 4 个 warpgroup × 4 个 warp = 512 线程（典型配置）

┌─────────────────────────┐
│ Producer Warpgroup      │  只发 TMA 搬运指令：把 Q/K/V 块从 HBM 搬进 SMEM
│ （1 个 warpgroup）       │  搬完用 mbarrier 发信号，然后立刻去搬下一块
├─────────────────────────┤
│ Consumer Warpgroup(s)   │  只发 WGMMA 计算指令：等数据就绪信号，
│ （2-3 个 warpgroup）     │  执行 QK^T 和 PV 两个 GEMM + softmax
└─────────────────────────┘
```

关键机制（对应论文 Algorithm 1）：

1. Producer 用 TMA 把 $K_j, V_j$（以及 $Q_i$）搬进共享内存，搬运完成后通过 **mbarrier** 提交一个“数据就绪”信号；
2. Consumer 的 warpgroup 在 mbarrier 上等待，信号到了就用 **WGMMA** 发起矩阵乘，然后立即回到等待下一个信号——**不等 GEMM 算完**（WGMMA 是异步的，算完会自己写回寄存器并提交完成信号）；
3. 共享内存用**多级环形缓冲**（multi-stage circular buffer）：Producer 提前搬第 $j+1$ 块时，Consumer 正在算第 $j$ 块，两块数据在 SMEM 里各占一格，互不覆盖。

论文还用了 Hopper 的 **`setmaxnreg`** 指令，按角色动态分配寄存器：Producer 只发指令，用不了多少；Consumer 的 GEMM 累加器很吃寄存器，需要更多配额。反向传播时角色多了一个：**dQ-writer**（专门负责把 dQ 梯度写回 HBM），因为反向的矩阵乘更多、数据流更复杂。

伪代码示意（**非逐字源码**，还原论文 Algorithm 1 的主干逻辑）：

```python
# FA3 前向：warp specialization 骨架（简化示意，非逐字源码）
if role == PRODUCER:                       # 生产者：只搬数据
    for j in range(T_c):
        tma_load(K_j, V_j, stage=j % s)    # 发 TMA 搬运，硬件异步执行
        mbarrier_arrive(stage=j % s)       # 通知消费者：第 j 块就绪
        # 不等搬运完成，立即进入下一轮循环
else:                                      # 消费者：只算数据
    for j in range(T_c):
        mbarrier_wait(stage=j % s)         # 等第 j 块数据就绪
        wgmma(Q_i @ K_j.T, stage=j % s)    # 发异步 GEMM，不等它算完
        softmax_update(...)                # 处理上一块 GEMM 的结果
        wgmma(P_ij @ V_j, ...)
```

💡 **提示**：这里的 mbarrier 有点像快递柜的“取件码”——搬运工（TMA）放好货发个码，消费者凭码取货；取货和送货互不阻塞，柜子（SMEM 环形缓冲）有多个格位才能让两边错开节奏。

### 2.3 收益：350 → 540-570 TFLOPS

PyTorch 官方博客给出的分解数字（head dim 128、seqlen 8K、H100 SXM5）：光是把 FA2 的同步 kernel 改成 Warp Specialization + TMA + WGMMA，**FP16 前向就从约 350 TFLOPS 提到约 540-570 TFLOPS**——还没动算法结构，只是把“搬运”和“计算”从串行变成并行，就把利用率从 35% 拉到 55% 上下。

⚠️ **注意**：这里省掉的是**指令发射与等待延迟**，不是带宽。Producer 提前搬运意味着 Consumer 永远有数据可算；但如果你的 kernel 本来就 Memory-Bound（比如短序列 Decode），搬运已经是瓶颈，分工的收益会大幅缩水——后面第 6 节再展开。

## 3. 核心设计二：把 Softmax 藏进 GEMM 流水线

### 3.1 问题是什么：exp 是注意力里的“慢动作”

先看一组悬殊的数字。H100 SXM5 上：

$$
\underbrace{989 \text{ TFLOPS}}_{\text{FP16 矩阵乘吞吐}} \quad \text{vs} \quad \underbrace{3.9 \text{ TFLOPS}}_{\text{特殊函数（exp）吞吐}}
$$

差距约 256 倍。而 Attention 前向里，矩阵乘的 FLOPs 是 exp 相关操作的约 512 倍（head dim 128）。把两个比值放一起，就能算出 exp 的相对耗时：

$$
\frac{T_{\text{exp}}}{T_{\text{GEMM}}} = \underbrace{\frac{1}{512}}_{\text{exp 的 FLOPs 占比}} \times \underbrace{256}_{\text{吞吐差距（989/3.9）}} = 0.5
$$

**也就是说，即使矩阵乘已经由 Tensor Core 异步执行，softmax 里的逐元素操作（减 max、exp、求和、缩放）仍可能占用与 GEMM 相当（约 50%）的“墙钟时间”。** 原因：这些操作只能用 CUDA Core / SFU 跑，而 FA2 里它们和 GEMM 是**串行**的——算完 $S_{ij}$ 才能做 softmax，做完 softmax 才能算 $P_{ij}V_j$。如果用 FP8，GEMM 吞吐再翻一倍，exp 的占比会涨到接近 100%——softmax 直接从“配角”变成“主角瓶颈”。

为什么不能把 softmax 拆开藏进 GEMM？因为 attention 的三步存在数据依赖：$S_{ij} \xrightarrow{\text{softmax}} P_{ij} \xrightarrow{\text{GEMM}} P_{ij}V_j$，后一步必须等前一步。**关键洞察：依赖是“块间”的，不是“步内”的**——第 $j$ 个 K/V 块的 softmax 只依赖第 $j$ 块自己的 $S_{ij}$，而第 $j+1$ 块的 GEMM（$Q_i K_{j+1}^\top$）完全独立。把两个相邻块的“算 softmax”和“算 GEMM”交错开，就能让 Tensor Core 和 CUDA Core/SFU 同时忙碌。

### 3.2 设计：两阶段 Pingpong 调度

FA3 的 2-stage 版本把 consumer 的循环改成“一次推进两个 K/V 块”：

```
时间轴 →（2 个 warpgroup 交替干活，head dim 128 典型配置）
warpgroup A:   [GEMM0: QK_jᵀ]    [softmax_j]        [GEMM1: P_j V_j]   ...
warpgroup B:        [GEMM0: QK_{j+1}ᵀ]   [softmax_{j+1}]     [GEMM1: P_{j+1}V_{j+1}] ...
```

warpgroup A 在算第 $j$ 块的 softmax 时，warpgroup B 的 Tensor Core 正在算第 $j+1$ 块的 $QK^\top$；等 B 的 softmax 跑起来，A 又开始了下一块。两个 warpgroup 像打乒乓球一样交替，**GEMM 和 softmax 在任何时刻都至少有一个在跑**。注意：softmax 依赖的 $S_{ij}$ 是 WGMMA 异步写进寄存器的。处理它之前，要先从“异步代理”里取回结果（论文里的 commit + wait），softmax 才能和另一个 warpgroup 的 GEMM 重叠。

在单个 warpgroup 内部，还可以再做一层**3-stage 流水**：把 $QK^\top$（Matmul0）、Softmax、$PV$（Matmul1）当成三级流水线，让第 $j+1$ 块的 Matmul0 与第 $j$ 块的 Softmax、第 $j-1$ 块的 Matmul1 重叠。代价是寄存器压力显著上升，需要精细排布——论文对生成的 SASS 做了逐指令验证，编译器不会自动帮你排好。

### 3.3 收益：570 → 620 → 640-660 TFLOPS

PyTorch 博客的分解（FP16 前向，head dim 128，seqlen 8K）：Warp Specialization 之后约 570 TFLOPS，加上 pingpong 调度到约 **620 TFLOPS**，再加 3-stage 流水到约 **640-660 TFLOPS**。论文的消融实验（逐项关掉某个改进，看性能掉多少）也确认：warp specialization 与 GEMM-softmax 流水各自都贡献了可观的加速。

📌 **关键点**：FA3 的第二个设计本质上是**把“计算图”重排成软件流水线**——用“块间交错”打破“步内依赖”的假象，让低吞吐的 softmax 藏在高吞吐的 GEMM 背后。这个思路和 CPU 的指令流水线、以及分布式训练的 pipeline parallelism 是同一个思想在不同尺度的复现。

💡 **提示**：流水线的收益依赖“每级耗时匹配”。如果序列很短、K/V 块很少，流水线还没填满就结束了，收益大打折扣；块太大导致 SMEM 放不下多级缓冲，也会逼你减少流水深度。FA3 论文里对不同的 $B_r, B_c$ 和流水深度都做了调参，工程实现远比伪代码复杂。

## 4. 核心设计三：FP8 低精度与数值稳定

### 4.1 为什么用 FP8：吞吐翻倍 + 带宽减半

FP8 有 E4M3（4 位指数、3 位尾数）和 E5M2（5 位指数、2 位尾数）两种格式，FA3 前向用的是 **E4M3**。相比 FP16（5 位指数、10 位尾数），它牺牲了精度，换来两笔硬账：

- **Tensor Core 吞吐翻倍**：H100 上 FP8 稠密算力 1979 TFLOPS，是 FP16（989 TFLOPS）的 2 倍——同一块芯片、同样的功耗，低精度把算力翻倍；
- **数据字节减半**：Q、K、V、O 各少一半字节，同样带宽下数据吞吐翻倍，对 Memory-Bound 的 Attention 是直接的收益。

一个直观的账本（呼应学习路线的 KV Cache 算账）：LLaMA-2-7B 配置（32 层、32 头、head_dim=128）、上下文 4096、batch=16：

$$
\underbrace{2 \times 32 \times 32 \times 128 \times 4096 \times 16 \times 2\text{B}}_{\text{FP16 KV Cache}} = 32 \text{ GB} \quad \xrightarrow{\text{FP8}} \quad \underbrace{32 \text{ GB} / 2}_{\text{每元素 1 字节}} = 16 \text{ GB}
$$

KV Cache 直接省下 16 GB——这对推理场景意味着能多塞一倍的并发请求。

### 4.2 问题是什么：E4M3 的动态范围扛不住 outlier

FP8 的问题也很直白：**3 位尾数 + 4 位指数，动态范围比 FP16 小得多**。而大模型（尤其是 attention 分数）里偏偏有大量 outlier 特征——个别元素比其他元素大几个数量级。

如果像朴素量化那样给整张 $S$ 矩阵配一个全局 scale，那么 scale 被 outlier 撑大，其余正常元素的有效精度全被压缩，误差惨不忍睹。FA3 用两招组合解决：

**招数一：Block Quantization（分块量化）**。不给整张矩阵一个 scale，而是**每个块一个标量 scale**：$Q$ 按 $B_r \times d$ 分块、$K$ 按 $B_c \times d$ 分块、$V$ 同理，每块各自算 max 定 scale。块内 outlier 的影响被限制在本块，其他块不受牵连。

**招数二：Incoherent Processing（非相干处理）**。outlier 再分散，也总有个别块特别“倒霉”。论文的做法是：**量化之前，先把 $Q$ 和 $K$ 乘一个随机正交矩阵 $M$**（$M$ 取随机对角 ±1 矩阵与 Hadamard 矩阵的乘积）。这样一来，outlier 的能量被“打散”到整个块里：每个输出元素都变成输入的随机加权和，个别大值不再集中在少数位置。

打个比方：全班量身高，有人 2.2 米有人 1.5 米。全局一把尺子（per-tensor scale）会让矮个子的读数全部挤在一起分不清；**分块量化**是每排人用一把自己的尺子，**incoherent processing** 则是先把几个巨人打散到不同排，别让某一排因为巨人而整排失真。

Hadamard 变换本身是带宽受限的（逐元素操作），所以**可以和同样带宽受限的 RoPE 旋转位置编码融合，几乎免费**——这是论文里一个非常巧妙的工程细节。

⚠️ **注意**：这还没完。FP8 的 WGMMA 对第二个 GEMM 的 operand B 有 **k-major 布局约束**（矩阵按 k 维连续存放），而 $V$ 按惯例是 row-major（按行连续存放）存储的。所以 FA3 的 FP8 版还得处理 $V$ 的转置布局问题——论文里用了 kernel 内转置。这也是 FP8 版比 FP16 版实现更复杂的原因之一。

### 4.3 收益：接近 1.2 PFLOPs/s

论文报告：FP8 前向在 H100 上**接近 1.2 PFLOPs/s**（约 60% 的 FP8 峰值），并且相比“per-tensor 量化”的朴素 FP8 attention 基线，**数值误差降低 2.6 倍**——也就是说 FP8 的加速不是靠牺牲精度换来的，而是靠更好的量化策略“白拿”的。

📌 **关键点**：FA3 的 FP8 和“直接砍一半精度”是两回事。分块量化 + incoherent processing 把 FP8 的误差压到了可接受区间，这才是它能用于训练/推理的前提。

## 5. 性能数字与工程可用性

### 5.1 论文报告的加速比

FA3 论文（Shah, Bikshandi, Zhang, Thakkar, Ramani & Dao，2024，ICLR 2025）在 **H100 SXM5 80GB（700W）、CUDA 12.3** 上，FP16 测了 head dim 64/128，FP8 补充了 head dim 128/256，序列长度覆盖 512 到 16K+。核心数字：

| 📊 指标 | 论文数字 | 说明 |
|---------|---------|------|
| FA2 在 H100 的利用率 | 约 35%（~350 TFLOPS） | 同期优化 GEMM 为 80-90% |
| FA3 FP16 前向 vs FA2 | **1.5-2.0x**，最高 740 TFLOPS（75%） | 摘要数字 |
| FA3 FP16 反向 vs FA2 | **1.5-1.75x** | 论文引言 |
| FA3 FP8 前向 | **接近 1.2 PFLOPs/s** | FP8 峰值 1979 TFLOPS 的约 60% |
| FP8 vs 朴素 FP8 基线 | 数值误差**降低 2.6x** | per-tensor 量化为基线 |
| FP8 前向 vs FA2 | 常见解读引论文图表称最高约 2.7x（head dim 256） | **「待核实」**：摘要未直接给出该倍率，以论文图表原文为准 |

PyTorch 官方博客给出了更细的分解轨迹（FP16 前向，head dim 128、seqlen 8K）：FA2 约 350 TFLOPS → Warp Specialization 约 540-570 → +Pingpong 约 620 → +3-stage 流水约 640-660 → FP8 接近 1200 TFLOPS。

### 5.2 问题是什么：flash-attention 仓库里 FA3 到底能不能直接用

打开 [Dao-AILab/flash-attention](https://github.com/Dao-AILab/flash-attention) 你会发现：FA3 不在主路径里，而是独立的 `hopper/` 子模块（以仓库当前 README 为准，代码持续演进）：

- **硬件要求**：H100 / H800 GPU（即 Hopper SM90a），CUDA >= 12.3，官方建议 CUDA 12.8 获得最佳性能；
- **独立安装**：`cd hopper && python setup.py install`，用法是 `from flash_attn_3 import flash_attn_interface`，与主仓库的 `flash_attn_func`（仍是 FA2 kernel）互不相干；
- **功能范围**：FP16 / BF16 前向 + 反向、FP8 前向已发布；
- **成熟度声明**：README 明确写着 **“This is a beta release for testing / benchmarking before we integrate that with the rest of the repo”**——官方定位是“测试/基准对比用的 beta 版”，尚未与主仓库集成。

💡 **提示**：H800 是面向中国市场的 H100 变体（SM 架构同为 SM90a，只是 NVLink 带宽被阉割），所以也能跑 FA3 kernel——**决定能不能用 FA3 的是架构（SM90a），不是显存大小**。A100（SM80）和 RTX 4090（SM89）都跑不了。

⚠️ **注意**：论文 benchmark 用 CUDA 12.3，仓库却推荐 12.8——Hopper 的底层指令（PTX）和编译器在快速迭代，不同 CUDA 版本下 FA3 性能可能有明显差异。你复现时看到和论文不同的数字是正常的，先核对 CUDA 版本和 kernel 形状（head dim、seqlen、causal 与否）。

## 6. 权衡与选型

### 6.1 FA3 牺牲了什么

FA3 不是“免费午餐”，它用三样东西换性能：

- **实现复杂度**：producer/consumer 状态机、mbarrier 同步、多级环形缓冲、`setmaxnreg` 动态寄存器分配、WGMMA 的布局约束（FP8 还要处理 V 的转置）——每一件都比 FA2 的同步代码难一个量级。论文自己都承认需要对生成的 SASS 逐指令检查，防止编译器把精心排布的异步序列打乱；
- **硬件绑定**：核心假设（TMA、异步 WGMMA、FP8、SM90a）全部是 Hopper 专属。FA3 的 kernel 在 A100 上**根本编译不了**，可移植性极差；代码写死在单代架构上，Blackwell 时代大概率又要重写（FA4 已经在做了）；
- **调试难度**：异步 bug 是出了名的难复现——数据竞争、mbarrier 丢失、缓冲覆盖，这类问题在 Nsight 里表现为偶发的数值错误或挂起，排查成本远高于同步 kernel；
- **工程成熟度**：官方 beta 定位，尚未与主仓库集成，依赖方（如训练框架）要自己打补丁跟进上游变更。

### 6.2 什么场景不值得上 FA3

| 场景 | 推荐 | 理由 |
|------|------|------|
| A100 / 非 Hopper 硬件 | FA2 | FA3 kernel 无法编译，别无选择 |
| H100 上短序列（seqlen < 2K）、小 batch | 先用 FA2 压测 | 流水线填不满、块间并行不足，FA3 收益可能只有 1.1-1.2x，却要背上 beta 风险和集成成本 |
| Decode 阶段（Memory-Bound） | FA2（或第 6 章预告的 Flash-Decoding 等 Decode 加速文章） | 瓶颈是 KV 带宽不是算力，异步流水救不了带宽 |
| H100 长上下文 Prefill（Compute-Bound） | **FA3 FP16** | 这是 FA3 的主场：利用率 35% → 75% |
| 训练 / 推理要压榨吞吐，且能接受 FP8 精度策略 | **FA3 FP8** | 1.2 PFLOPs/s + KV Cache 减半，但要先跑精度验证（对比 FP16 输出的下游指标） |
| 生产环境、没人维护 kernel、追求稳定 | FA2（或等待 FA3 集成进框架） | beta 代码 + 高维护成本，稳定性优先时别当小白鼠 |

决策规则：**卡是 Hopper、算的是长序列 Prefill、且你能接受 beta 软件与调试成本 → 上 FA3；否则 FA2 依然是正确选择。** 别为了“显得先进”在 A100 集群里强行移植 FA3——那只是把论文里的数字当信仰，换不来任何收益。

## 📝 总结

1. **FA2 的瓶颈**：同步编程模型 + Ampere 风格指令 + 无低精度，在 H100 上只有约 35% 利用率（~350 TFLOPS），而优化 GEMM 能到 80-90%——差距来自没用上 Hopper 的异步能力。
2. **Warp Specialization**：producer warpgroup 专职 TMA 搬运、consumer warpgroup 专职 WGMMA 计算，用 mbarrier + 多级环形缓冲解耦——仅此一项 FP16 前向就提到约 540-570 TFLOPS。
3. **GEMM-softmax 流水**：exp 吞吐只有 GEMM 的 1/256，head dim 128 时 softmax 耗时可达 GEMM 的 50%；用两阶段 pingpong（块间交错）和三阶段流水把 softmax 藏进 GEMM——570 → 620 → 640-660 TFLOPS。
4. **FP8**：E4M3 让 Tensor Core 吞吐翻倍（1979 TFLOPS）、数据字节减半；分块量化 + incoherent processing（Hadamard 变换）把数值误差做到比 per-tensor 基线低 2.6 倍，前向接近 1.2 PFLOPs/s。
5. **工程现实**：FA3 是 Hopper（SM90a）专属的 beta 模块，独立安装、独立接口，FP16/BF16 双向 + FP8 前向已发布，尚未与主仓库集成。
6. **权衡**：FA3 用实现复杂度、硬件绑定、调试难度和软件成熟度，换来了 H100 上 1.5-2.0x（FP16）乃至接近 3x（FP8，待核实）的加速——值不值，取决于你是不是“长序列 Prefill + Hopper + 有人维护”的组合。

## ⚠️ 常见错误做法

- ❌ **把 FA3 的收益完全归给 WGMMA 指令**：只记住“用了新的 Tensor Core 指令”。为什么错：FA3 的核心是流水线级重叠（生产者-消费者解耦）与异步拷贝（TMA），WGMMA 只是让计算更短的工具之一。正确做法：按“算得短（指令）+ 等得少（重叠）+ 搬得快（TMA）”三条线理解。
- ❌ **在 Ampere 上硬上 FA3 的代码路径**：把针对 Hopper 的 kernel 直接搬过去。为什么错：WGMMA、TMA、集群都是 Hopper+ 特性，Ampere 没有这些硬件，代码要么不兼容要么退化。正确做法：按硬件代际选择 FA1/FA2/FA3。
- ❌ **忽略累加器精度**：用 FP16 累加器做块内 GEMM 累加。为什么错：长序列累加误差会累积，精度受损。正确做法：用 FP32 累加器（Tensor Core 原生支持），仅在最终输出时转回 FP16。
- ❌ **以为 FA3 的 75% 利用率是白来的**：不做任何 profiling 就宣称“用了 FA3 就快”。为什么错：75% 是论文在特定形状与硬件上的结果，实际利用率取决于序列长度、头数、块大小的匹配。正确做法：用 Nsight Compute 实测 MFU，再调块大小。
