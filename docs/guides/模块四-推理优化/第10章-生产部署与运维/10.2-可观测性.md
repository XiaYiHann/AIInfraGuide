"服务慢了"和"哪里慢了、为什么慢、要不要扩"是两件事,可观测性解决的是后者。有个反直觉的实测:一个 L4 实例上,单个请求就能把 GPU 利用率顶到 **92%**,而真正过载时利用率反而掉到 73%、P95 TTFT 冲到 28 秒以上——**只盯 nvidia-smi,你会把"服务已死"看成"一切正常"**。本文给你一套能直接落地的 LLM 可观测性体系:vLLM 在 `/metrics` 上暴露的 Prometheus 指标怎么读(负载、延迟、KV Cache、抢占),Prometheus + Grafana 怎么采怎么画,结构化日志与请求级日志看什么,以及**把 SLO 变成三条能叫醒值班人的告警规则**——最后讲清楚为什么"先指标、后日志,先告警、后追踪"。9.5 的门禁管"合入前",这一节管"上线后"。

## 1. 可观测性三支柱:体检、门诊与影像

### 1.1 三支柱在 LLM 服务里长什么样

可观测性的三个支柱,在 LLM 服务里各有各的活儿:

- **指标(Metrics)**:数字化的健康度快照——每秒多少请求、TTFT 多长、KV Cache 用了多少。回答"**服务健康吗**";
- **日志(Logs)**:一次具体事件的过程记录——哪个请求超时了、报了什么错、拒绝原因是什么。回答"**这件事发生了什么**";
- **追踪(Traces)**:一个请求从网关到引擎再到 GPU 的完整路径。回答"**时间花在哪一段**"。

打个比方:这三者是**体检与门诊**的分工——指标是体检报告,定期量血压、看趋势,单次读数不重要、趋势才重要;日志是门诊病历,某次"不舒服"的详细记录;追踪是全身影像,把一次请求从头到尾的路径照出来。平时靠体检报告过日子,不舒服了翻病历,搞不清病因再拍片子。

### 1.2 为什么"看 nvidia-smi 调试"不够

开发期调试,`nvidia-smi` 看一眼显存和利用率就够了;生产期它有三宗罪:

1. **没有历史**:它是单次快照,昨晚 2 点发生了什么,今天早上查不到;
2. **没有关联**:GPU 利用率 90%,但你不知道这 90% 是在服务用户还是在空转——[7.1 讲过](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/71-混合batching互扰分析),大 prefill 把 GPU 顶满时,小请求的 TPOT 正在被拖到 5 倍;
3. **没有告警**:没有人会盯着终端看,只有系统能 7×24 盯指标并打电话叫醒你。

说白了：单次测量是快照，可观测性是长曝光——**快照告诉你“此刻”，长曝光让趋势显形**。这正是 9.5 讲门禁时的同一句话，门禁管代码，可观测性管服务。另外，GPU 利用率本身在 LLM 服务里是“穷人指标”：[2.2](/AIInfraGuide/inference/模块四-推理优化/第2章-推理引擎核心技术/22-continuous-batching) 说过 Continuous Batching 能让利用率长期 80%+，利用率低一定有问题，**利用率高却什么都说明不了**——判断容量够不够，看队列深度和 KV Cache 利用率，不看 GPU 利用率。

## 2. vLLM 的 Prometheus 指标:先认识这张体检表

vLLM 的 OpenAI 兼容服务默认在 **`/metrics`** 端点暴露 Prometheus 兼容指标(不需要任何开关,启动即有),全部带 `vllm:` 前缀,并且**每个指标都带 `model_name` 标签**(取值来自 `--served-model-name`,多副本按模型聚合就靠它)。指标名随版本演进,以你所用版本的 `/metrics` 输出为准;老版本被隐藏的指标可以用 `--show-hidden-metrics-for-version` 临时找回,方便迁移。

⚠️ **注意**:网上有教程让你找 `--metrics-format` 参数切换输出格式——**vLLM 目前没有这个 CLI 参数**(已查证最新 CLI 文档),`/metrics` 固定输出 Prometheus 文本格式。别把时间花在找不存在的参数上;`/load` 端点倒是可以通过 HTTP 头指定输出格式(以你所用版本的 API 文档为准)。

### 2.1 指标的三类基本款

Prometheus 指标只有三类,先分清再读表:

- **Counter(计数器)**:只增不减,重启归零。如累计生成的 token 数、抢占总次数;
- **Gauge(仪表)**:上下浮动。如当前 running/waiting 请求数、KV Cache 利用率;
- **Histogram(直方图)**:把样本按桶计数。如 TTFT:记录"多少个请求 TTFT < 1ms、< 5ms、< 10ms…"。**分位数(P95)要从直方图算出来**,公式长这样(记不住没关系,会用就行):

$$
\underbrace{\text{histogram\_quantile}(0.95, \underbrace{\text{sum}(\text{rate}(vllm:time\_to\_first\_token\_seconds\_bucket[5m]))}_{\text{近 5 分钟每秒的桶计数,按桶聚合}})}_{\text{95\% 请求的 TTFT 落在哪个桶}}
$$

### 2.2 延迟:TTFT、TPOT 与端到端

延迟是用户体验,也是 SLO 的主战场([9.1](/AIInfraGuide/inference/模块四-推理优化/第9章-性能分析与benchmark/91-推理指标体系) 的六件套口径)。三张直方图各管一段:

| 📊 指标(以你所用版本为准) | 含义 | 怎么读 |
|---|---|---|
| `vllm:time_to_first_token_seconds` | TTFT 直方图:首 token 延迟 | 用户等多久才开口;桶范围到几百秒,长 prompt 排队时 P95 会冲高 |
| `vllm:time_per_output_token_seconds`(V0 名称)/ `vllm:inter_token_latency_seconds`(V1 名称) | TPOT 直方图:逐 token 间隔 | 用户体感"卡不卡";**TPOT P95 是 9.5 门禁与 SLO 的核心判定线** |
| `vllm:e2e_request_latency_seconds` | 端到端延迟直方图(含排队) | 整个请求从进来到完成的时长,看容量饱和最直接 |
| `vllm:request_queue_time_seconds` / `request_prefill_time_seconds` / `request_decode_time_seconds` / `request_inference_time_seconds` | 分阶段耗时直方图 | 排队久=容量问题;prefill 久=算力;decode 久=KV 带宽 |

💡 **提示**:P50 均值被大 batch 掩盖的坑在 9.5 讲过——**读直方图一律看 P95/P99**,别让均值骗你"一切正常"。

### 2.3 负载:running、waiting 与队列深度

| 📊 指标 | 含义 | 怎么读 |
|---|---|---|
| `vllm:num_requests_running` | 正在执行的请求数 | 与 `--max-num-seqs` 对比:长期贴着上限 = 满载 |
| `vllm:num_requests_waiting` | 排队等待的请求数 | **容量预警第一指标**:持续 > 0 说明 GPU 喂不饱请求了 |
| `vllm:num_requests_swapped` | 被换出到 CPU 的请求数 | 长期 > 0 = KV 不够在反复换入换出,性能灾难 |

打个比方:running 是**正在拣货的订单**,waiting 是**挂在待处理区的订单**。偶尔有单排队正常;但待处理区越堆越高,不是订单太多,是**拣货台(GPU)产能到顶了**——这时候该加拣货台(扩容)或限单(限流),而不是催工人。

⚠️ **注意**：vLLM 有个反直觉特性——**waiting 只会在“请求还没进引擎”时排队**。V1 引擎下并发超限时新请求要么进 waiting、要么直接被拒，具体行为取决于版本与配置；所以告警要看“waiting 持续高位”而不是“waiting 出现过”，配合 `vllm:request_success`（按 finish_reason 计数的成功/失败计数，以版本为准）看拒绝率。

### 2.4 资源:KV Cache 利用率与抢占

这是 LLM 服务独有的体检项,也是**比 GPU 利用率更真实的容量信号**(10.1 第 3.2 节算过账:KV 余量决定并发上限):

| 📊 指标 | 含义 | 怎么读 |
|---|---|---|
| `vllm:gpu_cache_usage_perc`(较新文档也写作 `vllm:kv_cache_usage_perc`) | GPU KV Cache 利用率,1 = 100% | **> 0.9 就该扩缩容或限流**;持续 1.0 意味着抢占开始 |
| `vllm:num_preemptions` | 抢占累计次数（Counter，新版本去掉了 `_total` 后缀，以版本为准） | rate 看趋势：飙升 = KV 不够，调度器在“抢旧请求的缓存给新请求” |
| `vllm:prefix_cache_queries` / `vllm:prefix_cache_hits` | 前缀缓存查询/命中计数 | 命中率 = 前缀复用收益;多副本部署时命中率低,先查路由策略(10.1 的 Production Stack) |
| `vllm:cache_config_info` | 缓存配置信息（Info 型 Gauge，以版本为准） | 确认 `--max-model-len`、KV 分配是否与预期一致 |

打个比方：KV Cache 利用率像**水库的蓄水位**。水位 60% 一切从容；到 90%，就该提前泄洪（限流）或扩容，而不是等它漫坝——漫坝在 LLM 服务里的样子就是 **preemption 飙升、请求被换出、TPOT 尾延迟爆炸**。

### 2.5 吞吐:token 计数与 5 秒快照

- `vllm:prompt_tokens` / `vllm:generation_tokens`（旧版本带 `_total` 后缀）：累计处理的输入/输出 token 数，`rate` 一下就是吞吐（token/s），是[容量规划（10.4）](/AIInfraGuide/inference/模块四-推理优化/第10章-生产部署与运维/104-容量规划)和压测（9.2）的线上对照；
- `vllm:iteration_tokens_total`:每次引擎 step 处理 token 数的直方图,看"GPU 一个调度循环喂了多少 token",batch 效率的诊断指标。

**还有一个免费的"穷人版指标面板"**:vLLM 默认每 **5 秒**在 INFO 日志打一行快照——running/waiting 请求数、GPU KV Cache 利用率、近 5 秒 prompt token 速率、近 5 秒生成 token 速率、最近 1k 次 KV 块查询的前缀命中率。没有 Prometheus 时,`kubectl logs -f` 看这一行就能应急判断;有 Prometheus 后,它依然是最快的"人肉可读"摘要。

## 3. 采集与展示:Prometheus + Grafana

### 3.1 Prometheus 抓取配置

采集就一件事:让 Prometheus 定期 GET `/metrics`。最小配置(以你所用版本为准):

```yaml
# prometheus.yml(简化示意)
global:
  scrape_interval: 5s        # vLLM 指标是 Gauge 型,5~15s 都行
  evaluation_interval: 30s   # 告警规则评估周期

scrape_configs:
  - job_name: vllm
    static_configs:
      - targets: ['vllm-service:8000']   # 指向 K8s Service 或 Pod IP
```

K8s 里更规范的做法是 **ServiceMonitor**(Prometheus Operator 的 CRD):声明"抓取带 `app: vllm` 标签的 Service 的 8000 端口",自动发现副本,新 Pod 起来不用改配置——vLLM Production Stack 的 Helm 里就自带这个 ServiceMonitor,裸 K8s 部署时自己写一个也就 15 行。

⚠️ **注意**:Prometheus 的抓取周期别太激进。vLLM 的指标是内存里聚合的,**1 秒抓一次和 15 秒抓一次看到的值基本一样**,还白费资源;倒是 `scrape_interval` 和告警规则的 `for:` 窗口要匹配——抓取间隔 15s 时,`for: 5m` 的告警大约需要 20 次连续抓取确认,语义上没问题,但别设 `for: 10s` 这种比抓取间隔还短的窗口。

### 3.2 Grafana 看板:先抄再改

看板别从零画,三条现成路径:

1. **vLLM 官方 example**:官方文档的 Prometheus/Grafana 示例带一个 `grafana.json`,导入即可,覆盖 e2e 延迟、TTFT 分布、请求数等;
2. **Production Stack 自带看板**:`vllm-dashboard.json`、`vllm-model-metrics-dashboard.json`,随 Helm 安装,面板更全;
3. **自建七件套**(学完第 2 节你应该能自己画):实例健康数 → e2e 延迟分布 → TTFT P95 → running 请求数 → waiting 请求数 → GPU KV 利用率 → 前缀命中率。

📌 **关键点**:看板的面板数量要克制——**每个面板都要能回答一个问题**("要不要扩容"、"用户卡不卡"、"缓存有没有生效"),凑数的面板只会让值班人眼瞎。10.1 说过 Production Stack 的 Grafana 面板清单,和这里七件套是同一套口径。

## 4. 日志:结构化与请求级

### 4.1 结构化日志:让日志能进搜索引擎

默认的 vLLM 日志是给人看的纯文本,但生产排障要按字段过滤("这个 request_id 的所有日志""level=ERROR 的 5 分钟窗口"),纯文本做不到。vLLM 没有 `--log-format json` 这种一行参数(查证:该开关只存在于 Production Stack 的 Router 里),正确的做法是给**日志配置一个 JSON formatter**,通过环境变量 `VLLM_LOGGING_CONFIG_PATH` 指向一个 JSON 格式的 logging 配置(以你所用版本的官方文档为准):

```json
{
  "version": 1,
  "formatters": {
    "json": {
      "class": "pythonjsonlogger.jsonlogger.JsonFormatter"
    }
  },
  "handlers": {
    "console": {
      "class": "logging.StreamHandler",
      "formatter": "json",
      "level": "INFO",
      "stream": "ext://sys.stdout"
    }
  },
  "loggers": {
    "vllm": { "handlers": ["console"], "level": "INFO", "propagate": false }
  }
}
```

```bash
# 启动时指定日志配置(python-json-logger 已内置在官方镜像)
VLLM_LOGGING_CONFIG_PATH=/path/to/logging_config.json vllm serve <model>
```

配好之后每条日志带 `timestamp/level/logger/message/filename/lineno` 字段,接 Loki/Elasticsearch 后可以按 level、按时间窗、按关键字精确检索——**日志的价值不在"能看",在"能查"**。附带:级别用 `VLLM_LOGGING_LEVEL` 控制(默认 INFO),生产别开 DEBUG,否则 token 级日志会淹没磁盘。

### 4.2 请求级日志与访问日志

两层请求日志要分清:

- **访问日志(uvicorn access log)**:每个 HTTP 请求一行。生产上 **`/health`、`/metrics`、`/ping` 每秒被探针和采集器打几十次**,会淹没真正的业务请求日志——用 `--disable-access-log-for-endpoints /health,/metrics,/ping` 把这些端点静音,或用 `--disable-uvicorn-access-log` 全关(以你所用版本为准);
- **请求级日志(vLLM 层)**:`--enable-log-requests` 开启,INFO 级别输出 request_id、参数、LoRA 信息;DEBUG 级别连 prompt 文本都打。**排障利器,但生产慎开 DEBUG**(prompt 可能含敏感数据)。

### 4.3 日志里看什么

排障时按这个顺序翻日志:

1. **ERROR/WARNING**:`OutOfMemoryError`(权重 OOM,10.1 讲过)、`Client disconnected`(客户端断连,常见于超时)、`KeyboardInterrupt: terminated`(探针误杀,查 10.1 的探针配置);
2. **请求拒绝**:503/429 相关日志——`request_success_total` 指标告诉你"拒了多少",日志告诉你"拒的是谁";
3. **慢请求**:request_id 级别的时间戳差,配合指标定位"是排队慢(看 queue time)还是生成慢(看 decode time)";
4. **那行 5 秒快照**:启动后第一眼先看它,running/waiting/KV 利用率一眼尽收。

## 5. 告警设计:把 SLO 变成值班电话

### 5.1 黄金指标:先定哪些数字值得半夜叫醒你

告警设计的第一步不是写 PromQL,是回答"**哪些数字坏了值得半夜叫醒人**"。答案是黄金指标——直接反映用户体验和容量,且坏了有明确动作:

| 📊 黄金指标 | 为什么是它 | 动作 |
|---|---|---|
| TPOT P95 / TTFT P95 | 用户体感(SLO 本体) | 扩容 / 回滚 / 查引擎 |
| `num_requests_waiting` | 容量预警,比 GPU 利用率早 5~10 分钟 | 扩容 / 限流 |
| `gpu_cache_usage_perc` | 抢占与 OOM 的前兆 | 限流 / 扩容 / 降并发 |
| preemption rate | KV 不足的直接证据 | 同上 |

阈值怎么定,两条纪律(9.5 的 3σ 原则 + SLO 锚定,详见 [7.4](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/74-goodput与slo调度)):

1. **先测噪声,再定阈值**:同一负载重复测,TPOT P95 波动 3~5% 是常态;阈值必须 ≥ 3 倍噪声,否则天天误报,值班人两周后就把告警静音了;
2. **阈值锚在 SLO 的 80% 处**:SLO 是 60ms,告警线设 48ms——**留出 20% 的提前量**,等 SLO 违约再告警,用户已经受害了。

### 5.2 三条示例告警规则

假设 SLO:TPOT P95 < 60ms、TTFT P95 < 800ms。三条规则直接抄(指标名以你所用版本为准):

```yaml
# 简化示意:告警规则(Alertmanager 接收)
groups:
  - name: vllm-slo
    rules:
      # 规则 1:TPOT P95 超过 SLO 的 80%(48ms)持续 5 分钟 → P1
      - alert: TPOT_P95_Above_SLO_Budget
        expr: |
          histogram_quantile(0.95,
            sum(rate(vllm:inter_token_latency_seconds_bucket[5m])) by (le))
          > 0.048
        for: 5m
        labels: { severity: page }
        annotations: { summary: "TPOT P95 超过 SLO 预算" }

      # 规则 2:KV Cache 利用率 > 90% 持续 5 分钟 → P1(容量告警)
      - alert: KV_Cache_Usage_High
        expr: vllm:gpu_cache_usage_perc > 0.9
        for: 5m
        labels: { severity: page }

      # 规则 3:抢占速率飙升(近 5 分钟每秒抢占 > 0.5 次)→ P2(先观察)
      - alert: Preemption_Rate_Spike
        expr: rate(vllm:num_preemptions[5m]) > 0.5
        for: 5m
        labels: { severity: ticket }
```

**阈值推导示例**：规则 1 的 48ms 怎么来的？SLO 60ms × 0.8 = 48ms；`for: 5m` 保证“持续 5 分钟”而不是一次尖刺——vLLM 里偶发的大 prefill 会让 TPOT P95 瞬间冲高（[7.1](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/71-混合batching互扰分析) 的互扰），**一次尖刺是噪声，持续 5 分钟是事故**。规则 2 的 0.9 是 KV 池的水位警戒线：KV 池剩余 <10% 时抢占随时开始，与 10.3 的 0.7 目标同源——别和 `--gpu-memory-utilization` 的 0.9 混为一谈，那是整卡配额，这是 KV 池内的水位。规则 3 的 0.5 次/秒是经验起点，按你环境的噪声校准。

💡 **提示**:告警和扩缩容是同一批信号的两个消费方——`num_requests_waiting` 超阈值既可以发 P1,也可以作为 HPA 的输入([10.3](/AIInfraGuide/inference/模块四-推理优化/第10章-生产部署与运维/103-自动扩缩容与负载均衡) 展开)。HPA 的数学很简单:期望副本 = 当前副本 × 当前值 ÷ 目标值,例如 6 个副本、总 waiting 24、目标每副本 ≤ 2,则期望副本 = 6 × 4 ÷ 2 = **12**——**告警阈值和 HPA 目标值要保持同口径,否则出现"告警说扩容、HPA 说不用"的矛盾**。

### 5.3 告警风暴避免:聚合、去重与分级

告警系统最大的敌人是自己——一次 KV 打满,preemption、TPOT、waiting 三条规则同时触发,值班人被 3 条告警轰炸。三板斧:

1. **聚合**:多副本实例的同一指标聚合后再告警(`sum by(model_name)`),"集群级"问题一次告警,而不是每副本一条;
2. **分级**:P0(服务不可用)/ P1(立即处理,SLO 违约)/ P2(工作时间内处理,趋势问题)——**只有 P0/P1 半夜叫人**;
3. **去重与抑制**:Alertmanager 的 group_wait 把同一告警的重复通知合并;发布窗口期用静默(maintenance window)压掉已知告警——发布本身会触发探针和延迟告警,提前静默 30 分钟,别让值班人半夜为"已知的发布"爬起来。

## 6. 端到端追踪:OTel 现状与请求链路

指标回答"哪里慢",追踪回答"为什么慢"。vLLM 的 OpenTelemetry 支持现状(以你所用版本的官方文档为准):

- **Traces(支持,实验性)**:`--otlp-traces-endpoint` 指定 OTLP 接收端,配套标准环境变量 `OTEL_SERVICE_NAME`、`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`(默认 grpc 协议,可用 `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf` 切换);OpenTelemetry 核心包已内置在官方镜像,无需手动安装;
- **Metrics 走 OTel:尚未完成**——社区 issue 仍在讨论指标抽象层,目前 /metrics 只有 Prometheus 一条路;
- 更细的模块级追踪(`--collect-detailed-traces`)官方明确提示**有性能开销**,生产慎开。

最小链路怎么搭：客户端（或网关）注入 trace 上下文 → vLLM 的 FastAPI 层生成 span（一段执行的时间片段） → 引擎层 span → 汇入 Jaeger/OTel Collector:

```bash
# 简化示意:跑一个 Jaeger,让 vLLM 把 traces 送过去
docker run -d --name jaeger -p 4317:4317 -p 16686:16686 jaegertracing/all-in-one
export OTEL_SERVICE_NAME="vllm-server"
export OTEL_EXPORTER_OTLP_TRACES_INSECURE=true
vllm serve <model> --otlp-traces-endpoint=grpc://localhost:4317
```

看一次请求的 trace,能直接回答三个问题:**排队花了多久(WAITING span)、prefill 多久、decode 多久**——这正是 2.2 节三张直方图的单请求版本。日志、指标、追踪通过 `request_id`(vLLM 请求级日志里有)串起来,就构成完整闭环:指标发现异常 → 日志看细节 → trace 定位阶段。

## 7. 权衡与落成一句话

可观测性建设的投入产出比极高,但也不是越多越好。落成一句话的规则:

- ✅ **先指标,后日志**:指标能回答"要不要扩容",这是 80% 的运维决策;第一周只搭 Prometheus + 七件套看板;
- ✅ **先告警,后追踪**:告警是"止损",追踪是"查因"——没有告警,你根本不知道什么时候该去查;第三四周再加 OTel 追踪;
- ✅ **指标别贪多**:能回答"要不要扩缩容、用户卡不卡、缓存有没有生效"就够(七件套封顶),**每个面板和每条告警都要能说出它要回答的问题**;
- ✅ **阈值先测噪声**:阈值 ≥ 3 倍测量噪声、锚在 SLO 的 80%,误报是告警系统最快的死法;
- ❌ **别一上来就全上**:先指标后日志、先告警后追踪的顺序不是保守,是**让每一层在被需要时才引入复杂度**——追踪系统本身要运维,没人看的看板是负债不是资产。

牺牲与换取的总账:**可观测性牺牲"建设与维护成本",换取"故障定位时间从小时级降到分钟级、容量决策从拍脑袋变成看数据"**——这是 9.5 门禁逻辑的线上延伸:门禁让性能退化在合入前暴露,可观测性让它在线上 5 分钟内暴露。

## 📝 总结

1. **三支柱分工**：指标（健康度）/ 日志（事件细节）/ 追踪（链路阶段），对应体检报告、门诊病历与全身影像；nvidia-smi 是单次快照，只解决“现在”，不解决“趋势与关联”。
2. **指标三类型**:Counter 只增、Gauge 浮动、Histogram 算分位;P95 用 `histogram_quantile(0.95, sum(rate(..._bucket[5m])) by (le))` 从直方图取。
3. **核心指标**：延迟（TTFT/TPOT/e2e 直方图，TPOT 在 V1 叫 `inter_token_latency_seconds`）、负载（`num_requests_running/waiting/swapped`）、资源（`gpu_cache_usage_perc` > 0.9 即警戒、`num_preemptions` 飙升即 KV 不足）、吞吐（`prompt/generation_tokens`，旧版带 `_total`）；另有一行每 5 秒的 INFO 快照免费送。
4. **采集展示**:Prometheus 5~15s 抓 `/metrics`(K8s 用 ServiceMonitor 自动发现);Grafana 先导入 vLLM 官方或 Production Stack 看板,自建控制在七件套。
5. **日志**:`VLLM_LOGGING_CONFIG_PATH` 指向 JSON formatter 配置实现结构化;`--enable-log-requests` 开请求级日志;`--disable-access-log-for-endpoints /health,/metrics,/ping` 压访问日志噪声。
6. **告警**:黄金指标四条(TPOT/TTFT P95、waiting、KV 利用率、抢占率);阈值 = SLO × 0.8 且 ≥ 3σ 噪声;`for: 5m` 区分"尖刺"与"事故";聚合、分级、静默三板斧防风暴。
7. **追踪**:`--otlp-traces-endpoint` 接 Jaeger 即可用(实验性);OTel metrics 未完成;上线顺序"先指标后日志,先告警后追踪"。
