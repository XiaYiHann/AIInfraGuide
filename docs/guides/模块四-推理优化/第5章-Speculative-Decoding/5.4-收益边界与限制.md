投机解码不是免费的午餐。5.1 的公式告诉我们：加速比 = 期望接受 token 数 ÷ （1 + γ × draft 相对开销）。代入数字：接受率 0.8、投机长度 γ=4、draft 每 token 耗时只有 target 的 5% 时，理论加速约 2.8x;可一旦接受率掉到 0.4、draft 开销涨到 20%，加速比反而跌破 1--**投机解码从“赚”到“亏”，只隔着接受率和 draft 开销这两个变量**。本文承接 5.1 的公式，推导收益为负的边界条件；再逐一拆解温度、模型差距、任务类型、γ 选择四个影响接受率的因素。接着盘点与量化、Continuous Batching、Prefill 叠加时的工程耦合风险，最后给你一份“先测再上”的验证原则——这也是学习路线 3.4 检验标准里“不赚边界 ≥3 种”的完整答案。

## 1. 收益公式回顾：什么时候收益为负

### 1.1 从 5.1 接过来的两个公式

5.1 推导过两个核心结果，这里直接复用。假设 draft 每个位置的接受概率都是 β（独立同分布：每个位置互不影响，概率都一样），投机长度 γ,则每一轮“draft 猜 γ 个 + target 验证一次”里，**期望产出的 token 数**为：

$$
\mathbb{E}[\tau] = \underbrace{\frac{1 - \beta^{\gamma+1}}{1 - \beta}}_{\text{几何分布的期望，被 γ 截断}}
$$

推导拆成三步：

**步骤 1**：设第一个被拒的位置是第 $k$ 个（$1 \le k \le \gamma$），意味着前 $k-1$ 个 draft token 全被接受、第 $k$ 个被拒，概率 $\beta^{k-1}(1-\beta)$，这一轮产出 $k$ 个 token（$k-1$ 个直接用的 + 1 个 target 当场重采的）。

**步骤 2**：全部 $\gamma$ 个都被接受的概率是 $\beta^\gamma$，此时 target 还会再采一个自己的 token，产出 $\gamma+1$ 个。

**步骤 3**：对 $k=1..\gamma$ 求期望求和，加上全中情况：$\mathbb{E}[\tau] = \sum_{k=1}^{\gamma} k\beta^{k-1}(1-\beta) + (\gamma+1)\beta^\gamma$，化简就是上式（把求和写成几何级数导数的形式，代入即可验证）。

再除以单轮耗时得到**加速比**：

$$
S = \frac{\mathbb{E}[\tau] \cdot T_{\text{target}}}{\underbrace{\gamma \cdot T_{\text{draft}}}_{\text{draft 串行 γ 步}} + \underbrace{T_{\text{target}}}_{\text{target 并行验证一次}}} = \frac{\mathbb{E}[\tau]}{1 + \gamma c}, \quad c = \frac{T_{\text{draft}}}{T_{\text{target}}}
$$

其中 $c$ 是 draft 每 token 耗时相对 target 的比值（draft 通常小一个数量级，c 在 0.05~0.3 之间）。

💡 **提示**：代入 Leviathan 论文的经典算例验证公式一致性——β=0.6、γ=2、c=0（draft 白送）时，$\mathbb{E}[\tau] = (1-0.6^3)/0.4 = 1.96$，加速 1.96x，算术量放大 (γ+1)/E = 3/1.96 ≈ 1.53 倍——和论文报告的两个数字完全吻合。**公式没错，错的是假设**：真实接受率不是常数，这就是第 2 节要拆的事。

另一个实操问题：$c$ 怎么估？不用翻论文——在目标硬件上分别测一次 draft 和 target 的单 token decode 延迟，相除即可。Decode 是 Memory-Bound，同硬件上小模型大致按参数量比均摊带宽：1B draft 对 70B target，c 通常在 1/70~1/30 量级；如果用了 7B 级别的 draft（c ≈ 0.3+），第 1.2 节的账本会告诉你为什么它很难赚。

### 1.2 收益为负的边界

加速比小于 1 意味着什么？**开启投机后反而比普通解码更慢**。边界条件直接从公式反解：

$$
S < 1 \iff \mathbb{E}[\tau] < 1 + \gamma c
$$

用大白话翻译：**一轮投机平均产出的 token 数，必须大于“白付的 draft 开销”折算的 token 数，否则就是亏**。代入一组典型值看看边界在哪——γ=4 时不同 (β, c) 组合的加速比（以下为公式推算值，需在你自己的硬件上验证）：

| 📊 β（接受率） | c = 0.05 | c = 0.1 | c = 0.2 |
|---|---|---|---|
| 0.8 | 2.80x | 2.40x | 1.87x |
| 0.6 | 1.92x | 1.65x | 1.28x |
| 0.5 | 1.61x | 1.38x | 1.08x |
| 0.4 | 1.37x | 1.18x | **0.92x 亏** |
| 0.3 | 1.19x | **1.02x 勉强** | **0.79x 亏** |
| 0.2 | **1.04x 勉强** | **0.89x 亏** | **0.69x 亏** |

📌 **关键点**：接受率 0.4~0.5 是“灰色地带”——draft 足够便宜（c ≤ 0.1）还能勉强赚，draft 稍贵就亏。这就是学习路线里“**Draft 与 Target 能力差距过大导致 acceptance < 50% 时收益为负**”的数学来源：不是 50% 本身有魔力，而是代入常见 γ=4、c≥0.1 后它恰好是盈亏分界。

用这张表的正确姿势：**先估 c**（硬件上各测一次 decode 延迟相除），**再测 β**（拿 100 条真实 prompt 跑一轮，看首位接受率，统计方法见 5.5）。落在右下角（β < 0.4 且 c ≥ 0.1）直接放弃，别浪费时间调参；落在左上角（β ≥ 0.7、c ≤ 0.1）才值得花力气调 γ 和树宽。

🔑 **接受率 vs 加速比**：**接受率（β）是 draft 与 target 分布的“重叠度”，衡量“猜得准不准”；加速比（S）是期望产出除以总开销，衡量“赚不赚”**。接受率高只是赚的必要条件——5.5 会讲 vLLM Issue #16258 的 ngram 反例：接受率 69.8% 但吞吐反而下降，因为命中的片段太短、验证开销摊不平。面试官问“接受率 70% 是不是就能加速”，答案是：**不一定，还要看 γ 和 draft 开销**。

### 1.3 收益饱和：γ 不是越大越好

把加速比对 γ 求导会发现一个反直觉结论：**收益随 γ 先升后降**。原因是 $\mathbb{E}[\tau]$ 随 γ 增长而**饱和**——当 γ 很大时 $\beta^{\gamma+1} \to 0$，期望接受数收敛到 $1/(1-\beta)$（β=0.8 时上限 5 个 token），而分母 $1+\gamma c$ 却在线性上涨。β=0.8、c=0.05 的 γ 扫描：

| 📊 γ | E[τ] | 加速比 |
|---|---|---|
| 1 | 1.80 | 1.71x |
| 4 | 3.36 | 2.80x |
| 8 | 4.33 | **3.09x（峰值）** |
| 16 | 4.89 | 2.72x |
| 32 | 5.00 | 1.92x |

📌 **关键点**：γ=8 之后边际收益从 0.13 一路跌到 0.02，却要付一份 draft 开销——**最优 γ 只取决于 (β, c)，与模型大小无关**。vLLM 社区实测也印证了这一点：PR #24322 在 Qwen3 上最优 γ=3~4，在 Llama-3.3-70B 上最优 γ≈7（见 5.5 实战）。

把两个极限代进去，还能得到一句面试金句：当 draft 免费（c→0）且 γ 足够大时，**加速比上限 = 1/(1−β)**——β=0.9 的代码负载理论上限 10x，β=0.5 只有 2x。别人论文里的 6.5x 不是“参数调得好”，而是负载本身的 β 高；看懂这一条，就再也不会被单点数字误导。

## 2. 接受率的四个影响因素

### 2.1 采样温度：分布越平，命中越低

为什么线上把 temperature 调到 1.0，投机解码就突然不香了？

机制要从接受率的定义说起。5.1 讲过，接受概率本质是 draft 与 target 分布的**重叠度**：$\alpha = \sum_x \min(p_{\text{target}}(x), p_{\text{draft}}(x)) = 1 - \text{TV}(p, q)$（TV 是全变差距离，衡量两个分布差多远）。高温把 target 的 logits 除以更大的 T，分布被**抹平**——打个比方：考试从“单选题”改成“开放论述题”，复习过重点的实习生（draft）优势瞬间清零，因为答案空间从 4 个选项变成了无限种写法。注意关键前提：**被抹平的只有 target,draft 不会跟着变平**（它的分布是训练时固化的），于是两者从“高度重合”变成“错位”。

用微型词表把错位算给你看。假设词表只有 {a, b, c} 三个 token，draft 分布尖锐 $q = (0.8, 0.1, 0.1)$。target 也尖锐时（如 $p = (0.7, 0.2, 0.1)$），重叠度 $\alpha = \min(0.7,0.8)+\min(0.2,0.1)+\min(0.1,0.1) = 0.9$——几乎全中。target 被高温均匀化后 $p = (1/3, 1/3, 1/3)$，重叠度跌到 $\min(1/3,0.8)+\min(1/3,0.1)+\min(1/3,0.1) \approx 0.53$。一般地，均匀 target 与尖锐 draft 的重叠度可以写成：

$$
\alpha_{\text{均匀 target}} = \underbrace{\frac{k}{V}}_{\text{draft 高分 token 恰好被均匀分布分到的部分}} + \underbrace{(1 - Q_{\text{hi}})}_{\text{draft 散落在低概率区的那部分概率质量}}
$$

其中 $V$ 是词表大小，$k$ 是 draft 高分 token 的个数，$Q_{\text{hi}}$ 是它们的概率和。代入真实词表 $V \approx 32000$、$k \approx 5$、$Q_{\text{hi}} \approx 0.8$：$\alpha \approx 0.0002 + 0.2 = 0.2$——**从常温的 0.6~0.8 断崖式跌到 0.2 量级**，这就是“高温杀死投机”的数学全景。

💡 **提示**：这条规律的反面同样值得知道——如果 draft 也按同样的高温采样（温度对齐蒸馏，见下面的数据），两者一起变平，重叠度反而可能回升。所以“高温必亏”不是铁律，本质是**draft 没跟着 target 变平造成的错位**；对齐蒸馏是已知的解药。

查证到的定量数据：

- Leviathan 论文（ICML 2023）报告 T=1（标准采样）下的接受率：T5-XXL 英德翻译 0.62、CNN/DailyMail 摘要 0.53、LaMDA-137B 对话 0.57；并明确观察**更“尖锐”的采样分布（T=0 argmax）接受率更高**。
- EMNLP 2024 一篇温度专项研究（arXiv:2410.10141）给出了完整曲线：Llama-2-13B-chat + 用 T=0.2 蒸馏的 68M draft，推理温度从 0.2 升到 1.0，接受率从 85~88% 降到 ~84%，**加速比从 2.23x 跌到 1.72x（相对损失 ~30%）**。

💡 **提示**：这条曲线的下半段可以补救——把 draft 也用高温数据蒸馏（温度对齐）。同一研究里，用 T=1.0 蒸馏的 draft 在 T=1.0 推理时接受率 80.6%、加速 1.98x；用 T={1.0, 0.9, 0.8} 混合数据蒸馏后升到 83.0% / 2.23x。**draft 的训练温度要和你的线上推理温度对齐**，否则高温一开，收益就蒸发了。

### 2.2 Draft 与 Target 的能力差距

draft 是不是越小越亏、越大越赚？**两个方向都会死**：draft 太小，分布和 target 差异过大，重叠度低（接受率 < 50% 的典型成因）；draft 太大，c 逼近 1，分母爆炸。看 Chen 等人的原始实验就知道差距有多微妙——他们给 Chinchilla-70B 配的 draft 不是“越大越好”的 7B，而是定制的 **4B / 8 层**小模型，因为 7B draft 每 token 要 5ms，相对 70B 的 14.1ms（c≈0.35），投机成本已经吞掉了大半收益。

更重要的结论来自 EAGLE-1 论文：同样是 8B 级 target，**“同族同分布”比“更大”更关键**——greedy 解码下 HumanEval 首位接受率 0.81~0.85，Alpaca 也有 0.70~0.76。反过来说，跨族硬配（比如让一个 1B 通用模型给代码模型当 draft），接受率往往跌破 0.5，对应第 1 节账本里的“亏”区间。

怎么判断差距是不是过大？不用猜——拿 100 条真实 prompt 跑一遍，只看**首位接受率**（第 5.5 节会给统计命令）。首位接受率 < 0.5，说明 draft 和 target 已经“说不到一块去”，这时候换 draft 或换方案，别调 γ——γ 只能放大已有的命中，救不了没有的命中。

⚠️ **注意**：还有一类隐蔽的“差距”——draft 的训练分布与你的推理分布错位（比如 draft 是通用语料训练的，你的业务全是代码）。EAGLE-3 论文专门提出的“训练时测试”（training-time test）就是治这个病的：让 draft 在训练时就吃自己生成的 token 而不是干净的 target token，消除推理时的误差累积。

### 2.3 任务类型：代码 vs 开放对话

为什么同一套配置，代码生成能到 2.5x，开放对话却不到 1.1x？

机制在于**下一 token 的确定性**。代码、JSON、数学推导是“低熵”文本——`for` 后面几乎必然是 `(` 或空格，draft 命中率天然高；开放对话是“高熵”文本——同一句话有十种合法说法，draft 和 target 各猜各的，重叠度低。打个比方：**代码像填空题（答案唯一），对话像开放作文（十个人十种写法）**——填空题谁能猜中更多？必然是那个背过书的实习生。

查证到的实测数据：

- Chen 等人（arXiv:2302.01318）：Chinchilla-70B，K=4，**HumanEval（代码）2.46x vs XSum（摘要）1.92x**。
- EAGLE-1 论文：HumanEval 平均接受长度 4.24~4.52 token，Alpaca（指令对话）只有 3.61~3.95。
- 5.1 引用的 vLLM V1 实测同样如此：**代码类负载（InstructCoder）整体接受率 46.13%，而开放对话负载的整体接受率显著更低**——开放对话不是“收益低”，而是直接逼近不赚边界。
- vLLM 官方博客的 ngram 实验也遵循同一规律：摘要类负载（CNN/DailyMail，输出大量重复输入片段）QPS=1 时拿到 2.8x；同样的方案换到 ShareGPT 开放对话就只剩 1.5x（还是靠 draft 模型拿到的）。

📌 **关键点**：任务类型决定接受率的**上限**，配置只能逼近它、不能突破它。立项评估投机解码时，第一件事不是调参，而是确认你的负载是“填空题”还是“开放作文”。这里有个便宜的预判指标：**统计你线上输出的 n-gram 与输入的重叠比例**——重叠高的负载（摘要、续写、重排）连 ngram 都能赚，重叠低的（开放聊天、头脑风暴）基本只有模型类方案值得一试。

### 2.4 γ 与树宽：draft 开销的放大器

第 1.3 节已经证明存在最优 γ。EAGLE-2/Medusa 这类**树式投机**把问题放大了一档：树宽（每层保留几个候选）和 γ 一样，都是“用 draft 开销换接受率”的旋钮。树越宽，draft 要前向的次数越多——Medusa 论文里多个 head 的候选组合成树，EAGLE-2 则根据 draft 置信度**动态**决定树结构（置信度高的位置多分枝、低的位置少分枝），本质就是“把 draft 预算花在刀刃上”。

**权衡总结**：γ/树宽换取的收益是期望接受数，牺牲的是 draft 前向次数（c 放大）与树形 KV Cache 的显存；最优值由 (β, c) 决定，只能扫出来，不能拍脑袋。

再补一个树式投机独有的成本结构。线性投机（draft model / ngram）里，draft 要串行前向 γ 次；树式投机则把**同一层的多个候选节点拼进同一次前向**（共享前缀的节点可以一起算），前向次数从 γ 降到树的层数。但每一层要算的节点数变多了，总计算量未必更小。EAGLE-2 的动态树就是在“层数（收益）”和“节点数（开销）”之间做实时折中：置信度高的位置多分枝、低的位置少分枝。所以树式投机里 `num_speculative_tokens` 实际控制的是树的规模上限，调参思路和线性投机一样——从小的扫起，找到拐点就停。

## 3. 工程耦合风险

### 3.1 与量化叠加

4.6 讲量化时强调“优化不叠加，误差相乘”，投机解码和量化叠加时同样有**耦合损失**，而且方向总是坏的：

- **draft 也量化**：draft 的分布进一步偏离 target（量化误差），重叠度下降，接受率掉。draft 通常比 target 小得多，量化省下的显存绝对值有限，但接受率损失是实打实的——**典型的“省小钱、亏大钱”**。
- **target 量化**：target 分布整体偏移。Rejection Sampling 的**无偏性依然成立**——但注意，它保证的是“相对你实际运行的（量化后）target 分布无偏”，而 draft 是按原始 target 学的，两者错位更严重，接受率照样跌。

⚠️ **注意**：无偏性（正确性）和收益（速度）是两件事。量化+投机叠加后输出依然合法，但加速比可能从 2x 掉到 1.1x。验证方式只有一个：量化后重跑一遍接受率统计（第 4.2 节的流程），别拿量化前的数字当承诺。

执行顺序：**量化方案先定，投机最后叠加**；叠加后接受率重测，掉过 0.5 就拆掉投机、保留量化——宁可少赚，不要白忙。

### 3.2 与 Continuous Batching 叠加

单个请求的投机解码是“draft 串行 γ 步 + target 并行验证一次”，但放进 Continuous Batching 后，调度器要同时处理几十上百个请求，问题来了：

- **batch 展开（batch expansion）**：target 前向时，每个投机请求要占 γ+1 个 token 槽位（vLLM 官方文档里专门有 batch expansion 的设计说明）。每个请求的接受位置不同，实际有效产出是“每请求一串不齐的 token”，调度复杂度比普通 Decode 高一个量级。vLLM V1 用 `{request_id: num_tokens}` 的统一表示把投机验证纳入同一套调度框架（2.4 节讲过），复杂度被框架吸收了一部分，但 draft 的串行 γ 步仍然要排进每步调度：Draft Runner 和 Target Runner 是两套执行路径，draft 前向的 batch 是原始请求，target 前向的 batch 是展开后的 γ+1 倍——调度器每一步都要维护这两种批的对应关系。
- **大 batch 下 draft 抢算力**：draft 模型同样是 Memory-Bound 的，也吃显存带宽。batch 一大，draft 前向的绝对开销线性上涨，投机收益被稀释。PR #24322 的实测曲线触目惊心：Llama-3.3-70B + Llama-3.2-1B 的 3.55x 只出现在**并发 1~4**；**batch 128+ 时投机解码反而比普通解码更慢**。vLLM 官方博客 2024 年的数据同样：高 QPS 下 ShareGPT 负载 1.4x 减速、CNN/DailyMail 1.8x 减速。

📌 **关键点**：投机解码的收益区间是“**低 QPS、低并发、延迟敏感**”；吞吐型高并发场景，它从优化手段变成负担。动态投机解码（arXiv:2406.14066）的思路就是让系统按负载自动收缩投机长度——目前 vLLM 有实验性支持，方向正确但别把它当已成熟的能力，上线前依然要自己测。

### 3.3 与 Prefill 的关系

投机只加速 Decode，Prefill 一分钱都省不了。所以总收益取决于两者占比：

$$
S_{\text{总}} = \frac{T_{\text{prefill}} + T_{\text{decode}}}{T_{\text{prefill}} + T_{\text{decode}}/S} = \frac{1}{p + (1-p)/S}, \quad p = \frac{T_{\text{prefill}}}{T_{\text{总}}}
$$

算例：S=2x 的投机，如果 prefill 占总时长的 50%（长文档、长 prompt 服务），整体加速只剩 $1/(0.5+0.5/2) = 1.33x$——**一半的收益被 prefill 摊薄了**。再给一个量级感（示意数字，以你线上 profile 为准）：8K 输入 + 256 输出、7B 模型单卡，prefill 约几百 ms、decode 约几秒，p≈10%，S=2x 时总加速 ≈ 1.82x，基本吃满；反过来 32K 输入 + 64 输出，p≈60%+，总加速只剩 ~1.25x。判断方法：profile 一次线上请求，看 TTFT 占总时长比例，占比高就把投机解码的优先级往后放。

### 3.4 显存账本

投机解码的显存成本分三块：**draft 权重**（1B 模型 FP16 ≈ 2GB）、**树形 KV Cache 的瞬态占用**、以及 target 侧验证时给 γ 个候选 token 临时分配的 KV 槽位（拒绝后释放）。最后一块容易被忽略，算一下：LLaMA-2-7B 每 token KV = 2 × 32 层 × 32 头 × 128 × 2B = 512KB，γ=8 就是 4MB/请求，batch 256 时峰值多出 **~1GB**——这部分和 PagedAttention 的块池抢空间，会推高 preemption 频率（2.1 节讲过）。

| 📊 方案 | 额外权重 | 额外 KV | 说明 |
|---|---|---|---|
| 独立 draft 模型 | 0.5B~4B 权重（1~8GB） | 仅瞬态 | draft 与 target 各一套 KV Cache |
| ngram | 0 | 仅瞬态 | 无额外模型 |
| EAGLE | head 权重（几百 MB 级） | 树节点 KV | 树越宽瞬态越大 |

💡 **提示**：显存账本要在开投机前算，否则压测会直接 OOM 或频繁抢占。实战里通常要把 `--gpu-memory-utilization` 从 0.9 调低到 0.8 左右给 draft 腾地方（5.5 会给出具体命令）。

落一个完整算例感受量级。7B target + 1B draft 单卡 A100 80GB 部署，`gpu-memory-utilization=0.8` → 总预算 64GB；权重 14 + 2 = 16GB，KV Cache 池剩 ~48GB；投机瞬态 KV（γ=8、batch 256）约 1GB，占比只有 2%——听起来无所谓，但显存压到 90%+ 时，这一下可能就是触发 preemption 的最后一根稻草（2.1 讲过抢占的代价）。再看 70B target + 1B draft、2 卡 TP2：每卡权重 70GB，draft 若用 TP1 就整个压在某一卡上——0.9×80 = 72GB 的预算连权重都快撑满，KV Cache 几乎没有空间。**这个组合在账本阶段就被否决了**：要么换更小的 draft、要么 draft 也跟着 TP2 分摊（多付跨卡通信）、要么干脆换 EAGLE（没有独立权重）。

## 4. 收益为负的清单与“先测再上”

### 4.1 至少七种不赚的场景

把前面所有机制收拢成一张可直接对号入座的清单：

1. **高温采样**（T ≥ 0.8 的开放对话/创意写作）：target 分布被抹平，接受率骤降（2.1 的 2.23x → 1.72x 曲线）。
2. **Draft 与 Target 差距过大**（接受率 < 0.5，且 draft 并不便宜）：第 1 节账本的“亏”区间。
3. **大 batch / 高 QPS 吞吐型负载**（batch ≥ 128，64 起收益已大幅衰减）：draft 抢带宽，3.55x → 负收益（3.2）。
4. **ngram 用在无重复文本的开放生成**：prompt 里根本没有可匹配的片段，draft 全程瞎猜。
5. **长 Prefill 占比高的服务**：收益被 $p$ 摊薄（3.3 的 2x → 1.33x 算例）。
6. **量化叠加后接受率塌方**：输出依然“无偏”，但速度优惠没了（3.1）。
7. **短输出任务**（max_tokens ≤ 50）：投机有固定预热成本（draft 前几步上下文短、接受率低），总输出太短摊不平。

### 4.2 先测再上：半小时 A/B 验证

面对这么多“可能不赚”，工程上唯一的姿势是**先测再上**。不用搭完整压测平台，半小时能跑完的 A/B 协议：

1. **固定负载**：准备 100~200 条 prompt，**必须包含你的真实业务类型**（代码就代码、对话就对话），固定 `max_tokens`、`temperature`、`top_p`。
2. **固定并发档位**：1 / 8 / 32 三档各跑一遍——投机解码的收益对并发极其敏感（3.2 的曲线）。
3. **同一套命令模板**：只切换投机配置开关，其余参数（`--gpu-memory-utilization`、模型、采样参数）完全一致，控制变量。
4. **只盯四个指标**：TPOT P50/P95、TTFT、throughput、接受率（接受率的统计方法在 5.5 有完整命令）。
5. **判定线**：TPOT P50 提升 ≥15% 且 P95 不恶化 → 开；**接受率 < 0.5 或 TPOT 没有任何下降 → 关**，别犹豫。

⚠️ **注意**：最常见的失败不是跑错，而是**两个变量一起变**——比如第一次跑用 temperature=0.6，第二次为了“省时间”把并发从 1 跳到 32，结果 TPOT 变了根本不知道是谁的功劳。A/B 的核心纪律：**一轮只允许投机开关这一个变量变化**，其他全部冻结。

结果怎么归档：把 baseline 和 speculative 的 profile json、启动命令、prompt 集一起存进 repo（config 可复现，呼应第 9 章的回归门禁思路）。**模型一更新，接受率就要重测**——它是 （负载， 温度， draft, target） 的四元函数，任何一元变了，上次的结论就作废。

决策规则：

- ✅ **低 QPS + 延迟敏感 + 结构化输出** → 开，优先 EAGLE/同族 draft。
- ✅ **摘要/QA 等输出重复输入的负载** → 开 ngram，零成本。
- ✅ **高并发吞吐型 / 高温 / 短输出** → 默认关，测过再开。
- ❌ **别拿别人博客的加速比当自己的承诺**——接受率是 （负载， 温度， draft, target） 四元组的函数，只在你的硬件和业务上成立。

## 📝 总结

1. **盈亏公式**：$S = \mathbb{E}[\tau]/(1+\gamma c)$，收益为负当且仅当 $\mathbb{E}[\tau] < 1+\gamma c$——接受率与 draft 开销是仅有的两个变量。
2. **接受率四因**：温度（抹平分布）、模型差距（太小错位、太大费钱）、任务类型（代码 0.81+ vs 对话 0.36 的量级差）、γ/树宽（收益饱和，最优值只能扫）。
3. **工程耦合**：与量化叠加误差相乘、与 Continuous Batching 叠加在大 batch 下反噬、Prefill 占比摊薄总收益、多一份 draft 权重和树 KV 显存。
4. **不赚清单**：高温、差距过大、大 batch、ngram 错配、长 prefill、量化叠加、短输出——七种场景对号入座。
5. **先测再上**：半小时 A/B 协议 + 判定线（TPOT P50 ≥15% 且接受率 ≥0.5 才开），数字钉死在自己硬件上。

## ⚠️ 常见错误做法

- ❌ **只看接受率不看 γ 与开销**：α=0.8 就宣布 5x。为什么错：加速比 = 期望接受数 ÷（1 + γ × draft 相对开销），γ 大或 draft 慢，收益为负（本文把“由赚转亏”的边界推导出来了）。正确做法：用本文的公式代入自己负载的 α、γ、开销，算出预期加速比。
- ❌ **把投机解码与量化/Continuous Batching 简单叠加**：以为收益相乘。为什么错：投机解码吃算力余量，量化/动态组批改变瓶颈，叠加时收益可能互相挤压（本文的工程耦合分析）。正确做法：按 11.2 的叠加顺序与冲突清单规划。
- ❌ **在 Memory-Bound 的 Decode 上期待投机解码大赚**：Decode 本身带宽饱和。为什么错：投机解码用算力换延迟，带宽瓶颈下收益有限（prefill 重、decode 带宽重的负载要分别看）。正确做法：先确认瓶颈是算力还是带宽（9.3 的 profiling）。
- ❌ **不做 A/B 就上线**：直接在生产开投机解码。为什么错：命中率与负载强相关，纸面数字不可靠。正确做法：先测再上——A/B 对比 P95 TPOT 与吞吐（5.5 的实测协议）。
