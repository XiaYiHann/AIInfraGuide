5.7 的 DFlash 把草稿侧做成了"单次并行前向"，但它有一个结构性短板：块内的 token **互相看不见**——每个位置是在"假设前面所有 token 都可能"的前提下猜的，接受率因此从块首向块尾一路下滑（**后缀衰减，suffix decay**）。更麻烦的是第二个问题：草稿块变长之后，高并发 serving 里"验证那些注定被拒的块尾 token"成了实打实的算力浪费——DeepSeek 的生产数据直接证明了这个代价，固定多 Token 草稿（MTP-3/5）在高并发下**严格降低总吞吐**，V4 生产环境因此长期停在只起草 1 个 token 的 MTP-1。DSpark（Xin Cheng et al.，北京大学与 DeepSeek-AI，arXiv:2607.05147，2026-07）给这两个问题各配了一把手术刀：**给并行骨干（DFlash）加一个只看前 1 个 token 的轻量 Markov 头**（草稿侧），**加一个置信度头 + 硬件感知调度器**（验证侧，动态决定每个请求验证多长）。生产实测（DeepSeek-V4 Flash/Pro，线上真实流量，匹配系统吞吐口径）：单用户生成速度提高 **60%~85%（Flash）/ 57%~78%（Pro）**，且 V4-preview 发布**两周后**，DSpark 就替换了生产里的 MTP-1。

## 1. 瓶颈一：后缀衰减——并行草稿的块尾在"盲猜"

5.7 讲过 DFlash 的块内是**全并行**的：每个 mask 位置一次性预测，谁都不等谁。这个设计换来了 O(1) 的草稿延迟，代价是**块内没有 token 间依赖**——位置 $k$ 不知道位置 $k{-}1$ 最终会采样出什么词。

DSpark 论文用"逐位置条件接受率"（每个 draft 位置上，**剔除前面被拒的惩罚后**，该位置本身猜对的概率）把这个问题量化了（Qwen3-4B 目标模型，Figure 2）：

<img src="/AIInfraGuide/images/dspark-fig2-position-acceptance.png" alt="Qwen3-4B 上 Math、Code、Chat 各 draft 位置的条件接受率：DFlash 起点高但后缀下滑，Eagle3 后期回升，DSpark 全程更高更稳" style="max-width: 75%; display: block; margin: 0 auto;" />

*图源：DSpark 论文 Figure 2（arXiv:2607.05147）——三条线的形状就是三个草稿器的"性格"。*

三条线各自说明了什么：

- **DFlash（并行）**：起点最高（Code 0.87、Chat 0.72），但**一路下滑**（Code →0.78、Chat →0.63）——越到块尾越不可靠。
- **Eagle3（自回归）**：起点低（Chat 0.53），但**不降反升**（Chat →0.74）——因为它每一步都条件在"确切已采样的前缀"上，前面的 token 把语义路径锁死后，后面的词反而更好猜。
- **DSpark（半自回归）**：起点继承 DFlash 的高度，全程更稳。

为什么并行草稿的块尾会"盲猜"？论文给了一个很直观的例子（论文 §3.1 原文）：假设前文让 **"of course"** 和 **"no problem"** 都是合理的续写。自回归草稿器逐词采样，采到 "of" 之后位置 2 只会在 "course" 附近打转；但并行草稿器两个位置**独立**预测，"of"（来自路径 A）和 "problem"（来自路径 B）会被拼成 **"of problem"** 这种不存在的组合——论文把这叫**多模态碰撞（multi-modal collision）**：每个位置对"所有可能的前缀"取了平均，平均值恰好落在两个模式的中间。块越长，这种拼接错配越多，接受率衰减越快。

📌 **关键点**：后缀衰减不是"草稿模型不够大"——加层数（5 层→8 层）只能部分缓解。它是**并行生成的结构性缺陷**：位置间没有依赖建模。修它的正确方向不是堆容量，而是**补一点点顺序依赖**（第 3 节）。

## 2. 瓶颈二：验证浪费——固定草稿长度在高并发下是负资产

第二个瓶颈在系统侧。5.4 的账本在这里变成具体的痛点：**起草和验证共享同一张 GPU，验证的每个 token 都要占 batch 容量**。

固定长度投机解码（draft 长度 γ 写死，从 MTP-3 到 DFlash 都一样）有个隐含假设：**GPU 是空闲的，验证多几个 token 不花钱**。单请求、低并发时这个假设成立——验证 token 搭着 batch 的便车，几乎免费。但在高并发 serving 里，batch 是**所有请求共享的容量池**：

- 请求 A 的草稿块有 5 个 token，后 3 个置信度极低（几乎必拒）——固定策略照样送去验证，白占 3 个 batch 位置；
- 这些被占用的位置本可以分给请求 B 的有效 token；
- 结果：拒绝率越高的负载（比如开放对话），固定长草稿的**验证浪费越大**，总吞吐被拖垮。

DSpark 论文用生产数据给这个机制盖了章（§5.4 原文）：DeepSeek-V4 之前的生产基线是 **MTP-1**（只起草 1 个 token），而"这个单 token 配置被保留在生产里，恰恰是因为部署静态多 Token 草稿器（如 MTP-3/5）会因过高的验证开销**在高并发下严格降低总吞吐**"。换句话说：**"草稿越长越快"的结论只在低并发成立；高并发下固定长草稿不仅不赚，还拖别人**。

这两个瓶颈合成一句话：**并行草稿的块尾不可靠（瓶颈一），而系统还在为这些不可靠的块尾全额付费（瓶颈二）**。DSpark 的两个机制正好各修一个。

## 3. 机制一：半自回归草稿——给并行骨干加一个 Markov 头

DSpark 的草稿器 = **DFlash 并行骨干 + 一个轻量串行头**。论文称之为"半自回归（semi-autoregressive）"：重的部分（骨干）保持全并行，轻的部分（串行头）补上 token 间依赖。

一轮起草分两个阶段（DSpark 论文 §3.1，Figure 1）：

<img src="/AIInfraGuide/images/dspark-fig1-architecture.png" alt="DSpark 一轮解码：目标模型生成锚点，DFlash 并行骨干一次前向出基础 logits U，轻量串行 Markov 头按已采样前缀修正 logits 并逐位采样，置信度头给出每个位置的存活概率，硬件感知调度器决定验证前缀长度，目标模型并行验证" style="max-width: 75%; display: block; margin: 0 auto;" />

*图源：DSpark 论文 Figure 1（arXiv:2607.05147）——上半部分是草稿侧（并行骨干 + 串行头 + 置信度头），下半部分是调度与验证侧。*

**阶段 1：并行骨干（DFlash）。** 一次前向产出整块的 hidden states 和**基础 logits** $U_1,\dots,U_\gamma$。DSpark 对 DFlash 做了一个小改造：anchor（上一轮验证的 bonus token）不再只是条件，而是**作为第一个预测位置参与**——$\gamma$ 个输入（anchor + $\gamma{-}1$ 个 mask）产出 $\gamma$ 个草稿 logits，省掉一步计算、草稿质量基本不变。

**阶段 2：串行头（Markov 头）。** 在基础 logits 上叠加一个"前缀相关的转移偏置" $B_k$，按自回归方式从左到右逐位采样（论文 Eq. 4）：

$$
P(X\mid x_0) = \prod_{k=1}^{\gamma} p_k\!\left(x_k \mid x_0, x_{<k}\right),
\qquad
p_k\!\left(v \mid x_0, x_{<k}\right)
= \frac{\exp\!\left(\underbrace{U_k(v)}_{\text{并行骨干的基础 logits}} + \underbrace{B_k\!\left(x_0, x_{<k}, v\right)}_{\text{串行头的前缀偏置}}\right)}
{\sum_{u \in \mathcal{V}} \exp\!\left(U_k(u) + B_k\!\left(x_0, x_{<k}, u\right)\right)}
$$

其中 $x_0$ 是 anchor，$U_k$ 是骨干在位置 $k$ 的基础 logits，$\mathcal{V}$ 是词表。**关键设计：$B_k$ 只依赖"前一个已采样的 token"**（一阶马尔可夫），而不是完整前缀——这样串行循环每一步的计算量小到可以忽略（约束 $T_{\text{sequential}} \ll T_{\text{parallel}}$，整轮延迟仍由并行阶段主导）。具体实现（Eq. 5）：

$$
B\!\left(x_{k-1}, \cdot\right) = \underbrace{W_1\!\left[x_{k-1}\right]}_{\text{V}\times\text{r 嵌入查表}} \cdot \underbrace{W_2}_{\text{r}\times\text{V logit 投影}} \in \mathbb{R}^{V}
$$

完整的 $V \times V$ 转移矩阵在 $V \sim 10^5$ 量级的词表上有 $10^{10}$ 级参数，放不下也学不动；低秩分解 $B = W_1 W_2$（默认 $r=256$）把参数量压到 $2Vr \approx 2 \times 1.5\times10^5 \times 256 \approx 7.7\times10^7$（按 Qwen 系 $V\approx15$ 万词表估算），不到完整矩阵的 1/300。

**用第 1 节的例子走一遍**（数字为示意，思想实验）：前文让 "of course" 与 "no problem" 都合理，位置 1、2 的骨干基础 logits 大致是 $U_1(\text{of}) \approx U_1(\text{no})$、$U_2(\text{course}) \approx 8.0$、$U_2(\text{problem}) \approx 7.9$——两个词打平。

| 步骤 | 动作 | 位置 2 的 logits（示意） |
| --- | --- | --- |
| 采样位置 1 | 按 $p_1$ 采出 $x_1$ = **"of"** | — |
| Markov 头修正 | $B_2 = W_1[\text{"of"}]W_2$：boost "course"、suppress "problem" | $\text{course}: 8.0{+}1.2{=}9.2$；$\text{problem}: 7.9{-}2.0{=}5.9$ |
| 采样位置 2 | 按修正后的 $p_2$ 采样 | "course" 压倒性胜出 |

多模态碰撞就这样被按住了：**"of" 一旦采出来，位置 2 就不可能再漂到 "problem" 分支上去**。这正是自回归草稿器"后期接受率回升"能力的廉价近似——只花了一个查表 + 一次矩阵向量乘。

**成本与替代方案**（论文 §4.3.2）：batch=128、上下文 512~4096 混合，把草稿长度从 4 拉到 16，**整轮延迟只增加 0.2%~1.3%**（相对 DFlash 基线，Figure 4 右图），换来的是最高 30% 的接受长度提升——串行头的计算便宜到几乎可以忽略。论文还试了完整的 RNN 头（维护递归状态、看完整前缀）：**增益只在长块上边际可见，而实现复杂度明显更高**，所以默认用 Markov 头（论文原文结论）。"一点点自回归，去很远的效果"（A Little Autoregression Goes a Long Way，论文小标题）。

## 4. 机制二：置信度调度验证——验证多少由负载决定

机制一解决了"草稿的块尾更可靠"，机制二解决"不为不可靠的块尾全额付费"。它由两个部件组成：**置信度头**（预测每个位置能不能活）+ **硬件感知前缀调度器**（把验证预算分给最可能活的位置）。

**4.1 置信度头。** 草稿模型额外训一个头，输出每个位置 $k$ 的**条件接受概率** $c_k$（"假设前面全被接受，这个位置本身被接受的概率"）。训练监督信号不是拍脑袋的 logits 置信度，而是**解析的逐步接受率**——由草稿分布与目标分布的 total variation（全变差）距离直接算出（论文 §3.2.1）。为什么不用"排名"？因为静态阈值类方法（如 EAGLE 的动态树，5.3）只需要**相对排序**；而调度器要**算期望接受长度 $\tau$**，必须知道**绝对概率量级**——排第一的 token 有 90% 还是 30% 的存活率，调度决策完全不同。

**4.2 STS 校准。** 神经网络的置信度天生**过度自信**：DSpark 的置信度头原始输出判别力不错（ROC-AUC 0.81~0.90）但校准很差（ECE 3%~8%，Figure 6 可靠性图）。直接拿去过自信的概率算吞吐，调度器会系统性高估长前缀的收益。解法是 **Sequential Temperature Scaling（STS）**：前缀 $1..k$ 的联合存活率按链式法则分解为累积乘积 $\prod_{i\leq k} c_i$，在验证集上**从左到右**逐位置做一维网格搜索，为每个位置找一个温度标量最小化累积乘积的 ECE（前面的位置校准完就固定）。温度缩放是保序变换——只把概率"掰正"，不打乱置信度头学到的相对排序。校准后**平均 ECE 降到约 1%**（论文实测）。

**4.3 硬件感知前缀调度器（Algorithm 1）。** 把"验证多长"变成一个**显式的优化问题**：

- **输入**：当前活跃请求 $r=1..R$ 各自的存活概率序列（$a_{r,j} = \prod_{i\leq j} c_{r,i}$，前缀累积存活率）、引擎实测的**吞吐-批容量曲线** $\mathrm{SPS}(B)$（batch 里有多少验证 token 时，每步能吐多少 token——这是**profiled 的**，来自引擎实测而非理论值）；
- **贪心**：把所有候选位置 $(r,j)$ 按 $a_{r,j}$ 从高到低排序，逐个"决定是否验证这个位置"——每多验证一个 token，batch 容量 $B$ 加 1、期望接受数 $\tau^*$ 加 $a_{r,j}$，用 $\mathrm{SPS}(B)$ 算出此时的期望吞吐 $\Theta$，**全程保留 $\Theta$ 最大的那个前缀组合**；
- **输出**：每个请求的验证前缀长度 $\ell_r^*$——高置信的请求验整块，低置信的请求只验前几个。

代入算一下（示意数字）：某请求 $c=(0.9, 0.8, 0.7, 0.3, 0.2)$，则 $a=(0.9, 0.72, 0.50, 0.15, 0.03)$——位置 4 起存活率已经不值一个 batch 位置的钱了，调度器会在负载上来时把验证窗口剪在 3。负载低时 $\mathrm{SPS}(B)$ 平坦（验证 token 搭便车），同样的候选会验得更长。**同一条草稿，空闲时验 5，满载时验 3**——投机解码从"固定预算"变成"弹性预算"：有空闲容量就扩张，饱和了就收缩。

💡 **提示**：静态阈值（"置信度低于 0.5 就不验"）是这个机制的退化版，在单请求场景够用，但在动态 serving 里次优——因为"验证一个低置信 token 的机会成本"**取决于当前负载**：低并发时几乎免费，高并发时很贵（论文 §4.3.3 的阈值扫描，Figure 5，显示剪掉低置信后缀能把 Chat 场景的接受率从约 46% 提到约 96%）。

📌 **关键点**：读生产数字要区分三档口径——**匹配吞吐的单用户加速（60~85%）**是主结论；**中等 SLA 的吞吐提升（+51%/+52%）**是吞吐侧收益；**极端 SLA 的名义倍数（+661%/+406%）**是"基线已经跑不动了"的证据，引用时必须带论文的原话限定，不能写成"DSpark 比 MTP-1 快 6.6 倍"。

## 6. ⚠️ 错误做法对比

**错误做法 A："加速不够？把草稿块拉长到 16 就完了。"**

低并发下确实对（5.7 的 DFlash 就是靠长块拿到 6× 的）。但把它搬到高并发 serving，就踩中 5.4 的账本：固定长草稿把 batch 容量持续花在"注定被拒"的块尾上，**总吞吐严格下降**——这不是推测，是 DeepSeek 生产环境的既成事实（MTP-3/5 因此从未上过 V4 生产，基线一直是 MTP-1）。错误根源：**单请求视角的假设（GPU 空闲）当成了 fleet 视角的定律（容量共享）**。正确做法：草稿长度交给调度器按负载动态决定（DSpark），或者至少做一个"batch 占用率超过阈值就缩短草稿"的粗粒度负载感知（论文 §4.3.3 指出静态阈值在动态环境里次优，但负载感知方向是对的）。

**错误做法 B："置信度直接用模型 logits 的 max prob（或 softmax 熵）就行，省得再训一个头 + 校准。"**

两条理由都不成立。其一，logits 置信度量的是"草稿模型多确信"，而调度器需要的是"**目标模型**会接受这个 token 的概率"——前者过度自信（DSpark 的原始置信度头都要 STS 校准到 ECE~1%，直接拿 logits 置信度更糟）；其二，调度器算的是**前缀的联合存活率** $\prod_{i\leq j} c_i$ 与吞吐曲线的乘积，用未校准的数算出来的期望吞吐系统性偏高，调度器会持续高估长验证的收益。正确做法：专门的置信度头 + 解析接受率监督 + STS 事后校准（一次性成本，校准后离线使用）。

**错误做法 C："既然要建模 token 依赖，那就上完整 RNN/Transformer 解码器，看得越全越好。"**

论文 §4.3.2 已经替你做完了这个消融：RNN 头（递归状态看完整前缀）相对一阶 Markov 头的增益**只在长块上边际可见**，而实现与部署复杂度明显更高——生产配置（DSpark-5）用的就是一阶 Markov 头。错误根源：把"依赖越长越好"当成了单调规律；实际上**第一个被拒位置之后的依赖几乎不产生价值**（接受了 1 个 token 的信息就覆盖了大部分多模态碰撞），一阶依赖以 0.2%~1.3% 的延迟成本吃掉了绝大部分收益。

💡 **另一个答案（2026-08）**：DFlash 团队的后续工作 **DFlash 2**（Inco AI 博客）对同样的"块内不连贯 / 后缀衰减"问题给出了**并行**路线：2M 参数的**路径选择器**（top-16 候选成对打分，循环延迟 +0.6%）声称在 T=1 下接受长度超过 Markov 头校正（+77.8M / +9.6%，博客 Table 2：4.25 vs 4.08），外加二抽头局部卷积（+16.5M / +0.7%）修后缀衰减。注意证据级别差异：DSpark 有 DeepSeek 生产线上数据（第 5 节），DFlash 2 目前是博客自测 + 开源草稿器。完整拆解与两边数字对照见 [5.7 第 7 节](/AIInfraGuide/inference/模块四-推理优化/第5章-speculative-decoding/57-dflash-块扩散并行起草)。

## 7. 工程落地：DeepSpec 与 vLLM

**开源资产**（截至 2026-08-18）：

- **[DeepSpec](https://github.com/deepseek-ai/DeepSpec)**（DeepSeek-AI，MIT）：投机解码草稿模型的**全栈训练/评测框架**——数据准备（prompt 集 + 目标模型重生成 response + 目标缓存）、三种草稿器实现（**DFlash / DSpark / Eagle3**，同一框架同一数据可比）、训练（`train.sh`，每 GPU 一个 worker，config 指定算法与目标模型）、评测（`eval.sh`，覆盖 gsm8k / math500 / aime25 / humaneval / mbpp / livecodebench / mt-bench / alpaca / arena-hard-v2）。Qwen3-4B/8B/14B 与 Gemma4-12B 的三种草稿器 checkpoint 全部放出。
- **生产 checkpoint**：HuggingFace `deepseek-ai/DeepSeek-V4-Flash-DSpark` 与 `DeepSeek-V4-Pro-DSpark`——注意它们**不是新模型**，是"同一个 V4 checkpoint + 附挂的投机解码模块"。
- **vLLM 一行启用**（V4 HF 模型卡给出的命令要素）：

```bash
vllm serve deepseek-ai/DeepSeek-V4-Pro-DSpark \
  --speculative-config '{"method":"dspark","num_speculative_tokens":7,"draft_sample_method":"greedy"}'
  # 其余参数（fp8 KV、EP、CUDA graph 等）以官方 recipe 为准
```

**一个容易踩的部署细节**：DSpark 与 DFlash 的 `sample_from_anchor` 取值**相反**——DFlash 默认 anchor 只做条件、只产出 `block_size − 1` 个投机 token；DSpark 默认 anchor 也参与预测、产出 `block_size` 个（第 3 节的"小改造"）。**引擎的配置必须与草稿模型的训练配置一致**，错配会让草稿质量静默劣化（vLLM speculators 文档明确警告）。

**适用性判断**（工程推断，非论文结论）：

- ✅ 你**控制模型权重 + serving 栈**（自训/微调模型的推理服务）、流量里结构化输出（代码、数学、agent 工具调用）占比可观 → DSpark 是当前生产级投机解码的最优解；
- ✅ 有严格交互性 SLA（tok/s/user 下限）的 serving → DSpark 的负载感知验证正是为此设计（Figure 7 的右移前沿）；
- ❌ 租用第三方 API → 这些开关在引擎侧，你碰不到；
- ❌ 单用户/消费级硬件 → 投机解码要求草稿路径比目标快约 10~30 倍才划算，弱草稿器 + 小机器可能**负加速**（5.4 的"不赚边界"之一）。

**与本章其余部分的接线**：5.5 的 vLLM method 列表里，`mtp`（5.6，checkpoint 原生）→ `dflash`（5.7，块并行草稿）→ `dspark`（本文，块并行 + 置信度调度）正好是 2025~2026 年投机解码的三代生产形态；DeepSeek-V4 的演进（MTP-1 → DSpark，上线后两周）是这条路线的一个完整样本。

## 📝 总结

1. **DSpark 修的是 DFlash 的两个结构性洞**：并行草稿的块尾无依赖（后缀衰减，条件接受率 Code 0.87→0.78 / Chat 0.72→0.63）和固定草稿长度在高并发下的验证浪费（生产证据：MTP-3/5 严格降总吞吐，V4 基线长期停在 MTP-1）。
2. **两个机制各修一个洞，成本都极低**：Markov 头只看前 1 个 token（低秩 $B=W_1 W_2$，$r=256$），把草稿长度从 4 拉到 16 只付 0.2%~1.3% 整轮延迟，换最高 30% 接受长度提升（2 层 DSpark > 5 层 DFlash）；置信度头（解析接受率监督 + STS 校准到 ECE~1%）+ 硬件感知调度器（按前缀存活率贪心分配验证预算，$\mathrm{SPS}(B)$ 用引擎实测曲线）让验证长度随负载弹性伸缩。
3. **数字的正确读法**：离线宏平均 τ 比 Eagle3 高 26.7~30.9%、比 DFlash 高 16.3~18.3%（四模型重训同框架）；线上 V4 真实流量匹配吞吐下单用户加速 60~85%（Flash）/ 57~78%（Pro），极端 SLA 的 +661%/+406% 是"基线跑不动了"的前沿证据而非加速倍数。落地路径：DeepSpec（MIT）自训或拉官方 DSpark checkpoint，vLLM `method: dspark` 启用，注意 `sample_from_anchor` 与训练配置对齐。
