## 1. 方法论：先问诊，再开药

### 1.1 为什么不能"把所有优化都堆上去"

全模块四十多篇文章、几十种技术，如果全部堆上去会怎样？**堆满不等于变快，还可能互相拆台**——[11.2](/AIInfraGuide/inference/模块四-推理优化/第11章-推理优化选型与端到端实战/112-优化组合与叠加顺序) 会专门算这笔账（两个 1.5x 叠加往往只剩 1.6x，投机+量化甚至可能转负）。所以选型的第一步不是选方案，而是**确认症状**。

打个比方：你去看病，医生第一句话永远是"**哪里不舒服**"——不是"我这有 40 种药，你全吃了吧"。发烧、咳嗽、头晕各有各的病因，同一种症状也可能是完全不同的病（肺炎和感冒都咳嗽）。推理优化同理：**同一个"慢"字，背后可能是四种完全不同的病**：

| 📊 症状 | 用户体感 | 背后的阶段 |
|---|---|---|
| [A] TTFT 过高 | 问了问题，首 token 迟迟不来 | Prefill 阶段（compute-bound，算力是瓶颈） |
| [B] TPOT 过高 | token 一个一个蹦，体感卡顿 | Decode 阶段（memory-bound，显存带宽是瓶颈） |
| [C] 显存不够 | OOM、并发上不去、服务起不来 | 资源层（权重 + KV Cache） |
| [D] 尾延迟失控 | 均值还行，但 P95/P99 毛刺严重 | 系统层（调度、互扰、争抢） |

每类症状的"病根"不同，处方也完全排斥：TTFT 高去吃"投机解码"的药，就像咳嗽去吃止泻药——**药没错，病不对**。

### 1.2 第一步永远是压测拿基线

确诊之前先做检查。**推理优化的检查 = 压测基线**（9.2 的工具链）。为什么基线先行？打个比方：装修验收——**收房先验房**，闭水试验、敲空鼓、量地平，全过一遍才谈"怎么装"。不验房就开工，瓷砖贴完才发现墙面空鼓，返工成本是开工前的十倍。压测基线就是推理服务的"验房报告"：

- **工具**：`vllm bench serve` 跑一轮 1000 个请求、约 5 分钟出结果（9.2）；
- **指标**：9.1 的六件套——QPS、TTFT（P50/P95）、TPOT（P50/P95）、端到端吞吐（token/s）、显存峰值、GPU 利用率，一个都不能少；
- **口径**：客户端与服务器测同一个 TTFT 可能差出 30%+（9.1），统一口径才能对比；
- **可复现**：压测 config 进 repo，三个月后同一份配置还能跑出同样的数字（9.2 三原则：可复现、可对比、可解释）。

拿到基线后，把六件套和你的 SLO（TTFT/TPOT 的分位数目标，7.4）逐项对账：**哪项超标，就走哪个分支**。

### 1.3 症状叠加时怎么办

现实里往往不止一个症状：TTFT 和显存同时不达标。处理顺序学习路线 3.7 已经给死：**先解决 OOM（否则服务起不来）→ 再优化 TTFT（用户第一体感）→ 然后 TPOT/吞吐（延迟-吞吐 trade-off）→ 最后尾延迟（架构级改动，投入最大）**。后面 [11.2 的第 4 节](/AIInfraGuide/inference/模块四-推理优化/第11章-推理优化选型与端到端实战/112-优化组合与叠加顺序) 会给每一步配"怎么验证完成"的门禁，这里先记住：**症状可以叠加，但动手必须排队**。

## 2. 决策树全貌：四路症状，逐层分叉

把学习路线 3.7 的决策树按站内章节展开成完整版（每个叶子都指向具体的站内文章）：

```text
症状是什么？（压测六件套对号入座）
│
├─ [A] TTFT 过高（首 token 久等）
│   ├─ prompt 很长（数千到数万 token）？
│   │   → Chunked Prefill 分块 / 长 prompt 优化（2.4）
│   ├─ CPU 或调度成为瓶颈（GPU 在等 host）？
│   │   → Nsight Systems 定位（9.3）→ 图优化 / Attention 后端（2.5）
│   └─ 大量请求共享相同前缀（system prompt / few-shot）？
│       → Prefix Cache / RadixAttention（2.3）+ 前缀感知路由（10.3）
│
├─ [B] TPOT 过高（生成像挤牙膏）
│   ├─ 权重 / KV 搬运成为带宽瓶颈？
│   │   → 量化（4.x）砍权重带宽 / FlashAttention・FlashInfer（2.5）
│   ├─ 逐 token 串行是本质瓶颈（单请求已逼近理论下限）？
│   │   → 投机解码（5.x）
│   └─ 并发不足，GPU 没喂饱（利用率 < 60%）？
│       → Continuous Batching（2.2）/ 扩容与容量（10.4）
│
├─ [C] 显存不够（OOM 或并发上不去）
│   ├─ 模型权重占大头？
│   │   → Weight-only INT4（4.3）/ W8A8（4.2）/ FP8（4.5）
│   ├─ KV Cache 占大头（长上下文 / 高并发）？
│   │   → KV 量化（4.4）/ PagedAttention（2.1）/ 上下文管理
│   └─ 单卡放不下？
│       → 张量并行（6.2）/ 流水线并行（6.3）/ 多副本 DP（6.4）
│
└─ [D] 尾延迟 P95/P99 失控（均值还行，毛刺严重）
    ├─ Prefill 和 Decode 互扰？
    │   → PD 解耦（7.x）
    ├─ SLO 要求严格，需要全局最优调度？
    │   → Goodput / SLO 感知调度（7.4）
    └─ 资源争抢 / 容量不足？
        → 容量规划（10.4）/ 扩缩容与隔离（10.3）
```

📌 **关键点**：树上的每个判断都必须是"能用是/否回答"的工程问题，每个叶子都给具体方案名——**"视情况而定"不是方案**。下面四节逐个分支展开。

## 3. 分支 A：TTFT 过高

TTFT 主要受 Prefill 阶段影响：一次性处理完整个 prompt，是典型的 compute-bound（1.1）。三个子病因，先看是哪一种：

| 📊 子症状 | 诊断方法（看什么 / 做什么） | 推荐方案 | 预期收益量级 |
|---|---|---|---|
| prompt 很长（数千到数万 token） | 观察 prefill 耗时是否随 prompt 长度线性甚至超线性增长（9.3 profile） | Chunked Prefill 分块（2.4） | 长 prompt 下 TPOT P95 尖峰被削平；TTFT 均值略升、方差大降 |
| CPU 或调度成为瓶颈 | Nsight Systems 抓 trace，看 GPU idle gap 是否由 host 端引起（9.3） | 排查 tokenizer / 预处理；CUDA Graph 与 Attention 后端优化（2.5） | decode 单步 20-40ms 里 GPU 实算不到一半时，可追回可观比例 |
| 大量请求共享相同前缀 | 采样统计请求 prompt 的前缀重复率（2.3） | Prefix Cache（vLLM）/ RadixAttention（SGLang）（2.3）；多副本加前缀感知路由（10.3） | 前缀占 prefill 多久就省多少；llm-d 实测 P90 TTFT 最高快约 57 倍（10.3） |

### 3.1 prompt 很长 → Chunked Prefill

**怎么诊断**：用 9.3 的四层下钻，看 prefill 耗时是否随 prompt 长度线性甚至超线性增长；同时看同批 Decode 的 TPOT 是否出现周期性尖峰——尖峰的周期正好对应长 prompt 的 prefill 插队。

**为什么有效**：Chunked Prefill 把长 prefill 切成小块，掺进 Decode 的间隙里做（2.4），长 prompt 不再独占一步、拖垮整批。

**边界**：总计算量没变，只是摊平——2.4 自己说了"缓解不是根治"，7.1 进一步证明切块后的块间间隙仍会抖，极端 SLO 场景要走到 [D] 分支的 PD 解耦。**代价**：调度复杂度上升，TTFT 均值可能略升。

📌 **关键点**：这一支的收益不在 TTFT 均值，在 **TPOT 的方差**——削的是尖峰，不是总时长；如果你的 SLO 盯着 TTFT 本身，这一支可能帮不上忙。

### 3.2 CPU / 调度瓶颈 → 图优化

**怎么诊断**：Nsight Systems 的 trace 里，GPU 频繁空闲、kernel 之间有大段 gap，而 CPU 侧（tokenizer、采样、调度逻辑）在忙——这就是"GPU 等 CPU"（9.3）。

**为什么有效**：Decode 阶段单步只有 20~40ms（示意量级），其中 GPU 实算不到一半，大量时间耗在 kernel 启动间隙和 CPU 开销上（9.3）。2.5 的 CUDA Graph + 可插拔 Attention 后端（FlashAttention / FlashInfer）就是干这个的：把 launch 开销一次固化，把 Attention 换成更高效的 kernel。

**边界**：这套优化对"每一步都很短"的 Decode 收益最大；如果 GPU 本身已经跑满，说明瓶颈不在 host，走别的分支。

📌 **关键点**：CPU 瓶颈的判断必须靠 trace 证据（GPU idle gap），不能靠猜——"感觉调度慢"和"trace 里 host 侧确实在忙"是两回事，前者常常是误诊现场。

### 3.3 前缀重复高 → Prefix Cache

**怎么诊断**：从线上日志采样 100 条请求，统计 prompt 前 N 个 token 的重叠比例——Agent 场景的 system prompt、RAG 的固定指令、多轮对话历史都是典型的高重复来源（2.3）。

**为什么有效**：Prefix Cache 把共享前缀的 KV 缓存下来，后来的请求按块哈希命中就直接复用，跳过对应 Prefill（2.3）。SGLang 的 RadixAttention 更进一步，用前缀树管理共享（2.3）。

**边界**：单副本内缓存是"自动的"（vLLM APC 开箱即用），但**多副本场景 round-robin 会把前缀打散**——这属于 [11.2 冲突清单](/AIInfraGuide/inference/模块四-推理优化/第11章-推理优化选型与端到端实战/112-优化组合与叠加顺序)的第 f 条，解法是前缀感知路由（10.3）。单请求独占长前缀（如每个用户前缀都不同）时收益趋零。

📌 **关键点**：前缀重复率是这一支的"门禁指标"——重复率不高的业务，Prefix Cache 开了也是白开；先采样统计，再决定开不开。

## 4. 分支 B：TPOT 过高

Decode 阶段每步只生成一个 token，矩阵退化成一维向量，是典型的 **memory-bound**：每生成一个 token，GPU 都要把全部权重从显存里读一遍（4.3）。三个子病因：

| 📊 子症状 | 诊断方法（看什么 / 做什么） | 推荐方案 | 预期收益量级 |
|---|---|---|---|
| 权重 / KV 搬运成为带宽瓶颈 | Nsight Compute 看 Attention kernel 的 memory throughput 是否逼近 HBM 上限（9.3） | 量化砍权重带宽（4.x）；FlashAttention / FlashInfer 减少无效访问（2.5） | INT4 权重带宽 ÷4，吞吐约 ×2-3；W8A8/FP8 约 ×1.5-2（10.4，经验量级） |
| 逐 token 串行是本质瓶颈 | 单请求、低并发下 TPOT 仍超 SLO——已逼近理论下限 | 投机解码（5.x） | 低并发代码类 1.5-2.8x；高并发转负（5.4，必须测） |
| 并发不足，GPU 没喂饱 | GPU 利用率低于 60%，每步 batch 只有少量请求（9.1） | Continuous Batching 动态组批（2.2）；提高并发 / 扩容（10.4） | 利用率从约 30% 拉到 80%+（2.2） |

### 4.1 带宽瓶颈 → 量化 / Attention 后端

**怎么诊断**：Nsight Compute 打开 Attention kernel 的 SOL 面板，memory throughput 贴着 HBM 带宽上限走，就是带宽受限（9.3）。再算一笔账：70B FP16 权重 140GB，每 token 全部读一遍，A100 约 2TB/s 带宽下理论 TPOT ≈ 70ms——**这个下限只有砍带宽需求才能动**。

**为什么有效**：量化砍的是"每 token 要读的字节数"：INT4 把权重从 2 字节压到 0.5 字节（4.3），权重带宽需求 ÷4，decode 吞吐约 ×2-3（10.4 的经验量级）；W8A8 权重和激活一起压（4.2），FP8 在 Hopper 上原生支持（4.5），选型按 4.6 的决策树。FlashAttention / FlashInfer 则从另一头砍无效的 KV 访问（2.5，原理在[模块二 6.1](/AIInfraGuide/cuda/模块二-cuda编程与算子优化/61-flashattention-v1详解)）。

**边界**：量化的代价是精度，必须按 4.6 的评测协议验下游指标；而且**量化和后面要叠加的技术会互相干扰**（[11.2 冲突清单](/AIInfraGuide/inference/模块四-推理优化/第11章-推理优化选型与端到端实战/112-优化组合与叠加顺序)第 a、d 条）。

📌 **关键点**：INT4 不是"免费的四倍"——70B 压到 35GB 后单卡可装，但带宽红利和量化误差是一起来的；收益 ×2-3 是经验量级，吞吐和精度要同时验。

### 4.2 串行本质 → 投机解码

**怎么诊断**：把并发压到 1、单请求裸测 TPOT——如果仍然超 SLO，说明不是并发不够，是**每步生成一个 token 的串行本质**在拖后腿（1.1：自回归）。

**为什么有效**：投机解码让一个小模型（或 ngram / EAGLE 自草案）先批量猜 γ 个 token，大模型一次并行验证，猜中的直接产出（5.1）。低并发、代码类负载实测 1.5-2.8x（5.4）。

**边界**：收益由接受率 β 和 draft 开销 c 决定，接受率 < 0.5 或大 batch 下直接转负（5.4）——**这是全模块最"挑食"的优化**，5.5 给了半小时 A/B 验证协议，判定线：TPOT P50 提升 ≥15% 且 P95 不恶化才开。

📌 **关键点**：这一支的"先决问题"不是怎么调参，而是**你的负载是填空题还是开放作文**（5.4 的任务类型分析）——代码/JSON 类低熵负载才值得走进这一支。

### 4.3 并发不足 → Continuous Batching

**怎么诊断**：GPU 利用率 < 60%、每步 batch 里只有个位数请求，但 QPS 已经不小——说明请求在排队而不是在跑（9.1）。此时 TPOT 反而不高，高的是排队等待。

**为什么有效**：Continuous Batching 把调度粒度从"整批"细化到"迭代步"：完成即退、随到随补，利用率从约 30% 拉到 80%+（2.2）。

**边界**：如果你已经在用 vLLM 这类引擎，CB 是默认行为，问题就变成"并发够不够"——那是容量问题，走 10.4 的膝盖点标定，而不是继续调引擎参数。

📌 **关键点**：利用率 < 60% 时先确认瓶颈是"请求不够"还是"引擎没喂饱"——前者是容量/接入问题，后者才是调度问题，两味药完全不同。

## 5. 分支 C：显存不够

显存被两大块占据：模型权重和 KV Cache。**先算账，再选药**。7B 模型权重只有 14GB，而 32 层、4096 上下文、batch 16 的 KV Cache 就要约 32GB（4.4）——谁是刺客，算完才知道：

| 📊 子症状 | 诊断方法（看什么 / 做什么） | 推荐方案 | 预期收益量级 |
|---|---|---|---|
| 模型权重占大头 | 对比权重与 KV 的显存比例（10.4 第 3.3 节的账本公式） | INT4（4.3）/ W8A8（4.2）/ FP8（4.5），选型走 4.6 | 权重 140GB→35GB（INT4），单卡可装；KV 余量同步变大 |
| KV Cache 占大头 | 看 `vllm:kv_cache_usage_perc` 是否长期贴顶（10.2） | KV 量化（4.4）/ PagedAttention（2.1）/ 控制 `--max-model-len` 与并发 | KV 2-bit 压缩约 4 倍（4.4）；分页消除碎片（2.1） |
| 单卡放不下 | 权重 + KV 峰值超过单卡可规划容量（80-85%，10.4） | 张量并行（6.2）/ 流水线并行（6.3）/ 多副本 DP（6.4） | TP8 显存 ÷8、单 token 延迟近似 ÷8（6.6） |

### 5.1 权重占大头 → 量化

**怎么诊断**：启动日志看权重占用，线上看 KV 峰值，两者一对比就知道谁是大头（10.4 的显存校验三步：权重 + KV + 余量）。

**为什么有效**：INT4 把 70B 从 140GB 压到约 35GB，单张 A100 装下（4.3）；W8A8 压到约 70GB 两卡可放但 KV 余量紧张（4.6 的账本）；FP8 在 Hopper 上近似无损（4.5）。选型的本质不是位数越低越好，而是**先问瓶颈是显存、带宽还是吞吐**（4.6 的原话）。

### 5.2 KV 占大头 → KV 量化 / PagedAttention / 上下文管理

**怎么诊断**：`kv_cache_usage_perc` 长期贴顶、preemption 频繁，而权重还有大量富余——病根在 KV（10.2 的指标）。

**为什么有效**：KIVI 用 2-bit 把 KV 压缩约 4 倍（论文报告峰值显存省 2.6 倍、吞吐 2.35x-3.47x，4.4）；FP8 KV Cache 是 vLLM 原生支持的 2x 捷径（4.4）。同时别忽略两件"零成本"的事：PagedAttention 消除碎片（传统连续分配实际利用率可能只有两三成，2.1），以及把 `--max-model-len` 和并发上限压到业务真实需要的值（vllm快速入门 的显存估算）。

**边界**：KV 量化和权重量化是**两笔独立账**，叠加的精度影响必须评测——[11.2 冲突清单](/AIInfraGuide/inference/模块四-推理优化/第11章-推理优化选型与端到端实战/112-优化组合与叠加顺序)第 d 条。

📌 **关键点**：这一支最容易被忽略的是**免费项先行**——`--max-model-len` 压到业务真实值、并发上限收紧，往往比上量化更早见效且零风险。

### 5.3 单卡放不下 → 分布式并行

**怎么诊断**：可规划容量（约 80-85% 的卡上显存，10.4）装不下权重 + KV。

**为什么有效**：TP 把权重和 KV 都切开，显存 ÷TP，且 decode 的权重读取量同步 ÷TP，单 token 延迟近似 ÷TP（6.6 的算例：35GB INT4 单卡约 17.5ms vs TP8 约 8.75ms，待实测）——**TP 减延迟又减显存**；PP 是"装不下的最后手段"（6.3），DP/多副本加吞吐（6.4）。

**边界**：TP 吃 NVLink，不能跨机（6.2）；PP 低并发血亏且与投机解码不兼容（6.3，[11.2 冲突清单](/AIInfraGuide/inference/模块四-推理优化/第11章-推理优化选型与端到端实战/112-优化组合与叠加顺序)第 c 条）——**先量化再上并行**，顺序反了会多买卡。

📌 **关键点**：TP 的收益是"显存 ÷TP、单 token 延迟近似 ÷TP"，但通信开销随 TP 增长——TP 不是越大越好，6.2 有按模型大小的选型表。

## 6. 分支 D：尾延迟失控

这是最棘手的分支：均值还行、P95/P99 毛刺严重，往往不是单一环节慢，而是**系统层面的资源争抢和调度不当**（7.1）：

| 📊 子症状 | 诊断方法（看什么 / 做什么） | 推荐方案 | 预期收益量级 |
|---|---|---|---|
| Prefill 和 Decode 互扰 | 混合负载下对比纯 Decode 的 TPOT P95，差距超 2 倍即确认互扰（3.7 判据） | PD 解耦（7.x） | 互扰的 3-5 倍拖慢消除（7.1）；goodput 提升（7.4） |
| SLO 极严格 / 差异化 | 解耦后仍有请求超时，或不同请求 SLO 不同 | Goodput / SLO 感知调度（7.4） | DistServe 同资源服务请求量提升 7.4 倍（论文口径，7.4） |
| 资源争抢 / 容量不足 | 高峰时段 GPU 打满、队列堆积、跨副本互相挤占 | 容量规划（10.4）/ 扩缩容与隔离（10.3） | 峰值不违约；低谷不浪费（10.4） |

### 6.1 互扰 → PD 解耦

**怎么诊断**：做 7.1 的对照实验——同一份负载，分别跑"纯 Decode"和"混合负载"，对比 TPOT P95。学习路线 3.5 的检验标准是**拖慢 3-5 倍**即确认互扰；判定线更松的版本是差距超 2 倍就值得动手。

**为什么有效**：长 Prefill 插进某一步，该步所有 Decode 请求的 TPOT 一起遭殃（7.1 的 30ms → 210ms 算例）。解耦把两类请求分到独立 GPU 池，互扰从物理上消失（7.2）；代价是 KV 跨池传输（7B/2048 上下文约 4GB，IB 200Gb/s 约 160ms，7.5）和调度复杂度。

**边界**：解耦**不提升吞吐**（vLLM 官方原话，7.6），只治尾延迟；"小馆子别学大酒店开两个厨房"（7.5）——并发和 SLO 不够苛刻时，这笔账不划算。7.6 有完整的 vLLM 实战命令。

### 6.2 SLO 严格 / 差异化 → Goodput 与 SLO 感知调度

**怎么诊断**：解耦后仍有请求超时，或业务方给了差异化 SLO（普通问答一个标准、付费 Agent 另一个标准）——裸 QPS 报表已经无法指导决策（7.4）。

**为什么有效**：Goodput 的定义是"满足 SLO 的请求才算数"，有效吞吐 = 总吞吐 × 达标率 R（7.4）。TaiChi 类统一调度按 SLO 优先级动态分配 Prefill/Decode 资源（学习路线 3.7）。

**边界**：这是调度器层面的能力，投入在软件与调优；先确认你的服务已经把 SLO 落成监控告警（10.2），再谈调度。

### 6.3 资源争抢 / 容量不足 → 容量规划与隔离

**怎么诊断**：高峰时段 GPU 利用率贴顶、请求排队、HPA 扩到上限仍顶不住——问题在"卡不够"，不在"卡不快"。

**为什么有效**：容量规划从峰值 QPS × 平均长度算出总 token 需求，除以单副本膝盖点吞吐，乘冗余系数 1.4-1.5（10.4 的完整推导链）；扩缩容负责低谷不浪费、峰值不违约（10.3）。

**边界**：买卡是月-季度级决策，扩缩容是秒-分钟级决策——**扩缩容救不了算少了的预算**（10.4）。

## 7. 常见误诊：为什么优化经常白做

### 7.1 误诊一：把 TPOT 问题当 TTFT 问题治

用户说"慢"，先别急着上 Chunked Prefill。**先看压测：慢的是 TTFT 还是 TPOT？** 两个指标分别对应 Prefill 和 Decode，处方完全不同。最常见的翻车现场：TTFT 早就达标（P95 300ms），TPOT 却 200ms+ 蹦字，团队花一周调 prefill 参数——**指标看错，方向全错**。正确姿势：六件套和 SLO 逐项对账，谁超标治谁（9.1）。

### 7.2 误诊二：把显存问题当延迟问题治

显存不够的症状是 **OOM / 并发上不去 / 服务起不来**，不是延迟。但有个隐蔽的间接路径：**显存高水位 → 频繁 preemption → 被抢占的请求重新排队 → 延迟毛刺**（2.1 讲过抢占的代价）。所以"延迟毛刺"要先排除显存因素：看 `kv_cache_usage_perc` 是否贴顶、preemption 计数是否飙升（10.2），是的话先走 [C] 分支，再谈 [D]。

⚠️ **注意**：**把 preemption 毛刺当调度问题治，是尾延迟排查里最常见的无效加班**——显存高水位是"间接病因"，直接治调度等于给水管换新泵，但漏的是水箱。

### 7.3 误诊三：一个症状多个病因，不分顺序

TTFT 高可能是三个病因叠加（prompt 长 + CPU 慢 + 前缀重复高）。排查纪律：**从便宜到贵、从配置到架构**——先开引擎自带的开关（Chunked Prefill、Prefix Cache 都是参数级），再上算子/算法级（量化、投机），最后才动架构（PD 解耦）。每步之间必须**单变量验证**：一轮只改一个变量，改完压测，再动下一个（5.4 的 A/B 纪律：负载、并发档、采样参数全部冻结，只切目标开关）。

### 7.4 误诊四：用均值代替分位数

P50 好看、P95 爆炸的服务最容易被误判为"一切正常"——直到用户流失（7.4：聊天类 TTFT 超约 2 秒用户就开始流失）。**任何症状分类都建立在分位数上**：P95/P99 超标走 [D]，P50 超标走 [A]/[B]。

## 8. 落成一句话

- ✅ **先量后断**：没有基线不下结论——`vllm bench serve` 跑出六件套，和 SLO 逐项对账，谁超标治谁（9.2、9.1）。
- ✅ **先易后难**：配置（引擎开关）→ 算法（量化/投机）→ 架构（PD 解耦），每步验证完成再进下一步（3.7 顺序）。
- ✅ **单变量验证**：每次只改一个变量，改完压测，再动下一个；收益以你自己硬件上的实测为准。
- ✅ **先算显存账，再算延迟账**：OOM 时一切优化免谈；显存高水位导致的 preemption 毛刺先走 [C] 分支。
- ❌ **别拿"别人博客的加速比"当自己的承诺**；❌ **别把 P50 当体检表**——分位数才是用户体感；❌ **别让症状叠加打乱动手顺序**——排队做，不并做。

## 📝 总结

1. **方法论**：选型 = 问诊，先确认症状再开药；压测基线是"验房报告"，六件套与 SLO 对账定分支（收房不验房，返工十倍价）。
2. **决策树**：四路症状、十三个子分支——[A] TTFT 走 Prefill 侧（Chunked Prefill / 图优化 / Prefix Cache），[B] TPOT 走 Decode 侧（量化 / 投机 / CB），[C] 显存先算账（权重 vs KV）再选药（量化 / KV 量化 / 并行），[D] 尾延迟走系统层（解耦 / goodput / 容量）。
3. **数字锚点**：长 Prefill 把同批 TPOT 从约 30ms 拉到约 210ms（7.1）；权重带宽 ÷4 → 吞吐约 ×2-3（10.4）；KV 2-bit 压缩约 4 倍（4.4）；互扰拖慢 3-5 倍是解耦判据（7.1）。
4. **误诊四式**：指标看错（TTFT/TPOT 混治）、显存当延迟治（忽视 preemption 毛刺）、多病因不分顺序、用均值掩盖分位数。
5. **纪律**：先量后断、先易后难、单变量验证——三条纪律比任何一棵树都重要，它们保证你每次改动都能归因。
