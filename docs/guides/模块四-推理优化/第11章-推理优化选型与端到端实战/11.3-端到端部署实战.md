## 1. 需求分析：把需求钉死，才能开处方

### 1.1 模型规格与硬件：账先算清

问题：70B 模型在 4 张 A100 80GB 上装得下吗？先算显存账本（[4.6](/AIInfraGuide/inference/模块四-推理优化/第4章-量化/46-量化选型与vllm实战) 的公式）：

$$
\underbrace{70\text{B} \times 2\text{B}}_{\text{FP16 权重}} = 140\text{ GB} \quad \ll \quad \underbrace{4 \times 80}_{\text{4×A100 总显存}} = 320\text{ GB}
$$

**权重装得下，还剩下 180GB 给 KV Cache 和激活**——这是好消息。但“装得下”只回答了能不能跑，没回答能不能达标。真正的约束在后面三关：SLO、负载模型、带宽。

### 1.2 SLO：交互式产品的两条硬线

问题：RAG 问答的延迟目标怎么定？产品形态是“用户在对话框里提问，等答案”，属于交互式负载。参考 [MLPerf Llama-2-70B server 场景的口径](/AIInfraGuide/inference/模块四-推理优化/第10章-生产部署与运维/104-容量规划)（TTFT ≤ 2s、TPOT ≤ 200ms 是“可用”档），交互式问答要更紧一档：

| 📊 SLO | 目标 | 为什么 |
|---|---|---|
| **TTFT P95 < 1s** | 用户等首 token 超过 1 秒就会觉得“卡” | 2000 token 长输入下，这一条主要由 Prefill 决定（1.1 讲过 prefill 是 compute bound） |
| **TPOT P95 < 50ms** | 逐 token 输出，体感要像打字机不是挤牙膏 | 70B 的 Decode 是 memory bound，这条线直接决定量化/并行的选型（第 2 节会算） |

⚠️ **注意**：SLO 必须用分位数（P95）而不是均值——[9.1](/AIInfraGuide/inference/模块四-推理优化/第9章-性能分析与benchmark/91-推理指标体系) 的六件套教训：均值好看、P95 爆炸的服务，正是最伤重度用户的服务。判定线一律写“P95”，写进需求清单后不许偷换成均值。

### 1.3 负载模型：三个数字管住容量

问题：50 QPS 到底意味着多大的吞吐需求？负载模型 = 峰值 QPS + 平均 in/out 长度 + 峰值/均值比（10.4 的输入口径）：

- **峰值 50 QPS、均值 20 QPS**（峰值/均值比 2.5，线上对话产品的常见形状）；
- **平均输入 2000 token、输出 300 token**（RAG：检索段落拼进 prompt，输入天然长）；
- **长度分布**：90% 的输入落在 500~4000 token 之间，另有约 5% 的长尾（少数特别长的请求）直达 6K（压测必须覆盖，第 4 节）。

$$
T_{\text{req}} = \underbrace{50}_{\text{峰值 QPS}} \times \underbrace{(2000 + 300)}_{\text{每请求 token 数}} = 115{,}000 \text{ tok/s}
$$

这个 11.5 万 tok/s（其中 10 万 prefill + 1.5 万 decode）就是**硬需求**——和买多少卡无关，容量表、压测判定、量化决策全部从它长出来。工程结论先放这：**按 token 量算，prefill 占 87%（10 万 vs 1.5 万）——这是吞吐账的结构，决定容量和优化方向；但按耗时算 prefill 占比小得多（decode 每 token 慢一个量级），两条账要分开记**（2.5 会再讲）。

### 1.4 需求清单：开工前先签字

把上面四样收进一张表，这就是你的需求清单（交付物 #1）：

| 📊 需求项 | 取值 | 来源 |
|---|---|---|
| 模型 | 70B（如 Llama-3.3-70B-Instruct），FP16 权重 140GB | 业务方 |
| 硬件 | 4×A100 80GB（320GB），机内 NVLink | 预算 |
| SLO | TTFT P95 < 1s；TPOT P95 < 50ms | 产品方 |
| 负载 | 峰值 50 QPS / 均值 20；2000 in / 300 out；90% 在 500~4000 | 线上日志 + 业务预估 |
| 可用性 | 峰值时段不违约；单节点故障不降容量 | 业务方 |
| 总吞吐需求 | 115,000 tok/s（10 万 prefill + 1.5 万 decode） | 由负载模型算出 |

📌 **关键点**：需求清单里每一个数字都要有“谁定的、怎么来的”。老板问“为什么买 4 张卡”，你指着一行说“FP16 140GB，4×80=320GB，还得给 KV 留 180GB”——**没有签字的需求清单，后面所有决策都是空中楼阁**。

## 2. 方案设计：问诊后的第一版处方

需求清单在手，方案设计就像医生开处方：**先问诊（瓶颈在哪），再开药（上什么技术），不开“看起来高级”的药**（学习路线 3.7 的问诊比喻）。下面每一步都按 [11.1](/AIInfraGuide/inference/模块四-推理优化/第11章-推理优化选型与端到端实战/111-优化选型决策树) 的决策树走。

### 2.1 框架选型：vLLM，没有悬念

问题：框架选哪个？RAG 问答 = 通用 OpenAI 兼容接口 + 高并发吞吐 + 社区成熟度，[第 3 章](/AIInfraGuide/inference/模块四-推理优化/第3章-深入vllm/第3章-深入vllm) 的对比结论直接适用：**吞吐型在线服务选 vLLM**（SGLang 的 RadixAttention 对多轮/共享前缀也有优势，但那是进阶替换项；TensorRT-LLM 留给极限延迟场景）。本模块全程以 vLLM 为实例主线，部署、压测、监控的模板都是现成的——**选 vLLM 不是因为它最好，而是因为它的工程闭环最完整**。

### 2.2 量化选型：先看显存账本，再看带宽账本

问题：要不要量化？按 4.6 的决策树走两步：

**第一步，显存账本**（[4.6](/AIInfraGuide/inference/模块四-推理优化/第4章-量化/46-量化选型与vllm实战) 的四种方案）：

| 📊 方案 | 权重显存 | 4 卡能装？ | KV 余量（320−权重−激活） |
|---|---|---|---|
| FP16 | 140GB | ✅ | ~170GB，宽裕 |
| W8A8 / FP8 | ~70GB | ✅ | ~240GB，很宽裕 |
| INT4（AWQ/GPTQ） | ~35GB | ✅ | ~275GB，极宽裕 |

显存这一关：**FP16 就装得下，量化不是“装不下才做”，是“带宽不够才做”**——这就进入第二步。

**第二步，带宽账本**。Decode 每生成一个 token 要把整份权重读一遍（memory bound，[1.1](/AIInfraGuide/inference/模块四-推理优化/第1章-llm推理基础/11-llm推理基础) 讲过）。TP4 下每卡每 token 读 $140\text{GB}/4 = 35\text{GB}$，按 A100 ~2TB/s 带宽（[6.6](/AIInfraGuide/inference/模块四-推理优化/第6章-分布式推理/66-vllm分布式部署实战) 的口径）：

$$
\text{TPOT 地板}_{\text{FP16}} = \frac{35\text{GB}}{2\text{TB/s}} \approx 17.5\text{ms} \quad;\quad \text{TPOT 地板}_{\text{W8A8}} \approx 8.75\text{ms} \quad;\quad \text{TPOT 地板}_{\text{INT4}} \approx 4.4\text{ms}
$$

💡 **提示**：17.5ms 只是“读权重”的理论地板，实际 TPOT 还要加 KV 读取、采样、调度开销，P95 通常要 ×2 左右。对照 SLO（TPOT P95 < 50ms）：**FP16 在低并发下能达标，但余量很薄**——这就是“第一版先上 FP16、量化留给压测不达标时的迭代项”的理由：先跑通基线，让数字说话，别提前为没发生的问题付精度成本。

**第三步，RAG 专属的免费午餐**：RAG 请求共享同一个系统 prompt 和检索前缀，[2.3 的 Prefix Cache](/AIInfraGuide/inference/模块四-推理优化/第2章-推理引擎核心技术/23-prefix-cache-与-radixattention)（vLLM 的 Automatic Prefix Caching，V1 默认开启）能把共享前缀的 prefill 直接跳过——**对 token 量 87% 是 prefill 的 RAG 负载，这一项可能比量化更值钱，而且零精度损失**。部署后第一件事就是看 `vllm:prefix_cache_hits` 的命中率（10.2 的指标）。

### 2.3 并行方案：TP4，没有第二个选项

问题：4 张卡怎么切？候选只有两个——**TP4**（切矩阵，每层一次 AllReduce）或 **TP2 × DP2**（两卡一组，组间复制引擎）：

| 📊 方案 | 每 token 通信 | 单请求延迟 | 吞吐 |
|---|---|---|---|
| TP4 | 每层 2 次 AllReduce（机内 NVLink） | 低（权重读取 ÷4） | 单副本上限高 |
| TP2 × DP2 | 组内通信减半 | 较高（每卡读 70GB） | 两副本各自调度，排队灵活 |

[6.2](/AIInfraGuide/inference/模块四-推理优化/第6章-分布式推理/62-张量并行推理) 的结论：**TP 减延迟、DP 加吞吐**。本案例 SLO 里有 TPOT P95 < 50ms 这条硬线，TP4 是唯一能让单请求延迟达标的切法；吞吐不够时靠“多副本 × DP”解决（第 4 节的容量外推），而不是在单机内拆 DP。**TP4 每卡只背 35GB 权重，NVLink 机内通信，这是 6.6 说的“TP=每节点卡数”的官方推荐形态**。

### 2.4 要不要解耦：先压测，别拍脑袋

问题：尾延迟 SLO 严格，要不要直接上 PD 解耦？[7.6](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/76-vllm解耦实战) 的决策规则说得很死：**解耦的判据是“压测确认互扰”——混合负载下 TPOT P95 被拖慢 ≥2 倍，才谈得上解耦**。而且解耦是双份权重的固定成本 + KV 迁移开销（7.5 的账本），单机 4 卡连独立池子都凑不出来。结论：**第一版不解耦，但压测协议里专门设计“长 prompt 混入”的负载（第 4 节），把互扰量测出来**——有数据再决定，没数据不折腾。

### 2.5 投机解码：这单生意不划算

问题：RAG 问答要不要上投机解码？按 5.4 的收益公式过一遍：投机只加速 decode，总收益取决于接受率 $γ$ 和并发形态（[5.4](/AIInfraGuide/inference/模块四-推理优化/第5章-speculative-decoding/54-收益边界与限制) 的边界分析）：

1. **负载类型**：RAG 问答属于开放对话，接受率明显低于代码生成（5.4 引用的 EAGLE-1 论文实测：HumanEval 代码负载首位接受率 0.81~0.85，Alpaca 对话 0.70~0.76），收益先打折；
2. **并发形态**：投机收益区间是“低 QPS、低并发、延迟敏感”，本案例膝盖点在并发 16~32 之间——大 batch 下 draft 抢算力、batch expansion 摊薄收益（5.4 实测：batch 128+ 投机反而更慢）；
3. **成本**：draft 模型权重 + 瞬态 KV 都要从显存预算里出（5.4 的账本），而本案例显存余量正卡在长尾请求上。

落成一句话：**投机是给“短输入、长输出、低并发”的代码/补全场景的；RAG 问答在膝盖点并发下先跳过**。等哪天产品加了个“长文续写”功能（短输入、长输出、低并发）再回来翻 5.5 的配置。

💡 **提示**：别用“token 占比”代替“时长占比”估算投机收益——本负载 token 量上 prefill 占 87%，但 decode 每 token 慢一个量级，**按时长算 prefill 只占百分之几**；5.4 的公式里 $p$ 是 prefill 时长占比，代入前先 profile 一次线上请求。

### 2.6 最终方案表

| 📊 决策项 | 第一版方案 | 触发变更的条件（11.1 决策树） |
|---|---|---|
| 框架 | vLLM（OpenAI 兼容端点） | 结构化输出/多模态需求变化时看第 8 章 |
| 精度 | FP16（TP4） | TPOT P95 超 50ms → W8A8 或 INT4（2.2 账本） |
| 并行 | TP4，单副本 | 吞吐不够 → 加副本（DP）而非改并行切法 |
| Prefix Cache | 默认开启，监控命中率 | 命中率 < 20% → 检查请求前缀是否对齐 |
| 投机解码 | 不开 | 负载变成短输入长输出再评估（5.5） |
| PD 解耦 | 不开 | 压测确认互扰 ≥2 倍且有多机资源再上（7.6） |
| Chunked Prefill | V1 默认开启 | TTFT P95 超 1s 时调 `--max-num-batched-tokens`（2.4） |

📌 **关键点**：这张表的第二列是“第一版”，不是“最终版”——**每一行都配了触发变更的条件，这就是 11.1 决策树在真实项目里的用法：先跑起来，用压测数字决定要不要动下一行**。

## 3. 部署实施：把方案变成一条命令

### 3.1 权重获取与转换

问题：权重从哪来？两条路：

- **官方/社区现成权重**：HuggingFace 直接拉，70B 从零下载要 **15~30 分钟**（转引 [10.1](/AIInfraGuide/inference/模块四-推理优化/第10章-生产部署与运维/101-容器化与kubernetes部署) 的社区经验值，待核实），生产环境建议先落到内部对象存储，K8s 启动时从内网拉；
- **自己量化**（如果第 4 节压测后决定上 INT4/W8A8）：用 llm-compressor 离线量化，校准数据必须用 RAG 业务的真实分布（4.6 §3.3：用错校准数据 = 精度事故），产出 checkpoint 后 `vllm serve --quantization awq` 一行加载。

### 3.2 vLLM 启动参数：KV 预算先算后写

问题：启动参数怎么定？先把 KV 预算算出来再写命令。Llama-3.3-70B 的 KV 每 token（[2.1 的公式](/AIInfraGuide/inference/模块四-推理优化/第2章-推理引擎核心技术/21-pagedattention)，80 层、8 KV 头、head_dim 128、FP16）：

$$
\text{KV}_{\text{每token}} = 2 \times 80 \times 8 \times 128 \times 2 \approx 0.31\text{ MB}
$$

每请求 2300 token ≈ **0.71GB**；长尾 6K 输入 ≈ 1.9GB。每卡 KV 预算：$0.9 \times 80 - 35_{\text{权重}} - 3_{\text{激活/上下文}} \approx 34$GB，全机约 136GB → 长尾并发上限 ≈ $136/1.9 \approx 70$。**`--max-num-seqs` 取 64 起步**（留余量防抢占，2.1 讲过抢占的代价），压测时用 `vllm bench sweep` 校准。

```bash
# 第一版部署命令（参数以你所用版本的 vllm serve --help 为准）
vllm serve meta-llama/Llama-3.3-70B-Instruct \
  --tensor-parallel-size 4 \        # 单机 4 卡，NVLink 机内通信
  --max-model-len 8192 \            # 6K 输入上限 + 300 输出 + 余量
  --gpu-memory-utilization 0.9 \    # 默认值，KV 预算按它算
  --max-num-seqs 64 \               # 由 3.2 的 KV 账本推出，sweep 校准
  --served-model-name rag-70b \     # 多副本统一模型名（10.1 的约定）
  --shutdown-timeout 240            # 优雅停机排水期（10.1，默认 0 会掐请求）
```

💡 **提示**：V1 引擎下 Automatic Prefix Cache 和 Chunked Prefill 默认开启，**不需要显式传参**（以你所用版本为准）；想确认生效，看启动日志里 KV 分配行和 `vllm:cache_config_info` 指标（10.2）。

### 3.3 K8s 部署要点：四个坑一次填平

问题：上 K8s 最容易被什么坑死？[10.1](/AIInfraGuide/inference/模块四-推理优化/第10章-生产部署与运维/101-容器化与kubernetes部署) 的四个必改项，直接抄：

| 📊 要点 | 配置 | 为什么 |
|---|---|---|
| **三层探针** | startupProbe：`initialDelay 60s + period 10s × failureThreshold 120`（约 21 分钟窗口）；readiness：5s×3；liveness：10s×6 | 70B 冷启动 15~30 分钟，默认探针 30 秒就判死刑（CrashLoopBackOff 无限循环） |
| **资源申请** | `requests: {nvidia.com/gpu: "4", cpu: "8", memory: 64Gi}`，CPU 别写 1m | GPU request 必须 = limit；CPU 写太小会被排到拥挤节点，tokenize 和启动都慢 |
| **滚动更新** | `maxUnavailable: 0, maxSurge: 1` | 先起新的、健康后再杀旧的——vLLM 启动几分钟，默认策略等于每次发版都事故 |
| **优雅停机** | `--shutdown-timeout 240` + `terminationGracePeriodSeconds: 300` | 默认 0 = 收到 SIGTERM 立即掐断在飞请求；grace 必须大于 timeout 否则 K8s 提前 SIGKILL |

⚠️ **注意**：vLLM 的 OpenAI 兼容服务**默认不做任何认证**——Service 别绑公网，前面必须挂网关做 API Key 校验（10.1 的“别裸奔上线”）。灰度发布的具体做法在第 5 节。

### 3.4 模型加载验证：五分钟确认“真活了”

问题：怎么确认部署成功而不只是“进程起来了”？按顺序过四关：

```bash
# 1. 健康检查：返回 200 才算就绪（探针也打它）
curl -s localhost:8000/health

# 2. 模型列表：served-model-name 与请求体的 model 字段一致
curl -s localhost:8000/v1/models

# 3. 一次真实生成：20 token，temperature=0（可复现）
curl -X POST localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"rag-70b","messages":[{"role":"user","content":"用一句话解释什么是 KV Cache"}],"max_tokens":20,"temperature":0}'

# 4. 启动日志：确认 TP=4、KV 分配、max-model-len 与预期一致
```

四关全过再进压测。**日志里重点核对三行：tensor parallel size=4、KV cache 分配量、prefix cache 状态**——启动参数错了，压测数字全是废的（10.4 的“基准要跟着配置走”）。

## 4. 压测验证：验收不合格不交房

打个比方：**压测就是路考——需求清单是考试大纲，六件套报告是成绩单，SLO 是及格线。成绩单上写着“TPOT P95 < 50ms”，你拿“平均 30ms”糊弄，等于拿“大部分路段开得还行”糊弄考官**。验收不合格就交车（上线），后面天天扯皮。

### 4.1 压测协议：一份可复现的负载

问题：压测怎么压才不算白压？三个要素缺一不可（[9.2](/AIInfraGuide/inference/模块四-推理优化/第9章-性能分析与benchmark/92-压测工具) 的口径）：

1. **并发档位**：1 / 2 / 4 / 8 / 16 / 32 逐档压，画出延迟-吞吐曲线找膝盖点（9.1 的膝盖点概念）；
2. **长度分布**：必须复刻需求清单——90% 输入 500~4000 token、5% 长尾 6K、共享 500 token 系统前缀。用 GenAI-Perf 的合成参数 + 少量自定义长 prompt 注入（7.6 的混合负载做法）：

```bash
# 主体负载：RAG 分布（9.2 的模板改三个数）
genai-perf profile -m rag-70b --endpoint-type chat --service-kind openai \
  --endpoint /v1/chat/completions --url http://localhost:8000 \
  --concurrency 16 \
  --synthetic-input-tokens-mean 2000 --synthetic-input-tokens-stddev 800 \
  --output-tokens-mean 300 --output-tokens-stddev 100 \
  --streaming --random-seed 42 \
  --warmup-request-count 100 --request-count 1000

# 附加：脚本每 30 秒注入一个 6000 token 长请求（模拟 RAG 检索超长文档）
# 注入节奏写进 config 文件，保证每档压测可复现（9.2 的可复现要求）
```

3. **同配置可复现**：压测的引擎参数（TP、max-num-seqs、长度分布、并发档位）全部写进 config 文件随报告存档——**改任何一个参数，之前的压测作废重跑**（9.5 的门禁同理）。

### 4.2 六件套报告与判定

每档并发跑完，按 [9.1 的六件套](/AIInfraGuide/inference/模块四-推理优化/第9章-性能分析与benchmark/91-推理指标体系) 填验收单（下面数字是**演示用的示例值，必须换成你自己压出来的**）：

| 📊 指标 | 并发 1 | 并发 8 | 并发 16 | 并发 32 | SLO 判定线 |
|---|---|---|---|---|---|
| QPS | 0.3 | 0.9 | 1.05 | 1.1 | — |
| TTFT P50 / P95（ms） | 420 / 610 | 500 / 830 | 560 / 940 | 780 / 1480 | **P95 < 1000** |
| TPOT P50 / P95（ms） | 18 / 24 | 22 / 34 | 27 / 44 | 41 / 68 | **P95 < 50** |
| 输出吞吐（tok/s） | 90 | 270 | 315 | 330 | — |
| 显存峰值（GB） | 185 | 260 | 278 | 296 | < 320 |
| GPU 利用率（%） | 25 | 62 | 75 | 82 | — |

📌 **关键点**：这张表的读法是**找膝盖点**——并发 16 时六件套全绿（TTFT 940 < 1000 ✓、TPOT 44 < 50 ✓），并发 32 时 TPOT P95 直接 68ms 破线。**膝盖点就在 16~32 之间，对应单副本有效吞吐 ≈ 1.05 × 2300 ≈ 2,400 tok/s**（示例值）。同时注意显存：并发 32 时 296GB / 320GB，也快到顶了——两条腿都快到头，这不是巧合，是容量上限的两个侧面（10.4 的显存校验）。

### 4.3 不达标怎么办：走 11.1 决策树

问题：如果某一档不达标，怎么迭代？**先认症状，再开药**（11.1 的问诊表在项目里的用法）：

| 症状 | 诊断 | 处方（站内章节） |
|---|---|---|
| TTFT P95 > 1s | 看 `request_queue_time` vs `request_prefill_time`（10.2 的分阶段指标） | 排队久 = 容量不够 → 加副本；prefill 久 = 长输入吃掉算力 → 调 Chunked Prefill（2.4）、检查 Prefix Cache 命中率（2.3） |
| TPOT P95 > 50ms | 带宽地板算过（2.2：FP16 17.5ms） | W8A8（地板 8.75ms）或 INT4（4.4ms），量化后重跑精度评测（4.6 第 4 节流程） |
| 抢占频繁 / 显存顶穿 | `vllm:num_preemptions` 飙升 | 降 `--max-num-seqs`；或 KV Cache 量化（4.4，长上下文减半） |
| TPOT P95 有尖刺但均值正常 | 混合负载下对比纯 decode 的 P95，差 ≥2 倍 = 互扰确认（7.1） | 多机 + 严格 SLO 才上 PD 解耦（7.6 决策规则） |

⚠️ **注意**：一次只动一个变量。动了量化就只量化，重跑全档压测，把新六件套和旧报告并排对比——**没有对照的优化是自嗨**（9.5 的回归门禁思路：退化 >5% 直接回退）。

### 4.4 容量外推：把压测数字变成采购数字

问题：单副本膝盖点 2,400 tok/s（示例值），峰值 50 QPS 需要多少副本？走 10.4 的推导链：

$$
N_{\text{副本}} = \left\lceil \frac{115{,}000}{2{,}400} \right\rceil \approx 48 \text{ 副本} \Rightarrow 48 \times 4 = 192 \text{ 张 A100}
$$

$$
N_{\text{采购}} = 48 \times \underbrace{1.45}_{\text{估算误差 ×1.2 + 故障 ×1.1 + 扩容滞后 ×1.1}} \approx 70 \text{ 副本} \Rightarrow \sim 280 \text{ 张卡}
$$

这个数字会吓人一跳，但它讲了三件重要的事：**一，RAG 长输入场景的吞吐账就是这么贵，量化、Prefix Cache 这些优化的“报销理由”就在这里**；二，量化 INT4 后膝盖点 ×2~3（10.4 的杠杆表），副本需求降到 16~24——**一次压测驱动的量化决策，省下 100 多张卡的月租**；三，本案例的“4×A100”是**第一副本**，上线时 HPA 的 min/max 按它填（均值 20 QPS → min 约 20 副本，峰值 50 QPS → max 48 副本，采购 70 副本是节点池预算——10.4 的分工）。

## 5. 上线监控：让系统自己说话

### 5.1 指标与告警：三条规则先挂上

问题：上线后看什么？[10.2](/AIInfraGuide/inference/模块四-推理优化/第10章-生产部署与运维/102-可观测性) 的告警设计直接套，SLO 换成我们的（TPOT P95 < 50ms → 80% 预算 = 40ms；TTFT P95 < 1s → 800ms）：

```yaml
# 告警规则（简化示意，指标名以你所用版本 /metrics 为准）
groups:
  - name: rag-slo
    rules:
      # 规则 1：TPOT P95 超过 SLO 预算的 80%（40ms）持续 5 分钟 → P1
      - alert: TPOT_P95_Above_Budget
        expr: histogram_quantile(0.95, sum(rate(vllm:inter_token_latency_seconds_bucket[5m])) by (le)) > 0.040
        for: 5m
        labels: { severity: page }

      # 规则 2：KV 利用率 > 0.9 持续 5 分钟 → P1（容量告警，10.2 的口径）
      - alert: KV_Cache_Usage_High
        expr: vllm:gpu_cache_usage_perc > 0.9
        for: 5m
        labels: { severity: page }

      # 规则 3：抢占速率 > 0.5 次/秒 → P2（先观察，和容量告警配套）
      - alert: Preemption_Spike
        expr: rate(vllm:num_preemptions[5m]) > 0.5
        for: 5m
        labels: { severity: ticket }
```

💡 **提示**：`for: 5m` 是“持续 5 分钟才是事故，一次尖刺是噪声”——偶发长 prefill 会让 TPOT P95 瞬间冲高（7.1 的互扰），别让噪声半夜叫醒你。告警和 HPA 用同一批信号（10.3：`num_requests_waiting` 既发告警也喂 HPA），**阈值口径必须一致，否则出现“告警说扩容、HPA 说不用”的矛盾**。另加一条 RAG 专属观察项：`vllm:prefix_cache_hits` 命中率掉到 20% 以下，说明请求前缀结构变了，要查上游。

### 5.2 容量规划核验：月度对账

问题：容量表算得准不准？10.4 的闭环：**每月把线上实际峰值 QPS、实际 P95 延迟、实际 GPU 利用率拉出来，和容量表的假设对账**——预测 50 QPS 实际 42，预测 TPOT P95 44ms 实际 38ms，偏差写回容量表并注明原因。**容量规划像体检，月度复盘像复查**：体检报告当时是准的，血压（流量）变了，药量（GPU 数）就得调。

### 5.3 灰度与回滚：发版不事故

问题：模型/引擎更新怎么发？三步走（10.1 的滚动更新 + 9.5 的门禁）：

1. **金丝雀**：新版本先起 1 个副本，切 5~10% 流量，对比六件套（退化 >5% 立刻停，9.5 的门禁规则）；
2. **滚动**：通过后 `maxUnavailable: 0 / maxSurge: 1` 逐个替换——**任何时刻都有旧副本在扛流量**（10.1 的消防演习比喻）；
3. **回滚**：`kubectl rollout undo` 回上一版本镜像，HPA 自动缩掉新副本。**回滚预案在发版前写好，不是出事后现查**（10.1 的优雅停机配置保证回滚不掐在飞请求）。

## 7. 权衡与落成一句话

| 📊 决策 | 牺牲了什么 | 换取了什么 |
|---|---|---|
| 第一版 FP16 不量化 | TPOT 余量薄（地板 17.5ms vs SLO 50ms） | 零精度风险，先拿到干净的基线数字 |
| TP4 单副本起步 | 单副本吞吐上限低于 DP 拆法 | TPOT P95 达标（权重读取 ÷4） |
| 不开投机解码 | 放弃 decode 端潜在的加速（对话负载接受率明显低于代码负载，打折后所剩无几） | 不付 draft 显存、调度复杂度、大 batch 反噬风险（5.4） |
| 不解耦 | 尾延迟尖刺只能靠监控兜底 | 不付双份权重 + KV 迁移成本，架构保持简单 |
| 容量按峰值 ×1.45 采购 | 低谷期约 30% 卡闲置 | 峰值不违约，扩容滞后有缓冲（10.4） |

落成一句话的规则：

- ✅ **需求清单先签字，再谈方案**——SLO 写 P95 不写均值，负载模型四个数字缺一不可。
- ✅ **先跑 FP16 基线，让压测说话**——显存装得下 ≠ 带宽够用，TPOT P95 破线再量化，一次只动一个变量。
- ✅ **RAG 负载先吃 Prefix Cache 的免费午餐**，再考虑花钱的优化；投机解码在这个负载上是白忙（对话接受率低 + 膝盖点并发高，5.4 的边界）。
- ✅ **压测报告 = 验收单**：并发档位逐档压、六件套逐项填、膝盖点标出来，配置全进 config 可复现。
- ✅ **上线 = 七样交付物归档**：容量表是活表，月度对账，HPA min/max 从容量表来，告警与 HPA 同口径。
- ❌ **别跳过需求清单直接开压**；❌ **别用均值糊弄 P95 SLO**；❌ **别一次叠加两个优化**（11.2 的冲突教训：叠加效果不等于效果叠加）；❌ **别在没压测出互扰数据前上解耦**。

## 📝 总结

1. **需求先行**：50 QPS × 2300 token = 11.5 万 tok/s 是硬需求；70B FP16 140GB 在 4×A100（320GB）装得下，但装得下 ≠ 达标，SLO（TTFT P95 < 1s、TPOT P95 < 50ms）和负载模型才是决策的输入。
2. **方案克制**：vLLM + TP4 + FP16 起步；量化、投机、解耦全部留作“压测触发”的迭代项，每项配触发条件；RAG 的免费午餐是 Prefix Cache（2.3）。
3. **部署四坑**：三层探针（启动 21 分钟窗口）、资源申请（GPU request=limit）、滚动更新（maxUnavailable 0）、优雅停机（--shutdown-timeout + grace 300s）；KV 预算算出 max-num-seqs 64 起步。
4. **验收制压测**：并发 1→32 逐档压、长度分布复刻需求清单、六件套填验收单、膝盖点 ≈ 2,400 tok/s（示例值）——单副本只够约 1 QPS，容量外推 48 副本、采购 70 副本，这就是量化优化的“报销理由”。
5. **监控闭环**：三条告警规则（TPOT P95 > 40ms、KV > 0.9、抢占 > 0.5/s）+ 月度容量对账 + 金丝雀灰度 + 回滚预案；七样交付物归档才算上线。
