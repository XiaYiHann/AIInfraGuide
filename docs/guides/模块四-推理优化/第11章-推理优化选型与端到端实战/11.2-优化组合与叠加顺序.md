优化技术的收益不是线性的：**第二个优化吃到的是第一个优化剩下的瓶颈**。两个理论 1.5x 叠加，实际往往只有 1.6-1.7x；有些组合甚至转负——vLLM 社区实测里，投机解码在并发 128+ 时比不开还慢（5.4 引用的 PR #24322 曲线，3.55x 只出现在并发 1~4）。11.1 教你怎么按症状开处方，这一节讲**服药顺序**：先拆穿“两个 1.5x 不等于 2.25x”的乘法陷阱（附完整算例），再给六对已知冲突的清单（投机+量化、投机+Continuous Batching、PP+投机、量化+KV 缓存、PD 解耦+前缀缓存、多副本+前缀缓存，逐一引用站内分析），然后按学习路线 3.7 的操作顺序——**先解决 OOM → 再优化 TTFT → 然后 TPOT/吞吐 → 最后尾延迟**——给每一步配上“怎么验证完成”的门禁，最后落一张投入产出对照表。数字全部标注经验量级，以你自己硬件上的压测为准。

## 1. 核心认知：优化吃的是剩下的瓶颈

### 1.1 乘法陷阱：两个 1.5x 为什么不等于 2.25x

假设你在优化一个每请求耗时 100ms 的服务，有两项技术各声称“1.5x”。直觉上：$1.5 \times 1.5 = 2.25$，总耗时应该到 44ms。**问题出在哪？**——这个乘法的前提是两项优化作用于同一个瓶颈且互不干扰，而真实系统几乎从不满足。

打个比方：一条单车道公路堵车，你花大价钱把最堵的那段拓宽成两车道，车流快了 1.5 倍。再花同样的钱把**同一段**再拓宽——收益只剩一点点，因为瓶颈已经转移到下一个路口和收费站了。**优化 A 把瓶颈砍掉之后，优化 B 面对的已经不是原来的瓶颈**，它原本能省的那段时间，占比已经变小了。

### 1.2 算例：为什么叠加的收益递减

把一次请求拆开（示意数字，先感受结构再代入你的 profile）：prefill 20ms + decode 80ms = 100ms。

| 📊 方案 | 计算 | 总耗时 | 相对上一版 |
|---|---|---|---|
| 基线 | 20 + 80 | 100ms | 1.0x |
| +优化 A（decode 快 1.5x） | 20 + 53.3 | 73.3ms | **1.36x** |
| +优化 B（decode 再快 1.5x） | 20 + 35.6 | 55.6ms | **1.32x**（累计 1.8x） |
| +优化 C（prefill 快 2x） | 10 + 35.6 | 45.6ms | 1.22x（累计 2.19x） |

📌 **关键点**：三个“独立生效”的优化，累计只有 2.19x。注意，$1.36 \times 1.32 \times 1.22$ 算出来也正好是 2.19——乘积在这里成立，正因为每项优化砍的是**不同段**；但每一轮的“相对倍率”依然在下降（1.36 → 1.32 → 1.22），因为**越往后，剩下可砍的越少**。而一旦两项优化**抢同一段**（比如都依赖 decode 的带宽红利），第二个 1.5x 就只剩 1.1x，总加速 1.65x 而不是 2.25x——这就是乘法陷阱的两种来源：**收益递减**（吃剩下的瓶颈）与**互相干扰**（第 2 节的冲突清单）。

公式化地说：把请求时间分解成若干段 $T = t_1 + t_2 + \cdots + t_n$，优化 $i$ 只砍它负责的那段 $t_i$，则全局加速比

$$
S = \frac{T}{T - \sum_i \Delta t_i} = \frac{1}{1 - \sum_i \frac{\Delta t_i}{T}}
$$

——**每项优化的全局贡献 = 它省下的时间 ÷ 总时间**。这就是 10.4 那张“杠杆表”的数学依据：每个优化动了哪个变量、省了哪段时间，组合前先写清楚。

💡 **提示**：别把优化当折扣叠加——两笔“5 折”叠在**同一件商品**上是 2.5 折，因为两次折扣作用在同一个价格上；而优化作用的是**不同段的时间**，第二项还会改变第一项的运行条件。折扣是同一个基数的连乘，优化是不断变基数的递减——数学直觉在这里第一次失效，后面第 2 节还会失效第二次。

### 1.3 正确姿势：组合前先画时间分解

动手叠加任何两项技术之前，先回答三个问题：

1. **它们砍的是同一段吗？** 是 → 收益递减，第二个的期望值按 1.1-1.2x 估，别按 1.5x；
2. **它们会互相改变对方的运行条件吗？** 会 → 查第 2 节冲突清单；
3. **组合后怎么归因？** 答不上来 → 不允许同时上线，先单变量验证。

一句话版本：**优化叠加像叠 Buff，先看是不是同一层，再看会不会互相覆盖**。

## 2. 已知冲突清单：六对合不来的组合

### 2.0 冲突从哪来：抢同一根瓶颈

哪些组合会互相拆台？把第 1 节的框架再推一步：两项优化冲突，本质只有两种——**抢同一根瓶颈**，或**改变了对方的运行条件**。打个比方：优化技术像乐高零件——同一系列的颗粒严丝合缝（正交组合，收益接近乘积），跨系列硬拼要么咬不住（收益塌方），要么把旁边的结构顶松（精度或延迟恶化）。站内各章已经踩过六组“跨系列”的坑，下面逐一过：机制、出处、处理规则。

### 2.1 冲突 a：投机解码 + 量化

**机制**（5.4 第 3.1 节的分析）：方向总是坏的，两条路径都是——

- **draft 也量化**：draft 的分布进一步偏离 target（量化误差），重叠度下降，接受率掉。draft 通常比 target 小得多，量化省下的显存绝对值有限，**典型的“省小钱、亏大钱”**；
- **target 量化**：Rejection Sampling 的**无偏性依然成立**——但注意，它保证的是“相对你实际运行的（量化后）target 分布无偏”，而 draft 是按原始 target 学的，两者错位更严重，接受率照样跌。

⚠️ **注意**：无偏性（正确性）和收益（速度）是两件事。量化+投机叠加后输出依然合法，但加速比可能从 2x 掉到 1.1x（5.4）。**处理规则**（5.4 原话）：量化方案先定，投机最后叠加；叠加后重测接受率，掉过 0.5 就拆掉投机、保留量化——宁可少赚，不要白忙。

### 2.2 冲突 b：投机解码 + Continuous Batching

**机制**（5.4 第 3.2 节）：单请求的投机是“draft 串行 γ 步 + target 并行验证一次”，放进动态组批后有两个问题：

- **batch 展开（batch expansion）**：target 前向时，每个投机请求要占 γ+1 个 token 槽位。每个请求的接受位置不同，调度器每一步要维护“draft 批”和“展开后的 target 批”两套对应关系，复杂度高一个量级；
- **大 batch 下 draft 抢算力**：draft 模型同样 memory-bound，也吃显存带宽。PR #24322 实测：Llama-3.3-70B + Llama-3.2-1B 的 3.55x 只出现在并发 1~4，**batch 128+ 时投机解码反而比普通解码更慢**；vLLM 官方博客同样报告高 QPS 下 ShareGPT 1.4x、CNN/DailyMail 1.8x 的减速（5.4）。

**处理规则**：投机解码的收益区间是“低 QPS、低并发、延迟敏感”；吞吐型高并发场景默认关，测过再开（5.4 的半小时 A/B 协议）。

### 2.3 冲突 c：流水线并行（PP）+ 投机解码

**机制**（6.3 的记录）：截至 vLLM ≤ 0.15.0，官方口径是**流水线并行与投机解码不兼容**——draft 验证的批次结构没法穿过流水线。**开 PP 就得放弃投机解码的收益**。

⚠️ **注意**：这个状态在演进中（vLLM 论坛 2025 年确认不兼容，2026 年已有 MTP-under-PP 的进行中 PR）。**判断标准只有一个：打开你所用版本的 `vllm serve --help`，查投机与 `--pipeline-parallel-size` 的共存说明**——别信博客里的旧结论，也别拿旧版本的反例当永恒事实。

**处理规则**：模型大到必须 PP 时，默认放弃投机；想要两者兼得，先查版本、再做 A/B，以实测为准。

### 2.4 冲突 d：权重量化 + KV Cache 量化

**机制**：这是**两笔独立账**，最容易算混——权重量化（4.3，INT4 砍的是“每 token 读一遍的权重字节数”）和 KV 量化（4.4，KIVI 2-bit 砍的是“KV 的存储与搬运”）动的是不同的显存池和不同的带宽路径。单独看，KIVI 论文报告长上下文下 2-bit KV 近无损（4.4），INT4 权重的误差也在可接受范围（4.3）；**但叠加时精度误差会累积**——4.6 的原话是“每层量化误差是相乘的”。

**处理规则**：组合方案（如 INT4 权重 + FP8 KV，这是 vLLM 上常见的工程组合）必须按 4.6 的评测协议跑一遍下游指标（困惑度或业务评测集），别用“两个单独测都无损”推断“组合也无损”。反过来这也是**少有的叠加收益接近乘性的组合**——因为两笔账正交，只是误差要验。

### 2.5 冲突 e：PD 解耦 + 前缀缓存

**机制**（2.3 + 7.x 的组合分析）：Prefix Cache 是**实例内**的（vLLM 的块哈希缓存在单个引擎进程里，2.3）。解耦后链路变成“prefill 池算前缀与 KV → Connector 传给 decode 池”，出现两个问题：

- **decode 池不重算 prefill**，所以它天然没有前缀缓存——这是设计如此，不算 bug；
- 但**前缀复用的机会全落在 prefill 池**：如果路由把相同前缀的请求送到同一个 prefill 实例，第一次算完的 system prompt 仍可被后续请求命中（2.3 的哈希命中机制照常工作）；如果请求被轮询散开，前缀命中率趋近于零——**解耦把“前缀命中”问题从单实例内部放大到了路由层**。

**处理规则**：解耦架构下，前缀缓存的价值依赖**前缀感知路由**（10.3）——把同前缀请求钉在同一 prefill 实例；否则等于放弃了 2.3 的全部收益。vLLM 解耦实战（7.6）的前置检查清单里，路由与实例拓扑要在设计阶段一起定，别等上线后补。

### 2.6 冲突 f：多副本 + 前缀缓存

**机制**（10.3 第 3 节）：这是冲突 e 的“不和解耦版”——只要你有多个副本，K8s Service 默认的随机/轮询分发就会把相同前缀的请求撒到不同副本，**每个副本都只见过 1/8 的相同前缀，前缀命中率趋近于零**，每个请求都在重复做 prefill 的脏活。llm-d 的实测：cache-aware 路由下 P90 TTFT 最高快约 57 倍、吞吐从约 4,400 tok/s 提到约 8,700 tok/s（约 2 倍）——**同样的卡，只换路由策略**（10.3）。

**处理规则**：路由时按 prompt 前缀 hash 分桶，相同前缀 = 相同副本（10.3 的前缀感知路由，三条实现路径见原文）。

### 2.7 冲突速查表

六对冲突收成一张可直接对号入座的表：

| 📊 冲突对 | 一句话机制 | 处理规则 | 出处 |
|---|---|---|---|
| 投机 + 量化 | draft/target 分布错位，接受率掉 | 量化先定，投机后叠；接受率 < 0.5 拆投机 | 5.4 |
| 投机 + Continuous Batching | batch 展开 + draft 抢带宽，大 batch 转负 | 高并发默认关，测过再开 | 5.4 |
| PP + 投机 | draft 验证批次穿不过流水线 | 查 `vllm serve --help`，版本说了算 | 6.3 |
| 权重量化 + KV 量化 | 两笔独立账，误差相乘 | 组合按 4.6 协议评测 | 4.3 / 4.4 / 4.6 |
| PD 解耦 + 前缀缓存 | 前缀命中机会全落 prefill 池与路由层 | 配前缀感知路由 | 2.3 / 10.3 / 7.x |
| 多副本 + 前缀缓存 | 轮询打散前缀，命中率趋零 | hash（前缀）分桶钉副本 | 10.3 |

📌 **关键点**：六对冲突里五对涉及前缀缓存或投机——这两类技术的收益**依赖运行条件**（命中率 / 接受率），最容易在叠加时被悄悄破坏。

### 2.8 反过来看：哪些组合是真乘性

冲突清单不是“都不能叠”，正交组合的收益确实接近乘积。站内素材里的安全组合：

| 📊 组合 | 为什么正交 | 出处 |
|---|---|---|
| 量化 + Continuous Batching | 量化砍每 token 带宽，CB 提整体利用率，动的是不同变量 | 4.x / 2.2 |
| 量化 + PD 解耦 | 量化让每池膝盖点上移，两池独立标定互不干扰 | 10.4 第 4.2 节 |
| TP + 量化 | INT4 后单卡装得下，TP 需求下降（140GB 要 TP8，35GB 可 TP1） | 4.3 / 6.2 |
| 前缀缓存 + 前缀感知路由 | 缓存管“省不省 prefill”，路由管“命中率”，一对搭档 | 2.3 / 10.3 |

📌 **关键点**：判断一对组合是否安全，就看**它们是否动同一根瓶颈、是否改变对方的运行条件**——回答完这两个问题，比背任何清单都可靠。

## 3. 推荐优化顺序：先 OOM，再 TTFT，然后吞吐，最后尾延迟

学习路线 3.7 给了操作顺序的原文：**先解决 OOM（显存问题），否则服务都起不来；再优化 TTFT，因为首 token 延迟直接影响用户体感；然后提升 TPOT 和吞吐，这通常需要在延迟和吞吐之间做 trade-off；最后处理尾延迟，这需要系统架构层面的改动，投入最大**。下面给每一步补上“怎么验证这一步完成”的门禁（全部来自 9.x 的方法）。

**为什么不能反着来？**先解耦、后调参数的反序，等于把最大的变量（架构）和最小的变量（参数）同时扔进线上——出了问题无法归因，9.5 的门禁规则（退化 >5% block merge）会直接拦住你。**顺序的本质是归因优先级：先排除最便宜的变量，最后才引入最大的变量**。

### 3.1 第 1 步：先解决 OOM

**为什么最先**：服务都起不来，一切优化免谈。手段在 11.1 的 [C] 分支：量化（4.x）、上下文管理（`--max-model-len` 压到业务真实值，vllm快速入门）、TP 分摊（6.2）。

**验证门禁**：
- 目标负载（峰值并发）压测 30 分钟不 OOM、无 preemption（2.1 讲过抢占的代价）；
- `kv_cache_usage_perc` 峰值 ≤ 约 0.9，且按 80-85% 的可规划容量留余量（10.4 第 3.3 节）；
- 显存峰值记录进基准表，后续每次改配置都要回看（10.4 第 2.2 节：标定必须用生产同款配置）。

### 3.2 第 2 步：再优化 TTFT

**为什么第二**：首 token 直接决定用户留存——聊天类应用 TTFT 超约 2 秒用户就开始流失（7.4）。手段在 11.1 的 [A] 分支：Chunked Prefill（2.4）、Prefix Cache（2.3）、图优化（2.5）、前缀感知路由（10.3）。

**验证门禁**：
- 复现压测（9.2 的可复现三原则），TTFT P95 ≤ SLO（如 ≤ 2s，MLPerf server 场景口径，7.4）；
- 同时盯 TPOT P95 **不恶化**——Chunked Prefill 调过头会反过来伤 decode（2.4 的调度权衡）。

### 3.3 第 3 步：然后 TPOT 与吞吐

**为什么第三**：这一步是延迟-吞吐的 trade-off 主场——同样的卡，吞吐拉满和延迟达标往往是两个配置。手段：量化（若第 1 步没做）、投机解码（5.x，低并发场景）、Continuous Batching 与并发调优（2.2）、容量与扩缩容（10.4 / 10.3）。

**验证门禁**：
- 用 `vllm bench sweep` 扫膝盖点曲线（9.2）：找到“再压就满足不了 SLO”的并发档，确认优化后膝盖点吞吐上移；
- 投机类优化用 5.4 的判定线：**TPOT P50 提升 ≥15% 且 P95 不恶化 → 开；接受率 < 0.5 或 TPOT 无下降 → 关**；
- 吞吐与延迟**同时报**，别只报一个（9.1 的六件套纪律）。

### 3.4 第 4 步：最后处理尾延迟

**为什么最后**：需要架构级改动，投入最大（PD 解耦、SLO 感知调度）。手段在 11.1 的 [D] 分支：PD 解耦（7.x）、Goodput 与 SLO 调度（7.4）。

**验证门禁**：
- 达标率 $R = N_{\text{slo}} / N_{\text{total}}$（7.4）：压测与线上监控双口径，R 达到业务目标（如 P95 达标率 ≥ 99%）；
- 互扰对照实验（7.1）：混合负载 vs 纯 Decode 的 TPOT P95 差距从 3-5 倍收敛到 2 倍以内；
- 上线后接入回归门禁（9.5）：TPOT P95 退化 >5% 即 block merge，显存增长 >10% 需分析报告——**架构改动是最大变量，必须被门禁盯着**。

### 3.5 四步一览表

四步收成一张表，“完成”以压测数字为准：

| 📊 步骤 | 目标 | 主要手段 | 验证门禁（完成才算过） |
|---|---|---|---|
| 1 | 不 OOM | 量化 / 上下文管理 / TP | 峰值负载 30 分钟不 OOM、无 preemption；`kv_cache_usage_perc` 不超设定值（默认约 0.9） |
| 2 | TTFT 达标 | Chunked Prefill / Prefix Cache / 图优化 | 复现压测 TTFT P95 ≤ SLO，且 TPOT P95 不恶化 |
| 3 | TPOT / 吞吐 | 量化 / 投机 / CB / 容量 | 膝盖点上移；TPOT P50 ≥15% 且 P95 不恶化 |
| 4 | 尾延迟 | PD 解耦 / goodput 调度 | 达标率 R 达标；互扰差距收敛到 2 倍内；过 9.5 门禁 |

📌 **关键点**：每步的“完成”都以 9.x 的压测 / 门禁方法为准——不是“觉得好了”，是**数字说了算**；四步走完，等于把 11.1 的决策树从上到下执行了一遍。

### 3.6 贯穿始终的两条纪律

1. **每次只改一个变量**：改完压测、归因、再动下一个（5.4 的 A/B 纪律：负载、并发档、采样参数全部冻结）；
2. **每完成一步，回 3.2 重新标定**：10.4 的原话——“每做一步，回 3.2 重新标定膝盖点，容量表更新一版”。量化动显存/带宽，解耦动池结构，投机动 decode 吞吐，**每项优化动一根杠杆，改完重测**。

## 4. 投入产出对照表：先便宜的后贵的

下表是第 3 节顺序的“价格标签”（收益为**经验量级**，10.4/5.4/4.x 的口径，以你自己压测为准）：

| 📊 优化手段 | 投入 | 主要风险 | 收益量级（经验值） | 适用条件 |
|---|---|---|---|---|
| PagedAttention + Continuous Batching（引擎自带） | 低（换 vLLM 类引擎） | 低 | 利用率约 30% → 80%+（2.2） | 所有高并发在线服务，默认项 |
| Chunked Prefill | 低（参数开关） | 低 | 长 prompt 下 TPOT P95 尖峰削平（2.4） | 长 prompt 混合负载 |
| Prefix Cache + 前缀感知路由 | 低-中（路由层） | 低 | 高前缀重复下 TTFT 大降，llm-d 实测 P90 快约 57 倍（10.3） | Agent / RAG，高共享前缀 |
| Weight-only INT4 | 中（校准 + 评测） | 精度 | 权重显存 ÷4，吞吐约 ×2-3（10.4） | 显存或带宽受限 |
| W8A8 / FP8 | 中 | 低-中 | 吞吐约 ×1.5-2（10.4） | Hopper+，兼容性优先 |
| KV Cache 量化 | 中 | 长上下文精度 | KV ÷2（FP8）~÷4（KIVI 2-bit）（4.4） | KV 占大头 |
| 投机解码 | 高（draft + 评测） | **收益可为负** | 低并发代码类 1.5-2.8x（5.4） | 低 QPS、延迟敏感 |
| 张量并行 | 中（多卡） | NVLink 依赖 | 显存 ÷TP，单 token 延迟近似 ÷TP（6.6） | 单卡放不下 |
| PD 解耦 | 最高（双池 + 传输） | 复杂度、KV 迁移 | 互扰的 3-5 倍拖慢消除（7.1） | 大客流 + 严格 SLO |
| 容量规划 + 扩缩容 | 中 | 估算误差 | 峰值不违约、低谷不浪费（10.4） | 规模上线后 |

📌 **关键点**：这张表读起来有一条斜线——**投入最低的三项（引擎标配 + 参数开关）恰好收益最稳，投入最高的两项（投机、解耦）恰好风险最高**。所以优化顺序本质是“先便宜的后贵的”：把参数级的地基打好，再考虑算法级，最后才动架构级。反过来做（先上解耦再开 CB）等于没打地基就装修。

### 4.1 这张表能直接照抄吗？

不能——收益列全是**经验量级**（10.4 / 5.4 / 4.x 的口径），它们的使命是帮你排优先级，不是替你做承诺。每个数字都要用你自己的硬件和负载换掉：膝盖点靠 `vllm bench sweep` 扫（9.2），接受率靠 100 条真实 prompt 测（5.5），精度靠 4.6 的评测协议验。**表上的数字是地图，压测才是 GPS。**

### 4.2 怎么用这张表：三问过滤

拿到一张候选清单，先做三问，逐行过滤：

1. **投入扛得住吗？** 低投入的（引擎标配、参数开关）无脑先做——它们几乎不引入新风险，做了不亏；
2. **风险兜得住吗？** 精度（量化）、收益转负（投机）、架构复杂度（解耦）三类风险，对应业务能不能接受最坏情况——聊天客服能接受 INT4 的微小精度损失，医疗问答可能就不能；
3. **收益够付投入吗？** 用 10.4 的账本反推：量化让副本数 ÷2-3，省下的卡钱和校准+评测的工时比，哪个大？**投入是工时，收益是卡钱，单位要换成钱再比。**

过滤完剩下的，按第 3 节的顺序排队，一次一个。

## 5. 落成一句话

- ✅ **每次只改一个变量，改完压测，再动下一个**——归因比优化本身更值钱。
- ✅ **先便宜的后贵的**：配置（引擎开关）→ 算法（量化/投机）→ 架构（PD 解耦），每步验证门禁过了再进下一步。
- ✅ **组合前先画时间分解**：两项优化是否动同一根瓶颈、是否改变对方运行条件——答完这两个问题再决定叠不叠。
- ✅ **冲突清单对号入座**：投机+量化（接受率重测，<0.5 拆投机）、投机+CB（高并发默认关）、PP+投机（先查 `--help`）、量化+KV 量化（误差相乘要评测）、解耦/多副本+前缀缓存（必须配前缀感知路由）。
- ❌ **别同时开两个优化再归因**；❌ **别拿理论乘积当预期**（两个 1.5x 按 1.6-1.7x 估）；❌ **别把“输出无偏”当成“收益无损”**——正确性和速度是两本账。

## 📝 总结

1. **乘法陷阱**：优化吃的是剩下的瓶颈，每轮的相对倍率递减（算例：1.36x → 1.32x → 1.22x）；两项优化抢同一段时，第二个 1.5x 只剩 1.1x，总加速 1.65x 而非 2.25x。
2. **六对冲突**：投机+量化（接受率塌方）、投机+CB（大 batch 反噬）、PP+投机（版本口径，以 `--help` 为准）、量化+KV 量化（两笔账，误差相乘）、PD 解耦+前缀缓存（命中机会集中到 prefill 池与路由层）、多副本+前缀缓存（轮询打散，靠前缀感知路由救）。
3. **安全组合**：量化+CB、量化+解耦、TP+量化、前缀缓存+前缀感知路由——判断标准是“是否动同一根瓶颈、是否改变对方运行条件”。
4. **优化顺序**（3.7 原文 + 门禁）：OOM（30 分钟压测不 OOM）→ TTFT（P95 ≤ SLO）→ TPOT/吞吐（膝盖点上移 + TPOT P50 ≥15% 且 P95 不恶化）→ 尾延迟（达标率 R + 互扰差距收敛 + 9.5 回归门禁）。
5. **价格标签**：投入最低的三项收益最稳，投入最高的两项（投机、解耦）风险最高——先便宜的后贵的，别没打地基就装修。
