一个服务 QPS 从 20 涨到 25，表面看涨了 25%；但同一时期 P99 TTFT 从 500ms 涨到 3 秒——最慢的那 1% 请求（往往正是你的重度用户）体验从“还行”直接跌到“不可用”。单看任何一项指标，你都会得出相反的结论。这就是为什么本章把推理性能定义成**六件套**而不是“一个数”：QPS、TTFT（P50/P95）、TPOT（P50/P95）、端到端吞吐（token/s）、显存峰值、GPU 利用率。[1.1 节](/AIInfraGuide/inference/模块四-推理优化/第1章-llm推理基础/11-llm推理基础)给了这些指标的定义，这一节补上两个更重要的东西：**统一的测量口径**（同一个 TTFT 在客户端和服务端测出来能差出 30%+）和**指标间的 trade-off 地图**（并发、batch、SLO 怎么牵动六件套），最后把指标翻译成 [7.4 的 goodput](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/74-goodput与slo调度)——因为只有满足 SLO 的请求才算数。

## 1. 为什么单指标会骗人

### 1.1 两种“单指标谎言”

先看两个典型的线上场景：

**场景 A：QPS 高但 P95 烂。** 团队把 QPS 当唯一指标，压测报告一路飘红。某次发布后 QPS 涨了，大家庆祝。但用户投诉变多了——查下来发现 P99 TTFT 从 500ms 涨到 3s。为什么 QPS 会涨？**因为慢请求不释放连接，网关重试堆出更多请求**，系统像堵死的收费站，车流量（QPS）看着很大，每辆车都过不去。

**场景 B：TPOT 低但并发上不去。** 单用户测 TPOT 只有 20ms，体感飞快。但并发一到 64，TTFT 直接爆到 5 秒。为什么？TPOT 是单序列视角，它看不见排队——**并发上来后，新请求在调度队列里等的时间才是 TTFT 的大头**（1.1 的公式：TTFT ≈ 排队 + Prefill + 网络）。

这两个场景的共同教训：**推理系统是一个多指标耦合的系统，任何单指标都是截取的一个截面**。QPS 回答“机器忙不忙”，TTFT/TPOT 回答“用户爽不爽”，显存与利用率回答“钱花得值不值”——三个问题，一个数字答不了。

### 1.2 指标体系思维：延迟、吞吐、资源三维

打个比方：性能指标像一份体检报告。只报“体重正常”（QPS 高）没人敢说你健康——血压（TTFT P95）、血糖（TPOT P95）、体脂（GPU 利用率）各管一摊，**每一项都有参考区间，超出区间就是病**。体检报告从来不是“一个数字”，而是一组带区间的指标，这组区间就是后面的 SLO。

按“回答什么问题”把指标分成三维：

| 📊 维度 | 回答的问题 | 指标 |
|---|---|---|
| 延迟（用户体验） | 用户等多久、卡不卡 | TTFT P50/P95、TPOT P50/P95 |
| 吞吐（机器效率） | 机器每秒能干多少活 | QPS、端到端 token/s |
| 资源（成本账） | 显存够不够、GPU 用满没有 | 显存峰值、GPU 利用率 |

六件套正好覆盖三维。后面你会发现：**三维之间全是 trade-off，没有免费的提升**——把并发拉高，吞吐涨了，延迟就烂了；把 batch 调小，延迟好了，GPU 又吃不饱。指标体系的真正用途不是“报数”，而是**让你看清每一笔优化在拿什么换什么**（学习路线 3.6 的检验标准：报告至少 6 个指标，缺一个就看不见一类代价）。

⚠️ **注意**：单指标骗人还有一个隐蔽版本——**拿单指标当 KPI 考核**。指标一旦变成考核目标，就会被人为“优化”出好看的数字（第 6 节细讲），这是 Goodhart 定律在推理系统的翻版。

## 2. 指标六件套：定义与测量口径

### 2.1 六件套总览

问题：六件套各自怎么测、测的时候最容易踩什么坑？先看全景表，再逐个讲“怎么测、测什么、常见坑”：

| 📊 指标 | 维度 | 测量位置 | 一句话口径 |
|---|---|---|---|
| QPS（req/s） | 吞吐 | 压测客户端 | 成功完成的请求数 ÷ 压测时长 |
| TTFT P50/P95（ms） | 延迟 | 压测客户端 | 发出请求 → 收到第一个流式输出 |
| TPOT P50/P95（ms） | 延迟 | 压测客户端 | （端到端 − TTFT） ÷ （输出 token 数 − 1） |
| 端到端吞吐（token/s） | 吞吐 | 压测客户端 / 引擎日志 | 输出 token 数 ÷ 时长（或含输入） |
| 显存峰值（GB） | 资源 | 服务进程侧 | 压测全程显存占用的最大值 |
| GPU 利用率（%） | 资源 | 服务机遥测 | SM 活动占比（注意口径，见 2.6） |

📌 **关键点**：vLLM 官方文档有一句值得裱起来的话——**“指标术语没有统一标准，对比结果时要用测量点和公式，而不是指标名字”**。同一个“TTFT”，客户端测、网关测、引擎测，数字可以差出 30%+，而它们都不是“错”的。

### 2.2 QPS：每秒完成多少请求

怎么测：压测工具统计“成功完成的请求数 ÷ 压测总时长”，如 `vllm bench serve` 输出的 `Request throughput (req/s)`。

- **测什么**：系统在给定负载下的请求承载能力；
- **常见坑 1**：**超时/失败请求算不算完成？** vllm bench serve 只统计 `Successful requests`，失败的请求不进入吞吐也不进入延迟统计——如果你的服务大量超时，QPS 会“自动变好看”，这是报表里最阴险的假象；
- **常见坑 2**：QPS 强依赖输出长度。输出越短，单位时间完成的请求越多。**两个不同输出长度的 QPS 不可比**——A 服务 QPS 50（平均输出 64 token）和 B 服务 QPS 30（平均输出 512 token），B 的实际产能可能是 A 的 5 倍。

### 2.3 TTFT：首 Token 延迟的口径之争

问题是：**TTFT 从请求发出算，还是从进入调度算？tokenizer 时间算不算？** 答案是：都有人这么算，关键是**报告里写清口径**。三种常见口径：

| 口径 | 起点 | 包含什么 | 典型测量者 |
|---|---|---|---|
| 客户端口径 | 客户端发出请求 | 网络 + 排队 + Prefill + tokenize | 压测工具（vllm bench serve、GenAI-Perf） |
| 网关口径 | 网关收到请求 | 排队 + Prefill（不含公网） | 网关日志 |
| 引擎口径 | 请求进入引擎调度 | 排队 + Prefill（不含网络与客户端 tokenize） | vLLM `/metrics` |

💡 **提示**：用户体感 = 客户端口径。压测工具默认从客户端起算（vllm bench serve 官方定义：**TTFT 是从发送请求到收到第一个流式输出的时间**），这没问题；但如果你拿引擎日志的 TTFT 去对比压测报告的 TTFT，**必须先减掉网络与客户端开销**，否则你会在“优化了个寂寞”的错觉里浪费时间。

### 2.4 TPOT：每 Token 延迟与 ITL

vLLM 的官方公式（逐请求计算一次再聚合）：

$$
\underbrace{\text{TPOT}}_{\text{每 Token 延迟}} = \underbrace{\frac{\text{E2E} - \text{TTFT}}{\text{输出 Token 数} - 1}}_{\text{排除首 Token，把 Decode 总时长摊到每个输出 Token}}
$$

- **ITL（Inter-Token Latency）**：记录的是**相邻两次流式输出之间的间隔**，逐间隔聚合；
- 普通解码下每个流式输出只有一个 token，ITL ≈ TPOT。**投机解码时一次输出可能带多个 token：ITL 只统计输出块之间的间隔，TPOT 则把整个生成阶段摊到每个 token 上**，两者会明显分叉（vLLM 文档示例：两个 40ms 输出块内共 5 个 token，mean ITL = 40ms，而 TPOT = （180−100））/4 = 20ms）。
- **常见坑**：比较工具输出前先确认它是 TPOT 还是 ITL——1.1 提过 GenAI-Perf 的 ITL 也是排除首 Token 的，但不同工具实现细节不同，**别拿 A 工具的 ITL 对比 B 工具的 TPOT**。

### 2.5 端到端吞吐：token/s 的口径

问题：**“吞吐 500 token/s”里的 token 是输出 token 还是输出+输入？** 两个口径都有意义，混用才致命：

- **Output token throughput**：每秒生成的输出 token 数。压测里最常用（vllm bench serve 的 `Output token throughput (tok/s)`）；
- **Total token throughput**：输入 + 输出一起算（`Total token throughput (tok/s)`）。负载越长，这个数字越虚高；
- **常见坑**：`--ignore-eos`（强制生成满输出长度）会显著改变输出 token 数，进而改变一切吞吐与延迟口径——**同一次对比实验里，ignore-eos 必须一致**；
- **反直觉点**：短输出场景下 QPS 高但 output token/s 低；长输出场景反过来。**评估产能优先看 output token/s，评估承载能力看 QPS，两个都报**。

### 2.6 显存峰值与 GPU 利用率：资源维度

**显存峰值**：压测全程显存占用的最大值。怎么测：`nvidia-smi` 轮询、`torch.cuda.max_memory_allocated()`，或直接看 vLLM 启动日志的 KV cache 分配（`GPU KV cache size: 15,728,640 tokens`，除以 `max_model_len` 还能估算最大并发）。常见坑：**nvidia-smi 的利用率是整卡聚合视角、无法归因到单个进程**；CUDA context 本身就占几百 MB；峰值要扣掉其他进程的占用再对比。

**GPU 利用率**：这里的坑最深。`nvidia-smi` 的 `%util` 是**采样窗口内 SM 有没有活动的占比**——一个 kernel 只要在跑就算“忙”，哪怕 SM 只用了 30% 的线程。它衡量的是“有没有活干”，不是“干活效率”。更准的口径是 **DCGM 的 `sm_utilization`（SM 实际占用比例）**，GenAI-Perf 压测时会自动通过 DCGM Exporter 采集（`--server-metrics-urls`）。

⚠️ **注意**：利用率低不等于系统有问题。单请求、低并发时 GPU 利用率天然低（decode 是 memory-bound，算力本来就用不满）；**利用率是要结合并发一起看的**——并发 64 时利用率只有 20%，那才叫问题。

## 3. 指标间的 trade-off：延迟-吞吐曲线与膝盖点

### 3.1 并发上升：吞吐涨，延迟也涨

问题：并发和六件套是什么关系？**并发是把吞吐推上去的油门，也是把延迟拉下来的刹车**。

代入算例（示例数据，以你环境实测为准）：单并发下 TPOT P50 = 40ms，即单用户 25 token/s。并发拉到 32：

- 理想流水线：吞吐 ≈ 32 ÷ 0.04 = 800 token/s，延迟不变——**这是不可能的理想**；
- 现实：排队 + 争抢让 TPOT P50 涨到 60ms，吞吐 ≈ 32 ÷ 0.06 ≈ 533 token/s。**吞吐涨了 20 倍，但每个用户慢了 50%**；
- TTFT 涨得更狠：新请求要等前面的请求让出调度槽，TTFT P95 可能从 300ms 涨到 2s。

这就是 1.1 那条公式的工程含义：$\text{E2E} = \text{TTFT} + \text{TPOT} \times (n_{out} - 1)$——**并发先打 TTFT（排队），再打 TPOT（每步变慢）**，短输出场景 TTFT 先爆，长输出场景 TPOT 先爆。

### 3.2 batch 大小：三者的联动

问题：调大 batch 是“免费午餐”吗？不是，它在三个指标间做了一次隐蔽的转移：

- **吞吐↑**：Decode 是 memory-bound（1.1 讲过：每步要读全部权重），batch 越大，权重读取被越多序列摊薄，**这是 Continuous Batching 30%→80%+ 利用率的来源**（[2.2 节](/AIInfraGuide/inference/模块四-推理优化/第2章-推理引擎核心技术/22-continuous-batching)）；
- **TPOT↑**：一步的墙钟时间随 batch 变长（Kernel 排队、带宽争抢），每个用户出字变慢；
- **TTFT↑**：prefill 要和更大的 decode 批抢调度槽（这正是 [7.1 的互扰](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/71-混合batching互扰分析)）。

| 调整 | 吞吐 | TTFT | TPOT | 代价 |
|---|---|---|---|---|
| 并发 ↑ | ↑↑ | ↑↑ | ↑ | 排队变长 |
| batch 上限 ↑ | ↑ | ↑ | ↑ | 每步变慢、尾延迟尖刺 |
| 缩短输出 | ↑（QPS 虚高） | — | — | 业务不可控 |
| 拆分长 prefill（Chunked Prefill） | ~持平 | ↓（削峰） | 略↑ | 块间调度间隙 |

📌 **关键点**：没有“调到最大就最好”的参数，**每一档配置都在拿延迟换吞吐，或拿吞吐换延迟**。选哪一档，取决于你的 SLO（第 5 节），而不是“越大越好”。

### 3.3 延迟-吞吐曲线与膝盖点

把并发从 1 扫到 256，以吞吐为横轴、延迟（TTFT 或 TPOT 的 P95）为纵轴，画出的曲线长这样（形状定性，数字随负载与硬件变化）：

```
延迟(P95)
  ↑
  │                  ● 饱和区：加并发只涨延迟
  │               ●
  │            ● ←── 膝盖点（knee point）
  │         ●
  │      ●
  │   ●  ←── 低负载区：加并发几乎不涨延迟
  └──────────────────────────→ 吞吐
```

- **低负载区**：曲线近乎水平——GPU 还有余量，加并发白捡吞吐；
- **膝盖点附近**：延迟开始抬头，但吞吐还在涨——**这是“免费午餐”的终点**；
- **饱和区**：曲线近乎垂直——加并发只涨延迟，吞吐纹丝不动（甚至因排队抖动而下降）。

膝盖点的工程意义：**它就是你该待的工作点**。压测扫并发（9.2 的 `vllm bench sweep` 就是干这个的），找到膝盖点，再把 SLO 画成一条水平线——**膝盖点左侧的配置满足 SLO，右侧的全是浪费**。

### 3.4 为什么“最优”取决于 SLO

同一个系统、同一份负载，不同业务的最优配置完全不同：

| 业务形态 | 主指标 | 最优配置倾向 |
|---|---|---|
| 聊天/客服 | TTFT P95、TPOT P95 | 低并发、小 batch，宁可吞吐低 |
| 离线批处理/数据标注 | output token/s | 高并发、大 batch，延迟无所谓 |
| Agent/多轮工具调用 | goodput、TPOT P95 | 中并发 + 严格 SLO 门禁 |
| 长文档问答 | TTFT（长 prefill 占比高） | Chunked Prefill、prefix cache |

**“最优”不是一个点，而是“在 SLO 约束下吞吐最大的点”**——这正是 7.4 的 goodput 视角。指标体系的最后一块拼图，就是把 SLO 量化进指标里。

## 4. 尾延迟与统计口径：P50/P95/P99 与样本量

### 4.1 均值为什么骗人：一个长尾算例

问题：P50、P95、P99 到底差在哪？直接算。假设 100 个请求的 TTFT：99 个 40ms，1 个 4000ms（一次长 prefill 或排队尖刺）：

$$
\text{mean} = \frac{99 \times 40 + 1 \times 4000}{100} = 79.6\ \text{ms}
$$

- **P50 = 40ms**（一半请求比它快）；**P95 = 40ms**（95% 的请求都是 40ms）；**P99 = 4000ms**；
- 均值 79.6ms 看着“还行”，但**最慢的 1% 用户体验是 4 秒**——而这 1% 恰恰可能是你的付费用户。

打个比方：均值像**秒表**，掐一下只知道全程总耗时；分位数像**行车记录仪**，能回放每一段——哪段堵了 10 分钟、哪段一路畅通，全看得见。**秒表告诉你“平均 20 分钟到”，行车记录仪告诉你“周五晚高峰要 50 分钟”**，后者才是你能做决策的信息。

⚠️ **注意**：长尾还有一个放大器——**并发越高，尾越粗**。排队是 M/M/1 式（单队列、单服务台）的随机叠加，负载到 80% 以后 P99 会指数级抬升。所以**报告尾延迟必须同时报负载（并发/QPS）**，光报“P99 TTFT 500ms”不报“在什么并发下”，等于没报。

### 4.2 分位数的样本量要求

问题：跑 50 个请求能报 P99 吗？**不能，样本太少时 P99 就是最大值，完全不可靠**。给一个经验法则（工程口径，非严格置信区间推导）：

$$
\underbrace{n}_{\text{样本量}} \geq \underbrace{\frac{10}{1 - p}}_{\text{保证尾侧期望样本数} \geq 10}
$$

- P95：$n \geq 200$；P99：$n \geq 1000$；
- 直觉：P99 的估计实际上由**最慢的那 1% 样本（约 $n \times 1\%$ 个）**决定。100 个请求只有 1 个样本落在尾部，P99 ≈ 最大值，换个种子数字就天差地别；1000 个请求有 10 个尾样本，才勉强稳定；
- **低并发压测尤其危险**：并发 8、每请求 30 秒，一小时才 960 个请求，P99 基本是噪声。要报 P99，先算算样本量够不够。

💡 **提示**：这个法则也解释了为什么生产监控比压测更可靠——**生产是 24 小时全量数据**，P99/P999 都是真值；压测是抽样，永远带着不确定性。两套数据配合用：压测找趋势，监控验证事实。

### 4.3 报告的规矩：P50 与 P95 成对出现

一条可执行的口径纪律（学习路线 3.6 检验标准的落法）：

- **P50 和 P95 成对报**：P50 管“典型体验”，P95 管“会不会被投诉”，只报一个就是留了盲区；
- **只报 mean 的报表是红旗**：看到“平均延迟 80ms”的报告，先问 P95/P99 是多少；
- **每个延迟数字必须带负载上下文**：并发多少、输出长度多少、ignore-eos 与否。

---

## 5. SLO 与 goodput：把指标翻译成用户体验

### 5.1 达标率：一个请求算“完成”还不行

问题：六件套都齐了，怎么判断系统“行不行”？**给六件套划定红线，数一数多少请求在红线内**——红线就是 SLO（Service Level Objective）。7.4 给过定义：**一个请求只有同时满足全部 SLO 才算“合格”**，不合格的请求同样吃了 GPU、占了带宽，但对业务等于白做——用户已经走了。

$$
\underbrace{\text{达标率}}_{\text{SLO 通过率}} = \frac{\text{满足全部 SLO 的请求数}}{\text{总请求数}} \qquad
\underbrace{\text{goodput}}_{\text{有效吞吐}} = \underbrace{\text{QPS}}_{\text{裸吞吐}} \times \underbrace{\text{达标率}}_{\text{合格比例}}
$$

### 5.2 算例：QPS 没变，goodput 掉了 30%

设 SLO：TTFT < 500ms 且 TPOT < 50ms。某次发布后：

| 轮次 | QPS | 达标率 | goodput | 发生了什么 |
|---|---|---|---|---|
| 发布前 | 20 | 85% | 17 req/s | 基线 |
| 发布后 | 20 | 60% | **12 req/s** | TPOT P95 从 45ms 涨到 80ms，违约率从 15% 涨到 40% |

**QPS 一个数字都没变，goodput 掉了 30%**——这就是单指标报表看不见的退化。用户侧的体感是“变卡了”，但 QPS 曲线风平浪静。**goodput 把“系统吞吐”和“用户体验”接在了一起**，这也是为什么 7.4 说“Raw QPS 是给老板看的报表，goodput 才是用户感受到的体验”。

### 5.3 工具已经支持：--goodput 参数

好消息是，这条链路不用你手写脚本——两个主流压测工具都内置了 goodput：

- `vllm bench serve --goodput "ttft:500 tpot:50"`（键为 ttft/tpot/e2el，值为毫秒，多个键空格分隔）；
- `genai-perf profile --goodput "request_latency:300 output_token_throughput_per_user:600"`（键为指标名，值为毫秒或每秒吞吐）。

压测时把 SLO 直接传给工具，报告里除了六件套，还会多一行 **goodput**——从指标到用户体验的最后一公里，一行参数就打通了。

## 6. 决策规则：先定 SLO，再选指标

### 6.1 KPI 与作弊：指标成为目标就不再是好指标

打个比方：把 QPS 定为团队 KPI，会发生什么？**指标一旦成为考核目标，就会被优化出好看的数字，而真实目标被牺牲**（Goodhart 定律）。推理服务里最经典的三个“作弊”姿势：

- **压短输出**：max_tokens 从 512 砍到 64，QPS 翻倍，用户拿到半截答案；
- **拒绝长 prompt**：把超长请求挡在门外，TTFT P95 全线飘绿，用户被 429 教育；
- **降低采样温度/关掉流式**：延迟曲线变漂亮，产品体验变差。

这些都不是“造假”，是**指标设计错误逼出来的理性行为**——你考核什么，系统就优化什么。对策只有一条：**考核目标绑 SLO 达标率和 goodput，而不是裸指标**。

### 6.2 决策规则

决策规则：

- ✅ **先定 SLO**（业务侧回答“TTFT 多少用户能忍、TPOT 多少算流畅”），再把 SLO 写进压测工具（`--goodput`）和监控告警（7.4 第 7 节）；
- ✅ **主指标选 1-2 个，辅助指标全报**：聊天选 TTFT/TPOT P95，批处理选 output token/s，Agent 选 goodput——但六件套一个都不能少，少一个就看不见一类代价；
- ✅ **每个数字带口径与负载上下文**：客户端测还是引擎测、并发多少、样本多少（≥10/(1−p)）；
- ❌ **别拿单指标当 KPI**：QPS 会注水，P95 会漏掉（配 P50 一起看），mean 连 4 秒的尾都能藏；
- ❌ **别在样本不够时报 P99**：50 个请求的 P99 是最大值，不是分位数。

## 📝 总结

1. **体系**：推理性能是六件套（QPS、TTFT P50/P95、TPOT P50/P95、端到端 token/s、显存峰值、GPU 利用率），覆盖延迟/吞吐/资源三维——单指标必然骗人（QPS 高但 P95 烂、TPOT 低但并发上不去）。
2. **口径**：同一个指标有客户端/网关/引擎三种口径，可差 30%+；vLLM 官方的话——对比结果要用测量点和公式，别只看名字；TPOT=(E2E−TTFT)/（输出数−1），投机解码下与 ITL 分叉。
3. **trade-off**：并发和 batch 都是“拿延迟换吞吐”的旋钮，延迟-吞吐曲线的膝盖点是“免费午餐”的终点，工作点该选“SLO 约束下吞吐最大”的点。
4. **统计**：均值像秒表、分位数像行车记录仪；99×40ms+1×4000ms 的均值 79.6ms 藏得住 P99=4000ms；P99 至少 1000 样本，P50/P95 成对报、延迟必须带负载上下文。
5. **goodput**：达标率 = 满足 SLO 的请求占比，goodput = QPS × 达标率；QPS 不变时达标率从 85% 掉到 60%，goodput 掉 30%——工具（vllm bench serve / GenAI-Perf）已内置 `--goodput`。
6. **决策**：先定 SLO 再选指标，考核绑达标率与 goodput；拿单指标当 KPI 会诱发压短输出、拒长 prompt 的“理性作弊”。

## ⚠️ 常见错误做法

- ❌ **只看平均延迟**：压测报告“平均 50ms”。为什么错：均值被快请求稀释，长尾（P99）超标用户照样卡顿——“平均延迟是最容易骗人的指标”（本文原话）。正确做法：TTFT/TPOT 看 P95/P99，配合吞吐一起评估。
- ❌ **用 QPS 一个数字衡量服务好坏**：并发、负载长度不一样就不可比。为什么错：QPS 依赖负载模型（长度分布、并发），不同负载下的 QPS 没有可比性。正确做法：压测固定负载模型（9.2 的配置），跨场景用 goodput（7.4）。
- ❌ **把吞吐与延迟分开报**：吞吐高就说好。为什么错：高吞吐可能建立在尾延迟爆炸之上（batch 拉到最大）。正确做法：吞吐与 P95 延迟绑定报告（SLO 约束下的吞吐才有意义）。
- ❌ **忽略冷启动与预热**：服务刚起来就压测。为什么错：CUDA Graph 捕获、KV 分配预热前数字偏慢。正确做法：压测前预热（本文的预热步骤），记录稳定期指标。

- 能说出推理指标六件套及其所属维度（延迟/吞吐/资源），并解释为什么缺一个就看不见一类代价
- 能解释 TTFT 的客户端/网关/引擎三种口径差异（网络、排队、tokenize 各含在哪一层），并说出报告里必须写清口径
- 能用手算还原 TPOT：给定 E2E、TTFT、输出 token 数，用 $(E2E-TTFT)/(n_{out}-1)$ 算出结果误差不超过 10%
- 能解释投机解码下 ITL 与 TPOT 为什么不同（输出块内多 token：ITL 不计块内间隔，TPOT 摊到每个 token）
- 能画出延迟-吞吐曲线并标出膝盖点，说明低负载区/膝盖点/饱和区三段的 trade-off 性质
- 能根据业务形态选主指标：聊天→TTFT/TPOT P95，批处理→output token/s，Agent→goodput
- 能手算长尾算例：99×40ms + 1×4000ms 的 mean（79.6ms）、P50、P95、P99，并说出均值藏住了什么

- 能说出 nvidia-smi 利用率与 DCGM sm_utilization 的语义差异，并解释低利用率何时不算问题
