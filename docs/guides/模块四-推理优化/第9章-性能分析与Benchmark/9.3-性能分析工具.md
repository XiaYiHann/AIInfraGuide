一次 TPOT P95 异常，90% 的时间往往不是花在修，而是花在找“它到底坏在哪一层”：请求在排队？GPU 在等 CPU？还是某个 kernel 自己就慢？本节的答案是**四层下钻框架**——服务层（指标报表）→ 引擎层（调度与队列）→ 算子层（kernel 耗时）→ 硬件层（SM 与带宽），配上三件工具：torch.profiler 照算子、Nsight Systems 照 CPU-GPU 全链路、Nsight Compute 照 kernel 内部。一个典型事实：decode 阶段单次 step 只有 20~40ms（示意量级，以实测为准），其中 GPU 真正执行的可能不到一半，剩下的时间花在 kernel 启动间隙和 CPU 侧开销上。9.1 的指标报表是体检报告,告诉你"哪项超标";本节的工具是手电筒和内窥镜,告诉你"病灶在哪一层"。

## 1. 分析分层：从"指标异常"到"根因"的四层下钻

### 1.1 四层模型：服务 → 引擎 → 算子 → 硬件

先想一个问题：**一个请求从进来到出 token，时间都花在哪？** 拆开看，一个 TPOT（单 token 生成时间）由四段组成：

$$
TPOT = \underbrace{t_{\text{queue}}}_{\text{排队等待调度}} + \underbrace{t_{\text{launch}}}_{\text{kernel 启动间隙}} + \underbrace{t_{\text{kernel}}}_{\text{GPU 实际执行}} + \underbrace{t_{\text{sync}}}_{\text{同步/传输}}
$$

对应这四段，就是四个分析层：

| 📊 层 | 回答的问题 | 典型现象 | 用什么看 |
|---|---|---|---|
| 服务层 | 哪个指标坏了？ | TPOT P99 从 24ms 涨到 45ms | 9.2 的压测工具 + 9.1 的指标六件套 |
| 引擎层 | 是排队/调度问题吗？ | 队列堆积、prefill 抢占 decode | vLLM 日志与引擎 metrics（如 queue 深度、batch 大小） |
| 算子层 | 哪个 kernel 慢？ | attention kernel 占 step 的 45% | torch.profiler |
| 硬件层 | kernel 自身为什么慢？ | 带宽没打满 / 算力没打满 | Nsight Compute 的 SOL 面板 |

为什么要分四层？因为**同一个症状可能来自完全不同的层**。TPOT P95 高，可能是引擎层排队长（服务层指标异常），也可能是 decode step 本身变慢（算子/硬件层）。跳过前面的层直接钻 kernel，等于体检报告都不看就直接做胃镜——大概率找不到病灶，因为病灶根本不在胃里。

### 1.2 下钻路径：报表发现异常，手电筒照到根因

把四层串成一条**下钻路径**：

1. **服务层确认症状**：9.2 压测跑出指标六件套，确认是 TTFT 还是 TPOT、是 P50 还是 P95 坏；
2. **引擎层排除排队**：看引擎日志和内部 metrics——队列深度、running batch、preempt 次数；
3. **算子层定位 kernel**：torch.profiler 抓单次 step，看 top 算子与 CPU-GPU 间隙；
4. **硬件层问为什么**：Nsight Compute 对嫌疑 kernel 看 SOL，是 memory bound 还是 compute bound。

每一步都有明确的"退出条件"：**在某一层找到确定性根因，就停在这一层**，不用继续往下钻。比如引擎层发现请求被 long prefill 抢占，直接上 7.1 的互扰解法，kernel 层根本不用看。

💡 **提示**：这条路径和 9.1 的指标体系是配套的——报表负责"发现"，工具负责"定位"。报表里没有 P95 只有均值，你连"该下钻"都发现不了，所以 9.1 的六件套是这套分析流程的起点，不是可选项。

## 2. torch.profiler：算子和间隙的第一层放大镜

### 2.1 推理场景和训练有什么不同？

先问：**为什么不能照搬训练时的 profiling 习惯？** 因为关注点完全不同：

- 训练：关心**迭代吞吐**（iter/s）和 GPU 利用率，抓几十个 iteration 求平均；
- 推理：关心**单步延迟**（一次 prefill、一个 decode step）和**尾部分布**（P95/P99），一次只抓 1~2 步就够。

推理 profiling 的两个要点：**只抓单步**（不要 schedule 大循环），**同时开 CPU 和 CUDA**（推理的 CPU 侧开销占比远高于训练——decode 短 kernel 一个接一个，CPU 启动速度跟不上就是瓶颈）。工具本身的开销也不小（开启 `record_shapes`、`with_stack` 后 overhead 明显），所以别拿它跑全量压测，只抓"嫌疑样本"。

### 2.2 抓一次 decode step 的 trace

自己写的服务，直接在 forward 外圈套 profiler：

```python
# 抓单个 decode step 的 trace（推理场景：1~2 步即可，别抓长循环）
from torch.profiler import profile, ProfilerActivity, schedule

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],  # CPU 侧开销在推理里很关键
    schedule=schedule(wait=0, warmup=1, active=1),             # 跳过头几步，只留一个 step
) as prof:
    for step in range(3):
        logits = model.forward_one_step(input_ids, kv_cache)   # 你的 decode step
        prof.step()

prof.export_chrome_trace("decode_step_trace.json")
print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=10))
```

跑 vLLM 时不用改代码——基准 CLI 直接带 profiling（参数以你所用版本的 `--help` 为准）：

```bash
# 离线模式：profile 单个 batch 的生成过程
vllm bench latency --model Qwen/Qwen3-0.6B --input-len 512 --output-len 128 \
  --profile --num-iters 5 \
  # 旧实现的 profiler 输出目录用环境变量指定（以你所用版本为准）
  # export VLLM_TORCH_PROFILER_DIR=./vllm_profile

# 在线模式：服务端需先启用 profiler（--profiler-config），客户端再 --profile
vllm serve Qwen/Qwen3-0.6B --profiler-config '{"profiler":"torch","torch_profiler_dir":"/tmp/vllm_profile","warmup_iterations":1,"active_iterations":5}'
vllm bench serve --model Qwen/Qwen3-0.6B --profile ...
```

### 2.3 读 trace：三个信号

profiler 表格输出长这样（示意输出，字段名以你所用版本为准）：

```
Name                                       Self CUDA time   %
paged_attention / flash_attn kernel        18.2 ms         60.7%
gemm (fused 12288x512x...)                 7.1  ms         23.7%
rms_norm                                   1.4  ms          4.7%
sampling                                   0.9  ms          3.0%
...
```

看三个信号，按优先级：

1. **耗时 top 算子**：单步 30ms 里 attention 18ms（60%）——attention 是头号嫌疑；
2. **CPU 侧开销**：对比每个 op 的 CPU 时间与 CUDA 时间。若 CPU 时间普遍大于 CUDA 时间，说明 **CPU 在拖 GPU 后腿**（launch 跟不上）；
3. **kernel 间隙**：chrome://tracing 或 Perfetto UI 打开 json，看 kernel 方块之间有没有大段空白——空白就是 GPU 空转。

⚠️ **注意**：torch.profiler 只能看到"Python 调用栈 + PyTorch 算子"这一层。调度队列、HTTP 层、tokenizer 的耗时它看不到——那些属于引擎层，要用第 3 节的方法。换句话说：**profiler 说 attention 慢，不等于 attention 是根因**，它可能只是"被排队挤到后面执行"。

### 2.4 导出与可视化

`export_chrome_trace` 导出的 json 是 Chrome Tracing 格式，打开方式三选一：

- **Perfetto UI**（ui.perfetto.dev）：拖入 json 即可，支持放大、搜索 kernel 名；
- **chrome://tracing**：经典方式，功能够用；
- **TensorBoard 的 PyTorch Profiler 插件**（`torch_tb_profiler`）：除了时间轴还有算子统计视图。

📌 **关键点**：trace 文件可能很大（抓 10 秒 CUDA trace 轻松上百 MB），所以推理场景只抓 1~2 步——不是技术限制，是文件膨胀和 overhead 不划算。

## 3. Nsight Systems：CPU-GPU 全链路行车记录仪

### 3.1 三类 GPU idle gap

torch.profiler 回答“哪个算子耗时高”，但它回答不了“GPU 为什么空转”。打个比方：**torch.profiler 是单机位摄像头，Nsight Systems 是全景摄像头**——它同时记录 CPU 每个线程在干嘛、CUDA API 何时调用、kernel 何时在 GPU 上真正执行，把“谁在等谁”完整拍下来。

在时间轴上找 GPU 行的空白段（idle gap），对照 CPU 行判断归因，一共三类（模块二第 8 章的原理，这里给推理场景的判别法）：

| 📊 idle gap 类型 | 时间轴特征 | 推理场景典型来源 |
|---|---|---|
| CPU 瓶颈 | GPU 行空白，同时 CPU 行有长任务在跑 | tokenizer/sampling 在 CPU 单线程、调度器决策慢、数据搬移（H2D/D2H） |
| 通信等待 | GPU 行空白，CPU 行也在等 | TP 多卡间的 NCCL all-reduce（张量并行时每层都有） |
| launch 开销 | GPU 行空白很碎、每段都短，CPU 行是密集的 launch 调用 | decode 短 kernel 风暴：一个 step 里几十个 2~5us 的 kernel 排队启动 |

怎么区分 CPU 瓶颈和 launch 开销？看空白段的形态：**CPU 瓶颈的空白是"长而整"**（CPU 卡在某个函数上），**launch 开销的空白是"碎而密"**（CPU 一直在发启动命令，但 GPU 吃不满）。模块二第 8 章教你抓训练 iteration 的 gap，推理场景只是把"iteration"换成"一次 decode step"。

### 3.2 prefill 与 decode 的间隙差异：为什么 decode 更怕 launch 开销

这是推理场景最值得记住的一个对比：

- **prefill 是长 kernel**：一个 kernel 跑几百 us 到几 ms，启动开销（几个 us）占比不到 1%——gap 不重要，kernel 自身效率（SOL）才重要；
- **decode 是短 kernel**：一次 step 里几十个 kernel，每个只有几 us，launch 间隙占比可能到 30~50%——**decode 的敌人是间隙，不是 kernel**。

这也解释了 vLLM 默认开启 **CUDA Graph 捕获**（`--enforce-eager` 关闭时才不捕获）的动机：把固定形状的 decode kernel 序列捕获成图，一次 launch 执行整张图，把每 kernel 数 us 的启动开销压到亚 us 级（示意量级，以你所用版本的实现为准）。如果你的 trace 里 decode 段间隙异常大，第一反应应该是：**CUDA Graph 是不是没生效？**

### 3.3 命令行抓取与时间轴解读

```bash
# 抓 vLLM 服务的全链路 trace（cuda=GPU kernel 与 API、nvtx=引擎标注、osrt=OS 线程）
nsys profile --trace=cuda,nvtx,osrt --output=serve_trace.nsys-rep \
  vllm serve Qwen/Qwen3-0.6B --max-model-len 4096
```

服务起来后，用 9.2 的 `vllm bench serve` 打 30~60 秒负载，然后停掉进程，用 Nsight Systems GUI 打开 `.nsys-rep`：

1. 选中 **CUDA HW** 行（GPU kernel 执行）看总忙闲比；
2. 对照 **CUDA API** 行（CPU 侧调用）和 **NVTX** 行（vLLM 标注的 prefill/decode 区间）；
3. 在 decode 区间内放大，逐段看空白归因（3.1 的三类）；
4. 用 **GPU 利用率视图**（gpu metric sampling）看 SM 利用率曲线是否周期性塌陷。

💡 **提示**：trace 时长控制好——nsys 的 overhead 比 torch.profiler 小得多（典型几个百分点，视抓取选项而定），但文件照样会膨胀。先抓 30 秒定位问题窗口，再针对性地抓细节，别一次抓 10 分钟。

## 4. Nsight Compute：kernel 内部的手术台

### 4.1 SOL 面板：memory bound 还是 compute bound

torch.profiler 说"attention kernel 占 60%"，nsys 说"GPU 没空转"——那这个 kernel 为什么慢？**钻进 kernel 内部看**，这就是 Nsight Compute（`ncu`）的活。

对嫌疑 kernel 抓一份报告：

```bash
# 只抓 flash attention kernel，跳过前 50 次 launch（warmup），取 5 次
ncu --set full \
    --kernel-name "regex:flash" \
    --launch-skip 50 --launch-count 5 \
    -o flash_attn_prof python run_one_decode_step.py
```

打开报告看 **SOL（Speed of Light）面板**，核心是两个百分比：

$$
\text{Memory Throughput [\%]} \quad \text{vs} \quad \text{Compute (SM) Throughput [\%]}
$$

判断规则一句话：**哪个接近 100%，kernel 就是被哪个绑住的**。

| 📊 SOL 读数 | 结论 | 推理场景含义 |
|---|---|---|
| Memory 95% / Compute 20% | **memory bound**，已逼近带宽上限 | decode 的 attention 就应该是这样——每 token 要扫全量 KV，健康 |
| Memory 30% / Compute 85% | **compute bound**，算力打满 | prefill 的 GEMM 就应该是这样，健康 |
| Memory 40% / Compute 35% | **两个都没打满** | 有别的瓶颈：launch 间隙、依赖链、occupancy 不足、L2 命中差——最值得查 |

反直觉点在这里：**decode 阶段 attention kernel 显示 memory bound 不是 bug，是物理规律**——KV Cache 读取量随序列长度线性增长，带宽就是 decode 的天花板（1.1 的 KV Cache 账本）。看到 90%+ 的 memory throughput，正确结论是"kernel 已到极限，别在这上面浪费优化时间"，去查间隙和调度。

### 4.2 推理场景的典型 kernel 问题

- **decode 的 attention 带宽没打满**（Memory 60% 出头）：查是否用了 FlashAttention/FlashInfer 等优化实现、KV Cache 是否做了低效布局（cache hit 率、块大小），而不是怪 kernel 本身；
- **GEMM 利用率低**：decode 阶段 M 维度 = 当前 batch 大小，batch=1 时 GEMM 的 Tensor Core 利用率天然上不去——这是"形状问题"不是"实现问题"，解法是增大并发 batch（Continuous Batching，2.2）或换 fused 实现；
- **occupancy 低**：warp state 面板看每 SM 活跃 warp 数，寄存器/共享内存占用过大导致调度不足，GPU 空转但 SOL 显示"都没打满"。

### 4.3 与模块二第 8 章的分工

模块二第 8 章讲的是**工具原理**：Nsight 系工具怎么抓取、SOL 面板怎么读、怎么对 CUDA 算子（Reduce/GEMM/Softmax）做版本对比——那是"造轮子的人"的视角。本节的定位是**推理服务**：工具原理简要引用，重点是"服务指标异常 → 四层下钻 → 根因"这条完整路径。遇到 kernel 内部细节（如 bank conflict、共享内存用量），回到[模块二第 8 章](/AIInfraGuide/cuda/模块二-cuda编程与算子优化/第8章-性能分析工具链)补课。

⚠️ **注意**：`ncu` 的 full set 会对 kernel 做重放采样，**比正常执行慢一两个数量级**（这是官方文档明说的 overhead 特性），而且一次只适合抓 1~3 个嫌疑 kernel。把它当手术刀，别当体检仪。

## 5. 案例：TPOT P99 从 45ms 到 24ms 的下钻全流程

把上面四层串成一个完整案例。以下数字为**示意值**，用于展示方法，请在你的环境里实测（学习方法比记住数字重要）。

### 5.1 症状与第一步：服务层报表

压测结果（9.2 的 `vllm bench serve`，示意输出）：

```
ttft p99: 512ms    tpot p50: 26ms    tpot p99: 45ms
request throughput: 8.2 req/s        output token throughput: 2100 tok/s
```

**症状判读**：TPOT P50 是 26ms（正常），P99 是 45ms（基线 24ms）——典型的**尾延迟恶化**，均值没坏、尾巴坏了。怀疑对象先圈定在"偶发的慢 step"，而不是系统性的慢。

### 5.2 引擎层：排除排队

查 vLLM 引擎 metrics：running batch 平均 16、queue 深度为 0、无 preempt——**排队可以排除**。偶发慢 step 不是"请求等太久"，而是"某个 step 本身执行太久"。

### 5.3 算子层：torch.profiler 抓到 attention 大头

抓一次慢 step 的 trace（示意）：

```
paged_attention kernel          18.2 ms   60.7%   <- 嫌疑最大
fused gemm (FFN)                7.1  ms   23.7%
rms_norm / sampling 等          4.7  ms   15.6%
```

同时发现 **CPU 侧每 step 有 8~15ms 的间隙**（CUDA 时间小于 CPU 时间）。此时有两个假设：A) attention kernel 本身慢；B) kernel 没慢，但 GPU 在等 CPU。哪个对？交给硬件层和 nsys。

### 5.4 硬件层：Nsight Compute 排除 kernel 自身

对 `paged_attention` kernel 抓 SOL：**Memory Throughput 94% / Compute 35%**——带宽已打满，kernel 本身健康。**假设 A 被排除**：attention 不背锅，它只是"在慢的 step 里必然更慢"的受害者。

### 5.5 转折：Nsight Systems 发现 CPU 间隙 + git bisect

nsys 时间轴放大慢 step：GPU 行有 **8~15ms 的整段空白**，同时 CPU 行在跑一个长函数——**CPU 瓶颈**（3.1 的第一类）。对比正常 step：空白只有 2ms。

CPU 侧在干什么？追到调用栈，是 **CUDA Graph 捕获未生效导致的逐 kernel launch**。什么时候坏的？`git bisect` 把性能回归区间一分为二反复试跑，定位到某个 commit 把 `--enforce-eager` 意外带进了配置（示意）。

```
$ git bisect start bad_commit good_commit
$ git bisect run ./run_perf_regression_check.sh   # 脚本按 9.5 的门禁口径判好坏
```

💡 **提示**：git bisect 能用的前提是**可复现的基准脚本**——这就是 9.2 的可复现配置 + 9.5 回归门禁的意义：没有固定脚本，你无法二分定位，只能靠猜。

### 5.6 修复与回归验证

修掉配置后复跑同一份压测：**TPOT P99 回到 24ms**，P50 不变。结论归档一句话："TPOT P99 恶化 88% 的根因是 CUDA Graph 未生效导致 decode launch 间隙从 2ms 涨到 8~15ms；attention kernel 本身 SOL 94% 健康，全程未优化任何 kernel。"

📌 **关键点**：这个案例里 torch.profiler、ncu、nsys **三件工具缺一不可**——profiler 圈定嫌疑，ncu 排除 kernel，nsys 抓住真凶。如果一开始就上 ncu，你会在一个健康的 kernel 上浪费半天。

## 6. 权衡与落成一句话

每个工具都有代价，分析流程本身也有代价：

- **torch.profiler**：牺牲（overhead 高、看不到调度层），换取（算子级归因 + 形状信息），适用"确认哪个 kernel 耗时高"；
- **Nsight Systems**：牺牲（粒度粗、不深入 kernel 内部），换取（全链路视角、低 overhead），适用"定位 GPU 空转归因"；
- **Nsight Compute**：牺牲（重放慢 10~100 倍、信息过载、只能看 1~3 个 kernel），换取（kernel 内部最完整证据），适用"确认 kernel 自身 bound"；
- **先服务层后算子层**：牺牲（多几步前置排查的时间，每层最多 30 分钟），换取（不把时间浪费在错误的方向上）。

落成一句话的规则：

- ✅ **指标异常** → 先看引擎层日志/metrics（5 分钟），排除排队与抢占；
- ✅ **引擎层正常** → torch.profiler 抓单步（30 分钟），圈定 top 算子与 CPU 间隙；
- ✅ **kernel 耗时异常** → ncu 看 SOL（每 kernel 几分钟），问"为什么慢"；
- ✅ **GPU busy 正常但延迟高** → nsys 找 idle gap（1 小时），问"谁在等谁"；
- ❌ **别一上来就开 ncu**——它看不到排队、看不到间隙，只会给你一堆用不上的计数器。

---

## 📝 总结

1. **四层框架**：服务层（指标）→ 引擎层（调度/队列）→ 算子层（kernel）→ 硬件层（SM/带宽），每层有明确的退出条件，找到根因就停。
2. **torch.profiler**：推理场景抓单步（1~2 个 step），同时开 CPU+CUDA activities，重点看 top 算子、CPU-CUDA 时间差、kernel 间隙三个信号。
3. **Nsight Systems**：全链路行车记录仪，三类 idle gap（CPU 瓶颈/通信等待/launch 开销）按时间轴形态判别；decode 短 kernel 的间隙占比远高于 prefill，CUDA Graph 就是治它的。
4. **Nsight Compute**：SOL 面板用 Memory vs Compute 两个百分比判断 bound；decode attention 显示 memory bound 是健康信号，不是 bug。
5. **案例闭环**：TPOT P95 恶化 → 引擎层排除排队 → profiler 圈定 attention → ncu 排除 kernel → nsys 抓到 CPU 间隙 → git bisect 定位回归 commit，全程没优化一个 kernel。
6. **流程纪律**：先服务层后算子层，每层限时，别一上来就开 ncu。
