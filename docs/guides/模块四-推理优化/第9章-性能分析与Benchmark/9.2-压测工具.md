压测（Benchmark，基准测试/压力测试，固定软硬件与负载重复测量以建立性能基线）不是比赛，是**建立基线**。`vllm bench serve` 跑一轮 1000 个请求、5 分钟出结果，输出里就带齐了 9.1 的六件套——请求吞吐、输出 token 吞吐、TTFT（Time To First Token，首 token 延迟，用户提问到看到第一个字的等待）、TPOT（Time Per Output Token，逐 token 间隔，体感“卡不卡”的逐字延迟）、ITL（Inter-Token Latency，token 间延迟，流式相邻 token 的间隔）的均值/中位数/P99（Percentile 99，第 99 百分位，1000 次里第 990 名的延迟）全在一张表里。但工具只是起点：**同一份 config，三个月后还能跑出同样的数字，你才敢说一次优化是真有效**。这一节把压测的完整链路讲透：三个原则（可复现、可对比、可解释）、vllm bench 命令族（serve / latency / throughput / sweep）、后端无关的 GenAI-Perf，以及最容易被忽略的负载设计——为什么“平均长度”压测会骗人。9.1 定指标与口径，这一节把它们变成可执行的命令和可复现的配置。

## 1. 压测三原则：可复现、可对比、可解释

### 1.1 压测不是比赛，是建立基线

打个比方：F1 车队测圈速，必须在**同一条赛道、同样的轮胎配方、同样的计时规则**下测——换个赛道测出的 1 分 20 秒没有任何可比性。压测同理：赛道 = 负载（长度分布、并发模型），轮胎 = 硬件环境（卡型、驱动、引擎版本），计时规则 = 指标口径（9.1 那套客户端口径）。三者任何一个变了，数字就不能直接比。

三个原则，缺一不可：

- **可复现**：任何人拿到你的 config 文件，在同样的硬件上能跑出同样的数字（误差在噪声范围内）；
- **可对比**：两次压测的差异只来自“你想验证的那个变量”——比如开没开投机解码，而不是“顺便换了台机器”；
- **可解释**：每个数字都能说清它是什么口径、什么负载下测的，能回答“为什么是这个数”。

### 1.2 一份压测 config 应该包含什么

问题：什么算“可复现”？答案是**菜谱式完整**。一份只写“盐少许”的菜谱，换个人就做不出同一道菜；一份只写“vllm serve + 压测”的 config，换台机器就测不出同一个数。最小完备清单（学习路线 3.6 检验标准的落法：**任何人拿到 config 都能复现**）：

| 📊 类别 | 必填字段 | 为什么 |
|---|---|---|
| 模型 | 模型名 + revision/commit | 同名字不同权重文件，性能可差出几个点 |
| 硬件 | GPU 型号、数量、驱动版本、CUDA 版本 | 驱动影响 kernel 选择与带宽表现 |
| 引擎 | 框架版本、关键参数（`--max-num-seqs`、`--gpu-memory-utilization`、TP/PP） | 引擎参数是性能的最大变量之一 |
| 负载 | 输入/输出长度分布（均值+stddev 或数据集路径）、请求数、并发/到达模型 | 长度分布决定 Prefill/Decode 比例 |
| 行为 | 采样参数（temperature（采样温度，>1 更平更发散、<1 更尖更确定，见 [8.5 采样与解码](/AIInfraGuide/inference/模块四-推理优化/第8章-生产级服务特性/85-采样与解码算法)——该节讲温度对分布形态与多样性的影响；本文只管压测配置）、max_tokens（最大生成长度））、是否流式、ignore-eos | 采样与输出长度直接影响一切指标 |
| SLO（Service Level Objective，服务等级目标，达标阈值） | `--goodput`（Goodput，达标吞吐，满足 SLO 的有效吞吐）的阈值（如 ttft:500 tpot:50） | 9.1 的达标率与 goodput 全靠它 |
| 环境 | 种子、warmup 请求数、测试时段、机器独占情况 | 排除随机性与外部干扰 |

📌 **关键点**：config 不是“跑完就扔的命令”，它是**基线的法律文本**——三个月后对比性能，翻出当时这份文件，才能判断差异是优化带来的还是环境漂移带来的。

## 2. vllm bench serve：在线压测的主力

### 2.1 定位与最小示例

问题：在线压测和离线压测差在哪？`vllm bench serve` 是**在线（Online）压测**：先启动 `vllm serve`，压测客户端以 HTTP 请求打 OpenAI 兼容端点，测的是**用户真实路径**（含网络、排队、调度）。一条最小命令（以你所用版本的 `--help` 为准，参数名随版本演进）：

```bash
# 先起服务（另一个终端）
vllm serve Qwen/Qwen3-0.6B --port 8000

# 再压测
vllm bench serve \
  --backend vllm \
  --model Qwen/Qwen3-0.6B \
  --endpoint /v1/completions \
  --dataset-name random \
  --input-len 512 \
  --output-len 128 \
  --num-prompts 1000 \
  --max-concurrency 32 \
  --request-rate inf \
  --seed 42 \
  --save-result
```

关键参数：

- `--dataset-name`：负载来源，`random`（合成，配 `--input-len/--output-len`）、`sharegpt`（真实对话分布，配 `--dataset-path`）、`custom`（自己的 jsonl，每行 `{"prompt": "..."}`）、`hf`（HuggingFace 数据集）等；
- `--num-prompts`：请求总数。结合 9.1 的样本量法则，报 P95（Percentile 95，第 95 百分位）至少 200，报 P99（Percentile 99，已在首段定义）至少 1000；
- `--max-concurrency`：并发上限（默认不限），模拟网关/负载均衡器限流；
- `--request-rate`：请求到达速率（默认 `inf` = 立即全部发出，测最大吞吐）；
- `--seed`：随机种子，可复现性的第一块基石。

### 2.2 输出解读：六件套一次给全

成功跑完后输出长这样（**以下为 vLLM 官方文档的示例输出，数字不是你的机器跑出来的，以你实测为准**）：

```
============ Serving Benchmark Result ============
Successful requests:                     10
Benchmark duration (s):                  5.78
Total input tokens:                      1369
Total generated tokens:                  2212
Request throughput (req/s):              1.73        ← QPS（Queries Per Second，每秒请求数）
Output token throughput (tok/s):         382.89      ← 端到端吞吐（输出口径）
Total token throughput (tok/s):          619.85      ← 端到端吞吐（含输入）
---------------Time to First Token----------------
Mean TTFT (ms):                          71.54
Median TTFT (ms):                        73.88       ← TTFT P50
P99 TTFT (ms):                           79.49       ← TTFT P99
-----Time per Output Token (excl. 1st token)------
Mean TPOT (ms):                          7.91
Median TPOT (ms):                        7.96        ← TPOT P50
P99 TPOT (ms):                           8.03        ← TPOT P99
---------------Inter-token Latency----------------
Mean ITL (ms):                           7.74
Median ITL (ms):                         7.70
P99 ITL (ms):                            8.39
==================================================
```

对照 9.1 的六件套：QPS（Queries Per Second，每秒请求数，`Request throughput`）、TTFT P50/P95、TPOT P50/P95、端到端吞吐（`Output/Total token throughput`）都在里面——缺的只有显存峰值和 GPU 利用率（这两个要另配 `nvidia-smi`/DCGM 遥测，见 [4 GenAI-Perf：后端无关的一站式压测](#4-genai-perf后端无关的一站式压测)——该节讲 DCGM 遥测自动采集显存与利用率；本文的输出表只覆盖延迟与吞吐）。

⚠️ **注意**：**TTFT/TPOT 的统计只覆盖 Successful requests**——失败请求不进延迟统计。如果失败率很高，这张表会“虚绿”，所以先看失败数，再看延迟。

### 2.3 负载控制：request-rate、并发与 burstiness

问题：怎么模拟“真实流量”而不是“一口气全灌进去”？vllm bench serve 提供三个旋钮（官方文档的负载模式表）：

- `--request-rate inf` + `--max-concurrency N`：**测上限**。所有请求立即发出，并发被压到 N——最常用的生产摸底配置，模拟“用户无限多、网关限流 N”；
- `--request-rate 5`：**泊松到达**。每秒约 5 个请求，到达间隔服从指数分布（`--burstiness 1.0` 即泊松），接近真实用户到达模式；
- `--burstiness`：调节到达的波动性。**CV（变异系数）= 1/√burstiness**——`0.1` 是尖峰式突发（压测弹性），`1.0` 是自然泊松，`5.0` 是均匀节拍（测延迟稳定性）；
- `--ramp-up-strategy linear --ramp-up-start-rps 1 --ramp-up-end-rps 20`：**渐进加压**，从 1 rps 线性加到 20 rps，找“系统在哪个负载点开始崩”。

💡 **提示**：官方给过一个实用的容量估算起点——vLLM 启动日志会打印 `GPU KV cache size` 和 `Maximum concurrency for 8192 tokens per request`，容量规划时把 `--max-concurrency` 设在报告值的 80-90%，SLA 验证时用满值。

### 2.4 结果保存与 goodput

- `--save-result`：结果存成 JSON（默认 `{backend}-{qps}qps-{model}-{时间}.json`，可用 `--result-dir`/`--result-filename` 指定）；`--save-detailed` 额外保存每个请求的 ttft/tpot/错误信息——**做 P95/P99 与分布分析必须开**；
- `--metadata key=value`：把环境信息写进结果文件（如 `--metadata vllm_version=v0.12.0 gpu=A100-80G`），基线的“法律文本”就靠它；
- `--goodput "ttft:500 tpot:50"`：9.1 第 5 节的 SLO 达标率，一行参数直接进报告；
- `--metric-percentiles 50,90,95,99`：自定义分位数（默认 99）；`--plot-timeline --timeline-itl-thresholds 25,50` 输出 HTML 时间线，一眼看出发慢的请求卡在哪个阶段。

### 2.5 从 benchmark_serving.py 到 vllm bench

演进脉络（写报告/对比历史数据时要知道）：vLLM 早期压测靠 `benchmarks/benchmark_serving.py`、`benchmark_latency.py`、`benchmark_throughput.py` 三个独立脚本，参数和行为各不相同；后来官方把它们收敛为统一的 `vllm bench` 命令族并写入正式文档，旧脚本仍留在仓库里但不再是主推路径。⚠️ **注意**：社区有明确记录 `vllm bench serve` **不是 benchmark_serving.py 的 1:1 替代**（部分参数语义有差异，见参考资料里的 issue）——**对比历史数据前，先确认两次压测用的是同一套工具与参数**，别把脚本时代的结果和 CLI 时代的结果直接相减。

## 3. vllm bench 命令族：latency、throughput 与 sweep

### 3.1 vllm bench latency：引擎的裸延迟

问题：想快速知道“引擎本身单请求多快”，不想起 HTTP 服务怎么办？用 `vllm bench latency`——**离线**测，不走 HTTP，直接驱动引擎跑固定长度请求，测的是引擎毛延迟（不含网络、不含排队、不含并发）：

```bash
vllm bench latency \
  --model Qwen/Qwen3-0.6B \
  --input-len 512 \
  --output-len 128 \
  --batch-size 1 \
  --num-iters-warmup 10 \
  --num-iters 30 \
  --output-json latency.json
```

参数含义（以你所用版本为准）：`--num-iters-warmup`（默认 10，预热 CUDA graph 与内存分配）、`--num-iters`（默认 30，正式迭代次数）、`--output-json`（结果落盘）。输出按 Prefill/Decode 阶段给 mean/median/P99 延迟。

⚠️ **注意**：latency 测的是**没有并发、没有排队**的引擎能力，它是“这台机器的物理上限”，不是“你的服务表现”。**适合做回归快检**（每次改动后 5 分钟跑一遍看有没有退化），**不适合做容量评估**（那要 serve 模式）。

### 3.2 vllm bench throughput：离线最大吞吐

`vllm bench throughput` 是**离线吞吐**压测：不经过 HTTP 与调度器排队，把一批请求直接灌进引擎，测引擎的极限产能（官方文档示例输出）：

```
Throughput: 7.15 requests/s, 4656.00 total tokens/s, 1072.15 output tokens/s
Total num prompt tokens:  5014
Total num output tokens:  1500
```

- `Throughput` 一行三列：req/s、**total tokens/s（输入+输出）**、**output tokens/s（输出）**——对比时统一用 output 口径（9.1 的教训）；
- 用法：`--dataset-name random --input-len 1000 --output-len 100 --num-prompts 2048`，或 `--dataset-name sharegpt` 用真实分布；
- 与 `vllm bench serve --request-rate inf` 的区别：throughput 走引擎直连（LLM 类 API），**不含 HTTP 层与调度排队**，数字通常更高——它是“引擎上限”，serve 是“系统表现”，两个都要测，分别回答不同问题。

### 3.3 vllm bench sweep：参数扫描与膝盖点曲线

问题：9.1 的延迟-吞吐膝盖点曲线，手动画要跑几十次压测，有没有自动化？`vllm bench sweep` 就是干这个的，四个子命令：

**`sweep serve`：引擎参数扫描。** 用两个 JSON 文件声明要扫的组合，跑**笛卡尔积**：

```bash
vllm bench sweep serve \
  --serve-cmd 'vllm serve meta-llama/Llama-2-7b-chat-hf' \
  --bench-cmd 'vllm bench serve --model meta-llama/Llama-2-7b-chat-hf --backend vllm --endpoint /v1/completions --dataset-name sharegpt --dataset-path ShareGPT_V3_unfiltered_cleaned_split.json' \
  --serve-params serve_hparams.json \
  --bench-params bench_hparams.json \
  --output-dir benchmarks/results \
  --experiment-name demo
```

`serve_hparams.json`（引擎参数）与 `bench_hparams.json`（负载参数）两两取笛卡尔积，格式示例见官方文档。默认每组组合跑 **3 次**（`--num-runs` 可调）取稳定值，`--dry-run` 先预览命令，`--resume` 断了续跑。

**`sweep serve_workload`：负载扫描（Workload Explorer）。** 自动从串行（并发 1）扫到满载，中间均匀取点——**这就是膝盖点曲线的自动化**：

```bash
vllm bench sweep serve_workload \
  --serve-cmd 'vllm serve meta-llama/Llama-2-7b-chat-hf' \
  --bench-cmd 'vllm bench serve --model meta-llama/Llama-2-7b-chat-hf --backend vllm --endpoint /v1/completions --dataset-name sharegpt --dataset-path benchmarks/ShareGPT_V3_unfiltered_cleaned_split.json --num-prompts 100' \
  --workload-var max_concurrency \
  --output-dir benchmarks/results
```

**`sweep plot` / `plot_pareto`：出图。** `--var-x max_concurrency --var-y median_ttft_ms --curve-by max_num_seqs,max_num_batched_tokens` 画延迟-并发曲线；`plot_pareto` 画 **tokens/s/用户 × tokens/s/GPU 的帕累托前沿**——“用户体验 vs 单卡产出”的最优配置带，对应 9.1 的“SLO 约束下吞吐最大”。

📌 **关键点**：sweep 是“贵”的工具——组合数 × 每组 3 次，一次全扫可能跑几个小时。**先用手工压测定出 2-3 个候选参数，再用 sweep 在候选附近精扫**，别一上来就全空间搜索。

## 4. GenAI-Perf：后端无关的一站式压测

### 4.1 定位与指标维度

GenAI-Perf 是 NVIDIA 出品的 LLM 压测工具（`pip install genai-perf`），与 vllm bench 最大的不同：**后端无关**——它打的是 OpenAI 兼容端点（或 Triton KServe/gRPC），背后是 vLLM、TensorRT-LLM 还是别的服务，对它没有区别。这也意味着**它能拿同一份负载对比两个不同的推理服务**（4.6 节用它对比量化版本就是这么干的）。

指标维度比 vllm bench serve 更全（官方 README 的指标表）：

| 📊 指标 | 含义 |
|---|---|
| Time to First Token（TTFT） | 请求发出 → 第一个响应，每请求一个值 |
| Time to Second Token（TTST） | 第一 → 第二个流式响应 |
| Inter Token Latency（ITL） | 相邻流式响应间隔 ÷ 后者包含的生成 token 数 |
| Output Token Throughput Per User | 每请求生成阶段的有效出字速度 |
| Request Latency | 请求发出 → 最终响应 |
| Output / Input Sequence Length | 实际输出/输入 token 数 |
| Output Token Throughput / Request Throughput | 全局：总输出 token ÷ 时长、完成请求 ÷ 时长 |

所有延迟指标给 **avg/min/max/p99/p90/p75** 六种聚合——9.1 的“P50/P95 成对报”直接满足。**GPU 遥测**（显存峰值、GPU 利用率、功耗、温度）通过 DCGM Exporter 自动采集（`--server-metrics-urls`，默认 `http://localhost:9400/metrics`），**六件套里的资源二维不用另开 nvidia-smi**。

### 4.2 示例命令与输出

命令骨架（4.6 的模板加上了流式、种子与 warmup；参数以你所用版本的 `genai-perf profile --help` 为准）：

```bash
genai-perf profile \
  -m Qwen/Qwen3-0.6B \
  --endpoint-type chat \
  --service-kind openai \
  --endpoint /v1/chat/completions \
  --url http://localhost:8000 \
  --concurrency 32 \
  --synthetic-input-tokens-mean 512 \
  --synthetic-input-tokens-stddev 0 \
  --output-tokens-mean 128 \
  --output-tokens-stddev 0 \
  --streaming \
  --random-seed 42 \
  --warmup-request-count 100 \
  --request-count 1000 \
  --profile-export-file genai_perf.json
```

输出是一张表（**以下为官方 README 示例，数字以你实测为准**）：

```
                              NVIDIA GenAI-Perf | LLM Metrics
```

### 4.3 与 vllm bench 的差异

| 📊 维度 | vllm bench serve | GenAI-Perf |
|---|---|---|
| 绑定关系 | 随 vLLM 分发，天然适配 vLLM | 独立工具，后端无关（vLLM/TRT-LLM/Triton 都打） |
| 延迟指标 | TTFT/TPOT/ITL（mean/median/P99） | TTFT/TTST/ITL/E2E（avg/min/max/p99/p90/p75） |
| 资源指标 | 无内置 | DCGM 遥测自动采集（利用率/显存/功耗/温度） |
| goodput | `--goodput "ttft:500 tpot:50"` | `--goodput "request_latency:300"` |
| 负载模型 | request-rate/burstiness/ramp-up 丰富 | 并发/request-rate，`payload:` 文件回放真实 trace |
| 配置管理 | 命令行 + sweep JSON | YAML config 文件（`genai-perf config -f`） |
| 引擎级能力 | latency/throughput 离线模式、sweep 扫描 | 以在线为主，另有 `analyze` 多场景扫描 |

📌 **关键点**：**对比同一引擎的不同配置 → vllm bench 顺手**（sweep 直接出膝盖点曲线）；**对比不同引擎/后端、要 GPU 遥测、要回放真实流量 → GenAI-Perf**。两个都装，各司其职。

### 4.4 Triton Perf Analyzer

Triton Inference Server 生态里的老牌压测器（学习路线 3.6 知识点点名）：以 `perf_analyzer` 命令驱动，支持固定并发/request-rate、自定义输入张量、输出统计（latency 分位数与吞吐）。它对 LLM 的痛点是指标是**传统推理口径**（端到端 latency、inference count），不区分 TTFT/TPOT——LLM 场景要么配合 Triton 的 ensemble 手动拆分阶段，要么直接用 vllm bench / GenAI-Perf 更顺手。

📌 **关键点**：Triton Perf Analyzer 更适合**多模型/传统 CV-NLP 推理**的压测；纯 LLM 服务用 vllm bench 或 GenAI-Perf 即可——**别为了“官方工具”而多套一层它并不擅长的抽象**。

## 5. 负载设计：让压测接近真实流量

### 5.1 固定长度 vs 真实 trace

问题：用 `--input-len 512 --output-len 128` 固定长度压出来的结果，能代表生产吗？**固定长度只能代表“某个平均场景”，代表不了分布**。

打个比方：一条河的平均深度 1 米——看起来可以蹚水过河，但有的河段深 5 米，不会游泳的人下去就完了。**“平均长度”压测就是只看平均深度**：生产流量里 90% 是 200 token 的短对话、10% 是 8000 token 的长文档，平均 1000 token 看起来平平无奇。但长请求的 prefill 会把同批短请求的 P95 TPOT 拖出尖刺（[7.1 的互扰](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/71-混合batching互扰分析)）：3-5 倍是学习路线的经验区间。

三种负载来源，从假到真：

- **合成固定长度**（`--dataset-name random --input-len ...`）：最快、最可复现，但只适合“引擎对比”这类相对测试；
- **真实/公开数据集**（`sharegpt`、`hf` 上的 ShareGPT_Vicuna、VisionArena）：带真实长度分布，适合基线压测；
- **自己的生产 trace**：最真。vllm 支持 `timed_trace`（带时间戳回放）；GenAI-Perf 支持 `--input-file payload:xxx.jsonl`（moon_cake 格式，每行带 `timestamp`/`input_length`/`output_length`，可精确重放生产流量节奏，还能用相同 `hash_ids` 测 KV cache 复用）。

📌 **关键点**：**固定长度压测只能用来横向对比（A vs B），不能用绝对值回答“生产能扛多少”**——后者必须上真实分布或生产 trace。

### 5.2 恒定并发 vs 泊松到达

问题：并发和到达率不是一回事吗？不是，它们模拟的是两种完全不同的现实：

- **恒定并发**（`--request-rate inf --max-concurrency 32`）：系统里永远同时有 32 个请求在跑，全程满载——测的是**持续高压下的稳态表现**。这是容量评估的主力；
- **泊松到达**（`--request-rate 10`）：请求按真实节奏到达，系统有“忙”和“闲”的交替——模拟真实用户行为，测的是**平均体验与空闲恢复能力**。注意：系统空闲时延迟会虚低，**泊松模式的 P95 需要更长的压测时长才能攒够样本**（9.1 的 $n \geq 10/(1-p)$）；
- **突发流量**（`--burstiness 0.1`）：模拟秒杀/热点场景，考验排队与重试逻辑。

### 5.3 混合负载：长 prompt 混短对话

生产里最“毒”的负载是**少量超长 prompt 混在大量短对话里**——长 prefill 每隔一段时间插进 decode 步，把同批短请求的 TPOT P95 周期性抬高（7.1 讲过的互扰）。构造方法（7.6 实验一的协议，配置写进文件）：

```bash
# 95% 短对话：200 token 输入、128 token 输出
vllm bench serve --dataset-name random --input-len 200 --output-len 128 --num-prompts 950 ...
# 5% 长文档：8000 token 输入、256 token 输出，单独一轮
vllm bench serve --dataset-name random --input-len 8000 --output-len 256 --num-prompts 50 ...
```

更精细的做法：用自定义 jsonl 把长短请求按**时间序列混排**（如每 20 个短请求插入 1 个长请求），再 `--dataset-name custom` 加载——**混合比例和注入节奏写进数据集文件，才能保证两次压测可复现**。混排后对比“纯短负载 vs 混合负载”的 TPOT P95，你就能量化互扰在你环境里的真实倍数。

⚠️ **注意**：混合负载下**只报平均延迟 = 自欺欺人**——长 prefill 是周期性的，均值把尖刺抹平，必须看 P95 及以上的尾部（9.1 第 4 节的秒表/行车记录仪）。

## 6. 可复现性清单与结果报告模板

### 6.1 可复现性检查清单

压测前逐项打勾（任何一项不满足，结果就要打问号）：

- [ ] **种子**：`--seed 42`（vllm bench 与 GenAI-Perf 都有），数据集的采样顺序才可复现；
- [ ] **warmup**：`--num-warmups 100`（vllm）或 `--warmup-request-count 100`（GenAI-Perf）——让 CUDA graph、显存分配、KV cache 预热完成，**跳过 warmup 的第一轮压测数字普遍偏低**；
- [ ] **迭代/样本量**：报 P95 ≥ 200 请求、报 P99 ≥ 1000 请求（9.1 法则）；latency 模式 `--num-iters-warmup 10 --num-iters 30`；
- [ ] **硬件独占**：`nvidia-smi` 确认没有其他进程占卡；同机其他任务（训练、另一个服务）会直接污染延迟；
- [ ] **版本记录**：`vllm --version`、`nvidia-smi`（驱动）、`python -c "import torch; print(torch.__version__)"`，全写进报告；
- [ ] **引擎参数**：`--max-num-seqs`、`--gpu-memory-utilization`、TP/PP 等与生产一致（或明确标注“测试配置”）；
- [ ] **口径一致**：本次结果与历史结果用同一工具、同一指标定义（2.5 节的工具演进教训）；
- [ ] **多轮取稳**：同 config 至少 2-3 轮，确认差异在噪声范围（sweep 默认 3 次就是这个原因）。

### 6.2 结果报告模板

压测产出不是终端里的一张表，而是一份**带环境的存档**。模板如下（`--metadata` 帮你自动记录环境行）：

| 硬件 | 1× A100 80GB SXM4，驱动 550.54，CUDA 12.4 |
| 引擎参数 | `--max-num-seqs 128 --gpu-memory-utilization 0.9 --tp 1` |
| 负载 | random，input 512±0，output 128±0，1000 请求，并发 32，seed 42 |
| 采样 | temperature 0.0，max_tokens 128，流式开 |
| SLO | ttft:500 tpot:50 |
| QPS | 3.2 req/s |
| TTFT P50/P95 | 210 / 480 ms |
| TPOT P50/P95 | 28 / 41 ms |
| 吞吐（output token/s） | 402 tok/s |
| 显存峰值 / GPU 利用率 | 14.2 GB / 68%（DCGM sm_utilization） |

## 7. 权衡与决策规则

### 7.1 工具与模式的权衡

每个工具都在“快/真/全”之间取舍，选型前先看清代价：

| 场景 | 推荐工具 | 牺牲了什么 |
|---|---|---|
| 每次改动后的快速回归 | `vllm bench latency` | 真实感（无网络/排队/并发），只测引擎 |
| 引擎参数对比 / 找膝盖点 | `vllm bench sweep` | 时间（组合 × 3 次，小时级） |
| 生产容量摸底 | `vllm bench serve --request-rate inf --max-concurrency N` | 负载是合成的（除非用 trace） |
| 跨引擎对比 / GPU 遥测 | GenAI-Perf（新项目评估 AIPerf） | 需要 DCGM 环境；工具进入维护期 |
| 精确回放生产流量 | `timed_trace` / GenAI-Perf `payload:` | 要维护 trace 采集链路 |

决策规则：

- ✅ **先立基线再优化**：固定一份 config（模型/硬件/引擎参数/负载/SLO），跑出基线报告并归档，之后所有优化都对照它；
- ✅ **快检用 latency，评估用 serve，找最优用 sweep**：三个模式回答三个不同的问题，别用 latency 的数字写容量报告；
- ✅ **负载越接近生产越好**：固定长度只能横向对比，混合负载 + P95 才能暴露互扰；
- ❌ **别把压测当比赛**：把并发调高刷出好看数字没有意义，你的服务跑在生产负载下——**基线对了，优化才有意义；口径错了，所有对比都是噪音**。

## 📝 总结

1. **三原则**：可复现（config 菜谱式完整，任何人拿到能复现）、可对比（一次只变一个变量）、可解释（每个数字带口径与负载上下文）——F1 赛道比喻：赛道/轮胎/计时规则缺一不可。
2. **vllm bench serve**：在线压测主力，一次输出 QPS、TTFT/TPOT/ITL 的 mean/median/P99；`--request-rate`/`--max-concurrency`/`--burstiness` 三个旋钮分别模拟满载、限流与真实到达；`--save-result --save-detailed --metadata --goodput` 把基线存档和 SLO 一次性解决。
3. **命令族**：`latency`（引擎裸延迟，回归快检）、`throughput`（离线极限产能，注意 output vs total 口径）、`sweep serve/serve_workload/plot/plot_pareto`（参数扫描与膝盖点曲线自动化）；`vllm bench` 不是旧 `benchmark_serving.py` 的 1:1 替代，对比历史数据先确认工具口径。
4. **GenAI-Perf**：后端无关、指标更全（TTFT/TTST/ITL/E2E，avg/p99/p90/p75）、DCGM 自动采集 GPU 遥测、`payload:` 回放真实 trace；已进入维护期，新项目评估 AIPerf。
5. **负载设计**：固定长度只能横向对比，“平均长度”压测会骗人（河的水平均深度 1 米）；混合负载（95% 短 + 周期性长 prompt）才能暴露互扰，比例与节奏写进数据集文件。
6. **可复现**：种子/warmup/样本量/硬件独占/版本/口径八项检查清单 + 带环境字段的报告模板；压测不是比赛，是建立基线——基线对了优化才有意义。

## ⚠️ 常见错误做法

- ❌ **用均匀固定长度的负载压测**：所有请求 1000 token。为什么错：真实负载有长短尾分布，长请求的 prefill 会拖垮同批短请求；均匀负载测不出互扰（7.1 的问题）。正确做法：按生产长度分布构造负载（90% 短 + 长尾），本文的负载设计。
- ❌ **压测不固定随机种子/参数**：两次压测数字对不上。为什么错：采样随机性让结果抖动，无法比较优化前后。正确做法：固定 seed、温度、并发，重复多次取稳定值（本文的可复现配置）。
- ❌ **只看 vllm bench 的输出表**：不读 `/metrics` 与 trace。为什么错：输出表给汇总值，瓶颈定位需要细粒度指标（排队、KV、stall）。正确做法：压测 + `/metrics` + Nsight/trace 一起看（9.3）。
- ❌ **压测环境与生产不一致**：A100 压测、生产 H100 或反之。为什么错：卡型、量化、batch 不一致时数字完全不可比。正确做法：压测环境 = 生产环境（本文的 checklist）。
