## 1. 为什么需要权威基准：自报数字不可比

### 1.1 自报数字的问题：不是造假，是口径不同

先问：**为什么厂商和框架的自报数字不能直接比？** 因为性能数字是“硬件 × 负载 × 口径”三个变量的函数，任何一个变了，数字就不可比：

- **硬件**：A100 和 H100、单卡和 8 卡、FP16 和 FP8，吞吐差几倍很正常；
- **负载**：输入长度 512 与 8192 的 TTFT 完全不是一回事；`max_tokens`、并发数、是否 stream 都改变结果；
- **口径**：TPOT 是“第一个 token 之后的平均间隔”还是“所有间隔的中位数”？TTFT 含不含排队？同一个请求流，两种口径能差 30%。

打个比方：**自己出的题、自己监考、自己改卷，分数当然漂亮**——但它只能证明“这道题你会做”，不能证明你比隔壁班强。KPI 注水不是道德问题，是方法问题：没有统一规则，任何数字都无从证伪。9.2 里你学到的“压测配置写进 config、指标六件套一次报全”，本质就是在自家内部先立规矩；跨组织比较，需要更大的规矩。

### 1.2 MLPerf 是什么：MLCommons 与统一规则

**MLPerf 是 MLCommons（开放工程联盟，成员包括 NVIDIA、Google、Meta、Intel、AMD 等）主持的机器学习性能基准套件**，Inference 是其分支，目标是在“架构无关（不绑定特定硬件）、有代表性、可复现”的前提下测量推理系统性能。

它的可信度来自三个机制：

1. **统一规则**：模型、数据集、场景、SLO 全部由任务组（如 LLM task force）定义，参赛者不能自选负载；
2. **统一工具**：官方 LoadGen 负载生成器统一发请求、按规则判达标，分数不是自报的；
3. **审计提交**：结果经 MLCommons 复核后发布，作弊代价极高（行业声誉）。

💡 **提示**：MLPerf 只测“系统跑给定模型有多快”，不测模型质量——模型选型看别的榜单，MLPerf 回答的是“买了这套硬件/软件，能跑多快、能扛多少并发”。

### 1.3 Closed 与 Open 两个 Division

提交分两个 division，读结果前必须先分清：

- **Closed（封闭组）**：模型必须与官方参考等价，只允许校准（如量化）不允许重训；**只有 Closed 组的数据可以跨厂商直接比较**；
- **Open（开放组）**：允许任意预处理/后处理甚至重训，自由度高，但结果不可横向比较。

📌 **关键点**：新闻里说“某某拿了第一”，先问一句：Closed 还是 Open？哪个场景？哪个模型？这三个答案不定，这个“第一”没有比较意义。

## 2. MLPerf Inference 的 LLM 任务：v5.0 与 v5.1 设置

### 2.1 任务演进：GPT-J → Llama 2 70B → Mixtral → Llama 3.1

LLM 任务从 v3.1 开始引入，一路在追业界主流模型（以下时间线以 MLCommons 官方发布为准）：

| 轮次 | 新增/调整 | 说明 |
|---|---|---|
| v3.1（2023.11） | GPT-J 6B | 第一个 LLM benchmark，Offline/Server 场景 |
| v4.0（2024.03） | Llama 2 70B | Server 场景 SLO：TTFT 2s、TPOT 200ms 口径自此引入 |
| v4.1（2024.08） | Mixtral 8x7B（MoE） | 首个 MoE LLM benchmark |
| v5.0（2025.04） | Llama 3.1 405B Instruct + Llama 2 Chat 70B 交互场景 | 长上下文（128K）与交互式低延迟两个方向 |
| v5.1（2025.09） | Llama 3.1 8B 取代 GPT-J | 128K 上下文 + CNN/DailyMail 摘要任务；加入 Interactive 场景 |

注意 v5.1 的换血：**GPT-J 被 Llama 3.1 8B 取代**——基准模型必须跟随业界真实负载，这正是 MLPerf 保持“有代表性”的方式。

### 2.2 v5.0 与 v5.1 的关键设置

查证官方发布（mlcommons.org）后，最新两轮的 LLM 任务核心设置如下：

| 📊 设置项 | Llama 3.1 405B Instruct（v5.0） | Llama 2 Chat 70B 交互（v5.0） | Llama 3.1 8B（v5.1） |
|---|---|---|---|
| 平均输入长度 | ~9,400 tokens | 较短（4K 上下文窗口内） | 128K 上下文，CNN/DailyMail 摘要 |
| 平均输出长度 | ~680 tokens | 对话式 | 摘要式 |
| SLO（99 百分位） | TTFT ≤ 6s，TPOT ≤ 175ms | TTFT ≤ 450ms，TPOT ≤ 40ms | Server：TTFT ≤ 2s，TPOT ≤ 100ms；Interactive：TTFT ≤ 0.5s，TPOT ≤ 30ms |
| 场景 | Offline / Server | Interactive（新） | Offline / Server / Interactive |
| 精度门槛（Closed） | ≥ 99% of FP16 reference（ROUGE-L / 精确匹配 EM） | ROUGE | ROUGE（摘要任务） |

两个反直觉点值得记：

- **405B 的 SLO 反而最宽松**（TTFT 6s）——不是因为它不重要，而是长上下文 9400 token 的 prefill 物理上就慢，任务组“根据硬件能力与真实可用性”定的阈值；**SLO 是负载与硬件约束的妥协，不是拍脑袋的体验目标**；
- **70B 交互场景的 TPOT 40ms = 25 tokens/s/user**——MLCommons 原话是“为满足峰值负载下的可靠性，采用更严格的 99 百分位 25 token/s 阈值”。这就是 7.4 goodput 的官方版：**在 SLO 达标前提下的吞吐才是有效吞吐**。

### 2.3 场景与分数定义：同一个模型，三种考法

- **Offline（离线）**：所有请求一次性灌入，系统全力跑，**分数 = 总输出 token 数 / 总时间（tokens/s）**——纯吞吐，适合批处理；
- **Server（在线）**：请求按随机到达模式持续涌入（LoadGen 模拟 Poisson 到达），**分数 = 在 P99 TTFT/TPOT 达标前提下的最大吞吐**——有效吞吐，适合在线服务；
- **Interactive（交互）**：v5.0/v5.1 新增，SLO 更紧（如 8B 的 0.5s/30ms），面向聊天/代码助手这类“人对延迟敏感”的场景。

公式化 Server 场景的判分逻辑：

$$
\text{score}_{\text{Server}} = \max\left\{ \text{throughput} \;\middle|\; \text{TTFT}_{p99} \leq SLO_{TTFT} \wedge \text{TPOT}_{p99} \leq SLO_{TPOT} \right\}
$$

翻译成人话：**压测时不停加并发，直到 P99 延迟违约为止，违约前的吞吐就是分数**。这正是 9.2 里“扫并发找平台区”的官方版本——MLPerf 把 goodput 思想固化成了规则。

算个达标率账（呼应 7.4 的口径）：某提交在 Server 场景下共处理 1000 个请求，其中 950 个的 TTFT/TPOT 都在 SLO 内，达标率 = 95%。**分数看的是“达标的那些”**——剩下 50 个违约请求无论多快都不计入有效吞吐，这就是 goodput 与裸 QPS 的区别：裸 QPS 可能不降反升（违约请求挤占资源反而制造更多请求），有效吞吐却在掉。

💡 **提示**：所以读 MLPerf Server 分数时，脑子里要自动补一句“这是在 P99 不违约的前提下的数字”——它天然比同硬件的 Offline 分数低一截，低出来的那一截就是“延迟约束的定价”。

### 2.4 精度门槛：快的前提是“没变笨”

每个提交都要先过精度关：Closed 组要求精度不低于 FP16 参考的 99%（405B 任务用 ROUGE-L 与精确匹配评估摘要和检索问答）。**精度不过，成绩无效**——防止厂商用激进量化换速度。这条规则对应你[第 4 章量化](/AIInfraGuide/inference/模块四-推理优化/第4章-量化/42-w8a8-smoothquant)里学过的权衡：压缩换来的吞吐，必须证明没把模型改笨。

## 3. 怎么读 MLPerf 结果

### 3.1 先看场景和规则，再看数字

同一模型在三个场景下的数字不可互比（Offline 的 5000 tok/s 和 Server 的 3000 tok/s 没有矛盾，后者有 SLO 约束）。读结果四步：

1. 确认 **division**（Closed 才能横向比）；
2. 确认**场景与 SLO 档位**（Server 还是 Interactive，阈值不同）；
3. 确认**精度门槛**过了没（过了才有效）；
4. 再看吞吐数字，并且**优先看每卡/每美元归一化的数字**（系统大小不一，总吞吐不可比）。

举例（Red Hat 的 v5.1 公开提交，Llama 3.1 8B FP8 + vLLM 0.10.0）：单张 H100 Offline 5,777 tok/s、Server 5,103 tok/s；单张 L40S Offline 1,642 tok/s、Server 1,207 tok/s。同一套软件栈，**H100 是 L40S 的约 3.5 倍（Offline）**——这不是“L40S 不行”，而是你按这个比例算账：需要多少 L40S 才能扛住同样的 QPS，以及电费/机位成本差多少。

### 3.2 同一提交的多个配置：每 token 成本与绝对性能的权衡

NVIDIA v4.1 公开过一个对比：Llama 2 70B 上，**单张 B200 的 Server 吞吐约 10,756 tok/s（per-GPU 推导值），约为 H100 单卡成绩的 4 倍**。但注意官方同时声明：**per-GPU 吞吐不是 MLPerf 的主指标**——系统级成绩才是。这告诉你两件事：

- 厂商喜欢做“per-GPU 归一化”宣传，因为小系统更占便宜；你要按**整机成本 ÷ 整机吞吐**来算经济账；
- 同一硬件可以有不同的优化配置（FP8 vs FP16、不同引擎、不同并行度），**每个配置是一份独立提交**——“第一名”背后往往是“最卷的调优 + 最贵的硬件”，别直接外推到你的预算。

### 3.3 每百万 token 成本算例

把性能翻译成钱，公式：

$$
\text{每百万输出 token 成本} = \frac{C_{\text{GPU}}(\$/h)}{R_{\text{out}}(\text{tok/s}) \times 3600} \times 10^6
$$

代入示意算例：H100 时价 $2.5/h（以你实际的租用/折旧价为准），Server 场景输出吞吐 5,103 tok/s：

$$
\frac{2.5}{5103 \times 3600} \times 10^6 \approx 0.136 \text{ 美元/百万输出 token}
$$

工程结论：**吞吐翻倍 ≈ 每 token 成本减半**——所以买卡决策比的是“单位成本吞吐”，不是单卡绝对性能。这个口径也是 4.6 选型实战里“性价比对比表”的官方参照物。

## 4. LLM 评测趋势：工具换代与新的维度

### 4.1 工具换代：vllm bench / GuideLLM / AIPerf

评测工具本身也在快速换代，判断“哪个是当前推荐”别只看教程日期：

- **vLLM 生态**：`benchmark_serving.py` 等三个独立脚本已收敛为 `vllm bench` 命令族（9.2 已讲，**注意不是 1:1 替代**，部分参数语义有差异，对比历史数据前先确认工具一致）。官方文档明确建议：生产级基准用 **GuideLLM**——vLLM 社区推出的基准框架，数据集加载与请求格式更灵活；`vllm bench` 主要用于特性评测与回归测试；
- **NVIDIA 生态**：官方文档已声明 **GenAI-Perf 进入维护模式（不再积极开发新功能），新工具是 AIPerf**（ai-dynamo 项目，定位是 LLM 推理基准的一站式工具，覆盖 TTFT/ITL/吞吐与 GPU 遥测）——9.2 里你学的 GenAI-Perf 参数仍然有效，但新项目上手时优先看 AIPerf；
- **MLPerf 侧**：v5.1 起加入 Interactive 场景，v6.0 结果已开始发布（以 mlcommons.org 为准），reasoning 类模型与更细的延迟档位是明确的演进方向。

### 4.2 长上下文基准：TTFT 与 prefix 复用成为新考点

长上下文改变的不只是模型，还有评测方式：**prefill 变贵之后，“TTFT 增益”和“缓存命中率”成为独立考卷**。两个可查证的例子：

- vLLM 仓库的 `benchmark_long_document_qa_throughput` 与 LMCache 的 `long_doc_qa` 基准：用 20,000 token 量级的长文档做多轮问答，直接验证 **TTFT 加速倍数**（如“预热 vs 查询的 TTFT 增益”）——测的是 KV Cache 复用（第 2 章 Prefix Cache）能省多少重算；
- LMCache 论文（arXiv 2510.09665）公开数据：与 vLLM 组合后，在多轮问答与文档分析负载上**吞吐最高提升约 15 倍**——缓存命中率从此前的“锦上添花”变成长上下文负载的**主指标**。

### 4.3 从“跑分”到“每美元吞吐”

评测维度的演进主线：**裸吞吐 → SLO 达标率（goodput）→ 每美元吞吐**。三个信号：

1. MLPerf 给 LLM 加 SLO 约束（2.3），“跑得快”必须叠加“不违约”；
2. NVIDIA 官方页面引用 SemiAnalysis InferenceX 数据：B200 上 GPT-OSS-120B 的**每百万 token 成本从发布时 $0.11 降到两个月后的 $0.02（约 5 倍，且主要来自软件优化）**——价格-性能比已经成为和绝对性能并列的赛道；
3. Artificial Analysis 等第三方榜单默认同时展示“输出速度、TTFT、每百万 token 价格”三列——买家按自己的成本结构选。

📌 **关键点**：对你个人而言，“我的服务每百万 token 成本是多少”是一个可以且应该自己算的指标（3.3 的公式），它把厂商新闻里的“5 倍提升”翻译成你的账单。

## 5. 权威基准对我们工作的意义

### 5.1 选型参考：买卡、选框架

MLPerf 结果表是**选型的第一手资料**：想买卡，看同一模型下不同硬件的 Server 场景分数与整机配置；想选框架，看同一硬件上不同引擎的提交（如 vLLM 与 TensorRT-LLM 同场竞技的轮次）。但记住 3.1 的规则：**只看 Closed、对场景、对 SLO 档位**，再乘上你的预算约束，落到“每美元吞吐”再拍板。

### 5.2 SLO 设定参照：把别人的考卷当自己的及格线

MLPerf 的 SLO 是任务组按“真实可用性 + 硬件能力”调的，是**现成的体验基准**：

- 聊天助手起步线：参考 8B 交互场景的 **TTFT ≤ 0.5s、TPOT ≤ 30ms**；
- 文档问答/长上下文：参考 405B 的 **TTFT ≤ 6s、TPOT ≤ 175ms**；
- 峰值可靠性：参考 70B 交互的 **P99 TPOT ≤ 40ms（25 tok/s/user）**。

设 SLO 时先抄这些公开阈值（9.1 的指标体系里定 P50/P95），再按你的业务调：钱少的批处理任务可以放宽一个数量级，省钱；面向 C 端的交互任务只能更紧，不能更松。

### 5.3 回归门禁的锚点：CI 里放一把官方尺子

权威基准还解决一个实际问题：**你的回归门禁阈值从哪来？** 9.5 会讲门禁规则细节，这里给锚点——vLLM 自己的 CI 就是这么干的（官方文档可查）：

- **Performance Dashboard**：每次 commit（打 `perf-benchmarks` + `ready` 标签）和每次 merge 到 main 都自动跑基准，结果发布到公开面板；
- **连续基准**：GitHub Action 每 4 小时跑一轮 serving/throughput/latency 三类测试，自动盯回归；
- **SLA 默认值**：TTFT ≤ 3000ms、TPOT ≤ 100ms，跑 adaptive concurrency 搜索出“同时满足两个 SLA 的最大并发”——**这就是拿 SLO 当尺子量吞吐**，和 7.4 的 goodput 一个思路。

你的团队规模不需要照搬全套，但可以抄最低配置：**固定负载 + 固定 SLO（抄 MLPerf 或 vLLM 的默认值）+ 每次合入自动跑 + 违约即告警**，这正是 9.5 门禁的雏形。给一份 20 行以内能落地的门禁配置骨架（示意，9.5 会展开规则细节）：

```yaml
# .github/workflows/perf-gate.yml（示意骨架，按你的 CI 平台调整）
# 触发：PR 带 perf 标签或合入 main 时
bench:
  cmd: vllm bench serve --dataset-name random --random-input-len 1024 \
       --random-output-len 256 --max-concurrency 16 --save-result
  sla:            # 锚点：抄 vLLM CI 默认值与 MLPerf 交互档
    ttft_p99_ms: 3000
    tpot_p99_ms: 100
  compare: 对上一版本结果算 perf_ratio（9.5 的判定线：TPOT P95 退化 >5% 则 block merge）
  report: 结果 JSON 归档，供 git bisect 时回放
```

💡 **提示**：门禁的“锚”要分两级——**绝对锚**（MLPerf 档位的 SLO，回答“体验还够不够”）与**相对锚**（上一版基线，回答“这次改动有没有变慢”）。只挂绝对锚，小步退化会被噪声掩盖；只挂相对锚，整体滑坡没人发现。两个都挂才是 9.5 要讲的完整门禁。

## 6. 权衡与决策规则

- **权威基准**：牺牲（负载是官方的、不是你的；调优是参赛者的、不是你的），换取（跨厂商可比的统一数字 + 经过审计的 SLO 参照），适用“选型、定价、定标”；
- **自己的压测**：牺牲（自己做题、不可横向比），换取（精确复现你的负载与 SLO），适用“回归门禁、容量规划、上线验证”；
- **两者配合**：用权威基准选大方向（买哪家卡），用自己的基准做小决策（每个 commit 能不能合）。

决策规则：

- ✅ **买卡/选框架** → 看 MLPerf Closed 组对应模型的 Server 场景，算每美元吞吐；
- ✅ **设 SLO** → 抄官方阈值起步（聊天 0.5s/30ms，长上下文 6s/175ms，批量可放宽一个数量级）；
- ✅ **建门禁** → 固定负载 + 固定 SLO（TTFT 3000ms / TPOT 100ms 起步）+ 每次合入自动跑（9.5 展开）；
- ❌ **别拿 MLPerf 第一名当你的性能承诺**——它的负载不是你的负载，它的调优成本不是你的成本；**复现你自己的负载，才有意义**。

## 📝 总结

1. **为什么需要**：自报数字是“自己出题自己考”，硬件/负载/口径三个变量不同就不可比；MLPerf 用统一规则、统一 LoadGen、审计提交解决这个问题。
2. **LLM 任务**：v3.1 的 GPT-J 起步，v4.0 的 Llama 2 70B（Server TTFT 2s/TPOT 200ms），v4.1 的 Mixtral 8x7B（首个 MoE），v5.0 的 Llama 3.1 405B（输入 ~9400 token，P99 TTFT 6s/TPOT 175ms）与 70B 交互场景（P99 450ms/40ms = 25 tok/s/user），v5.1 的 Llama 3.1 8B（128K 上下文，交互场景 0.5s/30ms）取代 GPT-J。
3. **分数定义**：Offline = 纯 token 吞吐；Server = P99 TTFT/TPOT 达标前提下的最大吞吐（goodput 的官方化）；Interactive = 更紧 SLO 的 Server；精度门槛 Closed 组 ≥ 99% of FP16 参考。
4. **怎么读**：先 division、场景、SLO、精度四连确认，再比数字；per-GPU 归一化是厂商宣传口径，不是主指标；用“每百万 token 成本”把性能翻译成钱。
5. **趋势**：工具换代（vllm bench → GuideLLM；GenAI-Perf → 维护模式，新工具 AIPerf）；长上下文让 TTFT 增益与缓存命中率成为新考点（LMCache 多轮 QA 最高 ~15x）；从裸吞吐到 goodput 到每美元吞吐。
6. **落地**：选型看 Closed Server 分数、SLO 抄官方阈值、回归门禁抄 vLLM 的 CI 模式（每 commit + SLA 违约即拦）。

## ⚠️ 常见错误做法

- ❌ **把 benchmark 排名当购买决策**：MLPerf 第一就买。为什么错：benchmark 的负载形状（长度、batch、SLO）与你的业务不同，第一名未必适合你的负载。正确做法：用目标负载自己压测（9.2），benchmark 只当参考区间。
- ❌ **自报数字没有可比性**：不同配置的 throughput 直接比大小。为什么错：硬件、精度、batch、长度分布不同，数字不可比（本文“自报数字不可比”的警示）。正确做法：报告时注明完整配置（本文的口径清单）。
- ❌ **只看论文/博客的峰值数字**：把“up to 2x”当平均值。为什么错：厂商与论文报的是挑场景的上限。正确做法：把官方数字当上限参考，用自己负载实测验证。
- ❌ **忽略趋势的方向性**：只看当前排名不看演进（PD 解耦、投机解码的兴起）。为什么错：架构趋势决定选型方向，只看排名会选到正在被淘汰的方案。正确做法：结合本文的趋势分析（speculative、解耦、量化）做选型。
