上一节把 prefill 和 decode 拆到了两个 GPU 池，但拆完立刻冒出一个新问题：**prefill 节点算完的 KV Cache 必须搬到 decode 节点，decode 才能继续出字——不搬，前面的计算就全白做了**。这一搬，搬出了一笔新账：按学习路线 3.5 的口径，一个 7B 模型 2048 上下文的 KV 约 4GB，在 IB 200Gb/s（理论 25GB/s）的网络上也要约 160ms，而这 160ms 会直接加进用户的 TTFT。这一节讲透这笔账怎么算、传输方案怎么演进（vLLM 的 KV Connector 抽象、NIXL、LMCache），以及解耦到底要为网络付多少学费。

## 1. 解耦后的新问题：KV 不搬就白算了

### 1.1 为什么 decode 节点必须拿到 KV？

decode 节点为什么不能自己从头算？因为自回归的每一步 attention 都要和**完整的历史上下文**做交互——第 500 个 token 的 Q 要和前 499 个 token 的 K、V 全部做点积。如果 KV 不在本地，decode 只有两条路：要么每步都重算一遍 prefill（把解耦省下的算力全部吐回去），要么把 KV 搬过来（付网络账单）。**缓存的意义就是“用显存换计算”，解耦之后这条交换链被拉长了：KV 必须跨越网络才能继续换。**

打个比方：prefill 是中央厨房，负责把半成品菜批量做好；decode 是门店，负责加热上桌。**半成品（KV Cache）必须冷链送到门店，菜才能上桌**——送得慢，客人（用户）就得干等。这个“送菜时间”是解耦架构纯新增的延迟，混跑架构里根本没有这一项。

📌 **关键点**：传输延迟是解耦的“结构性账单”——不管用什么传输方案，GB 级数据跨节点这件事本身就要花时间，你能优化的是让它和计算重叠、把它变小，而不是消灭它。

### 1.2 传输账本：4GB 与 160ms

这笔账怎么算？KV 的总字节数就是它作为显存开销时的那个公式（第 1 章 1.1 节算过），只是这次它变成了“要搬的数据量”：

$$
KV = \underbrace{2}_{K \text{ 和 } V} \times \underbrace{L}_{\text{层数}} \times \underbrace{h_{kv}}_{\text{KV 头数}} \times \underbrace{d}_{\text{每头维度}} \times \underbrace{2\text{B}}_{\text{FP16}} \times \underbrace{S}_{\text{序列长度}}
$$

代入 LLaMA-2-7B（32 层、32 头、$d=128$）：每 token 512KB；2048 上下文单请求约 1GB。学习路线 3.5 的风险清单把“7B/2048 上下文”的 KV 定为**约 4GB**——这是含传输批次/更保守配置的口径，规划带宽时按这个量级算更稳。

💡 **提示**：具体数字随模型配置大幅浮动。GQA 模型小一个量级：Llama-3-8B 只有 8 个 KV 头，每 token 仅 128KB，2048 上下文约 256MB。所以**背数字不如背公式**——拿到任何模型的配置都能自己重算。

再算传输时间。200Gb/s 的 IB 是“吉比特每秒”，除以 8 才是字节：

$$
T_{trans} = \underbrace{\frac{KV_{\text{bytes}}}{B_{net}}}_{\text{数据量 ÷ 可用带宽}} = \frac{4\text{GB}}{25\text{GB/s}} = 160\text{ms}
$$

**工程结论**：GB 级的 KV、百毫秒级的传输，这是解耦绕不开的固定开销。而且 25GB/s 是理论值，实际打 7~8 折很正常（协议开销、拥塞、共享链路），保守按 20GB/s 算，4GB 要 200ms。

### 1.3 这 160ms 对 TTFT 意味着什么

这 160ms 加在哪里？解耦后的首字延迟链变成：

$$
TTFT \approx \underbrace{T_{queue}}_{\text{排队}} + \underbrace{T_{prefill}}_{\text{prefill 计算}} + \underbrace{T_{trans}}_{\text{KV 传输}} + \underbrace{T_{first\_decode}}_{\text{decode 首 token}}
$$

代入两个 SLO 场景看占比：

| 📊 场景 | TTFT SLO | 160ms 占比 | 感受 |
|---|---|---|---|
| 对话服务（宽松） | 2s | 8% | 可接受，但注意这是“裸传输” |
| 实时助手（严格） | 500ms | 32% | 不可接受，必须做流式重叠 |

⚠️ **注意**：上面算的是“算完再传”的最坏情况。第 6 节会讲流式传输让大部分传输和 prefill 重叠，真正“裸奔”的只有尾巴——Splitwise 论文实测，层间流式传输后不可重叠的部分在 A100（200Gbps）上约 8ms、H100（400Gbps）上约 5ms。**账本公式算的是上限，工程优化压的是下限。**

## 2. 传输方案演进：从朴素 RDMA 到 Connector

### 2.1 V0：算完再传的朴素实现

最早的解耦原型（包括论文里的朴素基线）长什么样？一句话：**prefill 全部算完 → 把整个 KV 张量一次性搬过去 → decode 才开始**。

```python
# V0: 朴素全量传输(示意,非逐字源码)
prefill_out = prefill_engine.run(prompt)      # 1. 先把 prefill 全部算完
kv_tensor   = extract_kv(prefill_out)         # 2. 把 KV 从输出里取出来打包
nccl.send(kv_tensor, dst=decode_node)         # 3. 全量搬过去(同步阻塞)
decode_engine.start(kv_tensor)                # 4. 传输完成,decode 才开始出字
```

这个实现有三个问题：

1. **同步阻塞**：算完才能传、传完才能算，传输期间 prefill 和 decode 两端 GPU 都在等——算力和带宽没法重叠；
2. **传输逻辑焊死在引擎里**：今天用 NCCL，明天想换 UCX、想加压缩，都要改引擎代码，传输成了业务代码的一部分；
3. **每次请求都全量重传**：多轮对话、共享前缀的请求，相同的 KV 反复在网络上跑——这和 2.3 节 Prefix Cache 的思路正好相反：缓存是“同样的东西只算一次”，V0 是“同样的东西传 N 次”。

### 2.2 演进方向：把“怎么传”和“传什么”解耦

怎么解决这三个问题？方向很清晰：**把 KV 传输从推理引擎里抽出来，做成一个可插拔的抽象层**——引擎只声明“我要把这批 KV 从 P 池送到 D 池”，至于走 RDMA、走 TCP、还是先落盘，由底层后端决定。这就是 vLLM 的 KV Connector 抽象（下一节），也是 NIXL 这类专用传输库存在的理由。

📌 **关键点**：传输方案的演进主线是**“从实现到抽象”**——V0 把传输写成业务代码，Connector 把传输变成接口，NIXL 再把接口背后的每条路都修成高速路。

## 3. vLLM 的 KV Connector 抽象

### 3.1 三件套：Connector、LookupBuffer、Pipe

vLLM 的 disaggregated prefill 实现（`vllm/distributed/kv_transfer`）把传输抽象成三个组件，先记住各自管什么：

- **Connector**：总入口，负责调度“把 KV 从生产者搬到消费者”这件事；每个 vLLM 进程都有对应的 connector，调度器进程里的负责排期，worker 进程里的负责执行；
- **LookupBuffer**：KV 的存取缓冲，只有两个 API——`insert`（把 KV 存进来，非阻塞）和 `drop_select`（按条件取走匹配的 KV，阻塞）。语义像 SQL：插入一条记录、按条件查询并删除；
- **Pipe**：单向 FIFO 的 tensor 传输管道，支持 `send_tensor` / `recv_tensor`。

```python
# 伪代码:三个抽象的分工(非逐字源码,理解原理用)
class LookupBuffer:
    def insert(self, kv, condition): ...   # 非阻塞:KV 先存进缓冲,传输异步进行
    def drop_select(self, condition): ...  # 阻塞:按条件取走 KV,取不到就等

class Pipe:
    def send_tensor(self, tensor): ...     # 单向发送
    def recv_tensor(self): ...             # 对端接收

class Connector:
    # prefill 侧:把算好的 KV insert 进缓冲,后台传输
    # decode 侧:drop_select 等到自己的 KV,开始 decode
    pass
```

角色由 `kv_role` 指定：`kv_producer`（只产出 KV，prefill 实例）、`kv_consumer`（只消费 KV，decode 实例）、`kv_both`（两者都干，单实例调试用）。

### 3.2 一个 JSON 换后端

换一个传输后端要改多少代码？答案是只改一个参数——`--kv-transfer-config` 接收一个 JSON，`kv_connector` 字段指定用哪个实现。官方文档列了 9 种 connector：`ExampleConnector`、`LMCacheConnectorV1`、`NixlConnector`、`MooncakeConnector`、`MoRIIOConnector`（ROCm）、`MultiConnector`（组合多个）、`OffloadingConnector`（KV 挪到 CPU 内存）等。第 4、5 节挑 NIXL 和 LMCache 两个最重要的讲。

⚠️ **注意**：vLLM 官方文档明确标注 disaggregated prefilling 是 **experimental** 特性，且原话是“Disaggregated prefill DOES NOT improve throughput”——**解耦不提升吞吐，它买的是尾延迟可控和 TTFT/TPOT 独立调优**。别拿它当吞吐优化手段（这是 7.1 就埋下的伏笔：它是“平稳性”优化）。

## 4. NIXL：为 KV 传输而生的专用库

### 4.1 定位：不是通用通信库，是“KV 搬运工”

NIXL 到底是什么定位？NIXL（NVIDIA Inference Xfer Library）是 NVIDIA 在 **GTC 2025 开源的点对点传输库**，目标非常聚焦：加速推理框架（如 NVIDIA Dynamo）里 KV Cache 这类数据的跨节点传输。它厂商中立——AWS EFA（Trainium/Inferentia）、Azure RDMA 都在支持列表里，不绑死 NVIDIA 硬件。

后端按“数据从哪来、到哪去”自动选择：

| 📊 传输路径 | NIXL 后端 | 典型场景 |
|---|---|---|
| GPU 显存 → GPU 显存（跨机） | UCX（底层 RoCE / InfiniBand / TCP） | KV 传输的主路径，默认后端 |
| GPU 显存 → 远端存储 / 文件 | GPUDirect Storage（NVMe-oF） | KV 落盘、offload |
| 对象存储 | S3 等（官方文档标注开发中） | 大规模缓存/冷数据 |

### 4.2 为什么比“通用 RDMA”快？——不是带宽变快，是把带宽用满

先泼一盆冷水：**NIXL 没有让物理带宽变大**，25GB/s 的 IB 还是 25GB/s。它快在“同样一条链路，你能拿到多少”：

1. **零拷贝**：GPU 显存直出直收，数据不经过 CPU/主机内存中转——手写 RDMA 最容易多付的一笔“过路费”就是多一次内存拷贝；
2. **完全异步**：API 非阻塞，`post_transfer_request` 发出后立刻返回，计算继续跑，通信和计算在时间上重叠；
3. **流式**：支持边算边传（第 6 节细讲），不用等全部 KV 生成完；
4. **控制面/数据面分离**：连接元数据（地址、内存段信息）在初始化时通过 side channel（旁路通道，用 etcd/Redis 实现）**只交换一次**并缓存，正式传输时零握手零等待——手写实现最常见的隐藏开销就是“每次传输前先建连”。

| 📊 维度 | 朴素 RDMA（手写） | NIXL |
|---|---|---|
| 数据路径 | 可能多一次 CPU 中转拷贝 | 零拷贝，显存直通 |
| 传输与计算 | 常同步阻塞 | 完全异步，可重叠 |
| 连接管理 | 每次传输前协商 | 元数据一次交换、缓存复用 |
| 后端选择 | 自己写死 | 按内存/存储类型自动选最优 |

📌 **关键点**：NIXL 的“快”是工程性的快——**省掉的是中间拷贝、同步等待、重复建连这三笔“隐形税”**。这也是为什么各家实现最终都从“自己写 RDMA”收敛到专用库。

### 4.3 vLLM 的 NixlConnector 用法

在 vLLM 里怎么用它？通过 `--kv-transfer-config` 启用（官方文档示例，以你所用版本的 `vllm serve --help` 为准）：

```bash
# prefill 实例:只产出 KV
vllm serve <model> \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer","kv_buffer_device":"cuda","kv_connector_extra_config":{"backends":["UCX","GDS"]}}'

# decode 实例:只消费 KV
vllm serve <model> \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer","kv_buffer_device":"cuda","kv_connector_extra_config":{"backends":["UCX","GDS"]}}'
```

要点：`backends` 数组可以列多个后端（如 `["UCX", "GDS"]`），NIXL 按传输路径自动挑；NixlConnector 支持**全异步 send/recv**，是官方文档里标注支持 fully async 的 connector。另外注意一个细节：如果 P/D 两侧各自用了 TP（6.2 讲过的 KV 头切分），传输是 **rank 对 rank** 进行的——prefill 的第 i 个 rank 把切分后的那部分 KV 发给 decode 的第 i 个 rank，不是“整池广播”。

## 5. LMCache：让 KV 复用起来

### 5.1 传输的终极优化：命中就不传

能不能让 KV 根本不用传？NIXL 解决的是“传得快”，LMCache 解决的是“**根本不用传**”。LMCache 是一个分布式 KV 缓存层，vLLM 通过 `LMCacheConnectorV1` 接入（进程内模式，底层用 NIXL 做传输；另有 `LMCacheMPConnector` 多进程模式，由独立的 `lmcache server` 持有 KV，供多个 vLLM 实例共享）。

```bash
# LMCacheConnectorV1(示意,以官方示例为准)
vllm serve <model> \
  --kv-transfer-config '{"kv_connector":"LMCacheConnectorV1","kv_role":"kv_both"}'
```

它和 2.3 节 Prefix Cache 是天然搭档：**prefix cache 让“相同的 KV 只算一次”，LMCache 让“算好的 KV 全局存一份、谁要谁取”**。多轮对话、Agent 场景里，前几轮的历史 KV 在 P 池算过一次之后，后续请求的 prefill 直接从缓存读，连算都省了——传输量直接归零。

💡 **提示**：把优化手段排个序：**复用（LMCache/prefix cache）＞压缩（KV 量化）＞加速（NIXL）**。复用把传输量变成 0，压缩把它变小，加速只是让它跑得快一点。先问“这笔 KV 能不能不传”，再问“能不能传小点”，最后才问“怎么传快”。

## 6. 传输的隐藏成本：流式、量化与同步

### 6.1 账本之外的三个隐形开销

除了 4GB/160ms 这笔“纯数据搬运”的账，真实传输还要付什么？至少三笔隐形开销：

1. **连接建立与元数据交换**：首次传输前要交换地址、注册内存段（NIXL 的做法是初始化时一次搞定并缓存，手写实现常在这里反复付费）；
2. **序列化与格式转换**：KV 在显存里按 PagedAttention 的分页块存放，这是引擎内部布局，不能直接搬。传输前要先重排成连续张量，或按 block 打包（Splitwise 的实现就是按 block 传输并尽量合并连续块）；
3. **跨机调度同步**：decode 节点必须等“自己的 KV 到齐”才能开始，双方要握手；并发多个请求时，谁的 KV 先到、先给谁解码，又是一层调度（LookupBuffer 的 `drop_select` 阻塞等待就是干这个的）。

### 6.2 流式传输 vs 全量传输

能不能边算边传？全量传输的问题在于**串行**：prefill 算完 → 传 → decode，中间两段空窗。流式传输把 KV 按层切碎：**算完第 1 层就传第 1 层，prefill 继续算第 2 层，传输和计算在时间上重叠**——就像中央厨房炒好一道菜就发一道菜，不用等整桌菜齐了才发车。

Splitwise 论文的实测数字（A100/H100 + InfiniBand）：

| 📊 传输方式 | 第二 token 延迟增幅 | E2E 影响 | 不可重叠部分 |
|---|---|---|---|
| 串行全量 | +64% | 大 prompt 时最高 3% | 随 prompt 线性增长 |
| 层间流式 | **+16.5%** | **0.8%** | 恒定：A100 ~8ms / H100 ~5ms |

实现上用 MSCCL++ 的零拷贝单边 put：prefill 端数据就绪即推送，decode 端等信号量唤醒，不需要逐层“请求-应答”。论文还做了一个务实的取舍：**小 prompt（<512 token）用串行，大 prompt 用流式**——小 KV 传得快，不值得为重叠付出逐层同步的复杂度。落成一句话：**流式传输把“传输时间”从 TTFT 里抠出来，和大头 prefill 计算重叠掉。**

### 6.3 KV 量化：把要搬的东西变小

还有没有更便宜的路——把要搬的东西本身变小？4.4 节讲过 KV Cache 量化（KIVI 2-bit、FP8 KV），在解耦架构里它多了一个新收益：**量化后的 KV 传得也快**。传输量正比于每 token KV 字节数，量化到 FP8 减半，KIVI 式 2-bit 激进压缩可以再降——**量化相当于免费的带宽扩容**。

⚠️ **注意**：前提是 decode 端能消费量化后的 KV（反量化逻辑两端都要有），且精度损失可接受。别为了省带宽把质量压崩了——先按 4.6 的评测流程验证质量，再谈传输收益。

## 7. 带宽压力与容量规划

### 7.1 一个算例：QPS 100 要多少条 IB 链路？

解耦规模一大，KV 流量就是实打实的网络工程问题。平均流量和峰值流量分开算：

$$
B_{avg} = \underbrace{QPS}_{\text{每秒请求数}} \times \underbrace{KV_{avg}}_{\text{平均每请求 KV}} \qquad
B_{peak} = \underbrace{B_{avg} \times k}_{\text{突发系数（如 2~3）}}
$$

代入：QPS 100、平均每请求 4GB（学习路线口径）→ 平均 400GB/s，峰值再翻 2~3 倍。按 IB 200Gb/s（25GB/s）单链路算：

$$
N_{links} = \frac{B_{peak}}{B_{per\_link} \times \eta} = \frac{400\text{GB/s}}{25\text{GB/s} \times 0.8} \approx 20
$$

（$\eta=0.8$ 是实际效率折损；100% 理想效率下也要 16 条）。**20 条 200G 链路只为搬 KV——这是解耦在“流量高峰”上的真实成本。**

打个比方：收费站的车道数决定了高峰期堵不堵。**带宽就是车道，QPS 和 KV 大小就是车流量**——你可以在淡季省车道，但高峰期该堵还是堵。唯一的好消息是车道可以只修在 P 池和 D 池之间（拓扑上做“池间专用网络”），而不是全集群铺满。

### 7.2 三条降流量的路

流量太大怎么办？三条路，按性价比排序：

- **换 GQA 模型**：KV 头数从 32 降到 8，传输量直接除以 4（Llama-3-8B 2048 上下文只有 ~256MB）；
- **KV 量化**（6.3）：FP8 减半、激进量化再减半；
- **前缀复用**（第 5 节）：命中缓存的请求传输量为 0。

📌 **关键点**：带宽规划先做“减法”再做“加法”——**先把 KV 变小（量化/复用），再数链路**。上来就按 4GB/请求买带宽，是最贵的方案。

### 7.3 拓扑与放置

P/D 池之间放多远有讲究吗？传输只在 P/D 池之间发生，所以网络规划可以聚焦：池间带宽要按峰值流量配，池内走 NVLink/机内网络。DistServe 论文专门讨论了**按集群带宽放置 P/D 位置**：带宽充裕时可以把 P、D 放得更远（调度更灵活），带宽紧张时让它们尽量同机架——放置本身就是一个优化变量，不是拍脑袋定的。

---

## 8. 权衡：解耦的网络学费

每一项技术都该回答“牺牲了什么、换取了什么”：

- **换取了**：解耦可行——没有 KV 传输，7.1 的互扰问题就只能靠 Chunked Prefill 打补丁（2.4 讲过：能缓解但 chunk size 难调、长 prompt 尾延迟仍不稳）；同时换来 TTFT 与 TPOT 的独立调优空间（7.4 的 goodput 优化全靠这个）。
- **牺牲了**：① 网络基础设施成本（池间 IB 带宽是真金白银，7.1 的算例说明量级）；② 实现复杂度（Connector/流式/握手/故障恢复，一套新的分布式系统组件）；③ 运维复杂度（P/D 两个池要分别监控、分别扩容，7.5 会讲池空转问题）。
- **适用边界**：没有 IB（只有千兆以太网）别解耦——4GB 在 1Gbps 上要 32 秒，解耦直接变成灾难；小集群、负载轻、没有严格尾延迟 SLO 的服务，混跑 + Chunked Prefill 更划算。

**落成一句话：传输让解耦“付得起”，但也只值“为了尾延迟和独立调优”这笔账——先算清 KV 流量和链路数，再决定要不要上车。**

---

## 📝 总结

1. **账本**：KV 传输量 = $2 \times L \times h_{kv} \times d \times 2\text{B} \times S$；7B/2048 上下文约 4GB（学习路线 3.5 口径），IB 200Gb/s 理论 160ms，实际按 7~8 折算——GB 级数据、百毫秒级延迟，是解耦的结构性账单。
2. **演进**：V0 朴素“算完再传”有三个问题（同步阻塞、逻辑焊死、无复用）→ vLLM 的 Connector/LookupBuffer/Pipe 三件套抽象 → 换后端只改一个 `--kv-transfer-config` JSON。
3. **NIXL**：GTC 2025 开源的 KV 专用传输库，零拷贝 + 全异步 + 流式 + 控制面/数据面分离——物理带宽没变，是把带宽用满；vLLM 的 NixlConnector 支持 fully async，P/D 各配 `kv_producer`/`kv_consumer` 角色。
4. **LMCache**：分布式 KV 缓存层，与 prefix cache 搭档实现“命中就不传”——复用（0 传输）＞压缩（量化减半/再减半）＞加速（NIXL）。
5. **隐藏成本**：连接建立、序列化、跨机同步三笔隐形税；流式传输把第二 token 延迟增幅从 +64% 压到 +16.5%（Splitwise 实测）；KV 量化让传输量等比下降。
6. **带宽规划**：QPS 100 × 4GB/请求 → 峰值 400GB/s → 约 20 条 IB 200G 链路（80% 效率）；先做减法（GQA/量化/复用）再做加法（数链路）。
7. **权衡**：换取了解耦可行与 TTFT/TPOT 独立调优，牺牲了网络基建、实现与运维复杂度；无 IB、无严格 SLO 的场景别上车。
