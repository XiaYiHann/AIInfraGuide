## 1. 解耦的总思路：让两类请求各得其所

### 1.1 从"一个厨师两头忙"到"分区分厨"

学习路线 3.5 给过这个比喻，值得原文引用：**这就像餐厅里让同一个厨师既负责快速出小炒（Decode 低延迟）又负责慢炖大菜（Prefill 重计算），互相拖累；解耦就是把快餐区和慢炖区分开，各配专属厨师。**

把这个比喻的映射钉死：小炒区（Decode 池）= 流水线短平快、要求每道菜稳定按时出锅（TPOT 稳定）；慢炖区（Prefill 池）= 重活大活、可以慢慢来但别堵住别人（TTFT 达标即可）。分区分厨之后，两个区还能各配各的厨具——小炒区用猛火灶（大带宽卡），慢炖区用大锅（算力卡），互不干扰。

拆开看，一套解耦架构由三件事组成：

1. **分池**：Prefill 实例和 Decode 实例跑在不同的 GPU 上，各自持有完整模型副本（可以配不同的 TP/PP 并行度）；
2. **KV 传输**：Prefill 算完 Prompt，把 KV Cache 搬到 Decode 实例，Decode 接着出 Token——这是解耦新增的、也是最大的工程成本；
3. **独立调度**：两个池各自按自己的 SLO 调度——Prefill 池盯 TTFT，Decode 池盯 TPOT，互不挤兑。

### 1.2 先立靶子：为什么优化目标是 Goodput 而不是 QPS

老板问："我们 QPS 明明很高，用户为什么还在抱怨慢？"答案是：**裸 QPS 不等于用户体验**。

打个比方：两家快递公司，A 家日均 10 万单但只有 60% 的包裹在承诺时间内送达；B 家日均 6 万单但有 99% 准时送达。你会用"日均单量"给谁好评？用户的满意度由"准时送达率"决定，不是总单量。LLM 服务的"准时"就是 SLO——比如 TTFT < 500ms 且 TPOT < 50ms。于是：

$$
\underbrace{\text{Goodput}}_{\text{有效吞吐}} = \underbrace{\text{Raw QPS}}_{\text{裸请求率}} \times \underbrace{P(\text{TTFT} \le \text{SLO}_{\text{TTFT}} \wedge \text{TPOT} \le \text{SLO}_{\text{TPOT}})}_{\text{达标率（SLO attainment）}}
$$

7.1 里 DistServe 的 1.6 rps 就是按这个定义算的——**raw QPS 可以被混批堆得很高，但满足 SLO 的请求率上不去，goodput 就上不去**。解耦的全部意义，就是让达标率这第二个因子从"被互扰拖垮"变成"两个池各自逼近各自的上限"。

## 2. DistServe：围绕 Goodput 的彻底解耦

### 2.1 核心洞察：两类请求不仅互相拖累，还偏好不同的"并行姿势"

DistServe（Yinmin Zhong 等，北大 + UCSD，OSDI'24）先把 7.1 的互扰问题重新表述了一遍，然后补了一个新观察：**混在一起时，连"怎么并行"都被迫用同一个方案，而两个阶段对并行方式的偏好完全不同**。

以 KV 长度为轴看计算量：Prefill 的计算量随 Prompt 长度线性增长（甚至更陡），是典型的 Compute Bound，**偏好张量并行（TP）**——多卡分矩阵乘，TTFT 直接下降；Decode 每步只有 1 个 Token，计算量小、靠批大（batch 大）摊薄权重读取，**偏好"大 batch + 少并行"**——TP 加多了反而通信开销盖过收益。混合部署时，系统只能选一个并行配置，结果要么 Prefill 吃不饱、要么 Decode 白付通信。

🔑 **核心概念**：DistServe 的洞察可以浓缩成一句话——**分池不只是"消除互扰"，更是"给两个阶段各自的并行偏好松绑"**。这是它和"单纯把请求分两堆"的本质区别。

### 2.2 设计：分池 + Goodput 最优放置

DistServe 在推理引擎之上做了一层编排：

1. **prefill instance / decode instance 分池**：每类实例持有完整模型副本，可以配**不同的 GPU 数量和并行策略**（比如 Prefill 池用 TP4、Decode 池用 TP1 + 大 batch）；
2. **Goodput 最优的资源分配**：给定 TTFT/TPOT 两个 SLO，用性能模型搜索"各池几卡、怎么并行"的组合，目标是最大化 per-GPU goodput；
3. **按集群带宽放置**：两个池之间要传 KV，DistServe 把 Prefill/Decode 的放置位置按集群拓扑带宽优化，最小化传输开销；
4. **复制扩展**：找到单副本最优配置后，按流量复制多套。

### 2.3 关键数字

论文在多种模型（OPT、LLaMA 系列）、三种真实负载（聊天、代码补全、文档摘要）上的评测结论：**相比当时最先进的系统，DistServe 能多服务 7.4 倍请求，或扛 12.6 倍更紧的 SLO，且 >90% 的请求保持在延迟约束内**。

📌 **关键点**："7.4 倍请求"和"12.6 倍更紧 SLO"是同一枚硬币的两面——互扰消除 + 并行解耦后，同样的卡要么装下更多请求，要么在同样的负载下把 SLO 压得更紧。哪个对你值钱，取决于你的瓶颈是"扛不住流量"还是"尾延迟超标"。

### 2.4 KV 传输账本：解耦的"过桥费"

分池的代价是：每个请求的 KV Cache 要从 Prefill 池搬到 Decode 池。这笔账必须算清，因为它决定了解耦能不能落地：

$$
\underbrace{V_{\text{KV}}}_{\text{单请求 KV 体积}} = \underbrace{2}_{\text{K 和 V}} \times \underbrace{L}_{\text{层数}} \times \underbrace{h_{\text{kv}}}_{\text{KV 头数}} \times \underbrace{d}_{\text{每头维度}} \times \underbrace{\text{len}}_{\text{Prompt 长度}} \times \underbrace{2\text{B}}_{\text{FP16}}
$$

代入 7B 模型（32 层、32 头、d=128）、2048 Token 的 Prompt：$2 \times 32 \times 32 \times 128 \times 2048 \times 2\text{B} = 1.07$GB——**单个请求就要搬 1GB**。学习路线 3.5 的检验标准按"约 4GB"规划（含并发与工程余量的保守口径），那么按 IB 200Gb/s（= 25GB/s）：

$$
t_{\text{transfer}} = \frac{V_{\text{KV}}}{B_{\text{net}}} = \frac{4\text{GB}}{25\text{GB/s}} \approx \textbf{160ms}
$$

💡 **提示**：论文给过一组实测锚点——OPT-66B 上单个 512-Token 请求的 KV 约 1.13GB，按 10 rps 到达率就是 11.3GB/s ≈ 90Gbps 的持续带宽；现代集群的 InfiniBand 通常 800Gbps，机内 NVLink 更是 600GB/s 量级，所以 DistServe 的结论是：**在高速网络集群里，KV 传输开销可以做到几乎不可见；但网络是 10GbE 以太网级别的集群，解耦的收益会被过桥费吃光**。

## 3. Splitwise：从成本角度做文章

### 3.1 洞察：Token 生成阶段"不配"用最新显卡

DistServe 的出发点是延迟（goodput），Splitwise（微软 + UW，ISCA'24）的出发点是**钱**。它的核心观察基于一组硬件数据：H100 相比 A100，算力涨了 **3.43 倍**、功耗涨了 **1.75 倍**，但内存带宽只涨了 **1.6 倍**、容量一分没涨——**算力在狂奔，带宽在爬行**。而 Decode 恰恰是吃带宽不吃算力的：

- 论文实测：Token 生成阶段的 GPU 功耗对计算量不敏感，**把 GPU 功耗限制砍掉 50%（如 700W→350W），Token 生成的延迟几乎不受影响**；而 Prefill 对功耗限制极度敏感；
- 结论（论文 Insight VII）：**Token 生成可以跑在算力更弱的硬件上**，换更好的每瓦性能（Perf/W）和每美元性能（Perf/$）。

🔑 **核心概念**：Splitwise 的一句话说清就是——**混合部署等于给"吃带宽的 Decode"也配了"吃算力的旗舰卡"，钱花在了刀刃以外**；分池之后，P 池用算力强的卡、D 池用带宽/内存比好的老卡（甚至功耗受限的旗舰卡），各花各的钱。

### 3.2 设计：同构/异构集群 + 两级调度 + 分层 KV 传输

Splitwise 的集群设计比 DistServe 更贴近"数据中心采购"视角：

- **四种机型组合**：Splitwise-AA（P/D 都用 A100）、Splitwise-HH（都用 H100）、**Splitwise-HA（P 池 H100 + D 池 A100）**、Splitwise-HHcap（P/D 都用 H100，但 D 池整机限到 70% 额定功耗、每卡限 50%）；
- **两级调度**：集群级调度器（CLS）负责把请求路由到一对"Prompt 机器 + Token 机器"（Join Shortest Queue），机器级调度器（MLS）负责机内组批；还有一个**混合池**兜底——负载波动时，机器可以临时跨界干活，闲下来再回原池；
- **KV 传输优化**：用 MSCCL++ 的 one-sided put，**逐层异步传输**——Prefill 每算完一层就把该层 KV 发走，与下一层计算重叠，传输开销被藏进计算里；小 Prompt 则退化为串行传输（反正数据小）。

### 3.3 配比怎么定：27 台 Prefill : 3 台 Decode 的来历

Splitwise 用事件驱动仿真器在"每种负载 × 每种 SLO"下搜索最优配比（性能模型 MAPE < 3%）。给一个论文里的具体结果：**编码工作负载（Azure 生产 trace，Prompt 中位 1500 Token、输出中位 13 Token）目标 70 RPS 时，成本最优的 Splitwise-HH 配置是 27 台 Prompt 机器 + 3 台 Token 机器**。

这个 9:1 的比例很反直觉——直觉上输出那么短，Decode 机器应该没几台？但算下来就懂了：**输出 Token 的"每 Token GPU 成本"远高于输入 Token**。27 台机器扛 1500×70 = 10.5 万输入 Token/s，3 台机器扛 13×70 = 910 输出 Token/s，折算下来**一个输出 Token 的 GPU 成本 ≈ 输入 Token 的 13 倍**——Decode 是 Memory Bound、每个 Token 都要读全量权重 + KV，贵得有道理。

### 3.4 关键数字与对比

- **1.4 倍吞吐 @ 20% 更低成本**（相对传统同构集群）；
- 或者**同成本、同功耗预算下 2.35 倍吞吐**；
- 无损：KV 传输是逐层原样搬运，不影响精度。

与 DistServe 的差异值得一张表钉死：

| 📊 维度 | DistServe（OSDI'24） | Splitwise（ISCA'24） |
|---|---|---|
| 优化目标 | Goodput（SLO 达标率 × 吞吐） | 成本 / 吞吐 / 功耗三目标 |
| 分池粒度 | Prefill/Decode 实例，各配专属并行策略 | Prompt/Token 机器池 + 弹性混合池 |
| 硬件观 | 同构卡，靠并行度差异区分两池 | 异构卡（H100/A100/限功耗），按阶段买硬件 |
| KV 传输 | 按带宽优化放置，传输可隐藏 | 逐层异步 + MSCCL++ one-sided put |
| 一句话 | 同样的卡，怎么布置让 SLO 达标率最高 | 不同的卡，怎么采购让每块钱产出最多 |

📌 **关键点**：两者不是竞争关系而是互补视角——**DistServe 回答"卡已经买了怎么摆"，Splitwise 回答"卡还没买怎么买"**。生产上常常是 DistServe 式调度跑在 Splitwise 式异构集群上。

## 4. TaiChi：把聚合与解耦统一起来

### 4.1 背景：一场"聚合 vs 解耦"的争论

2024-2025 年业界吵了一架：聚合（Chunked Prefill 混批，2.4 的路子）说解耦浪费卡、传输贵；解耦（DistServe/Splitwise 的路子）说聚合尾延迟没救。TaiChi（Chao Wang 等，2025，arXiv:2508.01989）先做了个系统对比，结论是：**两边都对，但各对一半**——

| 📊 SLO 形态 | 谁更优 | 直觉 |
|---|---|---|
| TTFT 很紧 + TPOT 宽松 | **聚合** | Prefill 随时插队、Decode 慢点无所谓，混批利用率最高 |
| TPOT 很紧 + TTFT 宽松 | **解耦** | Decode 池不被 Prefill 打扰，TPOT 稳如老狗 |
| 两者都紧（平衡 SLO） | **都不优** | 聚合尾延迟爆、解耦白占两池，需要新玩法 |

### 4.2 设计：滑杆调出来的"混合模式"

TaiChi 的关键创新是 **latency shifting（延迟转移）**：把资源从"稳达 SLO 的请求"那里挪给"快要超时的请求"，让达标请求数最大化——有点像交通疏导：不着急的车让一让，把路权给快迟到的那辆。

实现上它用了一个统一架构 + 三个滑杆：

1. **两类差异化实例**：prefill-heavy（Prefill 快、Decode 互扰高）和 decode-heavy（Decode 互扰低、Prefill 慢）——GPU 本身可以是不同的，调度把请求按需指派；
2. **三个可配置滑杆**：两类实例的比例、各自 chunk 大小——TTFT 紧就调向聚合形态，TPOT 紧就调向解耦形态；
3. **两种调度机制**：flowing decode scheduling 管 TPOT（让 decode 像水流一样平稳），length-aware prefill scheduling 管 TTFT（按长度感知决定 Prefill 何时插）。

### 4.3 关键数字

论文在平衡 TTFT/TPOT SLO 下，**goodput 相比当时最优系统最高提升 77%**。

📌 **关键点**：TaiChi 的工程价值不是又一个新系统，而是**把"聚合还是解耦"从二选一变成连续旋钮**——负载的 SLO 形态变了，扭一下滑杆就行，不用推倒重来。这也是学习路线 3.5 把 TaiChi 单独列出来的原因：它是"决策框架"层面的贡献。

## 5. MLC Microserving 与工程现状

### 5.1 MLC Microserving：把解耦变成"可编程的 API"

前面三个系统都是"论文里的编排"，MLC Microserving（MLC 团队，arXiv:2412.12488）想解决落地问题：**每种编排模式都要改引擎代码，太慢**。它的做法是把"sub-request 级动作"（prefill 一段、迁移 KV、decode 一步、复用缓存）暴露成细粒度 API，用户用**几行 Python** 就能重排这些动作，动态切换编排模式（今天聚合、明天解耦、后天投机解码），底层用一个统一的 KV Cache 接口处理"算、传、复用"各种场景。论文实测：用它探索出的新策略变体，任务完成时间（JCT）比既有策略最多降 **47%**。

🔑 **核心概念**：DistServe/Splitwise/TaiChi 是"给定一种编排，怎么优化"；Microserving 是"编排本身变成可编程的"——解耦从架构决策降级成了 API 调用。

### 5.2 vLLM 的 Disaggregated Prefill 现状

落地到主流引擎（以你所用版本的官方文档为准，该功能标注 **experimental**，vLLM 进入 V1 后是默认引擎）：

- **架构**：跑两个 vLLM 实例——prefill instance 和 decode instance，中间用 Connector 传 KV；实现位于 `vllm/distributed/kv_transfer`；
- **参数**：`--kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_both",...}'`——`kv_connector` 选传输后端，`kv_role` 标角色（`kv_producer` / `kv_consumer` / `kv_both`；示例仅示意，`kv_both` 在新版本已弃用，以你所用版本为准）；
- **Connector 全家桶（文档列了 9 种）**：NixlConnector（基于 NIXL，支持 UCX/GDS 等后端、全异步收发）、LMCacheConnectorV1（LMCache 方案，底层也走 NIXL，另有 LMCacheMPConnector 独立进程模式）、MooncakeConnector、OffloadingConnector、FlexKVConnectorV1 等；
- **官方明说的两条**：一是解耦**不提升吞吐**（它治的是尾延迟和 TTFT/TPOT 独立调优）；二是控制尾 ITL 时"chunked prefill 也能做到，但实际中正确的 chunk size 很难找，解耦是更可靠的方式"——这句正好接上 7.1 的"为什么切块不够"。

### 5.3 NIXL 与 Ray Serve：传输层的"水电煤"

NIXL（NVIDIA Inference Xfer Library，github.com/ai-dynamo/nixl，GTC 2025 前后开源）就是被 vLLM、SGLang、TensorRT-LLM、Ray、LMCache 共同采用的传输层：一个 vendor-agnostic 的数据搬运库，**UCX 为默认后端**，插件化支持 RDMA/InfiniBand、libfabric（含 TCP）、EFA、GPUDirect Storage、S3/Azure Blob 等——KV 从 GPU 搬到 GPU、搬到 CPU、搬到对象存储，一套 API。Ray Serve 的 prefill/decode 文档直接要求 vLLM V1，用 `build_pd_openai_app` 配 NIXLConnector 或 LMCacheConnectorV1 就能起分池部署（`kv_role: kv_producer` / `kv_consumer`）；Anyscale 的实测博客给出了一个诱人的数字：**Ray + vLLM 在 AMD MI325X 上做 P/D 解耦，成本最多省 67%**（2026-06，以原文为准）。

落成一句话：**论文负责证明"该拆"，vLLM/Ray/NIXL 负责让"拆"变成一条命令**——你在 2026 年想上解耦，不需要自己造轮子，但依然需要自己算清楚"该不该拆、怎么配比"。

## 6. 方案对比：四类路线的取舍

| 📊 方案 | 优化目标 | 调度粒度 | 工程复杂度 | 适用场景 |
|---|---|---|---|---|
| 聚合基线（Chunked Prefill，2.4） | 吞吐 + 利用率 | Token Budget 统一装箱 | 低（默认行为） | 短 Prompt、SLO 宽松、离线批处理 |
| DistServe | Goodput（SLO 达标率） | Prefill/Decode 实例 + 并行度独立优化 | 高（编排层 + 性能模型） | 延迟敏感在线服务、同构集群 |
| Splitwise | 成本 / 吞吐 / 功耗 | 机器池 + 两级调度 + 混合池 | 高（集群规划 + 仿真） | 大规模自建集群、异构采购 |
| TaiChi | 任意 SLO 组合下最优 Goodput | 实例比例 + chunk 滑杆 | 更高（差异化实例 + 双调度） | 负载 SLO 形态多变、追求极致达标率 |
| Microserving | 可编程性（编排灵活性） | sub-request 级 API | 中（API 层，引擎不变） | 探索多种编排模式、快速实验 |

📌 **关键点**：表里最反直觉的是第一行——**聚合基线在"短 Prompt + 宽松 SLO"下就是最优解**。解耦不是免费的升级，是"病到一定程度才值得动的手术"；5 行方案的复杂度递增，也对应了你要解决的问题的量级递增。

## 7. 权衡：换来了什么，牺牲了什么

### 7.1 换取的

- **尾延迟**：Decode 池永不被 Prefill 打扰，TPOT P95/P99 从"3-5 倍尖刺"回到稳态（7.1 的病直接消除）；
- **Goodput**：per-GPU goodput 从 1.6 → 3.3 rps（2.1 倍），或 7.4 倍请求 / 12.6 倍更紧 SLO（DistServe）；
- **资源利用率与成本**：两池各自吃满（Prefill 吃算力、Decode 吃带宽），异构采购 + 限功耗让每块钱产出更多（Splitwise 1.4x 吞吐 @ -20% 成本）；
- **独立扩缩容**：负载的 Prompt 变长只扩 P 池，输出变长只扩 D 池（Ray Serve 文档明说的卖点）。

### 7.2 牺牲的

- **调度复杂度**：一个调度器变三个（P 池、D 池、P→D 的配对路由），队列管理、失败重试都要翻倍；
- **KV 传输带宽**：每个请求多一次全量 KV 搬运（7B/2048 约 1-4GB，IB 200Gb/s 下 40-160ms），网络不是高速网就白拆；
- **双池负载不均**：P/D 比例配错，某一池空转烧钱——**配比是解耦的第一工程问题**；
- **TTFT 微增 + 首跳延迟**：请求先到 P 池、算完再转到 D 池，路由多一跳，极端场景下 TTFT 反而变差；
- **模型副本翻倍**：两池各持完整权重，权重显存 ×2（大模型上这笔账不小）。

### 7.3 P/D 池配比怎么推导（检验标准：2000 in / 500 out → 1:3~1:4）

配比推导分两步。**第一步**，先算两类请求的"每 Token GPU 成本比" $c_d / c_p$——这个数不靠猜，用 Splitwise 论文的实测反推：编码负载 27 台 Prefill + 3 台 Decode 机器，输入 10.5 万 Token/s、输出 910 Token/s，同成本下：

$$
\frac{c_d}{c_p} = \frac{\text{输入 Token 率} / N_{\text{P}}}{\text{输出 Token 率} / N_{\text{D}}} = \frac{105000 / 27}{910 / 3} \approx 12.8
$$

**第二步**，把工作负载（平均输入 2000、平均输出 500）代进总账：

$$
\underbrace{N_{\text{in}} \cdot c_p}_{\text{Prefill 池总需求}} : \underbrace{N_{\text{out}} \cdot c_d}_{\text{Decode 池总需求}} = 2000 \times 1 : 500 \times 12.8 = 2000 : 6400 \approx \textbf{1 : 3.2}
$$

**Prefill 池 : Decode 池 ≈ 1:3 ~ 1:4**——与学习路线 3.5 的检验标准一致。

💡 **提示**：这个结果很反直觉——输入 Token 数是输出的 4 倍，Decode 池反而要大 3 倍多。秘密全在 $c_d / c_p \approx 13$：Decode 每 Token 要读全量权重 + 全量 KV（Memory Bound），单个 Token 的 GPU 占用远贵于 Prefill 的并行 Token。**不同负载配比完全不同**：输入 1500/输出 13 的编码负载是 9:1（P 池大），输入 1000/输出 500 的对话负载大约 1:6。**别背数字，背推导**——精确值还受 SLO、batch、硬件影响，Splitwise 用仿真器搜（MAPE < 3%），生产上你至少要按本节公式 + 实测速率重算一遍，更精确的做法是像 Splitwise 那样用性能模型 + 仿真器搜索配置空间。

### 7.4 落成一句话的决策

- ✅ **P95 TPOT 尖刺 ≥3 倍 + SLO 严格** → 上解耦（DistServe 式：同构卡先拆池）。
- ✅ **成本敏感 + 大集群** → Splitwise 式：P 池买算力卡、D 池买带宽卡/限功耗，配比按 7.3 推导 + 仿真验证。
- ✅ **SLO 形态多变** → 关注 TaiChi 式滑杆框架（或 Microserving 的可编程编排）。
- ✅ **已有高速网络（IB 400Gbps+ / NVLink 跨机）** → 传输过桥费可接受，放心拆。
- ❌ **单机小规模、短 Prompt、SLO 宽松** → 别拆，Chunked Prefill 就是最优解，解耦只会让你多付"调度复杂度 + 双池空转"的学费。
- ❌ **10GbE 级别的网络** → 先修网络再谈解耦，KV 过桥费会吃掉全部收益。

## 📝 总结

1. **解耦 = 分池 + KV 传输 + 独立调度**，收益来自"让两类请求各得其所"，优化目标统一为 Goodput（满足 SLO 的有效吞吐），裸 QPS 会骗人。
2. **DistServe**（OSDI'24）：消除互扰 + 给两阶段各自的并行偏好松绑，按带宽优化放置；实测 7.4 倍请求 / 12.6 倍更紧 SLO，>90% 请求达标；KV 传输在高速网络下可隐藏（OPT-66B/512-Token ≈ 1.13GB，10 rps 需 ~90Gbps）。
3. **Splitwise**（ISCA'24）：Token 生成不需要旗舰卡（H100 算力 3.43x 但带宽仅 1.6x，限功耗 50% 无延迟影响）；异构集群 + 两级调度 + 混合池；1.4 倍吞吐 @ 20% 低成本，或同成本 2.35 倍；实测编码负载配比 27:3。
4. **TaiChi**（2025）：聚合在"紧 TTFT 松 TPOT"下最优、解耦在"紧 TPOT 松 TTFT"下最优，平衡 SLO 下用 latency shifting 混合模式再榨出最高 77% goodput。
5. **工程现状**：vLLM V1 的 `--kv-transfer-config` + NixlConnector/LMCacheConnectorV1（9 种 Connector，功能 experimental）、NIXL 统一传输层、Ray Serve 一条命令起分池——论文证明"该拆"，工具链负责"拆得动"。
6. **配比推导**：$c_d / c_p \approx 13$（Splitwise 实测反推）→ 2000 in / 500 out 负载下 P:D ≈ **1:3.2（即 1:3~1:4）**；不同负载配比天差地别，背推导别背数字。
7. **决策一句话**：尾延迟尖刺 ≥3 倍 + SLO 严格 + 网络够快 → 拆；短 Prompt + 宽松 SLO + 小集群 → 别拆，Chunked Prefill 就是最优解。
