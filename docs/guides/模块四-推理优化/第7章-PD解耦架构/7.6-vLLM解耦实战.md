## 1. 架构与前置：双实例加 Connector

### 1.1 官方架构：两实例 + 一个 Connector

vLLM 的实现思路非常直白（官方文档原话）：**跑 2 个 vLLM 实例，一个叫 prefill instance、一个叫 decode instance，用一个 Connector 把 prefill 算出的 KV Cache 和结果从前者搬到后者**。整个实现位于 `vllm/distributed/kv_transfer`，核心抽象只有三个：

- **Connector**：让 KV 的消费方（decode）能从生产方（prefill）取到一批请求的 KV；
- **LookupBuffer**：KV 的暂存区，只有两个操作——`insert`（写入 KV）和 `drop_select`（按条件取出并删除 KV），语义像 SQL；**`insert` 非阻塞、`drop_select` 阻塞**（没有就等）；
- **Pipe**：单向 FIFO 传输管道，只做 `send_tensor` / `recv_tensor` 两件事。

每个 vLLM 进程里其实有两个 Connector：**Scheduler Connector**（和调度器同进程，负责编排传输时机）和 **Worker Connector**（在 worker 进程里，真正执行传输）。KV 是**按层传输**的——prefill 算完某一层的 KV 就发走，不用等全部算完（这正是 7.5 说的“边算边传”）。

打个比方：整个链路像机场——**值机柜台（prefill 实例）负责办票和托运行李，行李（KV Cache）通过传送带（Connector）送到登机口，登机口（decode 实例）只负责让人上飞机（逐 token 生成）**。值机柜台慢了，乘客等首 token（TTFT 超标）；传送带断了，人到了登机口行李没到，照样走不了（KV 传输失败）。

### 1.2 为什么官方说“不提升吞吐”？

解耦的官方动机只有两个（文档原话的翻译）：

1. **TTFT 和 ITL 可以独立调优**：prefill 实例和 decode 实例可以配不同的 TP/PP 并行度，调 TTFT 不碰 ITL，反之亦然——单实例里这两件事是绑死的；
2. **控制尾 ITL（TPOT）**：单实例下调度器可能把 prefill 插进 decode 的 step，产生尾延迟尖刺；分池后 decode 实例**永远不做 prefill**，尾延迟天然可控。

至于吞吐：单实例的 Continuous Batching 把两类 token 混批填满 GPU（2.2 的 30%→80%+），分池后 prefill 池可能喂不饱、decode 池的 batch 深度也受限于到达率——**所以官方明确说不提升吞吐**。7.5 已经警告过：拿它当吞吐优化器是药不对症。

### 1.3 支持状态与 Connector 选型

以 2026 年中的 vLLM 版本为例（功能演进快，以你所用版本的官方文档为准）：

- **状态**：experimental，官方标注“subject to change”；只有 V1 引擎支持（V0 在 v0.11.0 已移除，6.6 讲过）；
- **Connector 数量**：官方文档列出 9 种——ExampleConnector（教学）、**NixlConnector（生产主力，全异步收发）**、**LMCacheConnectorV1（底层也走 NIXL，外加缓存层）**、MooncakeConnector（KVCache 中心化）、OffloadingConnector（KV 落 CPU/文件系统）、FlexKVConnectorV1、MultiConnector、MoRIIOConnector（ROCm）等；
- **历史教训**：早期示例用的 `PyNcclConnector`（基于 NCCL 传 KV）已被官方移除（2026 年中），网上很多旧教程还在抄它——**看到 PyNccl/NCCL 字样要警惕，认准 NixlConnector**。

本节的命令骨架用 **NixlConnector**：它底层是 NVIDIA 开源的 NIXL 库（GTC 2025 开源），支持 UCX（默认，可走 RoCE/IB/TCP）、LIBFABRIC（AWS EFA）、GDS 等多传输后端。NIXL 官方后端全景：RDMA/InfiniBand、RoCE（经 UCX）、TCP 回退、NVMe-oF、S3 对象存储——**从机内到跨机房都覆盖，这也是它能当生产主力的原因**。

### 1.4 动手前的前置检查清单

| 检查项 | 要求 | 为什么 |
|---|---|---|
| vLLM 版本 | 两个实例**必须同版本** | 传输协议与 KV 布局随版本变，不一致会静默失败 |
| 模型权重 | 同一个模型、同一个路径 | 实例间要能对上 KV 形状和词表 |
| 显存 | **双份权重**（7.5 的固定成本） | 两个实例各占一份权重 + KV 空间 |
| 传输后端 | 同机：UCX 开箱即用；跨机：IB/RoCE/EFA 就绪 | KV 是 GB 级，慢链路直接拖垮 TTFT |
| 端口 | `VLLM_NIXL_SIDE_CHANNEL_PORT`（默认 5600）两个实例各一个 | NIXL 握手通道，冲突必挂 |
| 网络环境变量 | 用 `UCX_TLS` / `UCX_NET_DEVICES`，**不是** `NCCL_*` | NixlConnector 不走 NCCL，官方文档明说 NCCL 变量无效 |

## 2. 部署三件套：prefill 实例、decode 实例与路由

### 2.1 prefill 实例（KV Producer）

起一个 prefill 实例，核心参数是 `--kv-transfer-config`（一个 JSON），加上 NIXL 的环境变量。下面的命令骨架取自 vLLM 官方 NixlConnector 指南（模型换成你自己的，端口可调）：

```bash
# prefill 实例（KV 生产方）：1 号 GPU
CUDA_VISIBLE_DEVICES=0 \
UCX_NET_DEVICES=all \
VLLM_NIXL_SIDE_CHANNEL_PORT=5600 \
vllm serve Qwen/Qwen3-0.6B \
  --port 8100 \
  --enforce-eager \      # 示例简化，生产按需取舍
  --kv-transfer-config \
  '{"kv_connector":"NixlConnector","kv_role":"kv_producer","kv_load_failure_policy":"fail"}'
```

### 2.2 decode 实例（KV Consumer）

```bash
# decode 实例（KV 消费方）：2 号 GPU
CUDA_VISIBLE_DEVICES=1 \
UCX_NET_DEVICES=all \
VLLM_NIXL_SIDE_CHANNEL_PORT=5601 \
vllm serve Qwen/Qwen3-0.6B \
  --port 8200 \
  --enforce-eager \      # 示例简化，生产按需取舍
  --kv-transfer-config \
  '{"kv_connector":"NixlConnector","kv_role":"kv_consumer","kv_load_failure_policy":"fail"}'
```

`--kv-transfer-config` 各字段的含义（以你所用版本的文档为准）：

| 字段 | 取值 | 含义 |
|---|---|---|
| `kv_connector` | `NixlConnector` 等 | 用哪个 Connector 实现 |
| `kv_role` | `kv_producer` / `kv_consumer` | prefill 实例填 producer，decode 实例填 consumer（`kv_both` 对 NixlConnector 已弃用） |
| `kv_load_failure_policy` | `fail`（默认）/ `recompute` | decode 侧取 KV 失败时：直接失败，还是本地重算（7.5 讲过的权衡） |
| `kv_buffer_device` | `cuda` / `cpu` | KV 暂存缓冲放显存还是内存（显存快但占空间） |
| `kv_connector_extra_config` | `{"backends":["UCX","GDS"]}` | 选 NIXL 传输后端；跨机 EFA 场景用 `["LIBFABRIC"]` |
| `kv_lease_duration` | 默认 30s | prefill 完成后 KV 的保留时长，decode 心跳可续期（7.5 第 4 节） |

⚠️ **注意**：两个实例的 `VLLM_NIXL_SIDE_CHANNEL_PORT` 在同一台机器上**必须不同**（示例里 5600 / 5601）；跨机部署时还要给两边都设 `VLLM_NIXL_SIDE_CHANNEL_HOST=<对端 IP>`，否则握手只会在 localhost 上找对方。官方文档原话：NCCL 的环境变量（`NCCL_IB_HCA` 等）对 NixlConnector **不适用**，配 `UCX_*` 才对。

### 2.3 客户端怎么路由：先打 prefill，再打 decode

两个实例各自是独立的 OpenAI 兼容端点，但**没有哪个实例能独立完成一个请求**——必须有人先把请求发给 prefill（`max_tokens=1` 让它只算 KV），再把后续的生成请求发给 decode。官方给了两种形态：

**形态 A：官方代理（推荐，XpYd）**。vLLM 仓库自带代理示例，支持 X 个 prefill + Y 个 decode 实例的轮询路由：

```bash
# 代理：统一入口 8000，内部轮询 2 个 prefill + 2 个 decode
python3 examples/disaggregated/disaggregated_serving/disagg_proxy_demo.py \
  --model $model_name \
  --prefill localhost:8100 localhost:8101 \
  --decode localhost:8200 localhost:8201 \
  --port 8000
```

代理的工作流（官方说明）：把请求先发给 prefill 实例（`max_tokens` 改成 1，只做 prefill），prefill 完成后带着 KV 位置信息转给 decode 实例继续生成。**代理要记住“每份 KV 在哪”，这正是 7.5 说的调度复杂度在代码里的样子**。

**形态 B：客户端两段式（官方文档的 API 用法）**。不架代理，客户端自己分两步——prefill 响应里带回 token ids，decode 请求再带上：

```python
# 第一步：发给 prefill 实例，要回 token ids
prefill = client.chat.completions.create(
    model=model, messages=messages,
    extra_body={"return_token_ids": True,
                "kv_transfer_params": {"do_remote_decode": True}},
)
ids = prefill.prompt_token_ids

# 第二步：发给 decode 实例，带上 ids 直接续生成（避免重复 tokenize）
decode = client.chat.completions.create(
    model=model, messages=messages, stream=True,
    extra_body={"kv_transfer_params": {"do_remote_prefill": True,
                                       "prompt_token_ids": ids}},
)
```

💡 **提示**：官方注释里说了，未来会引入 `vllm connect` 这类一键连实例的能力，代理形态也在演进——**先按官方示例跑通，再追新**。

### 2.4 跑通验证

```bash
# 两个实例各自健康检查（都在 /v1/models 上）
curl -s localhost:8100/v1/models | head
curl -s localhost:8200/v1/models | head

# 走代理发一个完整请求（形态 A 时）
curl -X POST http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen3-0.6B","prompt":"San Francisco is a","max_tokens":20,"temperature":0}'
```

能正常出 token 就说明 prefill → 传输 → decode 整条链通了。vLLM 还会周期打印 **KV Transfer metrics**（传输量、耗时、速率），这是后续排错的第一手数据。从 v0.10.0 时代一路跟过来的同学会记得当时的 run.sh 用的是 `PyNcclConnector` + `kv_rank`/`kv_parallel_size` 字段——**那套已被移除，别照抄旧教程**。

## 3. 实验一：互扰量化对比（聚合 vs 解耦）

### 3.1 实验设计：同一负载，两种模式

目的：把 7.1 说的“互扰 3-5 倍”在你的环境里复现出来，或者证伪。控制变量做到位，结果才有说服力：

- **同一份负载**：同一批 prompt、同一个 `max_tokens`、同一并发档位（1 / 16 / 64 三档）；
- **同一硬件**：聚合模式 = 1 个单实例（2 卡 TP2 或 1 卡均可）；解耦模式 = 同样 2 卡，1 张 prefill + 1 张 decode；
- **指标六件套**（3.6 的口径）：QPS、TTFT P50/P95、TPOT P50/P95、throughput、显存峰值、GPU 利用率；
- **压测工具**：沿用 4.6/6.6 的 GenAI-Perf，同一份 profile 配置跑两遍。

### 3.2 混合负载怎么构造

关键在负载要“病”得出来：**少量超长 prompt + 大量短对话**，长 prompt 还要周期性地涌进来。两种做法：

1. **GenAI-Perf 参数**（4.6 的命令骨架改两行）：
```bash
genai-perf profile -m <model> --endpoint-type chat --service-kind openai \
  --endpoint /v1/chat/completions --url http://localhost:8000 \
  --concurrency 32 \
  --synthetic-input-tokens-mean 200    # 大部分请求：短对话
  --synthetic-input-tokens-stddev 50 \
  --output-tokens-mean 128 \
  --output-tokens-stddev 0
```
2. **自定义脚本注入**：95% 的请求用 100~200 token 的短 prompt，每 N 秒注入一个 8000 token 的长 prompt（模拟“文档问答混进聊天”），长 prompt 的注入节奏用脚本循环控制。**注入比例和节奏写进 config 文件**，保证两次实验可复现（3.6 的 benchmark 可复现要求）。

### 3.3 预期结果与解读（数字待你在自己环境核实）

结果表模板（数值留空，跑完再填）：

| 📊 指标 | 聚合模式 | 解耦模式 | 预期方向 |
|---|---|---|---|
| TTFT P50 / P95（ms） | / | / | 解耦 P50 略升（+KV 传输），P95 明显更低（prefill 不再排队） |
| TPOT P50（ms） | / | / | 基本持平 |
| **TPOT P95（ms）** | / | / | **聚合被长 prefill 拖出尖刺（学习路线口径 3-5 倍），解耦平稳** |
| Throughput（token/s） | / | / | 解耦**不升甚至略降**（官方声明：不提升吞吐） |

解读要点：

- **看 P95 不看均值**：互扰的伤害集中在尾延迟（7.1 第 5 节：均值受害小、P95/P99 受害大），所以判定线绑在 **TPOT P95 上**——聚合比解耦慢 **≥2 倍即确认互扰**（7.1 的复现协议），3-5 倍是学习路线给的经验区间；更极端的混合负载下，单次大 prefill 能把 TPOT 抬到 2~30 倍（Hao AI Lab 2025 年回顾博客的实测区间）；
- **TTFT 会略升**：KV 传输 + 两段调用的固有延迟，重叠做得好可以压到几十 ms 以内（[7.3 的工程细节](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/73-kv传输与connector)）；
- **吞吐下降别慌**：这是解耦的预期代价之一，不是部署错了——**实验结论的写法是“牺牲 X% 吞吐，把 TPOT P95 从 A 降到 B，SLO 达标率从 X% 提到 Y%”**，用 goodput 说话（[7.4 的口径](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/74-goodput与slo调度)）。

⚠️ **注意**：解耦模式的 decode 实例上不要挂任何 prefill 流量（别拿 decode 端点当普通服务用），否则实验测的就是“半解耦”，结论作废。

## 4. 实验二：P/D 配比与 goodput 曲线

### 4.1 方法论：固定总卡数，扫描配比

7.5 给了配比公式的初值（2000/500 负载 + FP8 大模型 ≈ 1:3~1:4），实验二的任务是**验证并校准这个初值**。协议：

- **固定总 GPU 数**（如 8 卡），切分 P:D = 1:7 / 2:6 / 3:5 / 4:4 四档——总资源不变，只挪配比；
- **固定负载**：实验一的混合负载原样复跑（同 config 文件）；
- **指标**：每档测 goodput——**满足 SLO（如 TTFT < 500ms 且 TPOT < 50ms）的有效吞吐**，而不是裸 QPS（[7.4 的定义](/AIInfraGuide/inference/模块四-推理优化/第7章-pd解耦架构/74-goodput与slo调度)）；
- 配比 1:7 意味着 1 个 prefill 实例 + 7 个 decode 实例（代理的 `--prefill` / `--decode` 参数各给一个列表）。

### 4.2 预期曲线形状

结果表模板：

| 📊 配比（P:D） | TTFT P95 | TPOT P95 | goodput（req/s） |
|---|---|---|---|
| 1:7 | 爆表（prefill 不够） | 稳 | 低（TTFT 违约拖累） |
| 2:6 | / | / | / |
| 3:5 | / | / | 峰值平台（预期） |
| 4:4 | 稳 | 开始恶化（decode 不够） | 回落 |

预期的形状是**倒 U 曲线**：P 太少 → prefill 排队、TTFT 违约；D 太少 → decode 排队、TPOT 违约；中间存在一段“平台”——**平台就是你这套负载的合理配比区间**。把这个平台和 7.5 公式的初值对照：对上了，说明你的硬件参数估算（$r_P$、$r_D$）靠谱；对不上，说明假设（MFU、带宽效率）偏了，用实测反推修正。

💡 **提示**：配比实验很贵（每档都是一轮完整压测），**先按 7.5 公式算初值，再在初值附近 ±1~2 档扫描**，别从 1:7 到 7:1 全扫。

### 4.3 配比调优闭环

实验做完不是终点：负载会漂移（7.5 第 3 节），配比要能跟着动。生产闭环是：

1. 公式算初值 → 2. 实验校准平台 → 3. 上线按平台配比部署 → 4. 监控 goodput 与两池利用率 → 5. 漂移时按池扩缩容（第 10 章 10.3 的 HPA；Ray Serve 的 prefill/decode 各自 `autoscaling_config` 就是现成实现）。

## 5. 排错速查

解耦排错比单实例多一层“网络”维度。按症状查：

| 症状 | 诊断 | 修复 |
|---|---|---|
| 请求报 KV 传输相关错误 / 直接失败 | Connector 后端选错：UCX 没装或后端没编译进 NIXL | `--kv-transfer-config` 的 `backends` 显式指定（如 `["UCX"]`）；同机先跑通再上跨机 |
| 卡在握手 / 互相找不到对方 | `VLLM_NIXL_SIDE_CHANNEL_PORT` 冲突（两实例同端口）或跨机没设 `VLLM_NIXL_SIDE_CHANNEL_HOST` | 同机两实例端口不同；跨机两边都设 HOST 为对端 IP；检查防火墙 |
| 传输极慢 / TTFT 暴涨 | IB/RoCE 没就绪，走了 TCP 回退；或配了 `NCCL_*` 变量指望它生效 | 用 `ucx_info` 验证传输层；改配 `UCX_TLS` / `UCX_NET_DEVICES`；确认 `backends` 与实际链路一致（EFA 用 LIBFABRIC） |
| 两个实例版本不一致 | 传输协议 / KV 布局对不上，表现为偶发失败或卡死 | 两实例用完全相同的 vLLM 版本（最好同一容器镜像） |
| decode 排队久，请求超时失败 | KV lease（默认 30s）到期，KV 块被释放 | 调大 `kv_lease_duration`；或把 `kv_load_failure_policy` 从 `fail` 改成 `recompute`（接受 decode 侧抖动） |
| 偶发失败但日志无异常 | 传输失败被静默重试吞了 | 看 vLLM 周期打印的 KV Transfer metrics；必要时开 UCX 日志（`UCX_LOG_LEVEL=info`） |
| 多卡 TP 实例传 KV 失败 | NIXL 握手端口按 rank 递增，DP/TP 下端口没排开 | 按官方公式：同节点 base_port + dp_rank 递增分配 |

⚠️ **注意**：**排错顺序先网络后引擎**（6.6 的经验）：同机部署先跑通（UCX 走共享内存），再上跨机（IB/RoCE/EFA）——每一步只引入一个新变量。跨机首次联调前，用 NIXL 自带的测试/`ucx_info` 验证链路本身是通的，**别让 vLLM 替你测网络**。

## 6. 决策规则：什么规模才值得用 vLLM 解耦

把 7.5 的决策表和这一节的实验能力合起来，落成一句话的规则：

- ✅ **在线高并发 + 严格尾延迟 SLO + 长 prompt 混合**，且实验一确认互扰（TPOT P95 ≥2 倍）→ 用 Disaggregated Prefill：两实例 + NixlConnector + 代理路由，配比按 7.5 公式取初值、按实验二校准。
- ✅ **TTFT 和 TPOT 需要独立扩缩容**（流量结构会变）→ 解耦是唯一能“只扩一边”的形态，池子各自接 HPA（第 10 章）。
- ❌ **追求峰值吞吐** → 别用：官方声明不提升吞吐，去优化 Continuous Batching（[2.2](/AIInfraGuide/inference/模块四-推理优化/第2章-推理引擎核心技术/22-continuous-batching)）和 DP 副本（[6.4](/AIInfraGuide/inference/模块四-推理优化/第6章-分布式推理/64-数据并行与专家并行)）。
- ❌ **小规模 / 短 prompt / 宽松 SLO** → 别用：双份权重的固定成本（7.5 账本）白付，Chunked Prefill（2.4）足够。
- ❌ **没有高速网络**（跨机无 IB/RoCE/EFA）→ 别用：KV 是 GB 级，TCP 回退的传输延迟会吃掉全部收益。

💡 **提示**：上手顺序建议——单机双卡把官方 proxy 示例跑通（半天）→ 实验一量化互扰（一天）→ 实验二扫配比（一两天）→ 再决定要不要进生产。**解耦是架构级改动，先用实验证明收益，再谈上线。**

## 📝 总结

1. **架构一句话**：两个 vLLM 实例（prefill + decode）+ 一个 Connector；核心抽象 Connector / LookupBuffer（insert 非阻塞、drop_select 阻塞）/ Pipe；KV 按层边算边传。
2. **官方定位**：解耦不提升吞吐（官方声明原话），只治两件事——TTFT/ITL 独立调优 + 尾 ITL 控制。
3. **部署三件套**：prefill 实例（`kv_role=kv_producer`）+ decode 实例（`kv_role=kv_consumer`）+ 路由（官方 XpYd 代理，或客户端两段式 `do_remote_prefill/do_remote_decode`）；认准 NixlConnector，PyNcclConnector 已移除别抄旧教程。
4. **实验一**：同一负载跑聚合 vs 解耦，判定线绑 TPOT P95（≥2 倍确认互扰，3-5 倍为经验区间）；TTFT 略升、吞吐不升是预期，不是 bug。
5. **实验二**：固定总卡数扫 P:D 配比，goodput 倒 U 曲线找平台，与 7.5 公式初值互相校准。
6. **排错顺序**：网络（side channel、UCX 后端、端口）→ 版本 → 配置（lease、failure policy）；NCCL 变量对 NixlConnector 无效，配 UCX_*。
7. **决策**：高并发 + 严格 SLO + 长 prompt 混合才值得；小规模、求吞吐、无高速网都不该解耦。
