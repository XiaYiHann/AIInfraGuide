vLLM 的启动参数有几百个，但真正影响日常性能的不过一二十个。这一节的目标不是抄一份参数手册，而是建立一张"**症状 → 旋钮 → 机制 → 副作用**"的表：每个旋钮改变的是三样东西之一——**KV 池的大小**（内存类）、**每一步的形状**（调度类）、**kernel 的执行路径**（执行类）。所有默认值都锚定 vLLM 0.26.0 源码，并在本机（2×RTX 6000D，Qwen2.5-Math-7B）dump 了一份解析后的实际默认值（§3）——注意，默认值会按 GPU 显存和入口（离线 `LLM` vs API server）分叉，只看文档不看源码会拿错默认值。

## 1. 读前对齐：配置改变哪三样东西

回看 3.3/3.4/3.5 的结论，引擎的运行状态其实由三个量决定：**KV 池有多大**（显存划分的结果）、**每一步装多少**（预算与队列）、**forward 怎么执行**（编译与图捕获）。配置旋钮就是分别拧这三个量：

| 类别 | 拧的量 | 代表旋钮 |
| --- | --- | --- |
| 内存类 | KV 池大小 | `gpu_memory_utilization`、`max_model_len`、`kv_cache_dtype`、`block_size`、`quantization` |
| 调度类 | 每步形状 | `max_num_batched_tokens`、`max_num_seqs`、`enable_prefix_caching`、`async_scheduling`、`--no-scheduler-reserve-full-isl` |
| 执行类 | 执行路径 | `enforce_eager`（关 CUDA Graph）、`--compilation-config`（图尺寸桶）、`--tensor-parallel-size`、Model Runner 版本 |

调优的基本纪律：**先确认瓶颈在哪个量，再拧对应类别的旋钮**。池子装不下（KV usage 常 95%+）却去调 batch size，或者池子很空却去调显存比例，都是在拧错的螺丝。

## 2. 三组旋钮逐一拆解

### 2.1 内存类：KV 池大小

**`gpu_memory_utilization`（默认 0.92，`config/cache.py:68`）**

KV 池 =（该比例 × 总显存 − 权重 − profile 测出的激活峰值），公式推导见 3.4 §3。旋钮语义是"**允许 vLLM 吃到显存的多少比例**"，不是"KV 池占多少"。

- 调高（0.92→0.97）：池子变大，并发上限变高；但 profile 峰值（含 CUDA Graph 内存）是测出来的不是估算的，超过真实峰值会直接 OOM 在 profile_run 阶段。
- 调低（0.92→0.85，本文 3.3/3.4 复现用的就是 0.85）：池子变小，但给同卡上的其他进程（比如另一个 serve）留余地。
- **副作用**：它是启动时定一次的值，运行期不可热改；改完要重启。

**`max_model_len`（默认 = 模型上限，如 Qwen2.5 系是 4096）**

注意它**不增加 KV 池**——池子由显存决定，`max_model_len` 只是单请求长度上限。它的真实作用有三个：

1. 决定"Maximum concurrency for X tokens per request"那行日志里的 X（3.3 实测：4,096 token/请求 → 247.13x 并发）；
2. 参与严格准入检查：请求的"全序列"（prompt + 声明的 max_tokens）必须装得下才准入（3.5 §4）；
3. 显存不够时会**被自动下调**并同步给 worker（`vllm/v1/engine/core.py:292-299`，3.4 §2 讲过）——你传的 32768 可能实际按 8192 跑。

⚠️ 把它设得比模型 RoPE 上限大（如 Qwen2.5 传 6000）会直接报错（本文实测）；硬要用 `VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` 越过，相对位置编码会出 NaN，绝对位置编码会越界崩溃——这个环境变量名本身就写着"extreme caution"。

**`kv_cache_dtype`（默认 `auto`，`config/cache.py:76`）**

`auto` 跟随模型 dtype（bf16 模型 → KV 也是 bf16）。设成 `fp8`（或 `fp8_e4m3`/`fp8_e5m2`）后每 token 的 KV 字节数减半，**同样的显存池子装得下约 2 倍的 token 数**，并发上限近似翻倍。代价是 KV 被量化，精度有轻微损失（长上下文的 logprob 漂移更明显）。这是"用一点精度换一倍并发"的旋钮，池子是瓶颈时的第一选择。

**`block_size`（默认 16，`config/cache.py:49` 为 `None` 由后端解析）**

KV 块的 token 粒度。所有账本操作（分配、prefix 命中、释放）都以块为单位（3.3 §6）：块越大，碎片浪费越小（一个请求最多浪费 <block_size 个 token），但 prefix cache 的命中粒度越粗（最后不满一块的 token 不算命中——3.3 实测 68-token prompt 只命中 64）。不同 attention 后端要求不同的对齐（`uniproc_executor.py:71` 的 `update_block_size_for_backend` 会在启动时按后端修正它），所以这个旋钮**一般不用动**，动之前先确认你的 attention 后端支持。

### 2.2 调度类：每步的形状

**`max_num_batched_tokens`（默认按显存分叉：≥70GiB 且非 A100 的卡，离线 `LLM` 16384 / API server 8192；小卡 8192 / 2048。源码：`engine/arg_utils.py:2431 get_batch_defaults`）**

这是调度类里最重要的旋钮：每 step 的 token 预算上限（3.5 §2）。

- 调大：prefill 每步能塞下更大的 chunk，长 prompt 的 TTFT（首 token 延迟）更低；但单步时间变长，decode 请求这一步的间隔被拉长（step 里 prefill 和 decode 共享预算，3.5 §5 算例）。
- 调小：prefill 拆得更碎，单步更短更均匀，decode 的 ITL（token 间隔）更稳；代价是 prefill 总步数变多。
- **副作用**：budget 直接影响 CUDA Graph 的 capture 尺寸桶和 async scheduling 的在飞 KV（`max_concurrent_batches × max_num_batched_tokens`，`config/vllm.py:532`，3.4 §5）。

**`max_num_seqs`（同 `get_batch_defaults` 分叉：大卡 1024，小卡 256）**

同时在场的请求数上限（`max_num_running_reqs`）。注意它是**上限**不是目标：实际并发由 KV 池容量约束（池子只装得下 300 个请求时，1024 和 300 没区别）。真正的常见错误是反方向——小池子 + 大 `max_num_seqs` 不会变快，只会让更多请求"准入后挤在一起"（严格准入下其实进不来，3.5 §4）。

**`enable_prefix_caching`（默认 True，`config/cache.py:93`）**

3.4 §6 讲过零开销机制，这里讲什么时候该关：prefix cache 的块会被淘汰（LRU 式，`block_pool.py:585`），当你的流量**前缀几乎不重复**（每请求全新 prompt）且池子紧张时，缓存块占用池子、频繁淘汰、还带来哈希计算，收益趋近于零。判断依据就是 stats 行里的 `Prefix cache hit rate`（3.5 §6 日志实测过 `0.0%` 的场景）——长期接近 0 且显存紧张时可以关。

**`async_scheduling`（默认 `None` → 自动解析为**开**，`config/vllm.py:1059-1107`）**

3.4 §5 的机制：GPU 上"在跑 1 + 排队 1"，CPU 调度藏进 GPU 执行时间。0.26.0 的默认行为值得单独强调：**显式传 True 时不兼容会报错，默认 None 时不兼容会静默降级为关**（`config/vllm.py:1033-1107`）。不兼容场景：pooling 模型、EAGLE/MTP/NGram/DSpark 之外的投机解码、不支持的 executor 后端、ROCm DeepEP HT DBO。想关用 `--no-async-scheduling`。

**`--no-scheduler-reserve-full-isl`（默认开，`config/scheduler.py:140`）**

3.5 §4/§6 的实测旋钮：开 = 严格全序列准入（默认，waiting 队列吸收溢出，抢占几乎不触发）；关 = 首 chunk 装得下就准入（吞吐可能更高，但会触发抢占重算）。**生产默认不要关**，除非你用 3.5 的实验方式确认过重算成本可接受。

### 2.3 执行类：forward 怎么走

**`enforce_eager`（默认 False，`config/model.py` 经 `engine/arg_utils.py:555`）**

True = 跳过 torch.compile 和 CUDA Graph，每步 eager launch。启动时间立减（3.4 §8：24.78 s 的 init 里大头是抓 102 张图，enforce_eager 下这段归零），代价是 decode 失去图加速（3.4 §4：小 batch decode 的 kernel 启动开销直接暴露）。**调试、profile、快速验证用它；生产别用。**

**`--compilation-config`（cudagraph_capture_sizes 等）**

3.4 §4 讲过按尺寸桶抓图。显存紧张时桶多 = 图占的显存多（profile 阶段会算进去，`gpu/model_runner.py:705`）；缩短启动时间就调小桶数。

**`--tensor-parallel-size` / `--pipeline-parallel-size`**

多卡切模型。TP 下每个 rank 各存 1/TP 的 KV（池子总量不变，单卡占用下降），代价是每步的 all-reduce 通信（`multiproc_executor.py` 的 WorkerProc，3.3 §3）。**能单卡拉全就别上 TP**：7B bf16（14.19 GiB）在 85GB 卡上单卡绰绰有余（3.3 实测），上 TP=2 只是白白多一跳通信。

**Model Runner 版本（`VLLM_USE_V2_MODEL_RUNNER`，`config/vllm.py:550`）**

0.26.0 默认 V2（启动日志 "Using V2 Model Runner"，3.3 实测）；V1 runner 保留用于回退和兼容性。这个变量一般不用动，排障时可以试试 V1 对比行为。

## 3. 实测：本机解析后的默认值

在 RTX 6000D（85GB）上用 `EngineArgs(model=...).create_engine_config()` 直接 dump 解析结果（不加载权重，2026-08-19）：

| 配置 | 解析值 | 出处 |
| --- | --- | --- |
| `max_num_batched_tokens` | 2048（无 usage context 时）；**16384**（离线 `LLM` 路径，≥70GiB 卡） | `arg_utils.py:2431` |
| `max_num_seqs` | 128（无 context）；**1024**（离线 `LLM` 路径） | 同上 |
| `block_size` | 16 | `config/cache.py:49` → 后端解析 |
| `gpu_memory_utilization` | 0.92 | `config/cache.py:68` |
| `enable_prefix_caching` | True | `config/cache.py:93` |
| `kv_cache_dtype` | auto | `config/cache.py:76` |
| `async_scheduling` | **True**（None 自动解析） | `config/vllm.py:1059-1107` |
| `scheduler_reserve_full_isl` | True | `config/scheduler.py:140` |
| `max_num_partial_prefills` | 1（0.26.0 强制，设其他值报错） | `arg_utils.py:2405-2411` |
| `max_model_len` | 4096（Qwen2.5-Math-7B 模型上限） | 模型 config.json |
| `enforce_eager` | False | `arg_utils.py:555` |
| `tensor_parallel_size` | 1 | 默认 |

两个最容易踩的坑：

1. **默认值分叉**：`max_num_batched_tokens`/`max_num_seqs` 随"入口"（离线 `LLM` vs API server）和"显存档位"（≥70GiB 与否）走不同分支。看 3.3 实测的 `16384/1024` 时别以为是全局默认——那是"离线 LLM + 85GB 卡"这一支。
2. **`async_scheduling` 默认开**：很多旧资料（以及直觉）以为它默认关；0.26.0 的启动日志会明确打 `Asynchronous scheduling is enabled.`（`config/vllm.py:1109`），以日志为准。

## 4. 症状 → 旋钮：调优决策表

| 症状（怎么观测） | 先查什么 | 拧哪个旋钮 | 副作用/边界 |
| --- | --- | --- | --- |
| 启动 OOM（profile 阶段挂） | 日志里的权重 + 激活峰值 | `gpu_memory_utilization` 调低；或 `kv_cache_dtype=fp8` | 池子变小，并发降 |
| 运行中偶发 OOM | 同卡是否有其他进程吃显存 | `gpu_memory_utilization` 调低（3.3 复现用 0.85 留余量） | 同上 |
| 并发装不下（stats 行 `GPU KV cache usage` 长期 95%+，waiting 排队长） | 池子大小 vs 单请求 KV 占用 | ① `kv_cache_dtype=fp8`（池子近似翻倍）② 换更大显存的卡/加卡 ③ 降 `max_model_len` | fp8 有精度损失；降 max_model_len 伤长请求 |
| TTFT 高（长 prompt 首 token 慢） | prefix cache hit rate、budget 是否被调小 | ① 确认 prefix caching 开且命中 ② `max_num_batched_tokens` 调大 | 大 budget 拉长 decode 的 step 间隔 |
| ITL 抖（decode token 间隔不稳） | step 里是否混着大 prefill chunk | `max_num_batched_tokens` 调小，把 prefill 拆碎 | prefill 总步数变多 |
| 启动太慢 | 日志 "init engine ... took X s (compilation: Y s)"（`core.py:340`） | `--compilation-config` 调小 `cudagraph_capture_sizes`；调试场景 `enforce_eager` | 图桶变少 → decode padding 到更大桶，略慢 |
| 想同卡多实例 / 留显存给别的服务 | — | `gpu_memory_utilization` 按比例切分 | 各自池子变小 |
| 流量前缀高度重复（多轮对话/RAG） | stats 行 prefix cache hit rate | 保持 prefix caching 开；必要时调大 `block_size` 附近的池子 | 命中粒度 = 块粒度，尾部 <16 token 不算命中 |
| 抢占太多（`vllm:num_preemptions_total` 持续增长，3.5 §6 的指标） | 是否误关了严格准入、池子是否真的不够 | 恢复 `--scheduler-reserve-full-isl`；扩池子（fp8/显存） | 重算成本 = 整个 prompt 再 prefill 一遍 |

⚠️ **错误做法：一次拧很多旋钮。** 每个旋钮都有副作用（上表最后一列），一次改三个参数，性能变化时你分不清是哪个的功劳/锅。正确流程：改一个 → 用同一负载复测（stats 行的 Running/Waiting/KV usage 是免费的观测点）→ 记录 → 再改下一个。

## 📝 总结

三句话记忆：

1. **配置分三类**：内存类拧 KV 池大小（`gpu_memory_utilization`、`kv_cache_dtype`、`max_model_len`），调度类拧每步形状（`max_num_batched_tokens`、`max_num_seqs`、prefix caching、async scheduling），执行类拧 forward 路径（`enforce_eager`、图桶、TP）。
2. **默认值会分叉**：batch 默认按"入口 × 显存档位"走（离线大卡 16384/1024），`async_scheduling` 在 0.26.0 默认开——以启动日志为准，别背文档。
3. **先定位瓶颈再拧旋钮**：KV usage 高 → 内存类；TTFT/ITL 问题 → 调度类；启动慢/decode 慢 → 执行类。一次只改一个，用 stats 行复测。
