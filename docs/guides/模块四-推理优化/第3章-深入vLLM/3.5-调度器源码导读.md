3.3 给了调度器一个骨架："一个循环处理 prefill 和 decode"。这一节把 `schedule()` 拆开逐段读：**每一步的 token 预算怎么分、waiting 和 running 两个队列怎么推进、抢占到底由谁触发、被抢占的请求发生什么**。读完你会发现一个反直觉的结论：vLLM V1 的抢占（recompute）在默认配置下几乎是一条"死"的安全网——真正让请求排队的是更上游的准入控制，而抢占只在准入被刻意放松（或 speculative decoding 等场景需要额外预留块）时才会触发。这个结论不是猜的，是本文最后用 Prometheus 计数器实测出来的（§6）。

## 1. 读前对齐：调度器手里有什么

Scheduler 对象（`vllm/v1/core/sched/scheduler.py:70`）是 EngineCore 进程里唯一的决策者，它的全部状态：

| 状态 | 数据结构 | 锚点 |
| --- | --- | --- |
| waiting 队列 | 按策略建的队列，默认 **FIFO**（`SchedulingPolicy`，也可 PRIORITY） | `sched/request_queue.py:13`（策略枚举）、`:201`（`create_request_queue`）；`scheduler.py:183`（`self.waiting`） |
| running 队列 | 普通 `list[Request]` | `scheduler.py:186`（`self.running`） |
| KV 账本 | `KVCacheManager`（块分配 + prefix 命中，3.3 §6） | `kv_cache_manager.py:114` |
| 请求状态机 | `RequestStatus`：WAITING → RUNNING → FINISHED_\*，外加 PREEMPTED | `vllm/v1/request.py:343` |
| 每步预算 | `token_budget`（不是成员变量，`schedule()` 里的局部量） | `scheduler.py:445` |

`RequestStatus` 的完整取值值得看一眼（`request.py:343-358`）：`WAITING`、`WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR`、`WAITING_FOR_REMOTE_KVS`、`WAITING_FOR_STREAMING_REQ`、`RUNNING`、`PREEMPTED`、`FINISHED_STOPPED`、`FINISHED_LENGTH_CAPPED`、`FINISHED_ABORTED`、`FINISHED_IGNORED`、`FINISHED_ERROR`。除了 PREEMPTED 和四个 FINISHED，其余"等待"变体在本文主线里不展开。

一个重要的心智模型：**调度器每一步做两件事——给 running 队列"续命"，给 waiting 队列"开门"。前者先做，后者后做，共享同一个 token 预算。**

## 2. schedule() 的五块结构

`schedule()` 入口在 `scheduler.py:425`，函数注释直接写明设计意图："no prefill phase / decode phase"（没有 prefill 阶段和 decode 阶段的划分）。五块：

```python
# vllm/v1/core/sched/scheduler.py（节选 + 重排，非逐字源码）
def schedule(self) -> SchedulerOutput:
    # ① 预算初始化（:445）
    token_budget = self.max_num_scheduled_tokens   # 默认 = max_num_batched_tokens
    # ② running 循环（:471-605）：给已入场的请求续命
    while req_index < len(self.running) and token_budget > 0:
        request = self.running[req_index]
        num_new_tokens = 1 if 该请求在decode else min(剩余prompt, token_budget)  # :509 chunked prefill
        new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens)  # :564
        if new_blocks is None:
            # ③ 抢占循环（:575-605）：FCFS 下 pop running 队尾
            preempted_req = self.running.pop()
            self._preempt_request(preempted_req, ts)   # :1212
            if preempted_req == request: break         # 没得抢了，本请求这步不跑
        ...
    # ④ waiting 循环（:669-1011）：给新请求开门
    while (self.waiting or self.skipped_waiting) and token_budget > 0:
        if len(self.running) >= self.max_num_running_reqs: break   # :671-672
        request = request_queue.peek_request()
        computed_blocks, num_computed = self.kv_cache_manager.get_computed_blocks(request)  # prefix 命中
        num_new_tokens = min(剩余prompt - 命中, token_budget)
        new_blocks = self.kv_cache_manager.allocate_slots(
            request, num_new_tokens,
            full_sequence_must_fit=self.scheduler_reserve_full_isl,  # :944 准入控制，见 §4
        )
        if new_blocks is None:
            break        # :953-956 注意：是 break，不是抢占！
        request_queue.pop_request()
        self.running.append(request)   # :1011 入场
    # ⑤ 组装输出
    return SchedulerOutput(...)        # v1/core/sched/output.py:191
```

五个要点：

1. **预算是 token 数，不是请求数**（①）。`max_num_scheduled_tokens` 默认等于 `max_num_batched_tokens`（我们实测 16,384，见 3.3）。一个 step 里所有请求的新 token 加起来不超过它。
2. **decode 请求每步只花 1 token 预算**（②）。所以 100 个 decode 请求 + 1 个 8,000-token 的 prefill chunk，预算分配是 100 + 8,000 ≤ 预算上限才成立。
3. **chunked prefill 就藏在 ② 的 `min()` 里**（:509）。一个 12,000-token 的 prompt、预算 1024，会拆成 12 个 chunk 跨 12 个 step 完成——长 prompt 不会独占一个 step。
4. **waiting 循环分配失败就 `break`，不抢占**（④）。这是全文最关键的一行，§4 展开。
5. **prefix cache 命中发生在 ④ 的入场检查里**：`get_computed_blocks` 先算出这个请求有多少 token 已经有缓存块（3.3 §6 的 `find_longest_cache_hit`），`allocate_slots` 只为剩余部分分配。命中 = 少分配 = 更容易准入。

step 执行完之后，`update_from_output`（`scheduler.py:1589`）做收尾：逐请求检查停止条件（stop token / 达到 max_tokens），把终态请求标成 `FINISHED_*`、释放它的块（`kv_cache_manager.py:506`）、把完成的块注册进 prefix cache（`cache_blocks`，`kv_cache_manager.py:689`），并把输出交给前端 detokenize。

## 3. 抢占：谁触发、抢谁、发生什么

**触发者只有一个：running 循环（②/③）。** 场景：一个已经在 running 的请求，下一步需要新块（decode 每 16 token 需要 1 个新块，prefill chunk 需要一大片），但空闲块不够 → 进入抢占循环。

FCFS 策略下的抢占规则（`scheduler.py:599-603`）：**`preempted_req = self.running.pop()`——永远抢 running 队尾**（最晚入场、优先级最低的那个）。抢下之后调用 `_preempt_request`（`scheduler.py:1212`），逐行看它做了什么：

```python
# vllm/v1/core/sched/scheduler.py（节选自 _preempt_request, :1212）
def _preempt_request(self, request: Request, timestamp: float) -> None:
    assert request.status == RequestStatus.RUNNING
    self._free_request_blocks(request)          # 释放全部 KV 块
    request.status = RequestStatus.PREEMPTED
    request.num_computed_tokens = 0             # 计算进度清零
    request.num_preemptions += 1                # 计数（Prometheus 指标的来源）
    self.waiting.prepend_request(request)       # 插回 waiting 队首
```

三句话总结被抢占者：

1. **KV 块全部释放，没有任何数据被搬去 CPU**——V1 的抢占是**重算**（recompute），不是 V0 的 swap。
2. **`num_computed_tokens` 清零**——回来时整个 prompt 重新 prefill（如果 prefix cache 里还有它的块，能命中一部分，见 §6 对照实验）。
3. **`prepend` 到 waiting 队首**——FCFS 下它优先于所有后来者重新入场，保证不会饿死。

触发者自己呢？抢占循环是"抢一个、试一次"：每抢一个就重新尝试给触发者分配，直到成功；如果抢到了触发者自己（`preempted_req == request`，:596），说明池子连它自己都装不下——它本步出局，留在 running 里等下一步（或下一步被别人抢）。

## 4. 为什么默认配置下抢占几乎不触发

§3 说了抢占只发生在 running 循环。那么问题来了：running 里的请求什么时候会"要块而块不够"？答案是——**默认配置下，调度器根本不会把请求超卖进场**。两层机制共同保证：

**第一层：准入控制（waiting 循环）。** `allocate_slots` 的 `full_sequence_must_fit` 参数接的是 `self.scheduler_reserve_full_isl`（`scheduler.py:944`），它来自 `SchedulerConfig.scheduler_reserve_full_isl`，**默认 True**（`config/scheduler.py:140`）。这个开关的 docstring 写得很清楚：

> "If True, the scheduler checks whether the full input sequence length fits in the KV cache before admitting a new request, rather than only checking the first chunk. **Prevents over-admission and KV cache thrashing with chunked prefill.**"

翻译：waiting 请求入场时，检查的不是"第一个 chunk 装不装得下"，而是"**整个序列**（prompt + 声明的 max_tokens）装不装得下"。装不下就不入场——`new_blocks is None → break`，请求老实留在 waiting 队列里排队。**没有超卖，就没有后续的"要块而块不够"，也就没有抢占。** 这是 waiting 循环 `break` 而不抢占的原因：排队本身就是设计行为，不是失败。

**第二层：prefill 串行化。** 0.26.0 里 `max_num_partial_prefills` 被强制为 1（`engine/arg_utils.py:2405-2411`，设成别的值直接抛 `NotImplementedError: Concurrent Partial Prefill is not supported`）。每个 step 至多一个请求在 prefill chunk，其余请求只消耗 decode 的 1 token 预算。prefill 被串行化后，池子的水位变化是平缓的，running 请求的增量块需求（decode 每 16 token 才 1 块）几乎总能被满足。

两层机制合起来，默认配置下的资源管理策略其实是：**宁可让请求在 waiting 里等，也不抢占重算**。抢占保留给这些场景：

| 场景 | 为什么需要额外块 |
| --- | --- |
| 显式 `--no-scheduler-reserve-full-isl` | 准入放宽成"首 chunk 装得下就进"，超卖后必然有人要块而块不够 |
| Speculative decoding | 每个 running 请求额外预留 draft 验证的 lookahead 块（`allocate_slots` 的 `num_lookahead_tokens`） |
| 多模态 encoder 输入 | 图像 embedding 的块在序列中段才需要（`encoder_cache_manager.can_allocate`，`encoder_cache_manager.py:123`） |
| KV connector 异步加载 | 传输期间块被预留（`_inflight_prefill_reserved_blocks`，`scheduler.py:927-931`） |

## 5. 小数字算例：三步推一遍

设：block_size=16，KV 池 = 100 块（1,600 token），`max_num_batched_tokens`（预算）= 1,024，`max_num_seqs` = 不限（设 16）。3 个请求同时到达，prompt 各 600 token（=38 块），max_tokens=16，**严格准入开**（默认）。总需求 3×616 = 1,848 token > 1,600，池子装不下所有请求。

| step | running 循环 | waiting 循环 | 池内块数 |
| --- | --- | --- | --- |
| 1 | 空 | R1：整 prompt 600 ≤ 预算 1,024，且 600+16 全序列 ≤ 1,600 → 入场，分 38 块，预算剩 424；R2：首 chunk min(600, 424) = 424 token = 27 块，全序列检查通过（38 块 ≤ 剩余 62 块）→ 入场，预算 0 | 65 块 |
| 2 | R1 decode 1 token（预算 1）；R2 续 chunk min(600−424, 1,023) = 176 token = 11 块 | R3：全序列 616 token = 39 块，剩余 100−76=24 块 < 39 → **不入场，break（不抢占）** | 76 块 |
| 3 | R1、R2 各 decode 1 token | R3 仍不入场 | 76 块 |

R1 达到 max_tokens=16 结束，释放 38 块 → R3 全序列检查通过，入场。**整个过程 0 次抢占，R3 只是等了 15 个 step。** 把严格准入关掉（`--no-scheduler-reserve-full-isl`），step 1 的 R2 检查从"38 块 ≤ 62 块"变成"27 块 ≤ 62 块"——结论没变，但 R3 也会在 step 1 入场（首 chunk 27 块 ≤ 剩余）；三个请求全部在场后，池子需求 3×39=117 块 > 100 块，step 4 起某个 running 请求的块需求就会失败 → 抢占循环 pop 队尾 → 重算。§6 的实测就是把这个算例放大到 12 个请求。

## 6. 实测：把抢占逼出来

**一句话结论：默认配置下 12 个并发大请求 0 次抢占；关掉严格准入后，同样负载触发 2 次抢占（recompute），Prometheus 计数器 `vllm:num_preemptions_total` 从 0 变 2。**

实验设置（2026-08-19，GPU 1，vLLM 0.26.0 `vllm serve`，Qwen2.5-Math-7B-Instruct）：

| 项 | 值 |
| --- | --- |
| `--gpu-memory-utilization` | 0.20 → KV 池 **37,504 token = 2,344 块**（日志 `kv_cache_utils.py:2177`） |
| `--max-model-len` / `--max-num-batched-tokens` / `--max-num-seqs` | 4096 / 1024 / 16 |
| 负载 | 12 个**并发**请求，每请求 3,800-token 互不相同的随机 prompt + `max_tokens=250`；总需求 12×4,050 = 48,600 token ≫ 37,504 |
| 观测 | `/metrics` 的 `vllm:num_preemptions_total` 计数器 + stats 行（`loggers.py:310`） |

结果：

| 配置 | 抢占次数 | 负载中 stats 行 | 完成时间 |
| --- | --- | --- | --- |
| A：默认（严格准入） | **0** | `Running: 3 reqs, Waiting: 0 reqs, GPU KV cache usage: 31.6%` | 12/12 全部完成，11.4 s |
| B：`--no-scheduler-reserve-full-isl` | **2**（`vllm:num_preemptions_total = 2.0`） | `Running: 9 reqs, Waiting: 3 reqs, GPU KV cache usage: 95.2%` | 12/12 完成，11.5 s；后 3 个请求 11.4–11.5 s，前 9 个 7.1–8.5 s |

三个读法：

1. **A 组的水位只有 31.6%**——严格准入把同时 in-flight 的请求压到 3 个左右，池子远没满，waiting 队列吸收了全部溢出，抢占代码路径一次都没走到。
2. **B 组水位 95.2%、Running 9 + Waiting 3**——准入放宽后 9 个请求同时压满池子，9 个 running 请求中有 2 个被抢过重算（后 3 个请求的完成时间明显拉长就是 recompute 的成本）。
3. **抢占不丢输出，只花延迟**：B 组 12 个请求的输出都完整返回，被抢的请求只是从 `num_computed_tokens=0` 重新 prefill 了一遍（它的 3,800-token prompt 若留在 prefix cache 里，重算还能命中一部分——下一组对照实验直接展示了这一点）。

**对照实验（prefix cache 如何消灭抢占压力）**：同一小池（37,504 token），把 12 个请求的 prompt 换成**同一个** 3,501-token 文本（`/tmp/vllm_preempt_repro.py` 第一版，`gpu_memory_utilization=0.20`、预算 2,048、`max_tokens=8`）：12 个请求**0.5 s 全部完成，0 次抢占**。原因：第一个请求算出的 218 个完整块（3,501 ÷ 16 = 218）被其余 11 个请求共享（`ref_cnt` 机制，3.4 §6），池内总占用 ≈ 218 + 11 块，远低于池容量。**需求从 12×3,501 = 42,012 token 降到约 4,100 token——prefix cache 把"装不下"变成了"轻松装下"，抢占压力随之消失。**

📌 表 A/B 为本文 2026-08-19 实测（`/tmp/vllm_serve_preempt4.log`、`/tmp/vllm_serve_preempt6.log`、`/tmp/vllm_preempt_repro.log`），计数器来自 vLLM 0.26.0 内置 Prometheus 指标（`v1/metrics/loggers.py:662`）。对照实验的 0.5 s 完成时间是离线 `LLM()` 路径，与 serve 路径的 11.4 s 不直接可比（负载不同）。

## ⚠️ 常见误读

1. **"`max_num_batched_tokens` 是 batch 大小"** —— 错。它是每 step 的 **token 预算**；同时在场的请求数由 `max_num_seqs` 和 KV 池容量共同约束（§1、§2）。
2. **"waiting 请求会把 running 请求挤出去（抢占）"** —— 错。抢占只发生在 running 循环；waiting 循环分配失败是 `break` 排队，不是抢占（§2 第 4 点、§4）。
3. **"抢占 = 把 KV 换出到 CPU 内存"** —— 那是 V0 的 swap。V1 的抢占是**重算**：块释放、进度清零、回 waiting 队首（§3）。
4. **"FCFS = 全局严格先来后到"** —— 近似对但不完整：每 step 先服务 running 队列，waiting 请求必须等 running 的预算余量；被抢占的请求用 `prepend` 插回队首保公平（§2、§3）。
5. **"池子满了就一定会抢占"** —— 不一定。严格准入（默认）让池子满之前就没有新请求进场；满载 + 无新块需求 = 平稳 decode，不发生抢占（§4、§6 A 组）。

## 📝 总结

三句话记忆：

1. **`schedule()` = 预算分配 + 双队列推进**：running 先续命（decode 每请求 1 token，prefill 按 chunk），waiting 后开门（prefix 命中后只为剩余块分配），共享 `max_num_batched_tokens` 这个 token 预算。
2. **抢占只由 running 循环触发**，FCFS 下永远抢队尾；被抢者块全释放、进度清零、回 waiting 队首——重算，不是 swap。
3. **默认配置下抢占几乎不触发**：严格全序列准入（`scheduler_reserve_full_isl=True`）+ prefill 串行化（`max_num_partial_prefills` 强制 1）让 waiting 队列吸收溢出；实测 12 个并发大请求 0 次抢占，关掉严格准入才测出 2 次。
