3.1–3.6 把 vLLM 从安装到调度器源码读完，但选型时绕不开两个问题：**什么时候该用 SGLang 或 TensorRT-LLM？vLLM 慢在哪、快在哪？** 一句话结论：到 2026 年，三家的**表面功能已经趋同**（continuous batching、paged KV cache、FP8 量化、结构化输出都齐了），真正的分野是**架构赌注**——vLLM 赌"最宽的模型/硬件覆盖 + 可预期的性能"，SGLang 赌"前缀复用与 MoE 高并发"，TensorRT-LLM 赌"NVIDIA 硬件上的编译后极限性能"。选哪个不取决于"谁最快"（答案是：看你的流量形状），而取决于你的**模型更新频率、流量前缀重复度、硬件约束和运维带宽**（§5 决策表）。

## 1. 读前对齐：先分清"功能趋同"和"架构分野"

**"趋同"指的是能力清单，"分野"指的是实现路线。** 三家现在都能做的事（2026 年中口径）：

| 能力 | vLLM | SGLang | TensorRT-LLM |
| --- | --- | --- | --- |
| Continuous batching（迭代级批处理） | ✅ | ✅ | ✅（inflight batching） |
| Paged KV cache | ✅（PagedAttention） | ✅（RadixAttention） | ✅（paged KV） |
| FP8 量化推理 | ✅ | ✅ | ✅（另有 FP4/INT4 AWQ/INT8 SmoothQuant） |
| 投机解码 | ✅（MTP/DFlash/DSpark/EAGLE 等，见 5.6–5.8） | ✅（EAGLE-3、MTP、DFlash 等） | ✅（EAGLE-3 动态树、MTP 等） |
| 结构化输出（约束解码） | ✅（Outlines/XGrammar 等集成） | ✅（SGLang 语言原生，调度器层集成） | ✅ |

📌 能力清单为 2026 年中的第三方对比与各家官方文档汇总（见参考资料），三家发版节奏都很快（每月小版本），具体到某个版本请以各自 release notes 为准。

**分野**在四件事上：KV 前缀复用怎么做（§4.1）、调度器用什么语言跑在哪（§4.2）、执行路径是解释式还是编译式（§3.3）、以及各自的"主场"流量形状（§5）。

## 2. 三种架构赌注

用一个类比（只此一个）：三家像三种**后厨模式**——

- **vLLM = 标准中央厨房**：什么菜系（模型）都能做、什么灶具（硬件）都能装，流程标准化（PagedAttention + 统一调度），出品稳定可预期。单道菜不一定最快，但"来了就能做"。
- **SGLang = 带预制菜站的中央厨房**：前缀复用（RadixAttention）相当于预制菜台——高频共用的"备菜"（system prompt、多轮历史、RAG 检索段）只做一次，所有请求直接领用；对高重复、高并发的流量尤其赚。
- **TensorRT-LLM = 套餐预制模式**：开餐前把整条流水线固化（编译成 `.engine`：算子融合、kernel 自动调优、CUDA Graph 全覆盖），上菜速度最快，但**换菜单要重新预制**（模型更新后重新编译，分钟到几十分钟级）。

这个类比对应的真实机制分别落在 §3 的三家拆解里。

## 3. 逐家拆解：vLLM、SGLang、TensorRT-LLM

### 3.1 vLLM：宽度与可预期性

3.1–3.6 已经拆过它的内部（V1 引擎三层进程、统一调度、零开销 prefix cache、CUDA Graph、配置旋钮），这里只说**对比视角**下它的定位：

- **模型覆盖最广**：400+ 架构族注册在 model registry，新模型接入通常是几十到几百行 Python 类（第三方口径）；HuggingFace 模型一个 flag 就能换。
- **硬件覆盖最广**：NVIDIA、AMD ROCm、Google TPU、Intel Gaudi 都有后端（这是另两家没有的）。
- **投机解码全家桶**：本博客 5.6–5.8 的 MTP、DFlash、DSpark 三条线在 vLLM 里都有落地路径（`method="mtp"` / DFlash / `method="dspark"`），其中 DSpark 还强制走 Model Runner V2（`config/vllm.py:550`，3.3 讲过）。
- **性能的可预期性**：Python 调度器 + torch 执行路径的开销是"透明的"——你能用 nsys/日志把它定位出来（3.5 的 stats 行、3.4 的启动日志）；Model Runner V2（0.26.0 默认，3.3 实测）是 vLLM 团队近一年对执行路径的大重写，第三方基准里"vLLM 变慢/变快"的结论常常取决于**是否跑在 MRV2 上**——看到不带 vLLM 版本号的基准数字直接打个问号。
- **短板**（第三方口径）：小 batch decode 的 Python 调度每步开销（有第三方测得 200–500 µs/step 量级）；纯 NVIDIA 单模型、追求极限吞吐的场景，编译式引擎能压过它 15–25%（§4.3 的数据）。

### 3.2 SGLang：前缀复用与 MoE 主场

- **RadixAttention**：KV 前缀缓存组织成**基数树（radix tree）**，按 token 序列键控，跨请求自动发现并复用共享前缀，无需手动配置（对照 vLLM 的块级哈希复用，差异深挖见 §4.1）。这是它流量形状优势的来源：**多轮对话、agent 重放长 system prompt、RAG 重复检索段**这类前缀重复度高的负载。
- **MoE/专家并行**：第三方基准里 DeepSeek 系 MoE 模型上 SGLang 的优势最明显（有"3.1× 于 vLLM"的口径，见 §4.3 数据表），其 expert parallelism 实现被普遍认为是生产规模 MoE 服务的首选之一。
- **结构化生成**：SGLang 前端语言（SGL）把"生成 → 调用工具 → 再生成"的多步逻辑写成程序，约束解码在调度器层原生集成，第三方评测里结构化输出吞吐领先。
- **投机解码**：EAGLE-3、MTP（Gemma 4 MTP）、DFlash（本博客 5.7 的 SGLang PR）都在支持列表里。
- **短板**：硬件面窄于 vLLM（基本就是 NVIDIA 系）；模型接入速度偶尔落后 vLLM 半拍；基准结论高度依赖"你的 prompt 前缀重复率"——**前缀不重复的负载上它不必然赢**（§4.3 RunPod 那组数据：unique prompt 场景 vLLM 反而领先）。

### 3.3 TensorRT-LLM：编译引擎的极限与代价

- **两条执行路径**（1.x 起"Architected on PyTorch"，两条路并存）：
  1. **编译引擎路径**：HF/NeMo 权重 → 转 TRT-LLM 格式 → `trtllm-build` 编译出 `.engine`（算子融合、kernel 自动调优、CUDA Graph 全程覆盖）。上菜最快，但**模型每更新一次就要重编译**（第三方案例：70B 级模型一次编译约 28 分钟，乘上每周发版次数就是运维成本）。
  2. **PyTorch executor 路径**：免编译、启动快（分钟级），性能介于 vLLM 与编译引擎之间，2026 年成为更多团队的实际选择。
- **调度**：C++ 侧的 Batch Manager 做 inflight batching（新请求逐迭代进入、完成的逐迭代退出），paged KV + `enableBlockReuse`（前缀块复用，C++ API 默认关，需显式打开）；`freeGpuMemoryFraction` 默认 0.9 的语义同 vLLM 的 `gpu_memory_utilization`。
- **性能**：纯 NVIDIA、单模型稳定、追求极限的场景有 15–25% 的稠密模型吞吐优势（第三方 H100 口径）；MoE/FP4/NVFP4 新格式支持通常是**最先落地**的一家（1.3.0rc 里能看到 DeepSeek V4 NVFP4、DSv4 sparse MLA 等条目）。
- **短板**：**基本 NVIDIA-only**；模型转换 + 编译的管线是硬运维成本；社区生态（教程、K8s 部署、多硬件移植）小于 vLLM。

## 4. 关键差异深挖：prefix cache 与调度器

### 4.1 前缀复用：三种组织方式

| 维度 | vLLM（3.3–3.5 源码读过的） | SGLang | TensorRT-LLM |
| --- | --- | --- | --- |
| 结构 | 块级内容哈希 + 字典（`BlockPool`，16-token 块） | 基数树，按 token 序列键控 | 块复用（C++ API `enableBlockReuse`；Python 路径有 Radix 管理） |
| 命中粒度 | 整块（尾部 <block_size 不算命中，3.3 实测 68→64） | 序列前缀（树的公共前缀，理论上可精确到 token 级） | 块级 |
| 跨请求共享 | 共享块 `ref_cnt` 计数（3.4 §6） | 树节点天然共享 | 块复用 |
| 默认状态 | 开（0.26.0 默认 True，`config/cache.py:93`） | 开（核心卖点） | C++ 路径默认关，需显式开 |

**直觉差异**：vLLM 的复用是"哈希表"——相同块内容直接指过去，实现简单、零开销（3.4 §6），但对"部分前缀分叉"（比如同一个 system prompt 后面接不同用户输入）的复用效率取决于块对齐；SGLang 的基数树天然处理分叉——公共前缀只存一份，分叉点之后各自延伸，**前缀重复度越高、分叉越浅，优势越大**。这正是第三方基准里"前缀重复负载 SGLang 赢、unique 负载打平甚至输"的结构化解释。

### 4.2 调度器：三种实现

| 维度 | vLLM | SGLang | TensorRT-LLM |
| --- | --- | --- | --- |
| 语言/位置 | Python，独立 EngineCore 进程（3.3 §2） | Python，自称"零开销 CPU 调度器"（官方文档口径） | C++ Batch Manager（另有 Python executor 路径） |
| 与 GPU 执行的重叠 | async scheduling（默认开，3.4 §5）：CPU 调度藏进 GPU 执行时间 | 调度与执行重叠是其宣称的零开销的一部分 | `enableTrtOverlap`：两 microbatch 并发隐藏 CPU 开销 |
| 可观测性 | stats 行 + Prometheus（3.5 §6 实测过） | Prometheus 指标 | Prometheus 指标（KV 统计、投机解码统计等） |

⚠️ **常见误读："vLLM 用 Python 调度所以天生慢"** —— 不准确。调度开销的**绝对值**有差距，但 vLLM 用 async scheduling（默认开）把大部分 CPU 调度藏进了 GPU 执行时间，且这个开销对**大 prefill、大 batch** 的负载占比很小；对**小 batch 纯 decode** 负载占比才明显。SGLang/TRT-LLM 的语言优势在小 decode 步上更容易体现——这和 §4.3 数据里"70B 大 batch 差距缩到个位数百分比"是一致的。

### 4.3 性能数据（带口径）

📌 以下全部为**第三方独立测试**（H100 为主），非厂商口径；每个数字绑定硬件/模型/版本/负载形状，**方向性参考，迁移到你的硬件前必须自测**（任何基准缺 GPU 型号、引擎版本、并发度中任意一项，可信度直接减半）：

| 来源（2026） | 负载 | 结果 |
| --- | --- | --- |
| PremAI（via TECHSY，2026） | Llama 3.1 8B，H100 | SGLang ≈ 16,200 tok/s vs vLLM ≈ 12,500 tok/s（~29%，归因于 RadixAttention 前缀复用） |
| Spheron（2026-03，早于 vLLM MRV2） | Llama 3.3 70B Instruct FP8，H100 | SGLang 略高 3–5% |
| RunPod（2026） | DeepSeek-R1-Distill-Llama-70B，unique prompt | vLLM 60 tok/s > SGLang 52.7 tok/s |
| RunPod（2026） | 同上，cached-prefix prompt | SGLang 35 tok/s > vLLM 32.8 tok/s |
| cloudai.pt / Inference Engineering（H100） | 70B TP=4 FP8 总吞吐 | vLLM ≈ 2,800 / SGLang ≈ 3,400 / TRT-LLM ≈ 2,900 tok/s |
| Inference Engineering（2026-06） | 稠密模型，H100 | TRT-LLM 比 vLLM 高 15–25%（编译引擎路径） |
| gpuinsights.net（2026-08，案例） | 70B 生产迁移 | TRT-LLM 吞吐 +13%，但每次模型更新多 28 分钟编译 |

版本快照（2026-08 口径）：vLLM 0.24.0（2026-06-30 稳定版；本文 3.1–3.6 分析的本地版本 0.26.0 更新）、SGLang 0.5.14/0.5.15（2026-06）、TensorRT-LLM 1.2.1（2026-04-20 稳定版，1.3.0rc 系列推进中）。**三家都是每月级发版，相对性能可以在一个季度内移动两位数百分比**——本文所有对比数字都是 2026 年中快照。

## 5. 选型决策表

| 你的场景 | 建议 | 理由（对应 §2–§4） |
| --- | --- | --- |
| 默认 / 快速迭代 / 模型经常换 | **vLLM** | 换模型一个 flag；编译管线成本为零；生态最广（§3.1） |
| 多硬件（非 NVIDIA：AMD/TPU/Gaudi） | **vLLM**（基本是唯一选择） | 另两家基本 NVIDIA-only（§3.1/§3.3） |
| 高前缀重复流量：多轮对话、agent、RAG 共享 system prompt | **SGLang** 优先，vLLM 次之 | RadixAttention 的结构优势（§4.1）；vLLM 的块级 prefix cache 也能吃到部分收益（3.5 §6 对照实验） |
| 大 MoE（DeepSeek 系）+ 高并发 + 专家并行 | **SGLang** | EP 实现 + 基准主场（§3.2、§4.3） |
| 结构化输出是核心业务（JSON schema/语法约束高频） | **SGLang** | 调度器层原生约束解码（§3.2） |
| 纯 NVIDIA、模型稳定、追求极限吞吐、能承担编译管线 | **TensorRT-LLM** | 15–25% 稠密模型优势（§4.3）；模型更新频率低时编译成本可摊销 |
| 需要 FP4/NVFP4 等新量化格式首发支持 | **TensorRT-LLM**（首发快）或 vLLM（跟进快） | 按你的模型发布时间线选（§3.3） |
| 不确定 / 刚起步 | **vLLM** 起步，profile 到瓶颈再迁移 | "先 vLLM，profile 出的瓶颈证明值得再换"是 2026 年第三方共识口径 |

⚠️ **错误做法：用单一 tok/s 数字选型。** 上表里没有任何一行只靠吞吐数字就能判——RunPod 那组数据里 vLLM 和 SGLang 的胜负**随负载形状反转**（unique vs cached prefix）。正确的流程：拿**你自己**的流量分布（前缀重复率、prompt 长度分布、并发度、MoE/dense）在候选引擎上跑同一个基准，再决策。

## 📝 总结

三句话记忆：

1. **功能趋同，架构分野**：三家都有 continuous batching / paged KV / FP8 / 投机解码；分野在前缀复用的组织方式（哈希块 vs 基数树 vs 块复用）、调度器实现（Python 异步重叠 vs 零开销 CPU 调度 vs C++ Batch Manager）、执行路径（解释式+图 vs 解释式+图 vs 编译引擎）。
2. **各自主场**：vLLM = 宽度与可预期（多硬件、模型常换、默认选择）；SGLang = 前缀重复流量 + MoE 高并发 + 结构化输出；TensorRT-LLM = 纯 NVIDIA 稳定模型的编译式极限（以编译/运维成本为价）。
3. **选型不靠单点基准**：2026 年中的第三方数据方向一致——前缀重复负载 SGLang 领先、unique 负载打平或 vLLM 领先、NVIDIA 稠密模型极限 TRT-LLM 领先 15–25%；但每个数字都是版本+硬件+负载的快照，迁移前必须自测。
