模型最后吐出来的那个 token，不是"算出来的"，是**从概率分布里抽出来的**——而怎么抽，决定了一个模型能输出"北京的秋天很美"还是"北北北北北"。先给结论：模型每一步输出的 logits 会先被 temperature 缩放、被 top-k/top-p 裁剪、被各种 penalty 扣分，最后才归一化成概率做采样；**temperature 每减半，优势 token 的概率比就变成平方**（logits 差 1 的两个 token，T=1 时概率比 e≈2.72 倍，T=0.1 时约 22000 倍）；`n=4` 并行采样让 Decode 算力 ×4，但共享前缀 KV 每请求能省 GB 级显存；而 Beam Search 走的是一条与采样完全不同的路——**一个在抽签，一个在搜索**。本文把每个旋钮的语义、vLLM 里的实现口径和成本账本逐个拆开，这是你调出"稳定可复现的代码补全"和"千奇百怪的创意文案"的分水岭。

## 1. 为什么要采样：argmax 的确定性与退化问题

### 1.1 贪心解码（argmax）的问题

先把最简单的方式钉死：每一步都选概率最高的 token，这叫**贪心解码（Greedy Decoding）**。它有两个毛病：

- **确定性带来的单调**：永远选第一名，模型就永远沿着"最可能的路径"走。而最可能的路径往往是最平庸的——短、安全、套话连篇。就像每次都选同一条最宽的大路，永远到不了小巷里的好馆子。
- **重复与退化**：模型在局部循环里（比如"爱丽丝走进了房间"后）会反复选自己刚说过的高概率词，因为没有机制惩罚重复。长文本里"不断重复同一个短语直到撞上 max_tokens"是贪心解码最经典的翻车现场，这在 NLP 里有个专门的名字——**神经文本退化（Neural Text Degeneration）**（Holtzman et al., 2020）。

### 1.2 采样：从概率分布里抽签

模型的真实意图从来不是"一个答案"，而是一整个分布：每个 token 都有概率，只是高低不同。**采样（Sampling）就是从分布中按概率抽取一个 token**——高概率的多被抽中，低概率的偶尔也有机会。

打个比方：模型输出的概率分布就是**一个大转盘**，每个 token 占一块面积，面积与概率成正比。贪心解码等于"永远选扇区最大的那一格"；采样则是转一下指针，谁被指中算谁——大扇区经常中，小扇区也有中奖的夜晚。采样牺牲了"每次输出的可预测性"，换取了**多样性**：同一个 prompt 可以给出 n 个不同的答案，重复与套话的概率也被结构性压低。

于是问题变成：**转盘的"偏心度"怎么调？** 这就是下面每个参数干的事。

## 2. 核心参数逐个讲清

### 2.1 temperature：转盘的偏心度

**语义**：对 logits 做缩放后再做 softmax。设模型输出的原始 logits 为 $z_i$（$i$ 遍历词表 $\mathcal{V}$，$z_i$ 越大表示模型越倾向这个 token），则带温度的概率为：

$$
p_i = \frac{e^{z_i / T}}{\sum_{j \in \mathcal{V}} e^{z_j / T}}
$$

$$
\underbrace{T \to 0}_{\text{极端"偏心"}} \quad \Rightarrow \quad p \to \text{argmax（贪心）} \qquad
\underbrace{T = 1}_{\text{模型原始分布}} \qquad
\underbrace{T \to \infty}_{\text{完全"公平"}} \quad \Rightarrow \quad p \to \text{均匀分布}
$$

**数值算例**：设某一步三个候选 token 的 logits 为 $z = [5.0,\ 3.0,\ 1.0]$（模型很确信第一个），不同温度下的概率：

| 📊 T | token A（z=5.0） | token B（z=3.0） | token C（z=1.0） | 行为 |
|---|---|---|---|---|
| 0.1 | **0.99999** | ~0.0000 | ~0.0000 | ≈贪心 |
| 0.5 | 0.982 | 0.018 | 0.0003 | 极尖锐 |
| 1.0 | 0.867 | 0.117 | 0.016 | 模型原始分布 |
| 2.0 | 0.665 | 0.245 | 0.090 | 变平缓 |
| 10.0 | 0.402 | 0.329 | 0.269 | ≈均匀（1/3） |

📌 **关键点**：logits 差 1 的两个 token，概率比是 $e^{1/T}$——**T 减半，优势比变成平方**（T=1 时 2.72 倍，T=0.5 时 7.39 倍，T=0.1 时 ~22000 倍）。所以 temperature 不是线性旋钮，它是指数级的"偏心度"调节器。

**vLLM 的实现口径**（以你所用版本为准）：`temperature=0` 直接走贪心路径（连随机数都不生成，见第 5 节）；`(0, 0.01)` 之间会被钳到 0.01 并打警告（防止除零后产生 NaN/Inf 破坏张量）；参数范围校验为 `[0, 2]`。**别传 0.0001 这种值**——它不会更"贪心"，只会先被钳制再让你困惑。

### 2.2 top-k：只留前 k 个候选

**语义**：把概率最高的 k 个 token 保留，其余全部 mask 掉（概率置 0），再重新归一化。

- k=1 等价于贪心；k 越大越接近原始分布。
- **固定名额**是它的特点也是缺点：分布很尖锐时（模型非常确定），前 10 个之外本来就是噪声，k 截不截无所谓；分布很平摊时（模型犹豫不决），k=10 可能只覆盖了 30% 的概率质量，把大量合理候选拦在门外。

**工程细节**：vLLM 里 `top_k=0` 或 `-1` 都表示不限制（旧版本默认 -1，新版本默认 0，以你所用版本为准）。

### 2.3 top-p（Nucleus Sampling）：动态的候选集合

**语义**：按概率从高到低累加，**保留"累积概率刚好达到 p"的最小集合**，其余 mask 掉再归一化。这就是 Nucleus Sampling 原始论文（Holtzman et al., 2020）提出的方案。

**数值算例**：假设归一化后概率分布为 $[0.40, 0.25, 0.15, 0.10, 0.06, 0.04]$，累计概率依次为 0.40 / 0.65 / 0.80 / **0.90** / 0.96 / 1.00：

- `top_p=0.9` → 保留前 4 个（累积 0.90），归一化后变为 $[0.444, 0.278, 0.167, 0.111]$；
- `top_k=3` → 固定保留前 3 个，归一化后变为 $[0.500, 0.312, 0.187]$。

📌 **关键点**：top-p 的集合大小是**动态**的——模型确定时集合小、犹豫时集合大，它把"截断多少"这个决定交给分布本身，而不是拍脑袋定死的 k。**top-p 比 top-k 更常用，就是这个原因**。

💡 **提示**：`top_p` 合法范围是 `(0, 1]`，默认 1.0（不裁剪）。0.9~0.95 是常见取值——注意它和 top-k 一样只负责"筛掉谁"，不改变保留者之间的相对概率。

### 2.4 三者配合、常见组合，以及 seed

三个旋钮各管一段：**top-k/top-p 决定"从谁里抽"，temperature 决定"抽的时候偏心多少"**。工程上最常见的起点组合（站内 [vLLM 快速入门](/AIInfraGuide/inference/模块四-推理优化/第3章-深入vllm/vllm快速入门) 的推荐）是 `temperature=0.7, top_p=0.9`：稍微压扁原始分布让输出不那么死板，同时裁掉长尾噪声。

**seed：为什么工程上必须有它？** 采样需要随机数，随机数发生器要有个起点——seed 就是那个起点。设了 seed，同一 prompt 在同一模型上会得到**同一串输出**，这是评测、回归测试、演示、RLHF 数据复现的命根子。

vLLM 的官方口径（Reproducibility 文档，以你所用版本为准）：

- **V1 引擎里 seed 默认就是 0**——每个 worker 的随机状态被固定，同一进程内结果一致；官方说明"无法取消 V1 的 seed"，因为投机解码等工作流要求不同 worker 采样出相同结果（PR #17929）；
- 但"跨重启可复现"只承诺于**同硬件 + 同 vLLM 版本 + 离线推理**，且需要 `VLLM_ENABLE_V1_MULTIPROCESSING=0`；
- **在线服务（vllm serve）官方明说不保证可复现**——并发调度本身不确定，别拿在线环境做复现实验。

⚠️ **注意**：设了 seed ≠ 输出一定"合理"，只是"可复现"。温度越高，同一 seed 的两次输出也可能因浮点/调度差异发散（在线场景），所以**评测对比请用 temperature=0，需要多样性再开 seed+采样**（4.6 的评测协议就是这么定的）。

## 3. Logprobs 与并行采样

### 3.1 logprobs / prompt_logprobs：把分布要回来

默认情况下 API 只回传被抽中的 token 文本，分布信息就扔了。`logprobs` 参数把每一步的 top-k 概率**附带返回**：

- `logprobs=N`：每个输出 token 返回概率最高的 N 个候选的 logprob，外加被抽中 token 本身的 logprob（OpenAI 语义，最多 N+1 项）；
- `logprobs=-1`：返回**全词表**（vocab_size 个）的 logprob；
- `prompt_logprobs=N`：对 prompt 里的每个 token 同样返回 top-N；
- `logprob_token_ids=[...]`（较新版本）：只返回你指定的 token id 的 logprob，最多 128 个——**打分任务专用**，比 -1 便宜几个数量级。

**用途**：RLHF 数据制作（参考策略的 KL 项需要逐 token logprob）、perplexity 评估（算交叉熵）、Agent 里的置信度判断（"模型有多确定"）、多选题打分（比较几个选项的 logprob）。

**成本账本**：logits 本来就在 GPU 上，返回 top-N 的额外开销很小；但 `logprobs=-1` 是另一回事——vocab 128K 时，**每个 token 要搬运 128K × 4B ≈ 512KB 数据**，输出 256 个 token 就是 128MB/序列，会实实在在拖慢吞吐和序列化。所以：**只要知道少数几个 token 的概率，永远优先用 `logprob_token_ids`，别用 -1 图省事**。

### 3.2 n：并行采样——同一 prompt 生成 n 条答案

**语义**：`n` 是"同一 prompt 独立采样 n 条序列"。它与 batch 的关系要分清：**batch 是 n 个不同的请求凑一批跑；n 是同一个请求内部裂变成 n 条序列**。对引擎来说两者都是 Decode 阶段的一行，但 n 条序列共享三样东西：

1. **一次 Prefill**：prompt 只算一遍；
2. **前缀 KV Cache**：prompt 部分的 KV 只存一份，各序列在第一个生成 token 之后才分叉（PagedAttention 的写时复制/前缀缓存，[2.1](/AIInfraGuide/inference/模块四-推理优化/第2章-推理引擎核心技术/21-pagedattention) 讲过）；
3. **同一个采样配置**（每序列可再带自己的 seed 派生随机数）。

**显存账本**：LLaMA-2-7B（32 层、32 头、head_dim=128、FP16）每 token 每序列的 KV 约 512KB（账算法见[学习路线](/AIInfraGuide/guides/ai-infra学习路线)）。1024-token 的 prompt：单序列 KV = 512MB；`n=4` 时前缀共享让 KV 从 4×512MB=2GB 降到 512MB + 3 条分叉尾巴——**每请求省 ~1.5GB**。但 **Decode 算力一分不少：每步 4 条序列都要前向，计算量 ×4**。

📌 **关键点**：n 并行采样**用显存共享换算力翻倍**——KV 省了，计算不省。省显存是真的，想靠它白嫖吞吐是假的。

工程细节（以你所用版本为准）：`n` 上限受 `VLLM_MAX_N_SEQUENCES`（默认 16384）控制；**贪心模式下 n 必须为 1**（vLLM 会直接报错）；流式下 n>1 时所有序列的结果会累积式地流回来，想等全部完成再收结果用 `output_kind=FINAL_ONLY`。

### 3.3 best_of 与 rerank：从 n 条里挑一条最好的

`best_of` 的经典语义（OpenAI 兼容）：**先生成 best_of 条序列，按累计 logprob 排序，返回最好的 n 条**——`best_of` 必须 ≥ `n`，默认等于 n。这是"采样 + rerank"的朴素实现：多样性来自采样，质量靠分数兜底。

⚠️ **注意**：这个参数在 vLLM 历史上存在（约 v0.7 及以前的 `SamplingParams(best_of=...)`），但在 beam search 重构为独立 `BeamSearchParams` 后，**最新主分支已从 `SamplingParams` 和 OpenAI API 中移除**。需要 rerank 时，现在的等价做法是：`n=k` 拿 k 条结果 + `logprobs` 自己按累计分数挑，或直接上第 4 节的 beam search。**以你所用版本的 `--help`/API 为准，别照抄旧教程里的 best_of。**

## 4. Beam Search：搜索而非抽签

### 4.1 原理：每一轮只留最好的 B 条路

Beam Search 维护 **B 条最优序列**（B = beam width），每步每条序列展开 top-k 个候选（共 B×k 条），按累计得分（$\sum \log p_i$，可再乘长度惩罚）取前 B 条进入下一轮。

打个比方：这是**选秀海选**——每轮保留 B 名选手，下一轮每人表演 k 个才艺，评委按累计得分淘汰，最后只留 B 个晋级；贪心解码就是 B=1 的海选（每轮只留第一名）。流程（伪代码，非逐字源码，理解原理的示意）：

```
# 输入: prompt, 束宽 B, 展开数 k, 最大步数 T
beams = [prompt]                       # 初始只有 1 条空路径
for step in 1..T:
    candidates = []
    for beam in beams:                 # B 条现有路径
        top_k = model(beam) 取 logits 最高的 k 个 token   # 展开
        candidates += [beam + token for token in top_k]   # B×k 条候选
    beams = top_B(candidates, score=Σlog p + length_penalty)  # 只留前 B
return beams[0]                        # 得分最高的那条
```

### 4.2 与采样的本质区别

| 📊 维度 | 采样（Sampling） | Beam Search |
|---|---|---|
| 本质 | **随机抽样**，模拟分布 | **确定性搜索**，最大化累计得分 |
| 输出 | 每次可能不同（除非固定 seed） | 同一输入永远同一结果 |
| 目标 | 多样性、接近真实分布 | 找到"最可能"的整条序列 |
| 代价 | 无额外计算 | 每步 B×k 次展开，算力约 ×B |
| 适用 | 对话、创意、代码（要多样性） | 翻译、摘要（要一条最好答案） |

📌 **关键点**：贪心 = beam 1；beam 是"贪心的多路并行版"——它解决了贪心"一锤定音、错了没法回头"的局部最优问题，但**代价是算力 ×B**（还要叠加每步 k 路展开的排序开销）。

### 4.3 vLLM 的支持状态（以你所用版本为准）

- **beam search 没被砍**：2024 年社区提过 RFC #6226 提议移除 beam search（理由是系统复杂度），**因社区强烈反对而撤回**，官方继续支持；
- **旧 API**（约 v0.9 以前）：`SamplingParams(use_beam_search=True, best_of=束宽, length_penalty=1.0, early_stopping=False)`；
- **新 API**（近期版本）：独立的 `BeamSearchParams(beam_width, max_tokens, length_penalty=1.0, temperature=0.0, ignore_eos=False)` + `LLM.beam_search(...)`（离线）；在线 OpenAI 兼容接口里 `use_beam_search=True` + `n=束宽` + `length_penalty`（/v1/completions）；
- **实现方式**：官方文档明确 beam search 是"基于 generate 之上实现的"——每步用 `logprobs=2×beam_width` 取候选、CPU 侧排序扩束。**它不是融合的原生解码器**，束宽大了开销明显；
- **KV 共享**：各束共享前缀 KV（PagedAttention 的写时复制），这正是 vLLM 的 beam search 相比连续内存实现显存更省的原因（RFC #6226 原话：PagedAttention 能高效应对 beam 的动态性并最小化 KV 占用）。

### 4.4 什么时候用

- ✅ **翻译 / 摘要 / 标题生成 / 代码修复**：任务有"唯一最优答案"，输出质量优先，beam=4~8 能稳定提升 BLEU/ROUGE 类指标；
- ❌ **对话 / 创意写作 / 头脑风暴**：没有唯一答案，beam 只会让输出趋同、无聊，且 B 路展开的成本在在线服务里纯属浪费；
- ⚠️ **长文本谨慎**：beam 的累计得分偏向短句（除非调 length_penalty），且与投机解码等加速手段不兼容（见 5.2）。

## 5. 推理引擎里的采样实现

### 5.1 GPU 上的单步采样流水

把镜头拉进 vLLM V1 的采样器，每步 Decode 的采样流水大致是（伪代码，非逐字源码，理解原理的示意）：

```
# 输入: 本步 batch 的 logits (num_seqs × vocab)
1. penalties:  presence/frequency/repetition 罚分（见 5.3）
2. temperature: logits /= T（T=0 的请求直接标记 greedy，跳过后续随机）
3. 候选裁剪:   top-k / top-p / min_p mask
4. 归一化:     softmax → 概率分布
5. 采样:       greedy → argmax；sampling → 按概率抽签（seeded 用每请求 RNG）
```

两个工程要点：

- **采样在 GPU 上做**：整个 (batch × vocab) 的 logits 张量在显存里，罚分、缩放、mask、采样都是一次性 kernel（参考官方 [Logits Processors 设计文档](https://docs.vllm.ai/en/latest/design/logits_processors/)：logits processor 以 `(num_requests × vocab_size)` 粒度批量作用，采样器最后统一调用）；
- **贪心请求可以"抄近路"**：设计文档明确——不改变 argmax 的 logits 变换在贪心请求上可以跳过。所以贪心不只是"采样概率为 1"，它是**整个随机管线都不跑**，这也是 T=0 比 T=0.1 更快的原因之一。

### 5.2 投机解码下的采样一致性（呼应 5.1）

[5.1](/AIInfraGuide/inference/模块四-推理优化/第5章-speculative-decoding/51-核心原理与rejection-sampling) 讲过：投机解码的无偏性依赖 rejection sampling，接受概率 $\min(1, p/q)$ 里的 $p$ 和 $q$ 必须是**经受同样采样参数变换后的分布**——temperature、penalties 必须对 draft 和 target 施加**完全相同的变换**，否则接受率公式失真、输出分布偏离 target。具体表现：

- **temperature 影响接受率**：贪心（T→0）下接受判定退化为"draft 的 argmax 是否等于 target 的 argmax"，逐位比对、直截了当，接受率最高；采样模式下要求两个分布在每个候选上的概率比例都接近，经验上接受率明显下降——[5.4](/AIInfraGuide/inference/模块四-推理优化/第5章-speculative-decoding/54-收益边界与限制) 的"高温采样命中率骤降"就是这个机制；
- **参数兼容性**：vLLM 当前版本明确校验 `min_p` 和 `logit_bias` **与投机解码不兼容**（会直接报错）；beam search 与投机解码也是两条互斥的路线（以你所用版本为准）。

推论很实用：**想让投机解码加速在线服务，先问业务能不能接受贪心或低温**——不能的话，先测接受率再决定上不上（5.4 的决策框架）。

### 5.3 frequency / presence penalty：给重复收税

这两个参数解决第 1 节的"重复退化"，语义来自 OpenAI API（vLLM 完全兼容，范围校验 `[-2, 2]`）：

- **presence_penalty（存在税）**：token 在已生成文本里**出现过就扣一次**——罚的是"旧词"；
- **frequency_penalty（次数税）**：token **每出现一次都扣一次**——罚的是"高频词"；
- 两者都是**减法**（logits -= penalty × 出现情况）；而 `repetition_penalty` 是**乘法**（logits > 0 时除以 r，< 0 时乘以 r，默认 1.0 不生效）。

公式（vLLM 实现口径，以你所用版本源码为准）：

$$
\text{logits}[t] \mathrel{-}= \underbrace{F \times \text{count}(t)}_{\text{频率税：出现 } \text{count} \text{ 次扣 } F \times \text{count}} + \underbrace{P \times \mathbb{1}[\text{count}(t) > 0]}_{\text{存在税：出现过就扣一次 } P}
$$

打个比方（第三个也是最后一个比喻）：这是给热门 token 收**重复税**——presence 是"进过城就收一次进城费"，frequency 是"每进一次城都收一次"。税越重，模型越愿意绕开老词去说新东西。

💡 **提示**：presence 适合"别老说同一套词"（0.3~0.6 常见）；frequency 适合"别逐字重复句子"（0.3~1.0 常见，越大越激进）。两者都只统计**已生成的输出**（不含 prompt），调太大输出会变得支离破碎——它们和 temperature 一样，是"重税换多样性"的权衡，不是越大越好。

## 6. 工程决策表

### 6.1 任务 → 配置

| 📊 任务类型 | 推荐配置 | 为什么 |
|---|---|---|
| 代码补全 / 结构化生成 | `temperature=0`（贪心）或 `T≤0.2` | 确定性优先；贪心还省采样管线（5.1），且评测可复现 |
| 通用对话 / 助手 | `T=0.7, top_p=0.9` | 站内 [vLLM 快速入门](/AIInfraGuide/inference/模块四-推理优化/第3章-深入vllm/vllm快速入门) 的起点组合，平衡质量与多样性 |
| 翻译 / 摘要 | Beam Search（`beam_width=4~8`）或 `n`+rerank | 有"最好答案"，确定性搜索优于抽签（4.2） |
| 创意写作 / 头脑风暴 | `T=0.9~1.2, top_p=0.95`，可选 `presence_penalty=0.3~0.6` | 高多样性 + 重复税防复读 |
| RLHF 数据 / 评估 | 固定 `seed` + `n` 并行 + `logprobs` | 可复现 + 多样本 + 概率都要留档（3.1/3.2） |

### 6.2 落成一句话的规则

- ✅ **要确定性** → `temperature=0`（顺便白拿贪心跳过采样管线的提速），别用 seed 硬凑。
- ✅ **要多样性又要质量** → `T=0.7~0.9 + top_p=0.9~0.95`，先用 top-p 别先动 top-k（动态集合更稳）。
- ✅ **要"一条最好答案"** → beam search（离线 `BeamSearchParams`），在线用 `n`+logprobs 自选 rerank。
- ✅ **要复现** → 固定 seed，且只在**离线 + 同硬件 + 同版本**下承诺（官方口径），在线环境别较真。
- ❌ **别把 top-k 和 top-p 一起开**（除非知道自己在干什么）——双重裁剪让候选集合可能小到只剩几个 token，多样性白调。
- ❌ **别在贪心请求上传 `n>1`**（当前版本直接报错）、**别在投机解码下开 min_p/logit_bias**——先查你所用版本的校验规则。

## 📝 总结

1. **采样本质**：从概率分布抽签（转盘）而非永远选第一名；贪心（argmax）确定但退化——重复、单调、套话，这是所有采样参数的出发点。
2. **temperature**：$p_i = e^{z_i/T}/\sum_j e^{z_j/T}$，T 每减半优势比变平方（差 1 的 logits：T=1 时 2.72 倍，T=0.1 时 ~22000 倍）；T=0 走贪心快路径。
3. **top-k vs top-p**：固定 k 个 vs 累积概率 p 的动态集合——top-p 把截断决定交给分布本身，更常用。
4. **seed**：V1 默认 0、不可取消；可复现仅承诺于离线 + 同硬件 + 同版本；在线服务官方明说不保证。
5. **Logprobs 与 n**：logprobs=-1 每 token 搬运 ~512KB（vocab 128K）要省着用；n 并行采样共享前缀 KV（省 ~1.5GB/请求，7B/1024 token/n=4）但 Decode 算力 ×n；best_of 已随新版重构退场，rerank 用 n+logprobs 或 beam search。
6. **Beam Search**：确定性搜索（选秀海选），束宽 B 算力约 ×B，KV 前缀共享；vLLM 新 API 是 `BeamSearchParams`+`LLM.beam_search`；翻译/摘要用，对话/创意别用。
7. **引擎实现**：penalties（减法）→ temperature → top-k/top-p mask → softmax → 采样全在 GPU 上；贪心跳过整个随机管线；投机解码要求采样参数对 draft/target 一致施加，min_p/logit_bias 与它不兼容。
