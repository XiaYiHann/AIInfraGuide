靠 prompt 让模型“尽量”输出合法 JSON，等于把业务正确性押在概率上：格式错、字段缺、中途截断，下游 `json.loads` 一崩崩一片。结构化输出（又称受限解码 / Guided Decoding）把“尽量”变成“只能”——推理引擎在每一步生成时，先把文法（输出格式规则）不允许的 token 的 logits 置为 -inf，再从合法集合里采样。以 151,936 词表为例，这一步的合法性检查本质是生成一个词表大小的 bitmask（每个 token 占 1 位、标合法或非法，约 18.5 KB/请求/步），而现代后端把这部分开销压到了端到端“近零”：XGrammar 论文（MLSys'25）报告文法执行最高 100x 加速，vLLM 官方博客实测接入 XGrammar 后，负载下的 TPOT 相对旧后端最高提升 5 倍。本文讲清受限解码的原理、三种约束形式的表达力边界、xgrammar/cFSM 两类后端的设计差异，以及 vLLM 从 `guided_json` 到 `structured_outputs` 的开启方式。

## 1. 痛点：让模型“尽量”输出 JSON 的不可靠

### 1.1 业务侧解析崩溃的三种死法

假设你的下游代码是 `json.loads(response)`——模型输出不合法时，这一行直接抛异常。生产里最常见的三种死法：

1. **格式错**：输出里混进解释性文字（“好的，这是你要的 JSON：```json {…}”），或者多了尾逗号、注释、单引号；
2. **字段缺失或类型错**：schema 要求 `age` 是 integer,模型给了 `"age": "twenty-eight"`;
3. **中途截断**：输出撞上 `max_tokens` 上限，JSON 括号没闭合，直接半截。

有人统计过，让模型自由生成 JSON 的失败率在不同模型/任务上从百分之几到百分之三四十不等——这是个概率问题，不是运气问题。

### 1.2 为什么 prompt 救不了？

**因为模型是在分布上采样，不是在执行规则。** prompt 里写十遍“必须输出合法 JSON”、给 few-shot 示例，改变的只是这个分布的形状：合法 JSON 的概率变高了，但非法 token 的概率不会变成 0。只要是非零概率，在高并发下就一定会发生——一天的请求量上去了，哪怕 1% 的失败率也是事故。

打个比方：这就像过海关填申报单。**prompt 相当于工作人员口头叮嘱“请认真填写”**,但你没法保证每个旅客都填对；结构化输出则是在窗口前放了一个**逐格核对的检查员**——填错一个格子（输出一个非法 token），当场打回（把它的概率置为 0），你根本交不上去。检查员只认规则，不认态度。

关键结论：**结构化输出是把“格式保证”从“尽力而为”升级为“硬约束”,代价是采样自由度**。这一节先把原理讲透，代价在第 5、7 节算账。

## 2. 受限解码原理：从自由采样到文法约束

### 2.1 从“采样自由文本”到“在文法约束下采样”

正常的自回归生成，每一步是这样采样的：

$$
\underbrace{p_i = \text{softmax}(\text{logits}_i)}_{\text{第 }i\text{ 步:对整个词表算概率分布}} \quad \rightarrow \quad \underbrace{x_i \sim p_i}_{\text{从分布中抽一个 token}}
$$

受限解码只改了一件事：采样前先按当前文法状态算一个合法 token 集合 $V_{\text{valid}}$,把集合外的 logits 全部置为 -inf：

$$
\text{logits}'_i(t) = \begin{cases} \text{logits}_i(t) & t \in V_{\text{valid}} \\ -\infty & t \notin V_{\text{valid}} \end{cases}
$$

softmax 之后，非法 token 的概率严格等于 0——**只要 $V_{\text{valid}}$ 算得对，输出就一定落在文法定义的语言里**。这就是“强制合法 JSON”的机制：不是靠模型自觉，而是物理上不可能选到非法 token。

🔑 **核心概念**：受限解码 = **每一步用一个随状态变化的 token 集合去屏蔽 logits**。约束不是加在 prompt 里，而是加在采样路径上。

### 2.2 文法到自动机的编译：正则与 CFG 的边界

关键问题来了：$V_{\text{valid}}$ 怎么算？答案是**把约束编译成自动机（一个记录“输出已经走到哪一步”的状态机），用自动机的当前状态决定合法转移**。

- **正则表达式 → 有限状态机(FSM/DFA)**：正则语言的状态数有限，编译后每个状态对应一张“合法 token 表”。
- **JSON Schema / 上下文无关文法（CFG）→ 下推自动机（PDA）**：正则表达不了任意深度的嵌套——想想 JSON 里数组套数组，嵌套深度没有上限，有限状态机记不住“我还在第几层”。CFG 可以（递归产生式：规则允许一层层套自己），但识别它需要 PDA:FSM + 一个栈，压栈/弹栈来跟踪嵌套深度。

💡 **提示**：这就是为什么“一个正则搞定所有 JSON”是做不到的。outlines 那代方案把 JSON Schema 转成正则再建 FSM,对**嵌套深度有上限**的 schema 够用；而 XGrammar 直接走 CFG → PDA 路线，任意嵌套都能表达。**表达力边界：正则语言 ⊂ 上下文无关语言**。

### 2.3 一个完整的 FSM 例子

用一个最小 schema 走一遍：要求输出 `{"name": "Alice" | "Bob", "age": <整数>}`。它对应的正则大致是：

```
\{ "name": "(Alice|Bob)", "age": [0-9]+ \}
```

编译成 FSM 后，生成过程如下（状态 → 合法输出的下一个片段）：

| 步骤 | FSM 状态 | 当前已输出 | 该步唯一合法的选择 |
|---|---|---|---|
| 1 | S0 | （空） | 固定前缀 `{"name": "` |
| 2 | S1 | `{"name": "` | 只允许拼出 Alice/Bob 的 token |
| 3 | S2 | `{"name": "Alice` | 固定 `","age": ` |
| 4 | S3 | `{"name": "Alice","age": ` | 只允许数字 token |
| 5 | S4 | `...age": 28` | 固定 `}` |
| 6 | S5 | `...28}` | 结束 |

🔑 **关键点**：注意步骤 2 和 4——**合法集合可以小到只剩几个 token**。整个词表 15 万个候选，被文法砍到只剩个位数，模型在这几个里面按原分布采样。这就是“约束”的直观含义：像安检通道只留一条窄道，绝大多数候选被挡在门外，能通过的只有符合格式的那几个。

**数值算例**：这个 schema 的 FSM 大约只有 6~10 个状态；而一个生产级 schema（10 个字段、嵌套对象、`$ref` 复用）编译后的状态数可以到几千，首次编译耗时从几十毫秒到数秒不等（vLLM 官方文档承认：结构化后端首次使用时，FSM 编译可能带来数秒延迟，之后走缓存）。

## 3. 三种约束形式：正则、JSON Schema 与文法

### 3.1 三种形式的对比

| 📊 维度 | 正则(regex) | JSON Schema(json) | 文法(grammar) |
|---|---|---|---|
| 表达力 | 正则语言 | 递归对象 → 需 CFG 表达 | CFG,最强 |
| 适用输出 | 邮箱、日期、编号 | 结构化数据（最常用） | SQL、命令、任意 DSL |
| 定义方式 | `\d{4}-\d{2}-\d{2}` | JSON 描述字段类型/约束 | EBNF/GBNF 产生式 |
| 易用性 | 高 | 最高（Pydantic 模型直接转） | 低（要会写文法） |

以 vLLM 当前的结构化输出参数为例，三种形式分别对应 `structured_outputs` 里的 `regex`、`json`、`grammar` 字段，另外还有 `choice`（枚举列表，最简单）和 `structural_tag`（在自由文本中夹一段受约束的 JSON,8.2 的 Tool Calling 严格模式就用它）。

### 3.2 JSON Schema 到 token 级约束的转换流程

JSON Schema 不是直接喂给解码器的，中间隔着两步编译（伪代码，非逐字源码）：

```
# 输入:JSON Schema(或 Pydantic 模型)
schema = {"type":"object","properties":{"name":{"type":"string","enum":["Alice","Bob"]},
                                        "age":{"type":"integer"}},"required":["name","age"]}

# 流程 1:Schema → 文法(xgrammar 内部把 schema 转成 EBNF 产生式)
grammar = json_schema_to_grammar(schema)
#   root    ::= "{\"name\": " string_name ", \"age\": " integer "}"
#   string_name ::= "\"Alice\"" | "\"Bob\""
#   integer ::= "-"? [0-9]+

# 流程 2:文法 + tokenizer → 编译后的自动机(每个状态预计算合法 token 表)
compiled = compile(grammar, tokenizer)
#   每个状态存一张表:state -> 允许的 token id 列表

# 流程 3:运行时逐 token 推进
matcher = compiled.matcher()
for step in range(max_tokens):
    mask = matcher.next_token_bitmask()   # 词表大小的 bool 向量
    logits = apply_mask(logits, mask)     # 非法位置 -inf
    token = sample(logits)
    matcher.accept_token(token)           # 状态转移
```

⚠️ **注意**：第 3 步的“合法 token”判定发生在 **token 粒度**而非字符粒度。BPE 词表里 `"Alice"` 可能是一个 token,也可能是 `"Al` + `ice"` 两个 token——自动机必须枚举“该 token 拼出的字符串是否让输出仍属于该语言”。判定粒度不同，正确性和性能完全不同，这就是第 4 节各后端较劲的地方。

### 3.3 约束粒度：token 级 mask vs 字符级

- **token 级（主流）**：每个解码步生成一个词表大小的 mask。优点是每步只有一次检查、和现有采样管线天然契合；难点是 token 与字符的边界纠缠——经典翻车案例：模型想输出 `",`（右引号加逗号，这是词表里的高频 token），但正则只允许到 `"` 为止。`",` 被屏蔽后，模型不知道该怎么继续，可能陷入“想停停不下来”的循环（LMSys 在 cFSM 博客里专门记录了这个坑）。
- **字符级**：把解码粒度拆到字符，天然精确但每字符都要一次前向，慢一个数量级，几乎没人用。

💡 **提示**：cFSM 的解法是 jump-forward 时**先追加字符串、再对整个文本重新分词**,把“按 token 拼”的边界问题绕过去——代价约 4% 的额外开销（第 4.3 节）。

## 4. 后端实现：xgrammar、Outlines 与 cFSM

### 4.1 XGrammar：把词表分成“能预检的”和“要现算的”

XGrammar（MLC 团队，xgrammar.mlc.ai）是 vLLM V1 里结构化输出的主力后端。它的核心洞察是：**每个状态都重新检查全部 15 万 token 太贵，但绝大多数 token 的合法性其实与上下文无关**——比如 JSON 字符串里，`a`、`b`、`c` 这类普通 token 永远合法，可以预先算好缓存；只有少数“上下文相关”的 token（引号、逗号、特定关键字）才需要在运行时现场判定。

- 离线把词表切成两类：**context-independent**（预检查，结果缓存）与 **context-dependent**（运行时用持久化栈逐 token 检查）；
- 用文法变换扩大“上下文无关”的比例，进一步压缩运行时开销；
- 文法编译、mask 生成放在 C++ 侧，并与 GPU 前向**重叠执行**,不让 CPU 检查卡住 GPU。

论文(MLSys'25)报告：文法执行速度相对既有方案**最高 100x**,端到端服务中结构化生成接近**零开销**。

📌 **关键点**：XGrammar 的“快”来自两点——**能缓存的提前缓存（词表二分）+ 不能缓存的用栈快速判定 + 与 GPU 计算重叠**。这不是魔法，是把“每步全量检查”优化成“每步少量检查”。

### 4.2 Outlines 与 Guidance：两个不同时代的对手

- **Outlines**(dottxt-ai)：FSM 受限解码的鼻祖方案（Willard & Louf 2023），把 schema 转正则、正则建 FSM、每个状态算合法 token 表。它证明了“在 token 级屏蔽 logits”可行，但实现是 Python 侧的 logit processor（采样前逐 token 改写 logits 的钩子），FSM 编译和 mask 生成都在采样关键路径上，批量场景下还会阻塞同批其他请求。vLLM 博客的实测：换成 XGrammar 后负载下 TPOT 最高提升 **5x**——这 5x 主要就是省掉的 Python 侧开销。
- **Guidance**(guidance-ai/llguidance)：走“逐 token 现场计算”路线，FSM 不预先缓存，首次请求的 TTFT 更低，适合 **schema 频繁变化、多租户**的场景；代价是稳定状态下每 token 开销略高。vLLM 把 `--structured-outputs-config.backend` 的默认值设为 `auto`：按请求特征挑后端，JSON Schema 等常见场景通常落到 XGrammar,复杂/非常规约束回退 guidance。

| 📊 后端 | 策略 | 强项 | 弱项 | 适合场景 |
|---|---|---|---|---|
| XGrammar | 词表二分 + 预缓存 + PDA | 缓存命中后 TPOT 低、长输出稳 | 首次编译慢、动态 schema 无缓存可吃 | 固定 schema 复用（生产主流） |
| Guidance | 逐 token 现场计算 | 首请求 TTFT 快 | 稳态吞吐略逊 | 多租户、schema 频繁变 |
| Outlines | 正则→FSM(logit processor) | 思想鼻祖、简单 | 慢、阻塞同批请求 | 学习原理 / 老代码兼容 |

### 4.3 cFSM:SGLang 的压缩有限状态机

SGLang 的 cFSM（compressed FSM,LMSys 2024 年 2 月博客 + SGLang 论文）走了另一条路。它先用 token id 作为字母表把正则建 DFA,然后**压缩**：凡是从某状态出发只有一条“唯一确定”的转移路径（比如固定前缀 `{"name": "`），就把整条路径压成一个**单步**,解码时直接跳过这些状态、一次 prefill 多个 token——这叫 **jump-forward（跳步解码）**。

打个比方：普通受限解码像走迷宫，每个岔路口停下来选一次；cFSM 发现“这段路没有岔路”后，干脆**一口气跑完直道，只在岔路口减速**。

效果（博客实测，对比 guidance+llama.cpp 与 outlines+vLLM）：**延迟最高降 2 倍，吞吐最高升 2.5 倍**,甚至出现“受限解码比自由解码更快”的反直觉现象——因为跳过的固定前缀不再需要逐 token 采样。代价：跳步后要重新分词（约 4% 开销），且只对“存在长直道”的约束（如 JSON 的固定键名）有效。

## 5. 性能代价：mask 开销账本与投机解码兼容

### 5.1 mask 开销账本

受限解码每步多出来的工作有两块：**生成 mask（CPU 侧）** 和 **应用 mask（GPU 侧）**。

- 应用侧：mask 是一个词表大小的 bool 向量。以 151,936 词表的模型为例，每请求每步的 mask 是 $151{,}936 \text{ bits} \approx 18.5 \text{ KB}$;batch 256 个结构化请求同时解码，每步要搬运/应用 $256 \times 18.5 \text{ KB} \approx 4.7 \text{ MB}$。相比每步几十 MB 的 KV 读写，这个量级可忽略——应用 mask 本身几乎免费。
- 生成侧才是大头：每步要根据自动机状态算“哪些 token 合法”。朴素实现（逐 token 试走一遍 FSM）在 Python 里做，一个状态几十微秒起步，批量下还会串行阻塞；XGrammar 靠词表二分 + 缓存把它压到每步微秒级，并且和 GPU 前向重叠，才做到“近零开销”。

📌 **关键点**：**受限解码的性能问题从来不在 GPU,而在 CPU 侧的 mask 生成有没有缓存、有没有和计算重叠**。这也是 V0 时代“一个结构化请求拖垮整批”的根因——vLLM V1 把结构化输出从 logit processor 挪到调度器级、初始化改为非阻塞，单请求不再卡全批（Red Hat 2025 年实测：缓存 schema 下，结构化请求的 TPOT 仅比无约束略高）。

### 5.2 与投机解码的兼容：draft 也要受约束

第 5 章讲过投机解码(5.1~5.5)：小模型 draft 一批候选，大模型一次性验证。**受限解码叠加投机解码时，约束必须同时作用在 draft 和验证两条链上**——draft 模型如果自由采样，生成的候选几乎必然违反文法，接受率会跌到接近 0,投机彻底失效。

工程上的正确姿势有两种：

1. **draft 也做受限解码**（draft 端加同样的 mask,候选天然合法，验证端只需校验 KV 与概率）；代价是 draft 的生成也变慢，但 draft 模型小，CPU 侧开销占比可接受；
2. **约束感知的验证**：验证阶段按文法检查候选序列，不合法就截断回退（类似 5.1 的 rejection 逻辑）。

vLLM V1 已经打通两者（2025 年合并的 PR #14702 支持 Speculative Decoding + Structured Outputs），**但兼容性随版本演进，以你所用版本的特性矩阵为准**。

⚠️ **注意**：投机解码的收益模型在受限场景下会变——5.4 讲过“接受率低于 50% 不赚”,结构化输出把合法空间砍小后，draft 的接受率天然下降，收益边界要重测，别直接套自由解码的数字。

## 6. vLLM 开启方式：从 guided_json 到 structured_outputs

### 6.1 新版参数：structured_outputs

以 vLLM 近期版本为例，结构化输出在 OpenAI 兼容端点上是**默认开启**的，不需要额外启动参数（后端可用 `--structured-outputs-config.backend` 指定，默认 `auto`）。请求侧传 `structured_outputs` 字段：

```python
from openai import OpenAI
from pydantic import BaseModel

client = OpenAI(base_url="http://localhost:8000/v1", api_key="-")

class CarDescription(BaseModel):
    brand: str
    model: str
    car_type: str   # 用 enum 约束更严,见下文

# 方式 A:extra_body 传 structured_outputs.json(Pydantic 模型直接转 schema)
completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "生成一辆 90 年代代表车型的 JSON"}],
    extra_body={"structured_outputs": {"json": CarDescription.model_json_schema()}},
)

# 方式 B:OpenAI 标准的 response_format(type=json_schema)——与 A 等价
completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "生成一辆 90 年代代表车型的 JSON"}],
    response_format={"type": "json_schema",
                     "json_schema": {"name": "car", "schema": CarDescription.model_json_schema()}},
)

# 方式 C:正则(日期)
completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "给我一个 2024 年的日期"}],
    extra_body={"structured_outputs": {"regex": r"\d{4}-\d{2}-\d{2}"}},
)
```

**参数演进（易错！）**：早期版本用 `guided_json` / `guided_regex` / `guided_choice` / `guided_grammar` 四个字段，这些字段在 **v0.12.0 已移除**,统一改走 `structured_outputs`(`json` / `regex` / `choice` / `grammar` / `structural_tag`)。网上大量旧教程还在用 `guided_json`,照抄会直接报参数错误——以你所用版本的 `vllm serve --help` 和官方文档为准。

### 6.2 JSON mode 与严格 JSON Schema 的区别

这是最容易混的一对：

| 📊 对比 | JSON mode(`json_object`) | 严格 JSON Schema(`json_schema`) |
|---|---|---|
| 保证 | 输出是**合法 JSON** | 输出**符合指定 schema**（字段、类型、enum、嵌套全查） |
| 字段名/类型 | 模型自由决定 | 由 schema 钉死 |
| 约束成本 | 低（只约束“是个 JSON”） | 高（schema 越大，合法空间越小） |
| 典型用法 | 只想 `json.loads` 不崩 | 下游按固定字段解析、接 Agent/工具 |

```python
# JSON mode:只保证能 json.loads,字段随便
response_format={"type": "json_object"}

# 严格 schema:字段、类型全部约束
response_format={"type": "json_schema",
                 "json_schema": {"name": "person", "schema": {...}}}
```

💡 **提示**：JSON mode 在 vLLM 内部也是受限解码——它用一个“任意合法 JSON”的宽松 schema 去约束，只是约束得非常松。所以“JSON mode 更省”的说法不准确：省的是**约束强度带来的质量风险**,不是引擎开销。

### 6.3 离线推理

离线场景用 `StructuredOutputsParams` 包在 `SamplingParams` 里：

```python
from vllm import LLM, SamplingParams
from vllm.sampling_params import StructuredOutputsParams

llm = LLM(model="Qwen/Qwen2.5-7B-Instruct")
sampling_params = SamplingParams(
    max_tokens=128,
    structured_outputs=StructuredOutputsParams(choice=["positive", "negative"]),
)
out = llm.generate("这个电影好看吗:情节紧凑、特效炸裂", sampling_params)
print(out[0].outputs[0].text)   # 只会是 positive 或 negative
```

## 7. 权衡：约束越强，质量越险

### 7.1 结构化输出牺牲了什么

每项技术都要答“牺牲什么、换取什么”。结构化输出：

- **换取的**：语法级 100% 保证——下游解析零失败、Agent 动作可执行、评测可复现。这是硬约束，不是概率。
- **牺牲的**：采样自由度。合法集合从整个词表缩小到文法允许的子集，分布的熵下降，输出多样性降低；**约束得越狠，模型“想说的”与“能说的”差距越大，质量越可能下降**。

过度约束的典型翻车：把 `description` 字段的枚举定死为 `["positive", "negative"]`,模型本来想表达“中立但有保留”,被强制二选一后只能瞎选一个；再比如用正则把自由文本的长度钉死，模型被迫截断语义。**约束的是格式，不是语义——别用格式约束去替模型做语义决策**。

### 7.2 落成一句话的规则

- ✅ **下游要按固定字段解析 / 接 Agent / 接工具** → 严格 JSON Schema(`json_schema`),字段和类型钉死，解析零失败。
- ✅ **只要 `json.loads` 不崩、字段内容模型自由发挥** → JSON mode(`json_object`)或宽松 schema,别上重约束。
- ✅ **输出是 SQL / 命令 / 自定 DSL** → 用 `grammar`,正则表达不了递归结构。
- ✅ **多租户、schema 天天变、首请求延迟敏感** → 后端选 guidance;固定 schema 高并发 → 默认 auto（通常落 xgrammar）即可。
- ❌ **别把 enum 收得太死、别用正则钉死自由文本**——约束强度每加一档，质量风险升一档，先小步验证再收紧。
- ❌ **别为了“结构化”给纯闲聊请求也套 schema**——能省则省，约束不是越多越好。

## 📝 总结

1. **机制**：受限解码 = 每一步按自动机状态生成合法 token 集合，把集合外 logits 置 -inf;约束加在采样路径上，输出语法级 100% 合法——检查员逐格核对申报单，填错当场打回。
2. **表达力边界**：正则 ⊂ 上下文无关；任意深度嵌套的 JSON 需要 CFG → PDA,XGrammar 正是走这条路。
3. **后端差异**：XGrammar 用“词表二分 + 预缓存 + 重叠执行”把文法执行做到最高 100x 加速、端到端近零开销（vLLM 集成后 TPOT 最高 +5x）；cFSM 用压缩 FSM + jump-forward 把固定前缀一次 prefill 完，延迟降 2x、吞吐升 2.5x。
4. **性能真相**：开销在 CPU 侧的 mask 生成（词表 151,936 → 每步 ~18.5 KB/请求），不在 GPU 应用侧；vLLM V1 挪到调度器级后单请求不再卡全批。
5. **与投机解码**：draft 也要受约束，接受率会降，收益边界要重测（V1 已支持联用，以版本矩阵为准）。
6. **开启方式**：`structured_outputs`(`json`/`regex`/`choice`/`grammar`),`guided_*` 已移除；JSON mode 与 JSON Schema 是“松约束”与“紧约束”之别。
7. **权衡**：语法保证换采样自由度，约束越强质量越险；约束格式，别约束语义。
