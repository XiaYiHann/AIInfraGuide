一次 `time.time()` 得到的单个数字，既可能混入首次初始化，也可能在 CUDA 工作完成前就停表。**可信性能证据至少包含 4 类记录：正确性、固定输入与环境、预热与同步边界、重复测量分布。** `torch.utils.benchmark` 负责回答“这段代码在本机要多久”，`torch.profiler` 负责回答“时间和内存事件落在哪里”；两者职责不同，不能拿一张 trace 代替基准，也不能拿一个中位数解释根因。

## 本节定位

**前置知识**：完成 [4.0 PyTorch 框架快速入门](/AIInfraGuide/prerequisites/模块一-前置知识/pyroch/pytorch框架入门/)、[4.5 训练循环工程](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/45-训练循环工程/)、[4.6 CUDA 异步执行](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/46-cuda异步执行/)与 [4.7 显存管理](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/47-显存管理/)。你应能跑通 CPU 训练 step，知道 CUDA API 返回不等于 GPU 完成，并能区分当前与峰值显存。

**学习成果**：读完后，你能先写 correctness gate，再冻结输入、环境和控制变量；能用 `Timer.blocked_autorange()` 生成重复测量，用 `Compare` 对齐候选实现；能同时报告中位数、IQR 和原始分布；能用 `schedule(wait, warmup, active, repeat)`、`record_function` 和 Chrome trace 定位框架热点；能在 CPU-only 环境明确降级，而不假装收集过 CUDA activity。

**够用边界**：本节建立 PyTorch 框架侧的微基准和时间线纪律，不解释 Kernel 的 warp stall、带宽利用率、occupancy 或系统级跨进程时间线。那些问题进入模块二的 Nsight 工具链。本文与示例都不提供通用性能数字，也不设置“必须快多少”的测试阈值。

## 1. 为什么 correctness 必须先于 performance

### 1.1 更快的错误答案有意义吗？

想象两名仓库拣货员比赛：一人按单取齐 100 件货，另一人漏掉 10 件，所以更早回来。只比较秒表会奖励错误实现。**Benchmark 的第一个断言必须是候选实现满足同一个输出契约；性能只能在正确实现之间比较。**

本节示例把固定 Tensor 同时送入两个等价表达式：

```python
reference = torch.relu(input_tensor)
candidate = input_tensor.clamp_min(0)
assert torch.equal(reference, candidate)  # 通过后才创建 Timer
```

真实算子不能机械照搬 `torch.equal`。应根据语义选择判据：

- **精确整数/索引结果**：元素、shape、dtype 和 device 都精确一致；
- **浮点近似结果**：固定 `rtol/atol`，记录最大绝对/相对误差，并覆盖边界输入；
- **随机算法**：固定随机性口径，验证分布或统计性质，而不是只比某次样本；
- **训练改写**：至少验证 loss、梯度和参数更新边界，不能只看 forward 输出。

⚠️ **注意**：降低精度、删掉同步、少算分支都可能“提速”。如果这些是有意权衡，要先把新语义写成明确契约并单独验收；不能把行为变化藏在 benchmark 名字里。

### 1.2 性能测试为什么也要保留失败路径？

问题是：输入配置非法时，脚本应继续给一个数字吗？**不能；错误配置要尽早拒绝，否则不可解释的结果会混进报告。** 示例明确拒绝非正 shape、线程数、`min_run_time`、Profiler `active/repeat`，也拒绝在无 CUDA 时强行请求 CUDA。

这条纪律与 4.2 的 `gradcheck` 相同：不仅证明正确路径会通过，还要证明错误输入不会被静默接受。

## 2. 怎样冻结一个可比较的 benchmark

### 2.1 “只改一个变量”具体要固定什么？

打个比方：比较两种跑鞋，却让甲在塑胶跑道跑 100 米、乙在沙地跑 80 米，成绩没有可比性。**候选实现之外的输入、环境、线程和完成边界都要相同。**

一份最小实验配置至少记录：

| 类别 | 必须固定或记录的字段 | 为什么 |
|---|---|---|
| 正确性 | 参考实现、误差判据、失败输入 | 防止奖励错误结果 |
| 输入 | shape、dtype、device、布局、值分布、seed | 这些字段会改变算子路径 |
| 软件 | Python、PyTorch、CUDA runtime、编译选项 | 版本可能改变实现 |
| 硬件 | CPU/GPU 型号、逻辑核数、线程数 | 执行资源不同不可直接横比 |
| 运行 | 预热、正式时长、同步点、后台负载 | 冷启动和异步会污染区间 |
| 统计 | replicates、每块循环数、median、IQR、原始样本 | 单点看不见噪声与离群 |

本节示例固定 `256×256`、float32、strided contiguous 布局、值域 `[-3, 3]`、seed `20260810` 和 1 个 CPU 线程；比较时唯一变化是 `torch.relu(x)` 与 `x.clamp_min(0)`。报告还会明确写出预热由每次 `blocked_autorange` 承担、后台负载未受脚本控制；后者是应保留的限制，不是假装已经冻结的变量。这些配置只是**可复现的教学工作负载**，不是对模型训练的代表性声明。

### 2.2 环境固定是否意味着结果能跨机器复用？

不是。固定环境让同一实验可以解释和复跑，却不保证另一台机器得到相同数字。CPU 频率、GPU 型号、驱动、热状态、共享负载和 PyTorch 版本都会改变观测。

所以报告必须写清作用域：

```json
{
  "scope": "local_observation_not_general_conclusion",
  "environment": {"pytorch": "本机实际版本", "cuda_device": "本机实际设备"}
}
```

📌 **关键点**：可复现不是“数字永远相同”，而是“输入、环境、操作和统计口径足够完整，别人知道差异可能从哪里来”。

## 3. Timer、blocked_autorange 与 Compare 怎样配合

### 3.1 为什么不直接写 Python for 循环计时？

普通循环容易把计时器调用、线程池设置和 CUDA 异步边界混进结果。**`torch.utils.benchmark.Timer` 在 `timeit.Timer` 的基础上增加 PyTorch-aware 的预热、线程控制和必要的异步 accelerator 同步。** 它仍然只能测你圈定的 statement；错误边界不会因为换了工具自动正确。

```python
from torch.utils import benchmark

relu_timer = benchmark.Timer(
    stmt="torch.relu(input_tensor)",
    globals={"torch": torch, "input_tensor": input_tensor},
    label="fixed-shape elementwise activation",
    sub_label="256x256 float32 on cpu",
    description="torch.relu",
    num_threads=1,
)
measurements = [
    relu_timer.blocked_autorange(min_run_time=0.05)
    for _ in range(5)
]
```

`setup`/`globals` 中准备输入，`stmt` 中只保留要测的操作。若把随机数据生成、设备搬运或日志打印塞进 `stmt`，你测到的就不再是同一个问题。

### 3.2 `blocked_autorange` 做了哪两层工作？

问题是：一个操作很短，每次都启停计时器会不会喧宾夺主？**`blocked_autorange` 先预热并估计 `block_size`，让一次计时器调用包住多次 statement；当前官方文档说明，它把计时器开销目标压到该 block 总时间的 0.1% 以下，再持续采样到至少 `min_run_time`。**

每个原始 block 时间 $r_i$ 要除以该 block 内执行次数 $n$，才得到单次调用样本：

$$
\underbrace{t_i}_{\text{单次调用时间}}
=
\frac{\underbrace{r_i}_{\text{第 i 个 block 原始时间}}}
{\underbrace{n}_{\text{number\_per\_run}}}
$$

一次短 `blocked_autorange` 可能只返回一个大 block，因此示例对每个候选独立执行 5 次，再把各次 `raw_times` 归一化后的 `seconds_per_call` 合并；报告同时保存每次 `number_per_run` 和总样本数，并拒绝少于 3 个样本的报告。这样至少形成可计算 IQR 的课程 smoke 分布，避免只留下一个格式化字符串。

💡 **提示**：`min_run_time=0.05` 是课程 smoke 为控制时长采用的本地配置，不是稳定 benchmark 的通用充分条件。噪声大时增加测量时长和独立进程重复，并记录热状态与后台负载。

### 3.3 `Compare` 解决什么，不解决什么？

`Compare` 使用 Timer 的 `label/sub_label/description` 元数据对齐多组 `Measurement` 并打印对比表：

```python
measurements = [relu_result, clamp_result]
benchmark.Compare(measurements).print()
```

它换来统一展示，不会替你验证正确性、冻结环境或解释根因。若两项使用了不同 shape，即使表格排得整齐也仍是错误实验。

## 4. 统计量和分布应该怎样读

### 4.1 为什么不能只报“最好一次”？

最好值倾向于挑中最幸运的调度和缓存状态；均值又容易被少数长尾拉高。**至少同时报告中位数、IQR 和原始重复样本，让中心位置与离散程度一起出现。**

对排序后的样本：

$$
\underbrace{\tilde{t}}_{\text{median}}
=\operatorname{median}(t_1,\ldots,t_N),
\qquad
\underbrace{IQR}_{\text{中间 50\% 的跨度}}
=Q_{0.75}-Q_{0.25}
$$

取一个只用于说明统计量、不是本文实测的玩具序列 `9, 10, 10, 10, 11, 12, 40`：中位数是 10，最后的 40 清楚显示长尾；只报“最快 9”会隐藏波动，只报均值也会被 40 拉动。工程判断应回到完整分布，并追问长尾是否来自调度、首次路径、输入变化或同步。

### 4.2 中位数更小就能宣布优化成功吗？

不能机械宣布。至少检查：

1. correctness gate 是否仍通过；
2. 两组 IQR 相对差异是否大到淹没中位数差异；
3. 是否在多个独立进程/时间段复现；
4. 目标训练 step 中该操作是否真是热点；
5. 优化是否把成本移到未计时区间，例如额外预处理、复制或同步。

**Benchmark 证明“圈定区间的局部时间”，不自动证明端到端吞吐、延迟或成本改善。**

## 5. Profiler 怎样用计划采样截取时间线

### 5.1 Benchmark 和 Profiler 到底差在哪？

| 工具 | 首要问题 | 主要产物 | 不应该承担 |
|---|---|---|---|
| `torch.utils.benchmark` | 固定区间在本机耗时分布怎样 | `Measurement`、median、IQR、replicates、`Compare` | 解释每个算子/线程为何等待 |
| `torch.profiler` | CPU/CUDA 事件、算子、内存和用户标记落在哪里 | key averages、事件时间线、Chrome trace | 充当低扰动性能 baseline |
| Nsight Systems | 系统级 CPU-GPU、进程、通信和 idle gap 怎样排列 | 系统时间线 | 给出单个 Kernel 的指令级瓶颈 |
| Nsight Compute | 一个 CUDA Kernel 为什么受算力、内存或 stall 限制 | Kernel 指标与报告 | 描述完整训练控制流 |

📌 **关键点**：先用 benchmark 量“有没有稳定差异”，再用 profiler 找“差异落在哪里”；需要系统/Kernel 下钻时再进入 Nsight。工具越深，采集成本与解释责任通常越高。

### 5.2 schedule 的四个阶段怎样走？

连续记录完整训练会生成巨大 trace，也会让采集本身明显扰动工作负载。**Profiler schedule 用 wait、warmup、active 和 repeat 把长循环切成受控窗口。**

```python
schedule = torch.profiler.schedule(
    wait=1,
    warmup=1,
    active=2,
    repeat=1,
)
```

一次周期可理解为：

```text
step 0: wait      不记录
step 1: warmup    启动采集但丢弃这段结果
step 2: active    正式记录
step 3: active    正式记录，并在周期末交付 trace
```

总循环步数为：

$$
\underbrace{S}_{\text{调用 profiler.step 的总步数}}
=
(\underbrace{W}_{wait}+\underbrace{U}_{warmup}+\underbrace{A}_{active})
\times\underbrace{R}_{repeat}
$$

代入 $W=1,U=1,A=2,R=1$，得到 4 步。**循环每一步末尾都要调用 `profiler.step()`**，否则 schedule 不知道训练已经前进。本节的最小 exporter 固定 `repeat=1`，因为它只交付一个 trace 路径；若要多周期采样，`on_trace_ready` 必须为每个周期生成唯一文件名或交给 TensorBoard handler，不能反复覆盖同一文件。

```python
with torch.profiler.profile(
    activities=[torch.profiler.ProfilerActivity.CPU],
    schedule=schedule,
    on_trace_ready=export_ready,
) as prof:
    for _ in range(4):
        run_one_step()
        prof.step()
```

### 5.3 `record_function` 为什么值得加？

算子名字能看到 `aten::mm`，却不一定告诉你它属于 data、forward、backward 还是 optimizer。**`record_function` 用少量用户标记换来业务阶段边界，让 trace 能从框架算子回到训练语义。**

```python
with record_function("benchmark_profiler.step"):
    with record_function("benchmark_profiler.forward"):
        output = model(inputs)
        loss = output.square().mean()
    with record_function("benchmark_profiler.backward"):
        loss.backward()
```

标记要稳定、分层适度。若给每一行 Python 都加 marker，trace 只会更拥挤；优先标 data、forward、backward、optimizer、communication 等可作决策的阶段。

## 6. shape、stack、memory 和 trace 各换来什么

### 6.1 三个证据开关应该永久全开吗？

**不应该。它们换来更多诊断上下文，也会增加采集开销和 trace 体积。**

| 开关 | 换来的证据 | 代价与边界 |
|---|---|---|
| `record_shapes=True` | 算子输入 shape，可按 shape 解释动态路径 | 记录更多元数据；只在需要区分 shape 时开启 |
| `with_stack=True` | 事件对应的 Python/源码调用栈 | 栈采集和文件体积增加；聚焦短窗口 |
| `profile_memory=True` | Tensor 内存分配/释放事件与内存列 | 额外追踪开销；不等于 4.7 的完整 allocator/snapshot 诊断 |

正确用法是两条实验线分开：

1. **低扰动 baseline**：关闭这些选项，用 `Timer` 测分布；
2. **诊断 run**：只在短 active 窗口开启必要证据，定位 shape、调用栈或内存事件。

不要比较“Profiler 打开前后的时间”后把差异解释成模型退化；那里面包含 instrumentation 本身。

### 6.2 trace 怎样导出和验收？

本节示例在 `on_trace_ready` 回调中调用：

```python
def export_ready(profiler):
    profiler.export_chrome_trace("benchmark-profiler-cpu.json")
```

导出的 Chrome trace 是 JSON。示例和测试不只检查文件存在，还解析：

- 根对象包含非空 `traceEvents`；
- 事件中存在 `benchmark_profiler.step`；
- 文件字节数和事件数被写进报告；
- schedule 里的 wait/warmup/active/repeat 一并保存。

可在 Perfetto/Chrome trace viewer 等兼容查看器打开。Trace 可能含源码路径、算子名和运行元数据，分享前按项目的数据处理规则审查。

## 7. 跑通 CPU 示例与可选 CUDA 路径

### 7.1 CPU 怎样完成最小验收？

完整源码位于 `examples/pytorch/benchmark_profiler.py`，测试位于 `examples/pytorch/tests/test_benchmark_profiler.py`。从仓库根目录执行：

```bash
python3 examples/pytorch/benchmark_profiler.py \
  --device cpu \
  --output-dir /tmp/aiinfraguide-pytorch-4.8
python3 -m unittest examples/pytorch/tests/test_benchmark_profiler.py -v
python3 -m compileall examples/pytorch/benchmark_profiler.py \
  examples/pytorch/tests/test_benchmark_profiler.py
```

脚本依次执行：

1. `torch.relu(x)` 与 `x.clamp_min(0)` 的精确正确性断言；
2. 每个候选执行 5 次 `Timer.blocked_autorange`，合并且保留完整 per-call 分布；
3. `Compare` 表格；
4. schedule Profiler 与 `record_function`；
5. Chrome trace 结构验证；
6. 报告 schema 验证。

完成标志为：

```text
all benchmark-profiler checks passed; timings are local observations only
```

报告中的时间来自你运行命令的本机；文章不抄录某次输出，也不把它推广为 PyTorch API 的固定快慢关系。测试要求每个候选至少保留 3 个样本，并检查 schema、输入布局和值域、预热/后台负载口径、trace 生成与错误路径，**不设任何速度阈值**。

### 7.2 shape、stack、memory 怎样按需开启？

```bash
python3 examples/pytorch/benchmark_profiler.py \
  --device cpu \
  --record-shapes \
  --with-stack \
  --profile-memory \
  --output-dir /tmp/aiinfraguide-pytorch-4.8-diagnostic
```

把这次当诊断 run，而不是 baseline。比较两个候选实现的时间仍应回到未开启重型证据的 Timer 报告。

### 7.3 CUDA 可用与不可用时分别发生什么？

```bash
python3 examples/pytorch/benchmark_profiler.py \
  --device auto \
  --output-dir /tmp/aiinfraguide-pytorch-4.8-auto
```

- **CUDA 可用**：先跑 CPU 与 CUDA correctness/benchmark；Profiler activities 同时包含 CPU 和 CUDA；输入创建后、Profiler 结束后有显式同步，`Timer` 负责测量 block 的 accelerator 完成边界。
- **CUDA 不可用**：只跑 CPU benchmark 和 CPU activity；报告明确写 `GPU timing and CUDA activity were not measured`。
- **显式 `--device cuda` 但无 CUDA**：立即抛错，不静默切 CPU。

⚠️ **注意**：CUDA 路径通过只证明当前小工作负载的计时与 trace 管线能运行，不证明任何真实训练模型更快，也不代替 4.6 的 stream/Event 正确性实验。

### 7.4 报告 schema 为什么要稳定？

顶层字段固定为：

```json
{
  "schema_version": "1.0",
  "scope": "local_observation_not_general_conclusion",
  "environment": {},
  "protocol": {},
  "benchmarks": [],
  "profiler": {}
}
```

Benchmark 项保存 correctness、输入配置、唯一控制变量和各候选分布；Profiler 项保存 activities、schedule、证据开关、trace 与记录到的 operator 名。测试会删除必填字段、清空分布，确认校验器明确拒绝错误报告。

## 8. 常见错误与诊断

| 症状 | 首个检查项 | 最小修复 |
|---|---|---|
| “优化版”更快但输出不同 | correctness gate 是否在 Timer 前 | 先固定语义与误差判据，错误实现不进入性能比较 |
| 第一次特别慢 | 是否把初始化/缓存建立放进正式区间 | 用相同 shape/dtype/path 预热，再开始正式测量 |
| CUDA 时间小得像只执行了 Python | 是否等待设备完成 | 使用 Timer 的 accelerator-aware 边界，或按 4.6 显式同步/Event |
| 两组数字不可比较 | shape、dtype、device、线程或 seed 是否同时变化 | 一次只改实现，其他配置写进报告 |
| 中位数变化小于分布波动 | IQR 与原始 samples 是否重叠 | 增加测量时长/独立重复，先查噪声，不急着宣布收益 |
| `Compare` 表很漂亮但结论错误 | label 相同是否掩盖了输入不同 | 对照 config，而不是相信排版 |
| schedule 没有导出 trace | 循环中是否每步调用 `profiler.step()` | 按 `(wait+warmup+active)×repeat` 驱动完整周期 |
| trace 太大、训练明显变慢 | shape/stack/memory 是否长期全开 | 缩短 active 窗口，只启用当前诊断所需证据 |
| CPU-only 运行却添加 CUDA activity | `torch.cuda.is_available()` 是否为真 | activities 只放 CPU，并把 CUDA 路径列为未测 |
| Profiler 显示热点却不知道该怎么改 | 是否把“哪里慢”误当成“为什么慢” | 框架阶段先缩小热点，再到 Nsight/源码做根因分析 |
| 测得局部更快，端到端却没变化 | 热点占比与成本是否移出区间 | Profile 完整 step，并把预处理、复制、同步纳入端到端对照 |

📌 **关键点**：遇到性能数字时依次问四句——“结果对吗、口径同吗、分布稳吗、这个区间是端到端热点吗”。答不全就还不是结论。

## 9. 权衡、选型与课程边界

### 9.1 应该先选 Benchmark 还是 Profiler？

**先按你要回答的问题选工具，不按工具的“高级程度”选。**

| 工程问题 | 首选 | 换取什么 | 牺牲什么 / 风险 |
|---|---|---|---|
| 两种短实现谁在固定输入上更快 | `Timer.blocked_autorange` + `Compare` | 低噪声重复分布 | 只能解释被圈定区间 |
| 一个训练 step 的时间落在哪里 | `torch.profiler` + `record_function` | 框架算子与业务阶段时间线 | instrumentation 开销与大 trace |
| 动态 shape 是否触发不同热点 | Profiler `record_shapes` | shape 上下文 | 更多采集开销和元数据 |
| 哪行代码发起热点 | Profiler `with_stack` | 调用栈 | 栈采集与文件体积 |
| Tensor 分配事件在哪出现 | Profiler `profile_memory` | 事件级内存线索 | 不代替 allocator snapshot，采集有开销 |
| CPU-GPU/通信为何出现 idle gap | Nsight Systems | 系统级时间线 | 超出 PyTorch 章，工具链更重 |
| 单个 Kernel 为何 memory/compute bound | Nsight Compute | Kernel 级硬件指标 | 不能代替端到端框架上下文 |

落成一句话：**Benchmark 定量，Profiler 定位，Nsight 下钻；correctness 是三者共同的入口门禁。**

### 9.2 与 4.6、4.7、4.9 的边界是什么？

- **[4.6 CUDA 异步执行](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/46-cuda异步执行/)**：解释 enqueue/completion、Event、stream、隐式同步和正确 CUDA 计时。4.8 使用这些完成边界建立重复实验，不再展开跨 stream 依赖。
- **[4.7 显存管理](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/47-显存管理/)**：解释 allocated/reserved/peak、引用、碎片、summary 与 snapshot。4.8 的 `profile_memory` 只把内存事件放回算子时间线，不替代 OOM 证据链。
- **[4.9 自定义算子与 Dispatcher](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/49-自定义算子与dispatcher/)**：先定义算子 schema、后端注册、fake/meta 与 Autograd 组合性；4.8 提供 correctness-first 的性能验收方法。不能因为自定义 Kernel 更快就跳过 Dispatcher/梯度正确性。

### 9.3 与模块二 Nsight 的边界是什么？

本节停在 PyTorch 事件：能看见训练阶段、ATen 算子、CPU/CUDA activity、shape/stack/memory 线索。**[模块二第 8 章：性能分析工具链](/AIInfraGuide/cuda/模块二-cuda编程与算子优化/第8章-性能分析工具链/) 才使用 Nsight Systems 解释系统级 idle gap，使用 Nsight Compute 判断单个 Kernel 的 memory/compute bound、occupancy 与 warp stall。**

进入模块二前，你应先从 PyTorch trace 缩小到稳定热点，并带上固定输入、环境、正确性判据和 benchmark 分布。否则 Nsight 报告再细，也可能只是在精确分析一个不重要或不正确的路径。

## 📝 总结

1. **正确性门禁**：性能比较之前先证明候选实现满足同一输出、梯度或状态契约；错误实现不进入计时。
2. **实验冻结**：固定 shape、dtype、device、值分布、seed、线程、软件硬件和同步边界，一次只改一个变量。
3. **Timer 职责**：`blocked_autorange` 通过预热、block 估计和重复采样降低计时偏差，`Compare` 只负责对齐展示。
4. **统计纪律**：报告 median、IQR、replicates 和完整 per-call 样本；不挑最快一次，也不把一次本机观测推广为通用结论。
5. **Profiler 职责**：schedule 用 wait/warmup/active/repeat 控制窗口，循环每步调用 `profiler.step()`，`record_function` 建立业务阶段边界。
6. **证据开销**：shape、stack、memory 换来额外上下文，也增加 instrumentation；诊断 run 与 baseline 分开。
7. **Trace 验收**：导出的 Chrome trace 必须可解析、含 `traceEvents` 和用户 marker，报告同时保存 activities 与 schedule。
8. **降级与边界**：CPU 可以完成完整报告与 trace；无 CUDA 时明确列出 GPU timing/CUDA activity 未测；Nsight 下钻留给模块二。
