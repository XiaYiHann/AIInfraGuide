## 1. 动态 DAG 怎样记录一次计算

### 1.1 为什么每次前向都能走不同分支？

打个比方：食堂不是先印一张覆盖所有可能菜品的固定流程图，而是按你这一次真正点的菜打印小票。你点炒饭，小票记录“取饭→加蛋→翻炒”；你点面条，则记录另一条路径。**PyTorch 同样按本次实际执行的 Tensor 操作，从头创建一张有向无环图（DAG）；运行了哪条 Python 分支，就对哪条路径求导。**

在图里，Tensor 承载数值，Autograd 的 `Function` 节点表达操作历史；一个非叶 Tensor 的 `grad_fn` 是进入其反向图的入口。下面两次前向使用普通 Python 控制流，却得到不同节点：

```python
import torch


def branch(value: torch.Tensor, use_square: bool) -> torch.Tensor:
    if use_square:
        return value.square()
    return value * 3

x1 = torch.tensor(2.0, requires_grad=True)
y1 = branch(x1, True)
y1.backward()

x2 = torch.tensor(2.0, requires_grad=True)
y2 = branch(x2, False)
y2.backward()

print(type(y1.grad_fn).__name__, x1.grad)  # PowBackward0, tensor(4.)
print(type(y2.grad_fn).__name__, x2.grad)  # MulBackward0, tensor(3.)
```

`PowBackward0` 这类名字是调试线索，不是应写进业务逻辑的稳定接口。稳定事实是：`y1.grad_fn` 与 `y2.grad_fn` 都非空，而且反向结果分别服从真实执行的平方与乘法分支。

### 1.2 反向传播到底算的是什么？

问题是：图已经记下操作，梯度怎样沿图返回输入？**反向模式自动微分从输出沿边反向应用链式法则，实际传播的是向量—雅可比乘积（VJP），而不是在每个节点物化完整雅可比矩阵。**

取

$$
\underbrace{y=x^3}_{\text{前向}}
\quad\Rightarrow\quad
\underbrace{\frac{\partial y}{\partial x}=3x^2}_{\text{一阶导}}
\quad\Rightarrow\quad
\underbrace{\frac{\partial^2 y}{\partial x^2}=6x}_{\text{二阶导}}
$$

代入 $x=2$，一阶导为 $3\times2^2=12$，二阶导为 $6\times2=12$。这两个确定值会在后面的 CPU 测试中同时验证。

💡 **提示**：标量输出调用 `backward()` 时，传入梯度默认为 1。非标量输出不是“不能反向”，而是必须显式给出与输出兼容的 `gradient`，说明要计算哪一个 VJP；训练里常把 loss 规约成标量，所以最常见代码看不到这个参数。

### 1.3 leaf、non-leaf 与 `grad_fn` 怎样对应？

为什么 `x.grad` 有值，中间结果的 `.grad` 默认却没有？**`backward()` 默认只把梯度累积进 `requires_grad=True` 的叶 Tensor；参与可微图的 non-leaf 梯度用于继续链式传播，若要调试它，必须先调用 `retain_grad()`。**

```python
leaf = torch.tensor(2.0, requires_grad=True)
non_leaf = leaf * 3
non_leaf.retain_grad()          # 仅为调试保留中间梯度
loss = non_leaf.square()
loss.backward()

print(leaf.is_leaf, leaf.grad_fn)       # True, None
print(non_leaf.is_leaf, non_leaf.grad_fn)  # False, <MulBackward0 ...>
print(leaf.grad)       # tensor(36.)
print(non_leaf.grad)   # tensor(12.)
```

数值可以手算：`non_leaf=6`，所以 $\partial loss/\partial non\_leaf=2\times6=12$；再乘 $\partial non\_leaf/\partial leaf=3$，叶节点梯度为 $36$。

📌 **关键点**：`requires_grad=True` 回答“这条计算是否需要参与求导”，`is_leaf` 回答“它是否由被记录的操作产生”，`grad_fn` 回答“从哪个反向节点进入历史”。三者相关，但不是同一个字段。

## 2. 梯度为何会累积以及反向保存了什么

### 2.1 为什么第二次 `backward()` 不是覆盖 `.grad`？

想象一个收件箱：两条支路都把对同一参数的贡献投进来，Autograd 必须相加，才能得到总导数。**叶 Tensor 的 `.grad` 使用累加语义；清零、设为 `None` 或有意跨 micro-batch 累积，必须由训练循环决定。**

```python
x = torch.tensor(2.0, requires_grad=True)
(x * 3).backward()
print(x.grad)  # tensor(3.)

(x * 4).backward()
print(x.grad)  # tensor(7.)，不是 tensor(4.)

x.grad = None  # 下一轮从“没有梯度”开始
```

这里两次使用的是两张新图，所以不需要 `retain_graph=True`；只有 `.grad` 这个累加目标相同。训练中 `optimizer.zero_grad(set_to_none=True)` 常把参数梯度设为 `None`，而梯度累积训练则故意隔多个 micro-batch 再清零。两者的工程含义不同，不能靠“每次都清”或“永远不清”解决。

### 2.2 backward 为什么需要 saved tensors？

问题是：只知道“做过平方”还不够，平方的反向还需要原输入 $x$ 才能算 $2x$。**某些操作会在 forward 保存 backward 所需 Tensor；内置操作自动决定保存内容，自定义 Function 则通过 `ctx.save_for_backward()` 保存，并从 `ctx.saved_tensors` 取回。**

```python
from torch.autograd import Function


class CustomSinh(Function):
    @staticmethod
    def forward(input_tensor):
        return input_tensor.sinh()

    @staticmethod
    def setup_context(ctx, inputs, output):
        del output
        (input_tensor,) = inputs
        ctx.save_for_backward(input_tensor)

    @staticmethod
    def backward(ctx, grad_output):
        (input_tensor,) = ctx.saved_tensors
        return grad_output * input_tensor.cosh()
```

只保存反向确实需要的 Tensor，可以缩短无关对象的生命周期；多保存则会让更多数据活到反向。官方文档还提供 `saved_tensors_hooks` 控制保存 Tensor 的 pack/unpack，用于 offload 等高级场景，但那会引入数据移动、生命周期和正确性责任，本节只建立入口心智模型。

⚠️ **注意**：内置节点上以 `_saved...` 开头的属性适合教学观测，却属于实现细节。官方明确提醒，保存后的对象身份可能因 pack/unpack 改变；不要依赖 `_saved_self` 的具体名字或 `is` 身份编写业务代码。

### 2.3 版本计数怎样拦住过期数据？

4.1 已经证明视图和 base 可能共享 storage。问题是：forward 保存了 `x=2`，你却在 backward 前把同一数据原地改成 3，反向应该用哪个值？**每个 Tensor 带版本计数；原地修改会递增版本，读取 saved tensors 时若版本与保存时不一致，Autograd 抛错而不是用过期值静默计算。**

```python
x = torch.tensor([2.0], requires_grad=True)
y = x.square()                 # backward 需要保存 x
print(x._version)              # 教学观测：0

with torch.no_grad():
    x.add_(1)                  # 原地写入，版本变成 1

print(x._version)
try:
    y.backward()
except RuntimeError as error:
    print("version guard:", error)
```

`_version` 同样只用于教学和调试，稳定契约是“所需 Tensor 被原地改写时，正确性检查会报错”。Autograd 官方说明，原地操作还要处理图重写和别名，因此通常不建议使用；**原地写牺牲了图与别名管理的简单性，却往往换不到显著内存收益。** 没有可复现实验前，不要把名字带下划线的 API 当成性能优化。

## 3. 三种停梯度方式怎样选

### 3.1 `detach`、`no_grad`、`inference_mode` 有何不同？

为什么 PyTorch 提供三个看似都“不要梯度”的入口？**`detach()` 针对一个 Tensor 切断历史，`no_grad` 针对一段操作不记录图，`inference_mode` 进一步关闭 Autograd 跟踪，但限制其产物回到后续需要记录的计算。**

| 需求 | 选择 | 换取什么 | 牺牲什么 / 风险 |
|---|---|---|---|
| 从某个 Tensor 截断梯度 | `tensor.detach()` | 得到不跟踪历史的 Tensor | 默认共享 storage，原地修改仍有别名风险 |
| 参数更新、初始化或局部无图计算 | `torch.no_grad()` | 该代码块不进入反向图，产物可在之后的 grad mode 使用 | 块内即使输入需要梯度也不记录操作 |
| 纯推理或纯数据处理 | `torch.inference_mode()` | 关闭更多 Autograd 跟踪工作 | inference tensor 不能再进入需要 Autograd 保存它的计算 |

📌 **关键点**：选择依据不是“哪个听起来更快”，而是产物以后是否要参与被 Autograd 记录的计算。本文不做性能测量，只验证生命周期和错误边界。

```python
source = torch.tensor([1.0, 2.0], requires_grad=True)
intermediate = source * 2
stopped = intermediate.detach()
assert not stopped.requires_grad
assert stopped.untyped_storage().data_ptr() == intermediate.untyped_storage().data_ptr()

with torch.no_grad():
    reusable = source * 3
later = torch.ones(2, requires_grad=True)
(later * reusable).sum().backward()  # 合法，later.grad == [3, 6]

with torch.inference_mode():
    inference_value = torch.ones(2)
tracked = torch.ones(2, requires_grad=True)
# (tracked * inference_value).sum().backward()
# RuntimeError: inference tensor 不能被保存给 backward
```

若确实要把 `inference_value` 带回 grad mode，可在离开 inference mode 后 `clone()` 成普通 Tensor；这会付出一次复制。若这种交接频繁发生，说明 `no_grad` 可能更符合接口契约。

### 3.2 `model.eval()` 能替代这些模式吗？

常见误解是：调用 `model.eval()` 就关闭了梯度。**`eval()` 只切换 Module 的训练/评估行为，例如 Dropout 和 BatchNorm；它与 Autograd 的 grad mode 正交。** 验证模型时通常同时使用 `model.eval()` 和 `torch.inference_mode()`（或 `no_grad`），两者各管一层，不能互相替代。

## 4. 图复用、高阶梯度与 Hook

### 4.1 `retain_graph` 与 `create_graph` 分别保留什么？

一句话讲清：**`retain_graph=True` 保住当前反向所需的图资源以便再反向；`create_graph=True` 记录“求梯度”这次计算，以便继续求高阶导。** 前者解决复用，后者解决可微分的梯度计算，不要因为名字都有 graph 就混用。

```python
import torch

# 同一张前向图执行两次 backward
x = torch.tensor(3.0, requires_grad=True)
y = x.square()
y.backward(retain_graph=True)
print(x.grad)  # tensor(6.)
x.grad.zero_()
y.backward()
print(x.grad)  # tensor(6.)

# 为一阶导建立图，再求二阶导
z = torch.tensor(2.0, requires_grad=True)
cubic = z.pow(3)
first = torch.autograd.grad(cubic, z, create_graph=True)[0]
second = torch.autograd.grad(first, z)[0]
print(first, second)  # tensor(12.), tensor(12.)
```

`retain_graph=True` 会让原本可释放的反向资源继续存活；`create_graph=True` 会建立更大的可微分图。**两者都用额外生命周期与图复杂度换取能力，应只在确实要多次反向或求高阶导时开启。** 普通训练 step 不应习惯性打开它们来掩盖图复用错误。

### 4.2 Hook 应该用来观察还是修改？

问题是：你想看某个中间 Tensor 收到了什么梯度，是否必须改写 `Function.backward`？**`Tensor.register_hook` 可以在该 Tensor 的梯度被计算时观察梯度，也可以返回一个替代梯度；注册后要保留 handle，并在不需要时 `remove()`。**

```python
x = torch.tensor(3.0, requires_grad=True)
y = x.square()
observed = []


def halve_gradient(gradient):
    observed.append(gradient.item())
    return gradient * 0.5       # 返回新梯度，不原地改传入值

handle = y.register_hook(halve_gradient)
(4 * y).backward()
handle.remove()

print(observed)  # [4.0]，这是流入 y 的梯度
print(x.grad)    # tensor(12.)，4 被减半为 2，再乘 dy/dx=6
```

Hook 适合诊断、记录或明确设计的梯度变换，但它把行为藏在主计算代码之外。牺牲可见性换取插拔能力是否值得，要看团队能否追踪注册位置、触发顺序和移除时机。若是在定义一个新数学算子的导数，应写 `Function.backward`，而不是靠 Hook 拼出核心正确性。

## 5. 怎样实现并验证自定义 Function

### 5.1 什么时候才该写 `torch.autograd.Function`？

为什么不把所有公式都手写 backward？**如果 forward 已完全由 PyTorch 内置可微操作组成，Autograd 通常已经能记录它，普通 Python 函数更简单；只有接入非 PyTorch 实现、定义特殊导数，或有明确的保存策略需求时，才值得承担自定义 Function 的责任。**

一种与当前官方接口一致、组合性更清晰的结构是：

1. `forward` 只计算输出；
2. `setup_context` 只把 backward 需要的 Tensor 用 `save_for_backward` 保存；
3. `backward` 接收每个输出对应的 `grad_output`，并按输入顺序返回梯度；非 Tensor 或无需梯度的输入可返回 `None`；
4. 使用 `Function.apply(...)` 调用，不直接实例化类；
5. 用 `gradcheck` 对照数值雅可比与解析雅可比。

本节完整示例实现 $y=\sinh(x)$：

$$
\underbrace{y=\sinh(x)}_{\text{forward}}
\quad\Rightarrow\quad
\underbrace{\frac{\partial L}{\partial x}}_{\text{backward 返回}}
=
\underbrace{\frac{\partial L}{\partial y}}_{\text{grad\_output}}
\cdot
\underbrace{\cosh(x)}_{\text{局部导数}}
$$

```python
class CustomSinh(torch.autograd.Function):
    @staticmethod
    def forward(input_tensor):
        return input_tensor.sinh()

    @staticmethod
    def setup_context(ctx, inputs, output):
        del output
        (input_tensor,) = inputs
        ctx.save_for_backward(input_tensor)

    @staticmethod
    def backward(ctx, grad_output):
        (input_tensor,) = ctx.saved_tensors
        return grad_output * input_tensor.cosh()


y = CustomSinh.apply(x)
```

这里 backward 使用可微的 `cosh` 和乘法，所以这份实现还能参与更高阶求导。更复杂的 Function 若不支持 double backward，应按官方扩展说明显式声明并测试，而不是让错误悄悄流入训练。

### 5.2 `gradcheck` 怎样发现反向公式写错？

打个比方：解析 backward 是你写出的答案，有限差分是从函数两侧各挪一小步得到的独立验算。**`gradcheck` 分别构造解析与数值雅可比，再逐元素比较；正确反向应通过，故意把 $2x$ 写成 $3x$ 的 `WrongSquare` 必须失败。**

对实值函数的一维输入，中心差分的核心近似是：

$$
\underbrace{\frac{\partial f}{\partial x}}_{\text{数值梯度}}
\approx
\underbrace{\frac{f(x+\varepsilon)-f(x-\varepsilon)}{2\varepsilon}}_{\text{中心差分}}
$$

```python
value = torch.tensor(
    [-0.7, 0.2, 1.1],
    dtype=torch.double,
    requires_grad=True,
)
assert torch.autograd.gradcheck(CustomSinh.apply, (value,))
```

`gradcheck` 的默认容差面向 double precision。用 float32、在不可微点检查、或让输入含重叠内存（例如 `expand` 产生的 stride 0）都可能让数值扰动与解析结果无法正常比较。**先用 `torch.double`、远离不可微点、保证检查输入不重叠，再判断 backward 是否真的错。**

完整测试还包含这个故意失败路径：

```python
with self.assertRaises(RuntimeError):
    torch.autograd.gradcheck(WrongSquare.apply, (value,))
```

它不是装饰性测试：如果错误反向也通过，测试本身就失去了诊断价值。

## 7. 常见错误与诊断

### 7.1 为什么梯度越来越大？

**症状**：相同输入重复训练时，`.grad` 像 `3 → 7 → ...` 一样保留旧贡献。

**诊断**：在每次 backward 前后打印一个参数的 `.grad`，确认训练目标是单 step 还是跨 micro-batch 累积。

**方案**：普通 step 用 `optimizer.zero_grad(set_to_none=True)`；有意做梯度累积时，只在完成约定 micro-batch 数后清零。不要把累积语义误判为 Autograd 算错。

### 7.2 为什么第二次 backward 报图已释放？

**症状**：对同一个 forward 输出再次调用 `backward()`，出现“Trying to backward through the graph a second time”一类错误。

**诊断**：确认是否真的需要复用同一张图。多数训练循环应该重新 forward，生成下一张动态图。

**方案**：确需同图多次反向时，第一次使用 `retain_graph=True`；否则重新 forward。不要在所有 backward 上永久打开 retain，以免延长图资源生命周期。

### 7.3 为什么 non-leaf 的 `.grad` 是 `None`？

**症状**：中间激活有 `grad_fn`，反向后却看不到 `.grad`。

**诊断**：检查 `tensor.is_leaf`。non-leaf 的梯度默认只参与传播，不保存在 `.grad`。

**方案**：调试前调用 `retain_grad()`；生产代码不要为了“看得到”给所有激活保留梯度。

### 7.4 为什么原地操作在 backward 才报错？

**症状**：forward 和原地写入都完成，直到 backward 访问 saved tensor 才出现版本错误。

**诊断**：沿报错指出的 Tensor 检查带下划线操作、`+=`、切片赋值，以及 4.1 所讲的 base/view storage 别名。

**方案**：优先改成 out-of-place 操作；更新参数时放进 `no_grad`，但仍不能修改当前图 backward 所需的值。必要时用 `torch.autograd.detect_anomaly()` 缩小来源；它增加诊断开销，只在定位问题时开启。

### 7.5 为什么 `detach()` 后改值仍影响原 Tensor？

**症状**：`detached.requires_grad` 已是 `False`，原地写入却影响另一个 Tensor。

**诊断**：回到 4.1 比较 storage 指针。`detach` 切断 Autograd 历史，不承诺复制数据。

**方案**：既要停梯度又要独立存储时使用 `tensor.detach().clone()`，接受复制代价。

### 7.6 为什么 `gradcheck` 在“看起来正确”时失败？

**症状**：解析公式手算无误，但数值雅可比不匹配。

**诊断**：依次检查输入是否为 `torch.double`、测试点是否不可微、输入是否存在 stride 0 或其他重叠、实现是否非确定。

**方案**：先构造小而平滑、double、非重叠的输入；再检查 `backward` 返回数量、shape、dtype 和 `grad_output` 链式乘法。不要靠放大容差掩盖公式错误。

## 8. 权衡与选型

### 8.1 面对 Autograd 需求应怎样选工具？

**先问“要停一条 Tensor 历史，还是停一段记录”，再问“要复用旧图，还是对梯度继续求导”。**

| 工程问题 | 推荐工具 | 换取什么 | 牺牲什么 / 风险 |
|---|---|---|---|
| 只截断一个 Tensor 的历史 | `detach()` | 局部、显式的停梯度 | 与原 Tensor 共享 storage |
| 一段更新或计算不进图 | `no_grad()` | 产物之后仍可进入 grad mode | 块内不记录求导历史 |
| 产物永不回到训练图 | `inference_mode()` | 关闭更多 Autograd 跟踪 | 产物的后续 Autograd 使用受限 |
| 同一前向图再反向 | `retain_graph=True` | 允许图复用 | 延长 saved tensors 等资源生命周期 |
| 对梯度继续求导 | `create_graph=True` | 高阶梯度 | 创建更复杂的新图 |
| 临时观察或替换梯度 | `register_hook` | 插拔式诊断或变换 | 行为分散，需管理 handle 与顺序 |
| 定义新算子的反向 | `autograd.Function` | 自定义数学与保存策略 | 自己承担导数、组合性和测试责任 |

📌 **关键点**：这些 API 没有“高级就更好”的排序。最小工具通常最容易证明正确；只有当接口需求明确时，才支付额外图生命周期、复制、隐藏行为或维护复杂度。

## 9. 本节边界与后续接口

### 9.1 与 4.1 的边界是什么？

[4.1](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/41-tensor存储与视图语义/) 负责回答 shape/stride 如何映射 storage、哪些 Tensor 共享数据；本节接过别名关系，回答 saved tensors 如何借助版本计数发现原地修改，以及共享数据怎样进入反向图。**共享 storage 不等于共享 `.grad`，停梯度也不等于复制 storage。**

### 9.2 与 4.3 的边界是什么？

本节只研究 Tensor 操作的求导历史，不定义模型状态边界。[4.3 Module 与状态管理](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/43-module与状态管理/) 将回答 `nn.Parameter` 为什么默认需要梯度、parameter/buffer/普通属性如何注册、`state_dict` 保存什么，以及 Module Hook 与 Tensor Hook 怎样区分。**4.2 保证导数公式与图生命周期正确，4.3 保证这些 Tensor 被模型正确拥有和序列化。**

### 9.3 与模块二的边界是什么？

本节把 `Function` 当作可验证的 Autograd 扩展接口，不展开 C++/CUDA Kernel、Dispatcher 注册、AOTAutograd、`torch.compile` 或 Graph Break。高性能自定义算子、图捕获和编译优化进入[模块二 CUDA 编程与算子优化](/AIInfraGuide/cuda/)；本节提供的 `gradcheck` 与版本计数心智模型，是之后验证这些底层实现的正确性门槛。

落成一句话：4.1 管“数据在哪里”，4.2 管“梯度怎样流且何时拒绝错误”，4.3 管“模型怎样拥有状态”，模块二再管“这些计算怎样落到底层并被优化”。

## 📝 总结

1. **动态图**：PyTorch 每次 forward 按真实 Python 控制流重建 DAG，non-leaf 的 `grad_fn` 是反向历史入口。
2. **梯度落点**：leaf 的 `.grad` 默认累积；non-leaf 梯度用于链式传播，只有显式 `retain_grad()` 才保留。
3. **反向数据**：saved tensors 用生命周期换反向所需信息，版本计数阻止原地修改后的过期值被静默使用。
4. **停梯度选型**：`detach` 管单个 Tensor，`no_grad` 管代码块，`inference_mode` 面向不再回到 Autograd 的产物。
5. **图控制**：`retain_graph` 为同图复用，`create_graph` 为高阶求导；Hook 用于可控的观察或梯度替换。
6. **扩展正确性**：自定义 Function 必须正确保存上下文、乘上传入的 `grad_output`，并用 double、平滑、非重叠输入通过 `gradcheck`。
7. **失败证据**：CPU 测试既证明 `CustomSinh` 通过，也证明版本不匹配和 `WrongSquare` 错误反向会被拒绝；本文没有未经实验支持的性能数字。
