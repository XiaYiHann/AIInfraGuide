一个模型里同样是 Tensor，归宿却有 4 种：`Parameter` 进入优化器与 `state_dict`，持久 buffer 只进入 `state_dict`，非持久 buffer 只跟随设备转换，普通属性两边都不进入。**`nn.Module` 的核心不是帮你写 `forward`，而是建立“谁拥有这份状态”的可遍历注册表。** 这张表换来统一的设备迁移、保存和分布式包装，也要求你不能把层和参数随手塞进 Python `list` 后期待框架自动发现。

## 1. Module 怎样建立状态注册表

### 1.1 为什么给属性赋值就能注册？

打个比方：实验室有一张资产表。把仪器交给资产管理员登记后，搬实验室、盘点和交接都会带上它；把同一件仪器放进个人纸箱，虽然照样能使用，管理员却看不见。**`nn.Module` 会拦截属性赋值：赋给属性的子 Module 和 Parameter 会进入对应注册表，之后才能被递归遍历。**

```python
import torch
from torch import nn


class TinyBlock(nn.Module):
    def __init__(self) -> None:
        super().__init__()                    # 必须先初始化父类注册表
        self.proj = nn.Linear(3, 3)           # 注册子 Module
        self.gain = nn.Parameter(torch.ones(3))  # 注册 Parameter

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return self.proj(x) * self.gain
```

`model.modules()` 递归发现子模块，`model.parameters()` 递归发现参数，`named_parameters()` 再附上由属性路径组成的名字。优化器常接收 `model.parameters()`，所以“没注册”不只是保存时少一个键，还可能意味着这个值从未被更新。

`nn.Parameter` 是 Tensor 的子类；当它作为 Module 属性赋值时会自动进入参数表，而普通 Tensor 不会。Parameter 默认 `requires_grad=True`，但**“是否为模型参数”和“当前是否求梯度”是两件事**：可以用 `parameter.requires_grad_(False)` 冻结参数，它仍是 Parameter，仍会出现在 `state_dict` 中。

⚠️ **注意**：直接调用 `model.forward(x)` 会绕过 `Module.__call__` 包装的 Hook 等逻辑。正常调用应写 `model(x)`；`forward` 只定义计算本身。

### 1.2 Parameter、buffer 与普通属性怎样选？

问题是：均值、位置索引或临时缓存也是 Tensor，为什么不能全写成 Parameter？**分类标准不是“是不是 Tensor”，而是“是否需要优化、是否属于可恢复模型状态、是否应跟随 Module 迁移”。**

| 状态种类 | 优化器可见 | 跟随 `model.to(...)` | 默认进入 `state_dict` | 典型用途 |
|---|---:|---:|---:|---|
| `nn.Parameter` | 是 | 是 | 是 | 权重、偏置、可学习缩放 |
| 持久 buffer | 否 | 是 | 是 | BatchNorm 运行统计、固定索引 |
| 非持久 buffer | 否 | 是 | 否 | 可重建的临时表、运行缓存 |
| 普通 Tensor 属性 | 否 | 否 | 否 | 与模型状态无关的 Python 侧数据 |

持久与非持久 buffer 都要显式注册：

```python
class StateKinds(nn.Module):
    def __init__(self) -> None:
        super().__init__()
        self.weight = nn.Parameter(torch.ones(3))
        self.register_buffer("running_total", torch.zeros(3))
        self.register_buffer("scratch", torch.ones(3), persistent=False)
        self.plain_tensor = torch.full((3,), -1.0)
```

调用 `model.to(dtype=torch.float64)` 后，Parameter 和两种 buffer 都会变成 float64，普通 Tensor 仍保持原 dtype。持久性的唯一区别是非持久 buffer 不进入 `state_dict`；它并不意味着“不随设备移动”。

**权衡**：注册状态牺牲一点显式设计成本，换来统一迁移、遍历和保存；普通属性更自由，却把迁移与恢复责任全部交给调用方。可重建且可能很大的缓存用 `persistent=False`，可以减小保存状态，但加载后必须有可靠的重建路径。

## 2. 容器为什么决定状态能否被发现

### 2.1 Python `list` 为什么会漏掉层和参数？

你把三名新同事写在自己的便签上，他们确实存在，却不在公司的通讯录里。Python `list` 只是普通属性，往里面追加 Module 或 Parameter 不会再次触发父 Module 的注册逻辑。**动态数量的层要放进 `ModuleList`，动态数量的参数要放进 `ParameterList`。**

```python
class ContainerDemo(nn.Module):
    def __init__(self) -> None:
        super().__init__()
        self.good_layers = nn.ModuleList([nn.Linear(3, 3)])
        self.good_scales = nn.ParameterList([torch.tensor(0.5)])

        # 故意的失败路径：内容能被 Python 调用，但 Module 看不见。
        self.bad_layers = [nn.Linear(3, 3)]
        self.bad_scales = [nn.Parameter(torch.tensor(7.0))]
```

`ParameterList` 的构造、赋值、`append` 和 `extend` 会把 Tensor 转成 Parameter；`ModuleList` 则让其中 Module 对所有 Module 遍历方法可见。完整示例能观察到：

```text
layers.0.weight    # 出现在 named_parameters/state_dict
scales.0           # 出现在 named_parameters/state_dict
bad_layers...      # 完全不出现
bad_scales...      # 完全不出现
```

这条错误很隐蔽，因为 `forward` 仍可能运行。诊断不要只看“能不能算”，还要同时检查：

```python
print(dict(model.named_modules()).keys())
print(dict(model.named_parameters()).keys())
print(model.state_dict().keys())
```

⚠️ **注意**：`ModuleList` 负责注册和迭代，不负责定义前向连接；需要顺序串行执行时可以自己循环，或在确实符合串行语义时使用 `nn.Sequential`。不要为了少写一个循环改变模型计算图。

## 3. state_dict 保存的究竟是什么

### 3.1 键从哪里来，值包括什么？

问题是：为什么一个嵌套层会得到 `layers.0.weight` 这样的键？**`state_dict()` 递归遍历已注册 Module，用属性路径拼接键，只收集 Parameter 与持久 buffer。** 普通属性、非持久 buffer、优化器状态和 Python 控制变量都不在其中。

对本节 `ModuleStateDemo`，键是：

```text
scale
running_total
projection.weight
layers.0.weight
scales.0
```

键名是加载契约的一部分。把 `self.projection` 重命名为 `self.encoder`，即使 shape 完全相同，也会产生 `projection.weight` 缺失和 `encoder.weight` 多余的诊断。模型重构因此也是状态格式迁移问题。

### 3.2 为什么 `state = model.state_dict()` 不是冻结快照？

反直觉点在这里：官方 `state_dict` 文档明确说明，返回字典是**浅拷贝，值引用 Module 当前的参数和 buffer**。默认 `keep_vars=False` 会让这些 Tensor 脱离 Autograd，但不会复制底层数据。

```python
model = StateKinds()
live_state = model.state_dict()
before = live_state["weight"].clone()

with torch.no_grad():
    model.weight.add_(3)

print(before)                # 修改前的独立副本
print(live_state["weight"]) # 已跟着模型变化
```

所以，在内存里比较“训练前后 state”时，要先克隆：

```python
snapshot = {
    name: tensor.detach().clone()
    for name, tensor in model.state_dict().items()
}
```

而写入文件时，PyTorch 官方教程推荐保存 `state_dict`，再按需要加载：

```python
torch.save(model.state_dict(), "model_weights.pt")
state = torch.load("model_weights.pt", weights_only=True, map_location="cpu")
model.load_state_dict(state)
```

`weights_only=True` 限制反序列化器执行构造任意对象所需的动态导入；它降低加载不可信文件的攻击面，但**不能把不可信 checkpoint 变成可放心运行的内容**。文件来源、完整性校验和隔离仍是工程责任。

📌 **关键点**：`state_dict` 是“参数与持久 buffer 的命名映射”，不是完整训练 checkpoint，也不是调用时自动冻结的历史版本。

## 4. 加载、共享参数与初始化怎样保持模型契约

### 4.1 `strict=True` 与 `strict=False` 应怎样用？

为什么加载旧权重时不能直接把 `strict=False` 当万能修复？**`strict=True` 要求输入键与当前模型键完全一致；`strict=False` 允许继续复制匹配键，但会返回 `missing_keys` 和 `unexpected_keys`，调用方必须检查。**

```python
partial = {name: value.clone() for name, value in model.state_dict().items()}
partial.pop("projection.weight")
partial["legacy.weight"] = torch.ones(1)

result = model.load_state_dict(partial, strict=False)
print(result.missing_keys)     # ['projection.weight']
print(result.unexpected_keys)  # ['legacy.weight']
```

在相同输入上，`strict=True` 会抛出 `RuntimeError`，同时报告缺失和多余键。推荐顺序是：

1. 默认使用 `strict=True`，让状态契约破坏立即失败；
2. 确实在做迁移、裁剪头或加载预训练子集时才用 `strict=False`；
3. 对预期的 missing/unexpected 集合写断言，出现额外键就拒绝继续。

这项权衡很明确：非严格加载牺牲“完整一致”的自动保证，换取有控制的模型演进。若不检查返回结果，它就从迁移工具退化为静默漏载工具。

### 4.2 参数共享保存了什么，没有保存什么？

一个 Tensor 能不能被两个模块路径共同使用？可以。例如 tied embedding 或 encoder/decoder 共享缩放参数：

```python
class SharedParameterDemo(nn.Module):
    def __init__(self) -> None:
        super().__init__()
        shared = nn.Parameter(torch.tensor([1.0, -1.0]))
        self.encoder_scale = shared
        self.decoder_scale = shared
```

此时 `model.encoder_scale is model.decoder_scale` 为真。默认 `named_parameters()` 遍历会移除重复对象，只报告第一次遇到的 `encoder_scale`；`state_dict()` 则为两个属性路径都给出键 `encoder_scale` 和 `decoder_scale`。

**共享拓扑由模型构造代码定义，`state_dict` 主要携带命名 Tensor 值，不负责把两个独立 Parameter 自动改成同一个对象。** 加载后必须再次断言对象身份或 storage 指针。若新模型不再共享，两个键会加载进两个独立 Parameter；若共享模型收到两个值不一致的别名键，结果还会受复制顺序影响，因此生产迁移应先检查别名键数值一致。

共享参数牺牲模块独立性，换取权重绑定与更少的独立状态；它还会影响参数计数、优化器分组和保存键。统计“独立参数量”时按对象去重，审计保存格式时则按键检查，不能把两个口径混在一起。

### 4.3 初始化怎样覆盖完整模块树？

问题是：怎样在不手写每一层属性路径的情况下统一初始化？**`model.apply(fn)` 会递归访问当前 Module 及所有已注册子 Module，常与 `torch.nn.init` 组合。**

```python
def initialize_linears(module: nn.Module) -> None:
    if isinstance(module, nn.Linear):
        nn.init.constant_(module.weight, 0.25)
        if module.bias is not None:
            nn.init.zeros_(module.bias)


model.apply(initialize_linears)
```

`torch.nn.init` 函数在 `no_grad` 模式下修改 Tensor，不会把初始化写进 Autograd 图。这里再次暴露 Python `list` 的失败：其中未注册的 Linear 不在 `apply` 递归树里，也不会被统一初始化。

⚠️ **注意**：很多内置层在构造时已经调用自己的 `reset_parameters()`。自定义初始化是在覆盖默认策略；它换取实验可控性，也要求你明确初始化顺序、随机种子和共享参数是否会被重复访问。

## 5. train、eval 与 Hook 各管哪一层

### 5.1 `eval()` 为什么不能替代停梯度？

常见误解是 `model.eval()` 会关闭 Autograd。**`train(mode)` 递归切换 Module 的 `training` 标志；`eval()` 等价于 `train(False)`，只影响 Dropout、BatchNorm 等会读取该标志的模块。** Parameter 的 `requires_grad` 不会改变，eval 模式下输出仍可拥有 `grad_fn`。

```python
model.train()   # Dropout 随机丢弃，BatchNorm 更新运行统计
model.eval()    # Dropout 关闭，BatchNorm 使用运行统计

with torch.inference_mode():
    prediction = model(input_tensor)
```

验证阶段常把 `eval()` 与 `inference_mode()` 放在一起，因为前者控制层行为，后者控制 Autograd 记录。4.2 已经解释 `no_grad` 与 `inference_mode` 的区别；本节只强调它们与 Module 模式正交。

### 5.2 Hook 能在哪些边界插入观测？

你想观察模块输入输出、梯度或状态迁移，是否必须修改 `forward`？**Module Hook 提供插拔式入口，但会把行为移出主路径，所以更适合诊断、可观测性和受测试约束的扩展。**

| 入口 | 观察/修改时机 | 典型用途 |
|---|---|---|
| `register_forward_pre_hook` | `forward` 前 | 检查或规范化输入 |
| `register_forward_hook` | `forward` 后 | 记录激活 shape、捕获输出 |
| `register_full_backward_hook` | 模块反向阶段 | 诊断梯度流 |
| state-dict pre/post Hook | 生成状态前后 | 状态格式适配、补充元数据 |
| load-state-dict pre/post Hook | 加载状态前后 | 键迁移、审计 missing/unexpected |

```python
events = []
pre = model.register_forward_pre_hook(
    lambda module, inputs: events.append("forward_pre")
)
post = model.register_forward_hook(
    lambda module, inputs, output: events.append("forward")
)
model(torch.ones(1, 3))
pre.remove()
post.remove()
assert events == ["forward_pre", "forward"]
```

Hook 的具体签名、触发顺序和可否修改值要以当前官方 `nn.Module` 文档为准。注册后要保存 handle 并及时 `remove()`；关键数学逻辑若只能靠隐藏 Hook 才成立，通常应改成显式 Module 或函数，让调用者能从主代码读懂。

## 6. 跑通完整 CPU 实验

### 6.1 怎样把注册、加载与失败路径一次验完？

只打印 `model` 不足以证明状态正确。**仓库示例同时检查状态往返、浅引用、两类 buffer、普通属性、Python 容器漏注册、strict load、共享参数、初始化、train/eval 与 Hook。**

在仓库根目录执行：

```bash
python3 examples/pytorch/module_state.py
python3 -m unittest examples/pytorch/tests/test_module_state.py -v
python3 -m compileall examples/pytorch/module_state.py \
  examples/pytorch/tests/test_module_state.py
```

关键输出应包含：

```text
state_dict keys: ['scale', 'running_total', 'projection.weight', 'layers.0.weight', 'scales.0']
python-list contents omitted: True
strict=False missing keys: ['projection.weight']
strict=False unexpected keys: ['legacy.weight']
shared parameter kept: True
module hook events: ['forward_pre', 'forward']
all module-state checks passed
```

状态往返测试先用 `detach().clone()` 冻结快照，再修改全部 Parameter、持久 buffer、非持久 buffer 和普通属性。加载后只有 Parameter 与持久 buffer 恢复；`scratch` 保持修改后的 `[14, 14, 14]`，普通属性保持 `[15, 15, 15]`。这两个“没有恢复”的断言正是状态边界的失败证据，不是测试遗漏。

## 7. 常见错误与诊断

### 7.1 为什么参数能参与 forward，却不被优化器更新？

**症状**：层能算出结果，但 `named_parameters()` 和优化器参数组中没有它。

**诊断**：检查是否放进普通 Python `list`/`dict`，或是否只在局部变量中创建；打印 `named_modules()`、`named_parameters()` 和 `state_dict()`。

**方案**：分别改用 `ModuleList`/`ModuleDict` 或 `ParameterList`/`ParameterDict`，并给期望键写测试。

### 7.2 为什么切到 CUDA 或 float64 后出现设备/dtype 不一致？

**症状**：注册参数已经迁移，某个作为普通属性保存的 Tensor 仍留在 CPU 或 float32。

**诊断**：对照 `named_buffers()`；若不存在，该 Tensor 不会跟随 `model.to(...)`。

**方案**：属于模型运行状态就注册为 buffer；纯临时值可在 `forward` 中根据输入用 `x.new_...` 创建；不要手写一串容易遗漏的 `.to(device)`。

### 7.3 为什么“训练前 state”在训练后也变了？

**症状**：`before = model.state_dict()` 保存后，比较发现 before 与当前模型同步变化。

**诊断**：比较 `data_ptr()`；`state_dict` 的值是浅引用。

**方案**：内存快照逐项 `detach().clone()`；持久保存使用 `torch.save(state_dict)`。不要把变量名不同误认为数据已复制。

### 7.4 为什么 `strict=False` 后模型能跑却结果异常？

**症状**：加载不报错，但新增层保持随机初始化，或旧键完全没加载。

**诊断**：检查返回的 `missing_keys` 和 `unexpected_keys`，与批准的迁移清单逐项比较。

**方案**：默认恢复 strict；确需非严格加载时，对两组键写精确断言，并单独验证关键 Tensor 数值。

### 7.5 为什么 `eval()` 后仍然在建图？

**症状**：输出仍有 `grad_fn`，内存生命周期也像训练一样保留。

**诊断**：分别检查 `model.training`、`torch.is_grad_enabled()` 与 Parameter 的 `requires_grad`。

**方案**：推理时同时使用 `model.eval()` 和 `torch.inference_mode()`；需要之后回到 Autograd 的值则按 4.2 的规则考虑 `no_grad()`。

### 7.6 为什么共享参数的计数和状态键数量不同？

**症状**：`named_parameters()` 只有一个名字，`state_dict()` 却有两个别名键。

**诊断**：用 `is` 或 `data_ptr()` 检查对象身份，再分别按独立对象与状态键两个口径统计。

**方案**：构造模型时显式建立共享；加载后验证身份和别名键数值一致，不假设 `state_dict` 会重建共享拓扑。

## 8. 权衡与选型

### 8.1 一份 Tensor 状态应该放在哪里？

**先问“优化器要不要更新”，再问“恢复模型是否必须有它”，最后问“它是否要随设备迁移”。**

| 工程判断 | 选择 | 换取什么 | 牺牲什么 / 风险 |
|---|---|---|---|
| 需要学习 | `Parameter` | 自动遍历、优化和保存 | 进入模型可训练状态与优化器管理 |
| 不学习但恢复必须一致 | 持久 buffer | 迁移与保存统一 | 增大状态文件，格式变更需迁移 |
| 不学习且可可靠重建 | 非持久 buffer | 自动迁移，不占状态文件 | 加载后必须重建，不能依赖旧值 |
| 与模型状态无关 | 普通属性 | 最大自由度 | 不自动迁移、不保存、不递归管理 |
| 动态子层集合 | `ModuleList`/`ModuleDict` | 子层完整注册 | 前向顺序仍需显式定义 |
| 动态独立参数集合 | `ParameterList`/`ParameterDict` | 参数完整注册 | 每个元素都进入可训练/保存状态 |

📌 **关键点**：注册越完整，框架越能统一管理；状态越持久，恢复越可靠但格式与存储负担越大。没有一种分类适合所有 Tensor，选择必须由恢复契约驱动。

## 9. 本节边界与后续接口

### 9.1 与 4.2 的边界是什么？

[4.2](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/42-autograd自动微分/) 负责 leaf、计算图、版本计数、Tensor Hook 和梯度正确性；本节负责 Module 如何拥有 Parameter、buffer 和子模块，以及 Module Hook 在调用边界怎样观测。**Parameter 默认参与求导，但“注册为参数”不等于“Autograd 已经算出梯度”。**

### 9.2 与 4.4 的边界是什么？

4.4 负责 Dataset、采样、batch、worker、pin memory 与预取的数据流水线。本节不把数据集、DataLoader worker 或当前 batch 塞进 `state_dict`。Module 管模型状态，DataLoader 管输入生产；二者在 4.5 的训练循环里交接。

### 9.3 与 4.5 的 checkpoint 边界是什么？

本节只证明模型 `state_dict` 的精确往返。**能恢复模型权重，不等于能恢复训练。** 4.5 才把以下内容组成完整 checkpoint：

- 模型与优化器 `state_dict`；
- 学习率调度器、AMP scaler；
- epoch、global step 与梯度累积位置；
- Python、PyTorch、CUDA 随机数状态；
- 数据采样与可恢复数据进度；
- 原子写入、版本迁移和中断恢复验证。

本节不展开这些实现，避免把“模型序列化”和“训练任务恢复”混成一个概念。

### 9.4 与 4.11 的边界是什么？

4.11 负责 process group、rank、DDP 包装与梯度同步。DDP 能同步的前提是参数已被 Module 正确注册；buffer 广播等行为也依赖 buffer 注册。**本节建立单进程模型状态契约，4.11 再解释多进程副本怎样以这些已注册对象为边界协作。** FSDP 状态字典形态、分片策略与规模化 checkpoint 属于模块三，不在这里展开。

完整课程去向见[第 4 章章首页](/AIInfraGuide/prerequisites/模块一-前置知识/第4章-pytorch框架/)。落成一句话：4.2 管“梯度怎样流”，4.3 管“模型拥有谁”，4.4 管“数据怎样来”，4.5 管“训练怎样恢复”，4.11 管“多进程怎样同步”。

## 📝 总结

1. **注册机制**：赋给 Module 属性的子 Module 与 Parameter 会进入注册表；普通 Tensor 与普通 Python 容器内容不会自动注册。
2. **四类状态**：Parameter、持久 buffer、非持久 buffer、普通属性在优化、迁移和保存三个维度有明确差异。
3. **容器契约**：动态层与参数分别使用 Module 容器和 Parameter 容器；能 forward 不代表能被优化器、初始化和保存发现。
4. **状态语义**：`state_dict` 只含 Parameter 与持久 buffer，键由模块路径组成，返回值是浅引用而非冻结快照。
5. **加载纪律**：strict load 默认保证键完全匹配；非严格加载必须审计 missing/unexpected，不能静默忽略。
6. **共享与模式**：共享拓扑由构造代码定义；`train/eval` 只控制特定层行为，不关闭 Autograd。
7. **工程边界**：Module Hook 是插拔入口，模型权重往返只是 checkpoint 的一部分；完整训练恢复留到 4.5。
8. **验证证据**：6 个 CPU 单元测试覆盖状态往返、buffer/普通属性、容器失败、strict 诊断、共享参数以及模式与 Hook，不包含未经实验支持的性能数字。
