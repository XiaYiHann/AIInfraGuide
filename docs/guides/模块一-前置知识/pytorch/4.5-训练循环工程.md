一次参数更新可以消费 1 个大 batch，也可以累积 $K$ 个 micro-batch；当每个 micro-batch 有 $b=8$ 个样本、$K=4$ 时，两者的有效 batch 都是 **32 个样本/次更新**。关键不是把 API 排成一行，而是守住更新边界：loss 除以 4、累积完再裁剪和 `step`，调度器只跟成功的优化器更新一起前进，checkpoint 也只在这条边界保存。这样换来可恢复、可诊断的训练轨迹，代价是必须显式管理进度、随机数和数据位置。

## 1. train 与 eval 怎样组成完整生命周期

### 1.1 为什么一次验证不只是“少调用 backward”？

打个比方：同一间考场在“练习模式”会随机遮住部分提示，在“正式阅卷模式”则固定规则。`Dropout` 和 `BatchNorm` 也会读取 Module 的 `training` 标志。**训练前调用 `model.train()`，验证前调用 `model.eval()`；`eval()` 只切换层行为，并不会关闭 Autograd。**

```python
# 训练生命周期
model.train()
optimizer.zero_grad(set_to_none=True)
prediction = model(inputs)
loss = loss_fn(prediction, targets)
loss.backward()
optimizer.step()

# 评估生命周期：层行为与梯度记录分别关闭
model.eval()
with torch.inference_mode():
    validation_prediction = model(validation_inputs)
```

评估阶段不应修改参数，也不应更新普通的 update-based scheduler。`ReduceLROnPlateau` 这类读取验证指标的调度器是另一种契约：它在指标计算完成后接收 metric，不能机械套用本文 `StepLR` 的位置。

### 1.2 模式切换应该由谁恢复？

问题是：辅助函数在评估后要不要悄悄切回训练模式？**最容易审计的做法是让每段生命周期显式声明自己的模式。** 本节 `train_one_update()` 开头调用 `model.train()`，`evaluate()` 开头调用 `model.eval()`；调用者不依赖“上一个函数刚好留下什么状态”。

这种写法多两行，却把 Dropout/BatchNorm 的行为放回主路径。若项目必须保存并恢复调用前模式，可以记录 `was_training = model.training` 后恢复，但要为这条隐式状态转换写测试。

## 2. 一次参数更新的顺序为什么不能乱

### 2.1 `zero_grad → forward → backward → step` 各守哪条边界？

PyTorch 官方 optimizer 文档给出的基本循环是：先 `zero_grad()`，再 forward、计算 loss、`backward()`，最后 `optimizer.step()`。**`backward()` 只计算并累加梯度，`step()` 才读取当前 `.grad` 更新参数；顺序颠倒就会读取旧梯度或没有梯度。**

```python
optimizer.zero_grad(set_to_none=True)  # 本次更新从无梯度开始
prediction = model(inputs)             # 建立本次动态图
loss = loss_fn(prediction, targets)
loss.backward()                        # 把贡献累加到 Parameter.grad
optimizer.step()                       # 消费梯度更新 Parameter
optimizer.zero_grad(set_to_none=True)  # 尽早释放引用，防止误用
```

`zero_grad` 放在上一轮 `step` 后或下一轮 forward 前都可以，前提是边界一致且没有误清梯度。本节函数在更新开始和结束各明确一次：开始保证不混入旧值，结束保证 checkpoint 不会误以为还保存着可继续累积的梯度。

`set_to_none=True` 与把梯度填成 0 的行为有细微差别：没有收到梯度的参数仍是 `None`，优化器可能跳过它；显式 0 则表示该参数收到一个零梯度。不要在业务代码中假设两者永远等价。

### 2.2 为什么不能只保存 loss 最小的那一刻？

loss 是观测值，不是训练状态。**同一个模型权重若配上不同 Adam 动量、学习率阶段或 RNG，下一步就可能走向不同方向。** 这也是 4.3 的模型 `state_dict` 不能单独承担训练恢复的原因。

## 3. 累积、裁剪、优化器与调度器怎样对齐

### 3.1 梯度累积为什么要除以 $K$？

假设 $K$ 个 micro-batch 大小都为 $b$，第 $k$ 批样本损失的均值为 $L_k$。把它们拼成大小 $B_{effective}=bK$ 的大 batch 后，总均值是：

$$
\underbrace{L}_{\text{大 batch 均值}}
=
\frac{1}{K}
\sum_{k=1}^{K}
\underbrace{L_k}_{\text{第 k 个等大 micro-batch 均值}}
$$

因为求导是线性的，每批执行 `(loss / K).backward()` 后再更新一次，就得到：

$$
\underbrace{\nabla_\theta L}_{\text{一次大 batch 梯度}}
=
\sum_{k=1}^{K}
\underbrace{\nabla_\theta \frac{L_k}{K}}_{\text{逐批累积的梯度}}
$$

代入 $b=8,K=4$，有效 batch 为 $8\times4=32$。若忘了除以 4，梯度整体放大 4 倍；这通常等价于悄悄改变学习率，而不是“只是写法不同”。

```python
optimizer.zero_grad(set_to_none=True)
for inputs, targets in four_equal_micro_batches:
    loss = loss_fn(model(inputs), targets)
    (loss / 4).backward()
optimizer.step()
```

💡 **提示**：这个简单等价式要求 micro-batch 等大、loss 都按样本取均值，而且期间没有更新参数。尾批大小不同、按 token 加权、BatchNorm 统计、随机层调用顺序或样本依赖 loss 都会改变等价边界。大小不同时应按样本数或有效 token 数加权，而不是把每批均值等权相加。本节代码选择立即拒绝不等大的 micro-batch，让契约显式可见。

### 3.2 effective batch 还缺哪个维度？

本节是单进程，所以：

$$
B_{effective}=b_{micro}\times K_{accumulation}
$$

到 4.11 的数据并行后才加入 `world_size`：

$$
B_{effective}=b_{micro}\times K_{accumulation}\times world\_size
$$

这里建立计算口径，不展开 DDP 梯度同步、`no_sync()` 或跨 rank 数据去重；这些属于 4.11 与[模块三分布式训练](/AIInfraGuide/distributed/)。

### 3.3 梯度裁剪为什么放在累积之后？

问题是：能不能每个 micro-batch 都裁一次？**不能把它当成“最终梯度裁剪”的等价实现。** 裁剪是非线性变换；先分别裁剪再相加，通常不等于先相加再裁剪。

本节使用全局 L2 norm：

$$
\underbrace{g'}_{\text{裁剪后梯度}}
=
\underbrace{g}_{\text{累积完成的梯度}}
\times
\min\left(1,\frac{\tau}{\lVert g\rVert_2}\right)
$$

`max_norm` 是阈值。若累积后的全局 L2 norm 为 10、`max_norm=2`，所有梯度统一乘 $2/10=0.2$，方向保持不变，norm 变为 2。

```python
# 所有 micro-batch backward 完成后
pre_clip_norm = torch.nn.utils.clip_grad_norm_(
    model.parameters(), max_norm=1.0, error_if_nonfinite=True
)
optimizer.step()
```

`clip_grad_norm_` 返回裁剪前的总 norm，适合记录和诊断。裁剪牺牲大梯度的原始尺度，换取更新幅度上界；阈值太小也会长期压扁有效信号，所以它不是越小越安全。`error_if_nonfinite=True` 让 NaN/Inf 立即失败，而不是带着坏梯度继续更新。

### 3.4 scheduler 应按 micro-batch 还是参数更新前进？

**本文的 `StepLR` 按成功的 optimizer update 前进一步。** PyTorch 官方文档明确提醒：当前推荐顺序是先 `optimizer.step()`，再 `scheduler.step()`；反过来会跳过学习率序列的第一个值。

```python
optimizer.step()
scheduler.step()
```

梯度累积 $K=4$ 时，4 次 backward 仍只有 1 次参数更新，因此 update-based scheduler 只前进 1 次。若 AMP 检测到非有限梯度并跳过 optimizer step，本文也不推进 scheduler。epoch-based、metric-based 和 per-token schedule 必须在配置中写明单位，不能都用变量名 `step` 混过去。

## 4. AMP 怎样在 CPU 与 CUDA 间降级

### 4.1 CPU 为什么明确回退 FP32？

PyTorch 当前官方 AMP 文档支持 CPU BF16 autocast；但 CPU 指令集、算子覆盖与收益随环境而变。**本节为了让 smoke test 快速、稳定、广泛可运行，在 CPU 上明确关闭 autocast 与 GradScaler，使用 FP32 验证正确性。** 这是课程示例的降级策略，不是宣称“CPU 不支持 AMP”。

```python
policy = make_amp_policy("cpu", requested=True)
assert not policy.enabled
assert policy.dtype == torch.float32
assert policy.scaler is None
```

这条 CPU 路径不输出任何性能倍率。要判断 CPU BF16 是否值得，需要在目标 CPU、目标算子和目标模型上另做规范 benchmark。

### 4.2 CUDA FP16 何时需要 GradScaler？

FP16 的动态范围较小，小梯度可能下溢。**CUDA FP16 训练通常把 `torch.autocast` 与 `torch.amp.GradScaler("cuda")` 组合；BF16 路径在本示例中使用 autocast，但不启用 scaler。**

顺序如下：

```python
with torch.autocast(device_type="cuda", dtype=torch.float16):
    loss = loss_fn(model(inputs), targets) / accumulation_steps

scaler.scale(loss).backward()
# 所有 micro-batch 累积完成后：
scaler.unscale_(optimizer)                 # 裁剪前先还原真实梯度尺度
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
scaler.step(optimizer)                     # 非有限梯度时可能跳过更新
scaler.update()
```

Autocast 只包 forward 与 loss；backward 放在上下文外。裁剪若发生在 `unscale_` 前，看到的是被 scale 放大的梯度，阈值就失去原义。`GradScaler` 还可能因 Inf/NaN 跳过 `optimizer.step()` 并降低 scale；官方文档提醒 scale 不保证永远大于 1。调度器因此要与“更新是否真的发生”对齐。

⚠️ **注意**：FP16、BF16 的数值稳定性与性能都依赖模型、算子和硬件。本节 CUDA 路径未作为 GPU benchmark 验收，不给吞吐、显存或加速数字。

## 5. 可复现随机性需要保存什么

### 5.1 固定 seed 为什么还不等于可精确继续？

打个比方：seed 是洗牌前的初始牌序，RNG state 是“现在已经发到第几张”。中断后只重新写同一个 seed，会回到牌堆开头；恢复 state 才会继续发下一张。**从头重跑需要固定 seed，断点继续需要保存中断时的 RNG state。**

本节显式管理：

```python
random.seed(seed)
torch.manual_seed(seed)

rng = {
    "python": random.getstate(),
    "torch_cpu": torch.get_rng_state(),
    # 模型在 CUDA 上时，再保存 torch.cuda.get_rng_state_all()
}
```

恢复顺序也重要：构造新模型会消费随机数，所以应先构造同结构对象，再加载 checkpoint，最后恢复保存的 RNG。本文 `load_checkpoint()` 正是按这个顺序完成。Dropout 使 RNG 恢复可观察：恢复后的后半段 loss 列表和最终参数必须与不中断轨迹逐项相同。

### 5.2 可复现性的承诺边界在哪里？

PyTorch 官方 randomness 文档明确指出：不同 PyTorch 版本、提交、平台以及 CPU/GPU 之间，不保证完全可复现。`torch.use_deterministic_algorithms(True)` 可以要求部分操作使用确定算法或在无确定实现时报错，但可能降低单次运行性能，也不能消除外部数据源、第三方库和分布式时序的差异。

因此本节“精确恢复”的口径是：

- 同一代码、PyTorch 版本、设备类型与算子路径；
- 固定的 CPU 合成 batch；
- Python 与 PyTorch RNG 完整恢复；
- checkpoint 位于 optimizer update 边界；
- 测试要求后半段 loss 列表和最终参数逐项相同。

4.4 的 worker seed、DataLoader generator 和第三方 RNG 也属于真实项目的恢复契约；本例没有多 worker，所以不假装已经覆盖。

## 6. checkpoint 怎样精确继续训练

### 6.1 一份完整 checkpoint 至少包含什么？

**“能加载权重”与“能继续同一条训练轨迹”是两个验收目标。** 本节 checkpoint 包含：

| 状态 | 为什么必须保存 | 缺失后的现象 |
|---|---|---|
| 模型 `state_dict` | 当前参数与持久 buffer | 回到旧模型或随机初始化 |
| 优化器 `state_dict` | Adam 动量、参数组等 | 下一步更新方向改变 |
| scheduler `state_dict` | 当前学习率阶段 | 学习率序列错位 |
| GradScaler state | CUDA FP16 动态 scale | 溢出检测阶段改变 |
| `global_step` | 更新次数与日志/schedule 对齐 | 重复或跳过更新编号 |
| RNG state | Dropout 等随机操作继续 | 后续随机轨迹改变 |
| 数据位置 | 下一批从哪里开始 | 重复或遗漏样本 |
| 格式版本 | 未来迁移与拒绝未知格式 | 旧字段被错误解释 |

📌 **关键点**：`epoch` 往往不够。一个 epoch 中断在第 317 个 batch，至少还要知道“下一个已确认消费的 batch”在哪里。

### 6.2 数据位置为什么没有通用的一个整数？

本节数据是固定内存列表，所以 `next_batch_index=6` 足以恢复。真实数据位置取决于 4.4 的数据契约：

- 顺序 map-style 数据：epoch、sampler 顺序和下一索引；
- shuffle 数据：sampler/generator state 加当前位置，不能只存 batch 编号后重新洗牌；
- 多 worker 预取：保存“训练循环已确认消费”的位置，而不是队列已经预取到的位置；
- iterable stream：外部游标、分片位置与幂等/去重协议；
- 分布式数据：每个 rank 的 sampler epoch、位置和全局一致性。

PyTorch 没有一个能替所有数据源恢复游标的通用 `DataLoader.state_dict()` 契约。**checkpoint 必须和数据源共同定义“下一条是谁”。**

### 6.3 为什么只在 update 边界保存？

假设 $K=4$，只累积完第 2 个 micro-batch 就保存。模型尚未更新，但 `.grad` 已经含前两批贡献。若 checkpoint 不保存这些梯度和精确 micro-step，恢复后要么重复前两批，要么丢掉它们。

本节选择更窄、更可靠的契约：

```python
"data_position": {
    "epoch": 0,
    "next_batch_index": 6,
    "micro_step_in_update": 0,
}
```

`micro_step_in_update` 不是 0 就拒绝保存。若生产系统必须在 micro-batch 中间容错，还要保存每个 Parameter 的 `.grad`、累积权重、AMP 状态和精确数据游标，并为该路径单独证明等价；不能只把检查删掉。

### 6.4 原子保存解决哪种损坏？

进程在 `torch.save("checkpoint.pt")` 中途退出，目标文件可能只写了一半。**本节先写同目录临时文件，flush + `fsync` 后用 `os.replace` 替换正式路径；在本地同一文件系统上，读者看到旧完整文件或新完整文件，而不是半个新文件。**

```python
with NamedTemporaryFile(dir=checkpoint.parent, delete=False) as temporary:
    torch.save(payload, temporary)
    temporary.flush()
    os.fsync(temporary.fileno())
os.replace(temporary.name, checkpoint)
```

这用额外临时磁盘空间和一次同步写换取更安全的发布边界。远端对象存储、网络文件系统、多节点同时写和进程级租约有各自原子性协议，不能直接把本地 `os.replace` 保证外推过去。生产环境还应保留最近多个 checkpoint、校验完整性并验证实际加载。

PyTorch serialization 文档推荐保存 `state_dict` 而不是整个 Module。本节加载使用 `weights_only=True`，减少反序列化任意 Python 对象的能力，但它不能证明文件可信；来源、哈希、访问控制与隔离仍由系统负责。

## 7. 跑通完整 CPU 示例

### 7.1 示例验证哪些工程边界？

完整源码位于 `examples/pytorch/training_loop.py`，测试位于 `examples/pytorch/tests/test_training_loop.py`。在仓库根目录执行：

```bash
python3 examples/pytorch/training_loop.py
python3 -m unittest examples/pytorch/tests/test_training_loop.py -v
python3 -m compileall examples/pytorch/training_loop.py \
  examples/pytorch/tests/test_training_loop.py
```

示例只使用 PyTorch、Python 标准库和合成回归数据，不下载数据，也不新增依赖。六个 CPU 测试覆盖：

1. 固定数据训练 40 次更新后，loss 低于初始值的 20%；
2. 两个等大 micro-batch 的累积更新与一个拼接大 batch 的参数最大差小于 $10^{-6}$；
3. 全局梯度 norm 从阈值以上裁到 `0.2 + 1e-6` 以内；
4. checkpoint 恢复后的后半段 loss、最终参数与学习率逐项匹配不中断轨迹；
5. micro-step 中间保存被拒绝，缺关键字段的 checkpoint 被拒绝；
6. CPU 请求 AMP 时明确降级到 FP32，且没有 GradScaler。

关键输出以这两行为完成标志：

```text
AMP policy: CPU fallback: AMP disabled; correctness runs in float32
all training-loop checks passed
```

这些是正确性实验，不是性能 benchmark。测试没有报告 samples/s、GPU 利用率或混合精度加速比。

### 7.2 为什么累积测试只接受近似相等，恢复测试却要求完全相同？

累积和拼接会以不同的浮点加法分组计算梯度，所以测试用 $10^{-6}$ 容差判断同一数学更新。恢复测试则从同一个保存点、同一批次顺序和同一 RNG state 走相同代码路径，因此要求 loss 列表相等、每个 state Tensor 用 `torch.equal` 精确匹配。

这两条判定线回答不同问题：前者验证数学边界，后者验证状态是否遗漏。不要把所有正确性都压成一个宽松容差。

## 8. 常见错误与诊断

| 症状 | 先检查什么 | 最小修复 |
|---|---|---|
| loss 或参数更新突然放大 $K$ 倍 | 累积时是否执行 `loss / K` | 等大 micro-batch 对 loss 除以 $K$；不等大按样本/token 加权 |
| 梯度一直叠加 | `zero_grad` 是否只在 update 边界调用 | 普通更新每轮清零；有意累积时只延后到 $K$ 批结束 |
| 裁剪后仍像没裁 | AMP 下是否先 `scaler.unscale_` | unscale 后再计算 norm 和裁剪 |
| scheduler 比参数多走 $K$ 倍 | 是否每个 micro-batch 都 `scheduler.step()` | update-based scheduler 只在成功 optimizer step 后调用 |
| 验证结果随机或统计变化 | 是否遗漏 `model.eval()` | `eval()` 管层行为，`inference_mode()` 管 Autograd，两者同时使用 |
| 恢复后第一步就分叉 | 是否漏 optimizer/scheduler/scaler/RNG | 把各自 `state_dict` 与 RNG 一起保存并比较后半轨迹 |
| 恢复后重复或遗漏数据 | 只保存 epoch，没有 sampler/游标 | 定义并保存“下一条已确认消费的数据位置” |
| 中断后 checkpoint 无法加载 | 是否直接覆盖正式文件 | 同目录临时写、flush/fsync、`os.replace`，并保留旧版本 |
| FP16 出现 Inf/NaN | scaler 是否启用、模型是否适合 FP16 | CUDA FP16 使用 GradScaler；必要时改 BF16/FP32 并诊断算子 |
| `strict=False` 让错误继续运行 | 是否审计 missing/unexpected keys | 默认 strict；格式迁移时精确断言允许的键集合 |

📌 **关键点**：先把“一个 optimizer update”钉成唯一计数单位，再对齐梯度、scheduler、global step、日志与 checkpoint。很多训练恢复错误，本质上都是不同组件对 `step` 的定义不一致。

## 9. 权衡、边界与后续接口

### 9.1 每项工程手段牺牲了什么？

| 选择 | 换取什么 | 牺牲什么 / 风险 | 采用条件 |
|---|---|---|---|
| 梯度累积 | 用小 micro-batch 模拟大 effective batch | 更多 forward/backward 次数，随机层与 BatchNorm 边界更复杂 | 单次 batch 受内存限制且数学口径明确 |
| 梯度裁剪 | 限制异常更新幅度 | 改变原始梯度尺度，阈值需调 | 已观察到梯度尖峰或算法明确要求 |
| AMP | 低精度算子与潜在资源收益 | 数值范围、算子覆盖和 scaler 状态 | 目标 CUDA/模型经过正确性验证 |
| 确定算法 | 更容易重放和定位回归 | 某些操作更慢或无实现而报错 | 调试、测试或业务要求高于单次速度 |
| 完整 checkpoint | 精确继续训练 | 文件更大、格式和数据游标更复杂 | 中断成本高于保存与维护成本 |
| 原子替换 | 避免半写目标文件 | 临时空间与同步 I/O | 本地同文件系统 checkpoint 发布 |

📌 **关键点**：这些手段都不是免费开关。训练工程追求的不是“参数最多”，而是每个状态转换都能被解释、测试和恢复。

### 9.2 与 4.4、4.6、4.11、4.12 的边界是什么？

- **4.4 DataLoader**：负责产出不重不漏、结构稳定的 batch，并定义 sampler/worker 随机性；本节只消费 batch，并要求数据源提供可恢复位置。
- **4.6 CUDA 异步执行**：负责 stream、Event、隐式同步、异步 H2D 与正确计时；本节只规定 autocast/scaler 的训练顺序，不讲 CUDA 时间线。
- **4.11 分布式 PyTorch**：负责 process group、rank、DDP 同步和单机多进程入口；本节只给 effective batch 的 `world_size` 维度，不复制 DDP/FSDP 策略。
- **4.12 MiniGPT**：把本节循环接入 token 数据、AMP、checkpoint、Profiler、显存账本和单机分布式入口；本节的小回归模型只是可精确验证的最小底座。

完整去向见[第 4 章章首页](/AIInfraGuide/prerequisites/模块一-前置知识/第4章-pytorch框架/)。分工：4.4 保证“batch 怎样来”，4.5 保证“单进程更新怎样正确并恢复”，4.6 解释“CUDA 工作何时真正完成”，4.11 扩展“多进程怎样同步”，4.12 再把它们组合成项目。

## 📝 总结

1. **生命周期**：`train/eval` 控制 Module 行为，`inference_mode` 控制梯度记录；验证需要显式处理两层状态。
2. **更新顺序**：`zero_grad → forward → loss → backward → step` 的核心是让 optimizer 只消费本次更新边界内的梯度。
3. **累积等价**：等大 micro-batch、mean loss 和更新期间参数不变时，逐批 `loss/K` 可在 $10^{-6}$ 参数误差内匹配拼接大 batch。
4. **裁剪与调度**：累积完成后裁剪；CUDA FP16 先 unscale；update-based scheduler 只在成功 optimizer step 后前进。
5. **AMP 降级**：CPU smoke 明确使用 FP32；CUDA FP16 才附加 GradScaler，CUDA BF16 在本示例中不缩放。
6. **随机恢复**：seed 负责从头重跑，RNG state 负责从中断点继续；跨版本、平台和设备不承诺完全一致。
7. **完整 checkpoint**：模型、优化器、scheduler、scaler、step、RNG、数据位置和格式版本缺一项，都可能让后续轨迹改变。
8. **安全发布**：本节只允许 update 边界保存，并用同目录临时文件加原子替换降低半写风险；远端存储需要自己的协议。
