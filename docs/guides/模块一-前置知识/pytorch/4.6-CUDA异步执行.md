一行 `y = torch.sin(x_cuda)` 返回时，通常只说明 CPU 已把工作**入队**（异步执行 Asynchronous Execution，CPU 仅把任务提交到设备队列就返回，无需等待 GPU 算完，如同前台开单后不等后厨出锅），不说明 GPU 已算完。这个差别会同时制造三类问题：`perf_counter` 只量到提交时间、两个非默认 stream（Stream，GPU 任务队列，同一队列内顺序执行、不同队列可并发）发生读写竞争、Kernel（GPU 上执行的计算核函数）错误在后面的 `.item()` 才被报告。**正确做法不是到处 `synchronize()`，而是在真正的数据依赖、计时边界和主机取值边界建立最小等待。** 这样换来 CPU/GPU 与多 stream 并行的机会，代价是你必须显式管理依赖和 Tensor 生命周期。

## 1. Python 返回时 GPU 为什么可能还没完成

### 1.1 CPU 调用为什么不是 GPU 完成证明？

打个比方：CPU 像前台开工单，GPU 像后厨。前台把“切菜、炒菜、装盘”依次贴到传送带后就能继续接单；开完工单不等于菜已出锅。**PyTorch 的 CUDA 操作默认相对主机异步：Python 主要负责把工作 enqueue 到设备 stream，GPU 可以稍后执行。**

```text
CPU 时间线：launch A ─ launch B ─ launch C ─────────── host 继续工作
GPU 时间线：          kernel A ─ kernel B ─ kernel C ─ done
                   ↑ Python 可能已经从 launch C 返回
```

这解释了为什么下面的 `host_seconds` 不能当作 Kernel 时间：

```python
start = time.perf_counter()
y = torch.sin(x_cuda)             # 主要是提交 CUDA 工作
host_seconds = time.perf_counter() - start
```

`host_seconds` 的右边界没有等待 `sin` 完成。GPU 很快时，查询完成 Event 也可能已经返回 `True`；这不改变语义：**API 返回本身没有提供完成保证，只有明确完成边界才提供。**

### 1.2 为什么平常代码看起来仍像同步执行？

问题是：既然操作异步，为什么连续写 `a = x + 1; b = a * 2` 通常不会读到半成品？**同一 stream 内的操作按入队顺序串行执行；PyTorch 还会在 CPU/GPU 搬运等必要边界插入同步。** 因此单 stream 数据依赖常由队列顺序自然满足。

真正需要警惕的是三处：

1. **计时**：主机时钟可能只量到入队；
2. **跨 stream**：不同 stream 之间没有默认的相对执行顺序；
3. **主机取值**：CPU 要看 GPU 结果时必须等待，流水线会在这里收窄。

📌 **关键点**：异步不表示“乱序”。同一 stream 是有序队列；不同 stream 才需要显式依赖。

## 2. CUDA 工作怎样正确计时

### 2.1 计时前为什么要预热？

首次 CUDA 调用可能包含上下文、库或 Kernel 路径的延迟初始化。**预热应使用相同 shape、dtype、设备和代码路径，但放在正式计时区间外。**

```python
for _ in range(3):                # 次数只是本例配置，不是通用标准
    y = torch.sin(x_cuda)
torch.cuda.synchronize()          # 预热必须完成后再开始正式区间
```

预热 3 次并不保证所有工作负载都稳定。真实 benchmark 要记录预热停止条件、重复次数和离散程度；本节只把“预热不混入正式计时”钉死。

### 2.2 主机墙钟怎样量到完成时间？

问题是：仍想用 `time.perf_counter()` 测端到端区间怎么办？**在开始前清掉旧 CUDA 工作，在结束后等待本区间完成。**

```python
torch.cuda.synchronize()
start = time.perf_counter()
for _ in range(repeats):
    y = torch.sin(y)
torch.cuda.synchronize()
wall_seconds = time.perf_counter() - start
```

开始前的同步避免上一段工作混入；结束后的同步防止只量到 enqueue。这个墙钟区间包含主机循环、dispatch 和设备完成等待，适合回答“调用方等待这段代码用了多久”。代价是测量边界会排空队列，不能把它保留在正常训练热路径里。

### 2.3 CUDA Event 怎样量设备时间？

CUDA Event 是插入 stream 的进度标记。**开始和结束 Event 在同一目标 stream 上记录，等待结束 Event 完成后，`start.elapsed_time(end)` 返回两个标记之间的设备时间，单位为毫秒。**

```python
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)

start.record()                    # 记录到当前 stream
for _ in range(repeats):
    y = torch.sin(y)
end.record()
end.synchronize()                 # CPU 等到结束标记完成
elapsed_ms = start.elapsed_time(end)
```

`record()` 同样只是把 Event 入队；若没有等待结束 Event，就读取 elapsed time，时间戳可能还没准备好。Event 适合圈定 stream 上的设备工作，墙钟适合观察调用方端到端等待，两者回答的问题不同。

PyTorch 的 `torch.utils.benchmark.Timer` 进一步负责预热、必要的异步 accelerator 同步、线程池设置与重复测量，并推荐用 replicates 和中位数抵抗噪声。**本节不拿一组 Event 数字宣布“快了几倍”**；完整 benchmark 口径留给 4.8。

## 3. 哪些操作会让主机等待 GPU

### 3.1 为什么 `.item()` 会切断流水线？

GPU Tensor 的值还在设备上，CPU 想拿到 Python 标量，就必须等产生它的 CUDA 工作完成。**凡是要求主机看见设备数值的操作，都是同步边界或需要显式同步协议。**

常见例子包括：

| 写法 | 主机为什么要等 | 更合适的做法 |
|---|---|---|
| `loss.item()` | 要生成 Python 标量 | 降低日志频率，或先在设备上累计 |
| `tensor.cpu()` | 要返回可用的 CPU Tensor 值 | 只在交接边界搬运，不在每层搬 |
| `print(cuda_tensor)` | 格式化要读取 Tensor 数值 | 热路径只打印 shape/device 等元数据 |
| `tensor.tolist()` | 要构造 Python 容器 | 只在最终输出或调试时使用 |
| `if cuda_scalar:` / `bool(cuda_scalar)` | Python 控制流要读取真假 | 避免逐 step 的数据依赖主机分支 |
| CPU/NumPy 访问设备结果 | 主机要物化设备值 | 明确标出 D2H（Device to Host，设备到主机的拷贝）与完成边界 |

`print(x_cuda.shape)` 与 `print(x_cuda.device)` 只读主机已有元数据，不等同于打印全部数值。不要把“调用了 Python”泛化成“一定同步”；判断标准是**CPU 是否必须知道 GPU 计算出的值**。

### 3.2 同步点为什么既必要又昂贵？

同步换来的是确定性：日志拿到真实 loss、评估代码拿到 CPU 数组、测试看到最终结果。牺牲的是流水线宽度：CPU 不能继续提前提交，GPU 前后的工作也更难重叠。

原则：**把同步放在“主机确实要值”的接口边界，而不是用它掩盖你没理清的依赖。**

## 4. default、current 与 non-default stream 怎样区分

### 4.1 三个名字为什么不是同一层概念？

- **default stream**：每个 CUDA 设备都有的默认队列；未切换上下文时，PyTorch 通常把操作提交到这里；
- **current stream**：当前线程、当前设备此刻选择的提交目标；它通常等于 default，也可在上下文中临时等于某个 side stream；
- **non-default stream**：你另外创建的 stream 对象，例如 `torch.cuda.Stream()`；进入它的上下文后，它就是那一刻的 current stream。

```python
device = torch.device("cuda")
previous = torch.cuda.current_stream(device)
default = torch.cuda.default_stream(device)
side = torch.cuda.Stream(device=device)

with torch.cuda.stream(side):
    assert torch.cuda.current_stream(device) == side

assert torch.cuda.current_stream(device) == previous
```

**current 描述“现在往哪提交”，default/non-default 描述“这是哪一条队列”。** 把 current 当成永久固定的第三条 stream，会直接搞错上下文语义。

### 4.2 两个 stream 为什么不会自动互等？

同一 stream 内操作串行；不同 stream 可按任意相对顺序并发，除非加入同步。以下写法存在竞争：

```python
source = torch.randn(1024, device="cuda")
side = torch.cuda.Stream()
with torch.cuda.stream(side):
    result = source.sum()         # source 的生产工作可能还没结束
```

当 `source` 在原 stream 创建，而 side stream 要读取它时，要建立“生产者完成 → 消费者开始”的边。仅仅因为 Python 先写了创建、后写了 sum，并不能替不同 stream 排序。

## 5. Event、wait_stream 与 record_stream 各解决什么

### 5.1 Event 与 `wait_stream` 都能等待，差别在哪里？

打个比方：Event 是生产线某个工位贴下的“这一批已过站”标签；`wait_stream` 则是告诉另一条生产线“先等对方截至此刻已排的工单做完”。**Event 表达精确进度点，`wait_stream` 表达 stream 之间较粗的交接。**

`consumer.wait_stream(producer)` 的含义是：调用后提交到 consumer 的未来工作，要等 producer 在调用时已经排入的工作完成；它不会让两条 stream 从此永久绑定。

```python
origin = torch.cuda.current_stream()
producer = torch.cuda.Stream()
producer.wait_stream(origin)      # producer 等 source 的已有生产工作

with torch.cuda.stream(producer):
    produced = source * 2

origin.wait_stream(producer)      # origin 的后续消费等待 producer
answer = produced + 1
```

若只需要等待 producer 的某个 checkpoint，用 Event 更精确：

```python
ready = torch.cuda.Event()
with torch.cuda.stream(producer):
    produced = source * 2
    ready.record()

with torch.cuda.stream(consumer):
    ready.wait()                   # consumer 之后的工作等待 ready
    answer = produced + 1
```

`Event.wait()` 不阻塞当前 CPU 线程去轮询；它向目标 stream 插入设备侧等待。`Event.synchronize()` 则会阻塞 CPU，直到 Event 捕获的工作完成。两者不要混为一谈。

### 5.2 有了依赖，为什么还需要 `record_stream`？

问题是：计算顺序已经正确，Tensor 的 Python 变量被删除后会发生什么？PyTorch 的 CUDA caching allocator 可能很快把那块显存交给新 Tensor。allocator 默认只知道 Tensor 的**创建 stream**；若 Tensor 还被 side stream 使用，它可能不知道那条额外生命周期。

**`tensor.record_stream(side)` 告诉 allocator：这块内存在 side 上也有未完成使用，释放 Tensor 后也不要过早复用。**

```python
producer.wait_stream(origin)
with torch.cuda.stream(producer):
    produced = source * 2
source.record_stream(producer)    # 保护 source 的 side-stream 使用
```

这里有三条不能混淆的边：

1. **数据依赖**：Event / `wait_stream` 保证谁先算；
2. **主机对象生命周期**：Python 引用决定对象何时可析构；
3. **显存复用生命周期**：`record_stream` 延迟 allocator 复用旧 storage。

⚠️ **注意**：`record_stream` 不会替你建立数据依赖，也不会让错误的读写顺序变正确。它只补充 allocator 的 stream 使用信息。

`record_stream` 用自动生命周期保护换取 allocator 轮询 Event、复用时机更难预测等成本。若你掌握完整生命周期，也可以在合适的后续位置让创建 stream 等 side stream，再释放 Tensor。立刻让 origin 等 side 虽然安全，却会消灭并行机会；等待位置应由依赖与时间线决定。

## 6. non_blocking H2D 何时才可能真正重叠

### 6.1 `non_blocking=True` 到底放开了谁？

`cpu_tensor.to("cuda", non_blocking=True)` 允许调用方绕过每次 copy 后的主机同步。**它首先承诺的是主机可以继续提交，不是 copy 已经和 GPU 计算重叠。**

要让 H2D copy 与主 stream 的独立 Kernel 在设备时间线上重叠，PyTorch 官方 pin-memory 教程给出的核心条件包括：

1. **源 Tensor 是 pinned/page-locked 主机内存**；
2. **copy 提交到独立的 non-default CUDA stream**；
3. **GPU 有可用 DMA copy engine，并支持相关并发**；
4. **同时存在可独立执行、时间上能覆盖 copy 的计算**；
5. **消费者用 Event 或 stream wait 建立正确依赖**；
6. **源主机 Tensor、目标 CUDA Tensor 的生命周期都持续到异步工作完成**；
7. **最终用 Profiler/Nsight 时间线验证重叠，而不是凭参数名推断。**

```python
source = torch.arange(64, pin_memory=True)
copy_stream = torch.cuda.Stream()
copied = torch.cuda.Event()

with torch.cuda.stream(copy_stream):
    device_value = source.to("cuda", non_blocking=True)
    copied.record()

# source 在 copied 完成前保持存活且不被修改。
torch.cuda.current_stream().wait_event(copied)
result = device_value + 1
```

普通 pageable 内存搬到 GPU 时，CUDA 需要先准备 page-locked 中转；手动在热路径调用 `tensor.pin_memory().to(...)` 又多一次主机 copy，并不自动更快。[4.4](/AIInfraGuide/prerequisites/模块一-前置知识/pytorch/44-dataloader数据流水线/) 已说明更常见的做法是让 DataLoader 产出 pinned batch，再按批次异步搬运。

### 6.2 为什么 H2D 源不能提前改写？

异步 copy 可能在 Python 返回后仍读取 pinned source。若 CPU 立刻复用或修改那块内存，GPU 可能读到混合数据。**源 Tensor 必须保持存活且内容不变，直到 copy Event 完成；目标 Tensor 跨 stream 使用时还要处理设备依赖与 allocator 生命周期。**

这项优化牺牲页锁定主机内存、额外 stream/事件和生命周期复杂度，换取主机提前提交与潜在 copy/compute 重叠。只有时间线证明 GPU 原本在等 H2D，且收益覆盖复杂度时才值得保留。

## 7. 异步错误为什么常在错误的位置上报

### 7.1 报错栈为什么指向 `.item()` 而不是坏 Kernel？

GPU 错误只有在对应工作实际执行后才产生。CPU 已经继续提交了若干调用，直到 `.item()`、`.cpu()`、同步或下一次检查 CUDA 状态时才看见错误，于是 Python 栈可能指向“发现错误的位置”，不是“发起坏工作的地方”。

**第一步是缩短异步距离，而不是相信最后一行就是根因。** 可在新进程中运行：

```bash
CUDA_LAUNCH_BLOCKING=1 python3 your_script.py
```

该环境变量强制 CUDA 调用同步，更容易让错误靠近发起位置上报。应在进程启动前设置，完成定位后关闭。

### 7.2 为什么它只能诊断，不能修复？

`CUDA_LAUNCH_BLOCKING=1` 会改变执行时序、阻止正常重叠并污染性能测量；某些竞态还可能因为时序改变而暂时消失。**它是定位工具，不是生产配置、正确性证明或 benchmark 模式。**

推荐诊断顺序：

1. 缩小到最小输入与单个可疑区间；
2. 用 `CUDA_LAUNCH_BLOCKING=1` 让栈靠近发起点；
3. 检查索引、shape、dtype、设备和 stream 依赖；
4. 移除 blocking 配置，在正常异步模式下重新跑 correctness test；
5. 若涉及自定义 Kernel，再进入模块二使用 Compute Sanitizer、Nsight 等工具。

## 8. CUDA Graph 在这条时间线的什么位置

### 8.1 Graph 为什么能减少 CPU 提交开销？

CUDA Graph 记录一个 stream 及其依赖 stream 执行的工作，之后 replay 同一批 Kernel 和参数。**它牺牲 eager 的动态灵活性，换取一次 graph launch 提交整段工作的较低 CPU dispatch 开销。** 主要目标是减少 Python、C++ 与 driver 的逐 Kernel 发射成本，不等于自动把单个 Kernel 优化得更快。

入口心智模型只有四点：

- capture 前先在 side stream 预热；
- replay 使用相同 Kernel、参数和内存地址，输入/输出 Tensor 要长期持有；
- 静态 shape、静态控制流通常更容易 graph-safe；
- `.item()` 这类 CPU/GPU 同步操作不能出现在 capture 中。

本节不实现 CUDA Graph，也不提供 replay 倍率。`torch.compile` 与 CUDA Graph 的组合、动态 shape、capture-safe optimizer 和图内存池属于后续执行/编译课程与模块二；这里先理解“减少 CPU enqueue 开销”在时间线上的位置即可。

## 9. 跑通完整示例

### 9.1 示例验证了哪些事实？

完整源码位于 `examples/pytorch/cuda_async.py`，测试位于 `examples/pytorch/tests/test_cuda_async.py`。在仓库根目录执行：

```bash
python3 examples/pytorch/cuda_async.py
python3 -m unittest examples/pytorch/tests/test_cuda_async.py -v
python3 -m compileall examples/pytorch/cuda_async.py \
  examples/pytorch/tests/test_cuda_async.py
```

有 CUDA 时，示例会：

1. 打印 Python、PyTorch、CUDA runtime、设备和 `CUDA_LAUNCH_BLOCKING` 环境；
2. 验证 side stream 上下文会成为 current stream，退出后恢复；
3. 在计时区间外预热，用 Event 与同步墙钟观察同一段工作；
4. 用 `wait_stream`、Event 和 `record_stream` 串联 producer/consumer；
5. 用 pinned source、non-default stream 和 `non_blocking=True` 验证 H2D 正确性；
6. 每条 CUDA 路径都在断言前建立完成边界。

脚本会输出本机 Event/墙钟观测值，但明确标记为 `local, not a benchmark`，不计算加速倍率、不设性能阈值。硬件、驱动、后台负载或 shape 改变后，数值都可能变化。

### 9.2 没有 CUDA 时怎样验收？

没有 CUDA 时，示例明确打印：

```text
CUDA unavailable: skipped streams, Events, pinned H2D, and GPU timing; GPU performance was not measured.
```

单元测试中的 CPU 降级断言仍会运行；4 个 CUDA 专项测试使用 `unittest.skipUnless(torch.cuda.is_available(), ...)` 显式 skip。**skip 证明测试没有假装通过，不证明 GPU 路径正确。** 最终报告必须把这些项目列为“未实测”，待有 CUDA 环境再运行。

## 10. 常见错误与诊断

| 症状 | 先检查什么 | 最小修复 |
|---|---|---|
| CUDA 操作计时小得不合理 | 结束边界是否等待 GPU | 预热后使用双边同步墙钟或 CUDA Event |
| Event elapsed time 未就绪或报错 | end Event 是否已经完成 | `end.synchronize()` 或在正确总同步后再读取 |
| side stream 偶发读到旧值 | producer→consumer 是否有依赖 | 用 Event 或 `consumer.wait_stream(producer)` |
| Tensor 已删除却出现随机损坏 | side stream 使用是否告诉 allocator | `tensor.record_stream(side)`，或手动把 side 同步回创建 stream 后再释放 |
| 加了 `record_stream` 仍读错 | 是否把生命周期当成数据依赖 | 另加 Event/wait；`record_stream` 不负责排序 |
| 每步 `loss.item()` 后吞吐下降 | 日志是否逐步主机取值 | 降低频率、设备上累计，在日志边界一次同步 |
| `non_blocking=True` 没有重叠 | pinned 源、side stream、DMA、独立计算 | 逐项补齐并用时间线验证，不宣称参数即收益 |
| H2D 结果偶发错误 | pinned source 是否提前改写/释放 | 保持源存活且不变，等 copy Event 完成再复用 |
| 错误栈指向无关 `.cpu()` | 真正坏操作可能更早异步提交 | 新进程临时启用 `CUDA_LAUNCH_BLOCKING=1` 缩小范围 |
| blocking 模式下“性能变稳定” | 是否把诊断配置当 benchmark | 关闭 blocking，恢复正常异步模式后重新测 |
| Graph capture 在 `.item()` 处失败 | capture 中是否有 CPU/GPU 同步 | 把主机取值移到 capture 外，保持 graph-safe 路径 |

📌 **关键点**：跨 stream 正确性要同时问两个问题——“消费者何时能开始”和“allocator 何时能复用”。前者是依赖，后者是生命周期。

## 11. 权衡、边界与后续接口

### 11.1 每个工具牺牲了什么？

| 选择 | 换取什么 | 牺牲什么 / 风险 | 采用条件 |
|---|---|---|---|
| 全设备 `synchronize()` | 最简单的完成边界 | 排空并行队列、粒度粗 | 测端到端墙钟或缩小诊断范围 |
| CUDA Event | 精确 stream 进度点与设备计时 | Event 管理与正确 stream 责任 | 设备计时、细粒度跨 stream 依赖 |
| `wait_stream` | 简洁的 stream 交接 | 可能等待得比单个 Event 更宽 | 确实要等待对方截至调用时的全部已有工作 |
| `record_stream` | allocator 自动保护跨 stream 使用 | 轮询开销与复用时机更难预测 | Tensor 生命周期由调用方难以手工闭合 |
| pinned + non-blocking H2D | 主机提前提交与潜在传算重叠 | 页锁定内存、stream/事件和生命周期复杂度 | H2D 已被时间线证明为瓶颈 |
| `CUDA_LAUNCH_BLOCKING=1` | 错误靠近发起点上报 | 改变时序与性能 | 仅最小化诊断过程 |
| CUDA Graph | 降低重复工作 CPU dispatch 开销 | 静态地址/shape/control-flow 等约束 | 路径 graph-safe 且 CPU launch 确为瓶颈 |

### 11.2 与 4.4、4.5、4.7 和模块二的边界是什么？

- **4.4 DataLoader**：负责 worker、预取和产出 pinned batch；本节从 batch 已生成处接手，解释 H2D stream、依赖和生命周期，不重复 Dataset/Sampler。
- **4.5 训练循环**：负责 forward/backward/step、AMP 和 checkpoint 的更新顺序；本节只解释这些 CUDA 调用何时真正完成，不改变优化器语义。
- **4.7 显存管理**：将解释 caching allocator 的 allocated/reserved/peak、碎片与 OOM 账本；本节只讲 `record_stream` 防止跨 stream 过早复用，不展开显存统计。
- **模块二 CUDA**：深入 Kernel、硬件执行、合并访存、Nsight、Compute Sanitizer 与高性能重叠。本节只建立 PyTorch 框架侧正确使用 stream/Event 的门槛。

分工：4.4 管“数据怎样准备”，4.5 管“训练状态怎样更新”，4.6 管“CUDA 工作何时完成”，4.7 管“显存怎样分配与复用”，模块二再管“Kernel 为什么这样执行、怎样优化”。

## 📝 总结

1. **异步本质**：CUDA API 返回通常只表示工作已入队；同一 stream 有序，不同 stream 没有默认相对顺序。
2. **正确计时**：预热放在区间外；墙钟前后同步，或用开始/结束 Event 并等待结束 Event 后读取毫秒数。
3. **主机同步**：`.item()`、`.cpu()`、打印数值和 Python 数据依赖控制流都需要主机看见设备值，应只放在真实交接边界。
4. **stream 语义**：default 是每设备默认队列，current 是当前提交目标，non-default 是额外创建、可临时成为 current 的队列。
5. **依赖与生命周期**：Event/`wait_stream` 决定执行先后，`record_stream` 告诉 allocator 延迟 storage 复用；两者不可替代。
6. **异步 H2D**：`non_blocking=True` 首先放开主机；实际重叠还需要 pinned 源、side stream、硬件并发、独立工作、正确依赖和时间线证据。
7. **错误诊断**：异步错误可能延后上报；`CUDA_LAUNCH_BLOCKING=1` 只用于定位，关闭后必须回到正常模式复验。
8. **Graph 入口**：CUDA Graph 用静态执行约束换较低 CPU dispatch 开销；本节只建立入口，不提供未经规范实验支持的性能结论。
