## 1. 为什么需要把文字变成向量

计算机只认识数字，不认识文字。“猫”、“cat”、“Katze”——这些对计算机来说都是无意义的符号串，它不知道“猫”和“狗”都是动物，也不知道“happy”和“joyful”意思相近。

但神经网络的输入必须是数字矩阵。所以在文字进入 Transformer 之前，需要解决两个问题：

1. **切分问题**：怎么把一段连续文字拆成一个个可以处理的“单元”（Tokenization）？
2. **编码问题**：怎么把每个“单元”表示成一个能捕捉语义关系的数字向量（Embedding）？

这两个问题的解决方案，深刻影响着模型的理解能力和推理效率。

## 2. Tokenization：把文字切分成基本单元

### 2.1 Token 是什么

**Token** 是 Transformer 处理语言的最小单元——不是字，也不是词，而是介于两者之间的“词元”。

根据不同的切分策略，同一段文字会产生不同的 token 序列：

```
输入: "Tokenization"

字符级切分:  T / o / k / e / n / i / z / a / t / i / o / n      (12 tokens)
词级切分:    Tokenization                       (1 token)
子词切分:    Token / ization                    (2 tokens)  ← 主流大模型采用
```

### 2.2 子词切分：大模型的实际选择

现代大模型普遍采用**子词（Subword）切分**策略，最常用的是 **BPE（Byte Pair Encoding）**。

📌 **关键点**：BPE 从字符出发，把高频的字符组合逐步合并成更大的 token，最终得到一个覆盖常用词、生词用子词拼接的词表。

直觉上理解：BPE 把高频组合合并为单一 token，把低频组合保留为子词拼接。常见词（“play”、“run”）通常作为完整 token 存在；生僻词或新词（如 “tokenization”）可能被拆成 “token” + “ization”，用已有子词拼接表示，不会出现未知词（OOV）问题。需要注意的是，BPE 的切分是**纯数据驱动**的统计结果，不一定按语言学意义上的词根/后缀切分，具体结果取决于训练词表。

实际大模型的词表规模：

| 模型 | 词表大小 | 分词策略 |
|------|---------|---------|
| GPT-2 / GPT-3 | 50,257 | BPE |
| LLaMA-2 | 32,000 | SentencePiece BPE |
| LLaMA-3 | 128,256 | Tiktoken BPE |
| GPT-4 | ~100,000 | Tiktoken cl100k |

⚠️ **注意**：词表越大，覆盖越好，但 Embedding 矩阵（下文讲）也越大。LLaMA-3 把词表从 32K 扩到 128K，直接让 Embedding 层参数量增加了 4 倍。

### 2.3 Tokenization 的中文处理

中文没有天然的空格分隔，处理方式与英文不同：

- 大多数大模型对中文做**字符级 Tokenization**（每个汉字一个 token），或者将汉字的 UTF-8 字节序列作为切分依据
- 专门优化中文的模型（如 Qwen、ChatGLM 系列）通常有更大的词表，包含更多中文词组作为单独 token，生成效率更高

### 2.4 BPE 的学习流程（可手算的合并例子）

BPE 到底是怎样“学”出词表的？**它反复执行“数相邻 pair → 合并最高频 pair → 重新计数”这三步。** 这里的 pair 指同一个词内部相邻的两个 token；merge 指把这两个 token 合成一个新符号的规则。训练阶段学到的是一串有先后顺序的 merge 规则，不是一张“完整单词对应哪个 token”的静态查表。

打个比方：你在整理一盒积木，先统计哪两块积木最常挨在一起，把它们粘成一块新积木；粘完以后，原来的相邻关系变了，所以必须重新数一遍。下面用 6 个词把这件事纸笔走完。为避免边界符干扰，空格只表示“两个词不能跨过去”，不把空格本身列入 pair。

**初始语料**：`cat cat cat can can cap`

每个词先拆成字符 token：`c a t` 出现 3 次，`c a n` 出现 2 次，`c a p` 出现 1 次。

**第 1 轮：统计初始 pair**

| pair（相邻两个 token） | 次数 |
|---|---:|
| `c + a` | 6 |
| `a + t` | 3 |
| `a + n` | 2 |
| `a + p` | 1 |

最高频的是 `c + a`，于是加入规则 **R1：`c + a → ca`**，并把 6 个词里的这个 pair 全部替换。语料变成：`ca t` ×3、`ca n` ×2、`ca p` ×1。

**第 2 轮：合并后重新计数**

| pair | 次数 |
|---|---:|
| `ca + t` | 3 |
| `ca + n` | 2 |
| `ca + p` | 1 |

最高频的是 `ca + t`，得到 **R2：`ca + t → cat`**。注意，R2 不是从原始字符重新计算，而是接着 R1 产生的新符号继续计算。

**第 3 轮：继续在更新后的语料上计数**

此时语料是：`cat` ×3、`ca n` ×2、`ca p` ×1。单独的 `cat` 已经没有相邻 pair，剩下的计数是：

| pair | 次数 |
|---|---:|
| `ca + n` | 2 |
| `ca + p` | 1 |

于是得到 **R3：`ca + n → can`**。合并后语料为：`cat` ×3、`can` ×2、`ca p` ×1。

**第 4 轮：把最后一个可合并 pair 也记录下来**

| pair | 次数 |
|---|---:|
| `ca + p` | 1 |

得到 **R4：`ca + p → cap`**。最终学到的规则顺序是：`R1：c+a→ca`、`R2：ca+t→cat`、`R3：ca+n→can`、`R4：ca+p→cap`。

推理时（模型处理新输入、而不是学习规则的阶段）按学到的合并规则顺序应用。比如输入 `cap`，先从 `c a p` 开始：R1 把它变成 `ca p`，R2 和 R3 找不到匹配就跳过，R4 再把它变成 `cap`。**所以训练学的是规则顺序，推理是在基础符号上依次执行规则，不是直接查一张“cap → 某个 ID”的完整单词表。**

### 2.5 Byte-level BPE 与 UTF-8 字节 fallback

罕见词、拼写错误甚至表情符号不在词表里时，怎样保证仍然能编码？**Byte-level BPE（字节级 BPE）先把文字转换成 UTF-8 字节序列，再以 256 个单字节符号作为底座；没有合并成功的部分就 fallback（退回）到这些字节符号，因此不需要 `<UNK>`。**

这里的“字节”是 8 个二进制位组成的基本数据单元，取值范围是 0 到 255。UTF-8 是把 Unicode（为世界文字分配统一编号的字符标准）字符编码成字节的规则：英文常见字符通常占 1 个字节，阿拉伯语常见字符约占 2 个字节，日语假名或汉字常见占 3 个字节。`<UNK>` 是 unknown token（未知词元）占位符，表示 tokenizer 找不到输入的表示；字节级底座则可以把任何输入拆回原始字节。

忽略额外的控制符号，字节级 BPE 的词表可以写成：

$$
V_{\text{byte-BPE}} = B_{256} \cup M,\qquad |B_{256}| = 256,\qquad |V| \approx 256 + |M|
$$

其中，$V$ 表示整个词表，$B_{256}$ 是 256 个可能的单字节符号，$M$ 是训练过程中学到的多字节合并符号。比如：

| 输入 | UTF-8 字节（十六进制） | 没有更大合并时的 fallback |
|---|---|---|
| `A` | `41` | 1 个字节 token：`[41]` |
| `🙂`（表情符号） | `F0 9F 99 82` | 4 个字节 token：`[F0, 9F, 99, 82]` |

这套兜底机制换来了覆盖能力，却可能带来跨语言的 token 成本差异。看 4 句表达相近意思的短句，先只按字节底座估算：

| 短句 | 字符数 | UTF-8 字节数 | 只用 byte fallback 时的 token 量级 |
|---|---:|---:|---:|
| `I like tea` | 10 | 10 | 约 10 |
| `我喜欢茶` | 4 | 12 | 约 12 |
| `أحب الشاي` | 9 | 17 | 约 17 |
| `お茶が好き` | 5 | 15 | 约 15 |

这不是所有模型的实际 token 数：真正的 BPE 还可能把常见英文词、中文片段或日文片段合并。数字要表达的是一个量级事实：同样的语义，非单字节文字往往先付出更多字节，能被合并成的片段又取决于训练语料和词表。

这种差异会落到推理账本上。Prefill（模型第一次把整段输入送入并计算各位置状态的阶段）至少要按 token 数处理输入；KV Cache（Key/Value Cache，把注意力已经算过的两类中间向量缓存起来）则近似随 token 数线性增长。设原始输入 token 数为 $N$，$M_{\text{KV}}$ 表示 KV Cache 的显存占用：

$$
N \rightarrow 1.5N \quad \Longrightarrow \quad M_{\text{KV}} \rightarrow 1.5M_{\text{KV}}
$$

也就是说，输入 token 从 $N$ 增加到 $1.5N$ 时，KV Cache 显存大约增加到 1.5 倍；Prefill 中逐 token 的线性计算也约为 1.5 倍，而标准全注意力的 token 两两交互部分可能接近 $1.5^2 = 2.25$ 倍。**字节级 BPE 解决了“能不能表示”的问题，但没有消除“不同语言 token 数不同”的成本。**

[Parity-Aware Byte-Pair Encoding](https://arxiv.org/abs/2508.04796) 只在这里补充一句：它在每轮用 max-min/fair-max（优先最大化当前压缩最差语言的改善）规则选 merge，并用 Gini coefficient（衡量各语言 token 成本不均程度的指标）观察跨语言公平性；这不是本文的展开重点。

## 3. 独热编码：第一次尝试的失败

有了 Token ID，最简单的向量化方法是**独热编码（One-Hot Encoding）**：假设词表有 $V$ 个 token，每个 token 用一个长度为 $V$ 的向量表示，对应位置为 1，其余全为 0。

举例：假设词表 = [“猫”, “狗”, “鱼”, “河”, “银行”]，词表大小 $V = 5$：

$$
\text{猫} = [1, 0, 0, 0, 0] \qquad \text{狗} = [0, 1, 0, 0, 0] \qquad \text{鱼} = [0, 0, 1, 0, 0]
$$

看起来可以用，但有两个致命问题：

**问题一：维度爆炸**

真实词表有数万个 token，每个 token 的向量就有数万维，存储和计算开销极大。更严重的是，把这个稀疏向量作为神经网络输入，后续层需要极大的权重矩阵才能处理它——效率极差。

**问题二：语义丢失**

独热向量之间完全正交——“猫”和“狗”的向量内积为 0，“猫”和“鱼”的内积也是 0。从数学上看，所有 token 的距离完全相等，彼此之间毫无关联。这意味着模型无法从编码中学到任何语义关系：“猫”和“狗”都是宠物、都是动物，这个信息在独热编码里完全不存在。

$$
\text{猫} \cdot \text{狗} = 0, \quad \text{猫} \cdot \text{鱼} = 0 \quad \Rightarrow \text{模型看来"猫狗"关系 = "猫鱼"关系}
$$

## 4. Word Embedding：几何空间里的语义地图

### 4.1 核心思想：语义相似的词距离相近

Word Embedding（词嵌入）的核心思想是：**把每个 token 映射到一个低维连续向量空间，使得语义相似的词在这个空间里距离相近**。

从独热编码的 $V$ 维稀疏向量，压缩到 $d_{model}$ 维稠密向量（通常 $d_{model} \ll V$）：

| 模型 | 词表大小 $V$ | 向量维度 $d_{model}$ | 压缩比 |
|------|------------|-------------------|-------|
| BERT-base | 30,522 | 768 | ~40:1 |
| LLaMA-2-7B | 32,000 | 4,096 | ~8:1 |
| GPT-3 | 50,257 | 12,288 | ~4:1 |

用一个二维示意图来理解（真实 Embedding 空间维度远高于此）：

```
         动物类
    狗 ●   ● 猫
             ● 兔
       ● 鸟
                   金融类
              ● 银行  ● 钱
                    ● 贷款

         ● 河流   地理类
    ● 湖泊
```

可以看到，“猫”和“狗”在这个空间里距离很近（都是常见宠物）。需要注意：在静态 Word Embedding（如 Word2Vec）中，“银行”这个 token 只有**一个**固定向量，位置由它在所有语料中的平均共现模式决定——金融语境和河岸语境各占一部分，向量会落在两者之间。真正消除歧义是 **Self-Attention** 的工作：它根据上下文中其他词（“money” 或 “river”）动态调整每个 token 的表示，为“银行”在不同语境中生成不同的上下文向量。Embedding 层提供的是起点，Self-Attention 完成动态消歧。

### 4.2 Embedding 空间的神奇属性

经过大量语料训练的 Word Embedding 会涌现出令人惊叹的几何属性：

**词语类比关系**：

$$
\text{king} - \text{man} + \text{woman} \approx \text{queen}
$$

这意味着在 Embedding 空间里，“王”→“女王”的方向向量，和“男人”→“女人”的方向向量几乎平行！语义关系被编码成了几何关系。

**语法变形的平行性**：

$$
\text{walking} - \text{walk} \approx \text{swimming} - \text{swim} \approx \text{running} - \text{run}
$$

所有动词从原形到进行时的位移向量几乎相同——“时态变化”这个语法规律变成了一个统一的位移方向。

💡 **提示**：这些属性不是人工设计的，而是模型从海量文本中自动学习到的。正是因为全人类几百年的文字记录里，“狗追猫”、“猫抓鱼”这类共现关系远多于“猫追猫”，这些词语的空间位置才逐渐形成了今天的格局。

### 4.3 Embedding 矩阵：一张可学习的查找表

在 Transformer 中，Word Embedding 实现为一个**可学习的查找矩阵** $W_{emb}$：

$$
W_{emb} \in \mathbb{R}^{V \times d_{model}}
$$

输入一个 Token ID，直接取对应行，得到 $d_{model}$ 维的向量：

```
Token ID = 1234  →  W_emb[1234, :]  →  [0.12, -0.34, 0.07, ..., 0.91]  (d_model 维)
```

这等价于一个输入为独热向量的线性层，但实现为查表（index lookup）操作，计算效率远高于实际的矩阵乘法。

**Embedding 层的参数量**：$V \times d_{model}$

以 LLaMA-2-7B 为例：$32000 \times 4096 \approx 131M$ 参数。看起来不少，但在 6.7B 总参数中只占约 2%，原因是其余参数都在 32 层 Decoder Block 里。

## 5. 位置信息的空缺：为什么还需要 Positional Encoding

Word Embedding 解决了“语义编码”的问题，但留下了一个关键缺陷：**它不包含任何位置信息**。

把句子 “猫追狗” 的三个 token 打乱为 “狗猫追”，它们的 Embedding 向量完全不变——模型根本分不清顺序。但语言的意思高度依赖词序：“猫追狗”和“狗追猫”意思截然相反。

这就是为什么 Transformer 在输入层还需要额外加上 **Positional Encoding（位置编码）**：

$$
\text{Input}_{i} = W\_{emb}[\text{token}_i] + \text{PE}(\text{pos}_i)
$$

Word Embedding 提供语义信息，Positional Encoding 提供位置信息，两者相加，才构成 Transformer 的完整输入。Positional Encoding 的详细设计（Sinusoidal 和 RoPE）在 [3.6 位置编码深入理解](/AIInfraGuide/prerequisites/模块一-前置知识/transformer/35-transformer位置编码深入理解) 中详细讲解。

## 6. 从 Token ID 到输入矩阵：Transformer 的输入层

把上面的流程串起来，看一个完整的例子：

```
用户输入: "猫在桌子上"

Step 1: Tokenization
────────────────────────────────────────────────────
"猫在桌子上" → Tokenizer → [3421, 528, 11082, 319] (4 个 Token ID)
                             猫    在   桌子    上

Step 2: Embedding Lookup
────────────────────────────────────────────────────
Token 3421 (猫)  → W_emb[3421]  → e_1: (d_model,)
Token 528  (在)  → W_emb[528]   → e_2: (d_model,)
Token 11082(桌子)→ W_emb[11082] → e_3: (d_model,)
Token 319  (上)  → W_emb[319]   → e_4: (d_model,)

组合成输入矩阵 X: (4, d_model)

Step 3: 加 Positional Encoding
────────────────────────────────────────────────────
X[0] = e_1 + PE(0)   ← "猫" 在位置 0
X[1] = e_2 + PE(1)   ← "在" 在位置 1
X[2] = e_3 + PE(2)   ← "桌子" 在位置 2
X[3] = e_4 + PE(3)   ← "上" 在位置 3

最终输入矩阵 X: (4, d_model)  ← 送入第 1 层 Decoder Block
```

最终，4 个 token 变成一个 $(4, d_{model})$ 的矩阵，每行是一个 token 的向量表示（包含语义 + 位置信息）。这个矩阵就是 Transformer Block 的输入。

**AI Infra 视角**：Embedding 层的 $W_{emb}$ 矩阵有时会和输出层的 LM Head 共享权重（称为 Weight Tying），这样可以节省 $V \times d_{model}$ 的显存。例如 LLaMA-2 就采用了 Weight Tying，将 Embedding 参数量从 262M 降到 131M（只算一次）。在做量化时，Embedding 层通常不量化（因为它是查表操作，量化收益有限但精度损失较大）。

## 7. 从词嵌入到文本嵌入：语义检索入门

Token 级词嵌入回答“这个 token 的向量是什么”，但搜索一段资料时，你真正要比较的是“这整段话想表达什么”。**文本嵌入（text embedding）把句子或文档压成一个稠密向量，让整段语义可以用距离或角度比较。**稠密的意思是：向量有很多维，而且大多数维度都不是 0。

### 7.1 从查表向量到整段文本向量

前面的 Embedding 矩阵是 token 级查找表：给定一个 Token ID，取出对应的一行 $W_{emb}[id,:]$。它只回答单个 token 的初始表示；文本嵌入还要让这些位置经过上下文计算，再汇总成一个向量。

```text
一段文字 → Token ID → 每个 token 查表向量 → 上下文计算 → 一个句子/文档向量
```

为什么“逐词查表再平均”不够？平均确实是一个便宜的 baseline（基线方案），但它把顺序和组合关系抹平了：

$$
\mathbf{e}_{\text{avg}} = \frac{1}{T}\sum_{i=1}^{T}\mathbf{e}_i
$$

这里 $T$ 是 token 数，$\mathbf{e}_i$ 是第 $i$ 个 token 的向量，平均操作把 $T$ 个向量压成一个向量。比如不改变词袋、只交换顺序：

$$
\frac{\mathbf{e}_{\text{猫}}+\mathbf{e}_{\text{咬}}+\mathbf{e}_{\text{狗}}}{3}
=
\frac{\mathbf{e}_{\text{狗}}+\mathbf{e}_{\text{咬}}+\mathbf{e}_{\text{猫}}}{3}
$$

所以“猫咬狗”和“狗咬猫”会得到同一个平均结果，尽管主客体关系相反。否定、词义随上下文变化等情况也不适合只靠独立 token 向量相加。更强的文本嵌入模型会先让每个位置读取整段上下文，再从这些上下文向量中取出一个代表整段话的结果。

### 7.2 用余弦相似度找语义近邻

语义检索就是：把用户问题变成查询向量（query embedding），把候选文章变成文档向量（document embedding），再找最相近的向量。常用的余弦相似度把两个向量的方向当作主要比较对象：

$$
\operatorname{cos}(\mathbf{q},\mathbf{d})
= \frac{\mathbf{q}\cdot\mathbf{d}}{\|\mathbf{q}\|\,\|\mathbf{d}\|}
$$

直觉是先问“两个箭头是不是朝同一个方向”，再用长度把点积带来的大小影响除掉。$\mathbf{q}$ 是查询向量，$\mathbf{d}$ 是文档向量，$\mathbf{q}\cdot\mathbf{d}$ 是对应维度相乘后相加的点积，$\|\mathbf{q}\|$ 与 $\|\mathbf{d}\|$ 是两个向量的长度。

**二维算例**：设查询向量 $\mathbf{q}=(1,1)$，候选文档向量 $\mathbf{d}_1=(2,2)$。点积是 $1\times2+1\times2=4$，长度乘积是 $\sqrt{2}\times\sqrt{8}=4$，所以：

$$
\operatorname{cos}(\mathbf{q},\mathbf{d}_1)=\frac{4}{4}=1
$$

两个向量方向完全相同。若另一个候选是 $\mathbf{d}_2=(1,-1)$，点积为 $0$，余弦相似度就是 $0$，表示方向正交。欧氏距离是向量端点之间的直线距离，会把“同方向但长度更长”也当成差异；余弦相似度忽略这种整体缩放，更符合“语义方向”的比较目标。若预先把所有向量归一化，欧氏距离和余弦排序会等价，但工程上仍常直接使用余弦或点积。

### 7.3 InfoNCE：把正例拉近、把负例推远

InfoNCE（Information Noise-Contrastive Estimation，一种对比学习损失）训练的不是“记住某篇文章的 ID”，而是让匹配关系在向量空间里变得明显。它至少需要三类样本：

| 样本角色 | 白话定义 | 例子 |
|---|---|---|
| 正例（positive） | 真正能回答查询的文档 | “如何重置 Gmail 密码” ↔ 密码重置指南 |
| 负例（negative） | 与查询无关的文档 | 上面的查询 ↔ 手机发布新闻 |
| 难负例（hard negative） | 看起来相关、但实际答非所问的文档 | 重置密码 ↔ 修改 Gmail 显示名 |

一个训练批次（batch，一次并行送入模型的一小组样本）里，其他查询对应的正例文档也可以暂时当作当前查询的 in-batch negative（批内负例）。对每个查询，InfoNCE 同时比较自己的正例、这些批内负例和人工或模型挖出的 hard negative：**提高正例相似度，降低所有负例相似度，尤其压低那些“看起来很像”的难负例。**

难负例之所以难，是因为它可能共享相同关键词、实体或主题；只看词面会把它排得很靠前，模型必须进一步理解意图和答案关系。这样，训练目标才从“搜到含有相同词的文章”推进到“搜到真正能解决问题的文章”。

### 7.4 用 decoder LLM 提取句子向量

Decoder-only LLM（只能按从左到右处理文本、当前位置看不到未来 token 的大语言模型）可以用最后一个位置的隐藏状态作为句子向量。隐藏状态是模型某一层在某个位置输出的向量，它已经汇总了该位置能看到的上下文；EOS（End Of Sequence，序列结束标记）则是专门放在文本末尾的 token。

```text
输入 token：t₁  t₂  …  tₜ  EOS
最后一层： h₁  h₂  …  hₜ  h_EOS
文本向量：                         h_EOS
```

做法是：先在文本末尾加 EOS，把整段文字送进模型，再取最后一层 EOS 位置的隐藏状态。如果没有显式 EOS，也可以取最后一个真实 token 的隐藏状态。为什么选最后位置？因为这种从左到右的模型让末位可以看到前面所有 token；前面的某个位置却看不到后面内容，所以末位天然有机会汇总整句话。它是一个简单的汇总方案，不代表所有模型都必须用同一种 pooling（把多个位置合成一个向量的方法）。

### 7.5 E5 案例：训练数据从哪里来

E5 是一类文本嵌入模型；这里不展开论文实验，只看它怎样获得训练数据。课程幻灯片用 GPT-4（OpenAI 的大语言模型）合成数据来概括流程，E5 论文更精确地描述为使用 GPT-3.5/4 等大语言模型生成约 50 万条查询—正例—难负例样本，覆盖 93 种语言，再进行少于 1,000 步的微调。这样做的意义是**减少对人工标注查询—文档对的依赖**，而不是宣称人工评测从此没有价值。

把文档向量预先存进向量数据库（专门存储向量并快速查找近邻的数据库），查询时找出最相近的若干段，再交给大语言模型生成答案，就是 RAG（Retrieval-Augmented Generation，检索增强生成）的基本连接：文本嵌入负责“找到什么”，RAG 负责“拿找到的内容生成什么”。

## 📝 总结

1. **为什么需要切词**：模型只能吃数字向量，Tokenizer 把文本切成基本单元（Token），映射成整数 ID；子词切分（BPE 等）在“词表大小”与“覆盖能力”之间取平衡。
2. **中文的特殊性**：中文没有天然空格分词，BPE 从字符/字节层面切分，一个汉字可能对应 1-2 个 token——中文 tokenizer 的词表设计与英文差异很大。
3. **独热编码为什么失败**：维度爆炸、无语义、无相似性——这是“看起来合理但错误”的典型；Embedding 用可学习的低维稠密向量解决，语义相似的词在向量空间里距离相近。
4. **Embedding 矩阵**：一张 (vocab_size, hidden_dim) 的可学习查找表，训练中不断调整；它既是输入层也是输出层（LM Head），常做权重共享（Weight Tying）。
5. **位置信息的空缺**：Embedding 本身不携带位置，需要 Positional Encoding 补上——这是 3.5 的位置编码专题要解决的问题。
6. **字节级 BPE 的兜底**：256 个单字节符号保证罕见字符仍能被表示，但跨语言的 UTF-8 字节数差异会传导成 token、Prefill 和 KV Cache 成本差异。
7. **文本嵌入与语义检索**：句子或文档先变成一个稠密向量，再用余弦相似度比较语义方向；InfoNCE 用正例、负例和难负例训练这种空间。

## ⚠️ 常见错误做法

- ❌ **用独热编码直接当模型输入**：把 token 转成 one-hot 向量喂进网络。为什么错：维度等于词表大小（几万维）、无语义信息、无法学习相似性——本文第 3 节完整演示了它为什么失败。正确做法：用可学习的 Embedding 查找表（低维稠密向量）。
- ❌ **以为 tokenizer 只是“预处理工具”，不影响模型能力**：随便换 tokenizer 或词表。为什么错：词表决定模型能表示的字符/子词集合，也决定有效上下文长度（token 数≠字符数）；换 tokenizer 意味着重新训练。正确做法：把 tokenizer 当作模型的一部分，训练与推理必须一致。
- ❌ **用字符数估算 token 数**：中文里“1 个汉字 ≈ 1 token”只是粗略近似。为什么错：BPE 会把常见词合并、罕见字拆开，同样长度的句子 token 数差异可达 2 倍，直接影响成本与上下文预算。正确做法：用目标模型的 tokenizer 实测计数（`tokenizer.encode`）。
- ❌ **忽略 Embedding 矩阵的显存**：算模型大小时只算 Transformer 层。为什么错：词表 32K-128K × hidden 维的 Embedding 是实打实的显存（7B 模型里约 0.7B 参数）。正确做法：把 Embedding + LM Head 计入参数量与显存账本。
