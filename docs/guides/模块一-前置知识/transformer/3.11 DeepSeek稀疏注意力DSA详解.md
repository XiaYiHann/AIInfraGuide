上一章的 MLA（Multi-head Latent Attention，多头潜在注意力：把历史 Key（标签）和 Value（信息）压成较窄的 latent）留下了一个尖锐问题：序列有 $L$ 个 token 时，主注意力仍然要看 $L\times L$ 个位置对。DeepSeek-V3.2 的 DSA（DeepSeek Sparse Attention，DeepSeek 稀疏注意力）在 MLA 之上先用轻量的 Lightning Indexer（可学习的相关性索引器）给当前查询 token（query）挑出分数最高的 $k=2048$ 个 latent Key/Value（KV）条目；top-k 的意思是“只保留最高的 $k$ 个分数”，decode 的意思是“每次生成一个新 token”。它再只对这些条目做主注意力，把核心注意力从 $O(L^2)$ 降到 $O(Lk)$；论文 Figure 3 在 NVIDIA H800 GPU（用于论文服务测量的计算卡）的 128K decode 成本曲线上读到约 2.15 美元降到约 0.25 美元/百万 token，但这是 H800 实际服务成本的读图值，不应改写成所有场景都有 8.6 倍速度。

## 0. 读前 3 分钟

### 0.1 先把问题钉死：我们到底在缩什么？

**DSA 不是把 KV Cache 再压小一遍，而是把“每个 query 要参与注意力的历史位置数”从 $L$ 变成 $k$。**

把一本很长的书交给问答员。普通注意力要求问答员把每一页都和当前问题比一遍；MLA 把每页的资料先压成更薄的卡片，减轻了卡片的存储；DSA 再加一个索引员，先快速找出最相关的 $k$ 张卡片，问答员只精读这些卡片。这里的对应关系是：书页是历史 token，卡片是 MLA 的 latent KV，索引员是 Lightning Indexer，$k$ 张重点卡片是稀疏注意力的输入。

用技术语言重述：MLA 主要改变“每个历史 token 存多少维”；DSA 主要改变“一个 query 读取和计算多少个历史 token”。两笔账不同，不能因为 KV Cache 变小，就自动推出 $L^2$ 的注意力计算也变小。

### 0.3 先写出普通注意力，后面所有复杂度都从这里来

注意力先计算 Query 和所有 Key 的相关性，再把对应的 Value 加权相加。最小公式是：

$$
\operatorname{Attn}(Q,K,V)=\operatorname{Softmax}\left(\frac{QK^{\mathsf T}}{\sqrt d}\right)V,\qquad Q,K,V\in\mathbb{R}^{L\times d}。
$$

直觉上，这个式子做三件事：第一，$QK^{\mathsf T}$ 为每个 query 和每个历史 key 配对；第二，Softmax 把分数变成总和为 1 的权重；第三，用这些权重汇总 Value。

- $L$ 是序列里 token 的数量；
- $d$ 是每个向量的宽度；
- $QK^{\mathsf T}$ 的形状是 $L\times L$，因为每个 query 都和每个历史 key 配对；
- $\sqrt d$ 只是让点积的数值尺度稳定，不改变“要配多少对”的数量关系。

做一个最小数量检查：$L=4$ 时，分数矩阵有 $4\times4=16$ 个位置；如果按 128K 取 $L=128\times1024=131072$，稠密位置对数是：

$$
L^2=131072^2=17\,179\,869\,184\approx1.72\times10^{10}。
$$

这是**位置对的数量**，不是论文报告的 FLOPs 或端到端耗时。它说明为什么“缓存向量变窄”还不够：只要每个 query 仍然检查全部 $L$ 个位置，$L\times L$ 的关系就还在。

> 💡 **回顾：MLA 与 KV Cache 的关系**  
> MLA 把每个历史 token 的完整 K、V 压成较窄的 latent $\mathbf c_s$，Decode 时主要缓存 $\mathbf c_s$；KV Cache 的通用账可以写成 $M_{\mathrm{KV}}=2\times L\times H_{\mathrm{KV}}\times d\times b$，其中 2 是 K、V 两份，$H_{\mathrm{KV}}$ 是 KV 头数，$b$ 是每个元素的字节数。站内 [3.10 KV Cache 为什么能省 93%？MLA 低秩压缩与解耦 RoPE（DeepSeek-V2 §2.1 精读）](/AIInfraGuide/prerequisites/模块一-前置知识/transformer/310-mla与decoupled-rope精读) 解释了低秩联合压缩、训练期 Query 压缩和 Decoupled RoPE；本文只把这份缓存状态作为 DSA 的输入，继续追踪“选哪些条目参与注意力”。

## 1. MLA 为什么还不够

### 1.1 KV 压缩为什么没有自动消灭 $L^2$？

**因为“每个条目存多宽”和“条目之间要配多少对”是两件事。**

把 MLA 的效果写进注意力式子：历史 K、V 不再以完整宽度保存，而是变成 $L$ 个 latent 条目 $\mathbf c_1,\ldots,\mathbf c_L$。当前 query 仍然要问：“我和第 1 条相关吗？第 2 条呢？一直问到第 $L$ 条。”条目的宽度变小了，但问题的数量仍是 $L$ 个。

站内 [3.3 Self-Attention机制深入理解 的 §9.5 MLA 小节](/AIInfraGuide/prerequisites/模块一-前置知识/transformer/33-self-attention机制深入理解#95-mla-multi-latent-attention) 给出了 MHA、MQA、GQA、MLA 的入门对比，并明确区分“减少 KV Cache”与“注意力矩阵仍然稠密”；本文在此基础上把 DSA 的稀疏选择接到 MLA latent 上，补上计算数量这一条分支。

> 💡 **回顾：GQA 是什么**  
> GQA（Grouped-Query Attention，分组查询注意力）把 $H$ 个 query 头分成 $G$ 组，同组 query 头共享一组 K、V；它把每层缓存从 MHA 的 $2LHdb$ 变成 $2LGdb$，但每个 query 仍然面对全部 $L$ 个历史位置，所以主注意力仍是 $O(L^2)$。例如 $H=16、G=4$ 时，KV Cache 只剩 MHA 的 $4/16=1/4$，位置对数量却没有变。站内 [3.3 Self-Attention机制深入理解 的 §9.5 MLA 小节](/AIInfraGuide/prerequisites/模块一-前置知识/transformer/33-self-attention机制深入理解#95-mla-multi-latent-attention) 负责基础的头共享对比；本文只把 GQA 作为“缓存缩小但计算仍稠密”的参照，继续引出 DSA。

### 1.2 MHA → MQA → GQA → MLA → DSA：一张表看完两笔账

先固定缓存公式。对**一层、一个序列、忽略 batch**的 KV Cache，若有 $H_{\mathrm{KV}}$ 个 KV 头、每头宽度为 $d$、数据类型每元素占 $b$ 字节，则：

表中的 $H$ 是 query head 数，$G$ 是 KV group 数，$d_{\mathrm{lat}}$ 是每个 latent 条目的宽度；它们分别回答“有多少路头”“多少组共享头”和“每条压缩状态有多宽”。

$$
M_{\mathrm{KV}}=\underbrace{2}_{\text{K 与 V 两份}}\times\underbrace{L}_{\text{历史 token 数}}\times\underbrace{H_{\mathrm{KV}}}_{\text{KV 头数}}\times\underbrace{d}_{\text{每头宽度}}\times\underbrace{b}_{\text{每元素字节数}}。
$$

例如 $L=4096$、$d=128$、FP16（16 位浮点数）的 $b=2$：MHA 若有 16 个 KV 头，需要 $2\times4096\times16\times128\times2=33\,554\,432$ 字节，约 32 MiB；MQA 只有 1 个 KV 头，则约 2 MiB；GQA 若有 4 个 KV 头，则约 8 MiB。这是手算账，不是 DeepSeek-V3.2 的实测配置。

下面的复杂度列按幻灯片的结构口径，省略每次向量点积中的宽度因子；“持久缓存”指历史状态长期留在 KV Cache 里的大小，“主注意力候选数”指一个 query 要参与的历史条目数。

| 方案 | 主注意力候选 | 主注意力复杂度 | 持久缓存账 | 缩的是什么 |
|---|---:|---:|---:|---|
| **MHA** | 稠密 $L\times L$ | $O(L^2)$ | $O(LHd)$ | 不缩；每个 query 头各存一份 K、V |
| **MQA** | 稠密 $L\times L$ | $O(L^2)$ | $O(Ld)$ | 缩 KV 头数：$H\rightarrow1$ |
| **GQA** | 稠密 $L\times L$ | $O(L^2)$ | $O(LGd)$ | 缩 KV 组数：$H\rightarrow G$，但仍扫描全部 $L$ 条 |
| **MLA** | 稠密 $L\times L$ | $O(L^2)$ | $O(Ld_{\mathrm{lat}})$ | 缩每个历史表示的宽度：完整 K、V → latent 宽度 $d_{\mathrm{lat}}$ |
| **DSA（构建在 MLA 上）** | 索引器先看 $L$，主注意力只看 $k$ | 主注意力 $O(Lk)$；索引器仍是 $O(L^2)$，但向量宽度小、头数少、可用 FP8 | 仍是 MLA 的 $O(Ld_{\mathrm{lat}})$ | 缩每个 query 的主注意力读取与计算：$L\rightarrow k$；不再缩持久 KV Cache 宽度 |

📌 **关键点**：MQA、GQA、MLA 主要是在“少存一点、少搬一点”上做文章；DSA 才把主注意力的候选位置数从 $L$ 改成 $k$。但 DSA 不是凭空得到 $O(Lk)$：它先付出一次轻量的全历史打分，论文也明确写着 Lightning Indexer 自身仍有 $O(L^2)$ 结构复杂度，只是计算量显著小于 MLA 的主注意力。

### 1.3 DSA 为什么要“实例化在 MLA 之下”？

论文的原话不是“任何稀疏注意力都必须使用 MLA”，而是：为了从 DeepSeek-V3.1-Terminus 继续训练，DeepSeek-V3.2 **选择以 MLA 为基础实例化 DSA**；在 kernel（GPU 上执行一块具体计算的程序）层面，一个 key-value 条目需要被多个 query 共享，才能获得计算效率，于是实现采用 MLA 的 MQA 模式，让每个 latent 向量被当前 query 的多个 query 头共享。

为什么这个选择合理？这是把论文事实翻译成工程因果链：

1. **索引器的输入更窄**：它为当前 query 产生低维 $\mathbf q^I$，为历史 token 产生低维 $\mathbf k^I$，不必先展开每个完整多头 K、V。
2. **每个历史位置只有一个主要缓存入口**：MLA 把历史状态收成 latent $\mathbf c_s$，top-k 选中一个位置后，多个 query 头可以复用同一条 latent KV。
3. **低精度更容易发挥作用**：论文说明索引器可以用 FP8；小 head 数、低维 q/k 和一条共享的 latent 读取路径，让索引器的常数项更小。
4. **主注意力才真正变稀疏**：索引器返回位置集合 $S_t$，主注意力读取的是 $\{\mathbf c_s\mid s\in S_t\}$，而不是所有完整的历史 K、V。

因此，“DSA 必须建在 MLA 上”更准确的说法是：**DeepSeek-V3.2 的高效实现依赖 MLA 的共享 latent KV；这不是数学上的唯一可能架构，而是让索引、缓存和 kernel 共享对齐的一种关键工程选择。** 如果直接在 MHA 的完整、多头 K、V 上做同样的选择，稀疏选择本身仍然可以定义，但每个位置要处理的表示更宽、跨头重复读取更多，索引收益会被常数成本削弱。这一句是文章解释，不是论文声称的不可行性定理。

## 2. Lightning Indexer 怎样选 token

### 2.1 它不是第二个完整 Attention，而是一张便宜的相关性草图

**Lightning Indexer 只负责回答“哪些历史位置值得送进主注意力”，不负责生成最终输出。**

对当前 query 位置 $t$ 和一个历史位置 $s$，论文从隐藏状态 $\mathbf h_t$、$\mathbf h_s\in\mathbb R^d$ 出发，构造低维索引 query、索引 key 和 query 相关的头权重：

- $\mathbf q^I_{t,j}\in\mathbb R^{d^I}$：当前 query 在第 $j$ 个索引头上的低维向量；
- $\mathbf k^I_s\in\mathbb R^{d^I}$：历史 token 在索引空间中的低维向量；
- $H^I$：索引头数量，论文强调它较小，以换取速度；
- $w^I_{t,j}$：随当前 query 变化的第 $j$ 个头的权重，用来调节这一头的证据重要性；
- $d^I$：索引向量宽度，通常远小于主模型隐藏维度；
- 论文说明索引 q/k 可以用 FP8 表示，以减少索引打分的带宽和计算压力。

### 2.2 一行公式拆成四个动作

论文公式（1）是：

$$
I_{t,s}=\sum_{j=1}^{H^I} w^I_{t,j}\cdot \operatorname{ReLU}\left(\mathbf q^I_{t,j}\cdot\mathbf k^I_s\right)。
$$

这个式子不是把完整 Attention 再算一遍，而是把每个历史 token 压缩成一个可以排序的分数。按动作拆开：

1. **点积问相关性**：$\mathbf q^I_{t,j}\cdot\mathbf k^I_s$ 是一个数。若两个方向相近，点积偏大；若方向相反，点积偏小。
2. **ReLU 截掉负项**：$\operatorname{ReLU}(x)=\max(0,x)$。一个索引头给出的负相关不再继续拉低总分，硬件只需要做截断和乘加。
3. **$w^I_{t,j}$ 调整头的声音大小**：不同 query 可能依赖不同的索引头，$w^I_{t,j}$ 让当前 query 决定每个头的贡献比例。它不是一个固定的全局常数。
4. **对所有索引头求和**：把多条低维证据合成一个 $I_{t,s}$，然后才交给 top-k 排名。

> ⚠️ **一个容易说错的细节**：ReLU 不会自动把“所有未选中的 token”都变成 0。它只保证每个 head 的负点积贡献变成 0；如果一个 token 在某个 head 上是正相关，它的总分仍可能大于 0。真正让未入选 token 不参与主注意力、因而不读取对应 Value 的动作，是后面的 top-k 选择掩码。只有当某 token 在所有相关 head 上都给出非正点积，且权重取非负的示意条件成立时，它的 index score 才会变成 0。

这一区分也说明了 Lightning Indexer 的边界：**索引器仍要扫描历史索引 key 来产生分数；它省掉的是主注意力对未入选 latent KV 的读取和计算。**

### 2.3 最小矩阵走查：真的算一次 top-k

下面是文章构造的纸笔例子，不是论文的模型参数。为了看清 ReLU 和 top-k 的分工，设有两个索引头、二维索引向量：

$$
\mathbf q^I_{t,1}=[1,2],\qquad \mathbf q^I_{t,2}=[-1,1],\qquad w^I_{t,1}=1,\quad w^I_{t,2}=0.5。
$$

四个历史 token 的索引 key 为：

$$
\mathbf k^I_1=[1,0],\quad \mathbf k^I_2=[0,1],\quad \mathbf k^I_3=[1,-1],\quad \mathbf k^I_4=[2,1]。
$$

逐个位置算点积、ReLU 和最终分数：

| 历史位置 $s$ | $q_{t,1}^I\cdot k_s^I$ | $q_{t,2}^I\cdot k_s^I$ | ReLU 后 | $I_{t,s}=1\times a+0.5\times b$ |
|---:|---:|---:|---|---:|
| 1 | $1$ | $-1$ | $(1,0)$ | $1$ |
| 2 | $2$ | $1$ | $(2,1)$ | $2.5$ |
| 3 | $-1$ | $-2$ | $(0,0)$ | $0$ |
| 4 | $4$ | $-1$ | $(4,0)$ | $4$ |

现在令文章例子的 $k=2$：分数从大到小是位置 4、位置 2、位置 1、位置 3，所以：

$$
S_t=\{4,2\}。
$$

- 位置 3 因为两个 head 都是负点积，经过 ReLU 后分数为 0；
- 位置 1 分数为 1，仍然是正数，但因为它排在 top-2 之外，也不会被主注意力读取；
- 位置 2 和位置 4 才会把对应的 latent KV 条目送入主注意力。

这就是一张完整的“输入 → 输出”走查：输入是 $q^I$、$k^I$ 和 $w^I$，中间先做低维点积与截断，输出是被选中的位置集合，而不是最终隐藏状态。

### 2.4 top-k 之后，哪些 Value 真的被读？

论文把选中集合写成：

$$
\mathcal S_t=\left\{s\ \middle|\ I_{t,s}\in\operatorname{Top\mbox{-}k}(I_{t,:})\right\}。
$$

随后主注意力只接收这些位置的 latent KV：

$$
\mathbf u_t=\operatorname{Attn}\left(\mathbf h_t,\left\{\mathbf c_s\ \middle|\ s\in\mathcal S_t\right\}\right)。
$$

其中：

- $I_{t,:}$ 是当前 query 对所有历史位置的分数行；
- $\operatorname{Top\mbox{-}k}$ 取分数最大的 $k$ 个位置；
- $\mathcal S_t$ 是离散的选择集合；
- $\mathbf c_s$ 是 MLA 缓存的 latent KV 条目；
- $\mathbf u_t$ 是主注意力的输出。

如果历史有 128K 条、$k=2048$，按 $128\times1024$ 计算：

$$
\frac{L}{k}=\frac{131072}{2048}=64,\qquad Lk=131072\times2048=268\,435\,456。
$$

这表示主注意力每个 query 的候选条目从 131072 个变成 2048 个，位置对数量按结构口径减少 64 倍。它**不等于**端到端速度必然提升 64 倍，因为索引器仍要生成全历史分数，top-k 和稀疏 gather 也有额外开销。

## 3. 两阶段训练怎样把稀疏化训稳

### 3.1 为什么不能一上来就只看 top-k？

**因为一个刚初始化的 indexer 还不知道哪些位置重要；如果它一开始就随机挑走真正有用的历史信息，主模型看到的输入会立刻变坏。**

直接稀疏训练的因果链是：

1. 新 indexer 的分数没有对齐主注意力；
2. top-k 可能选中不相关 token，丢掉关键的 Value；
3. 离散选择没有平滑梯度，语言模型损失很难直接告诉 indexer“应该换哪一个位置”；
4. 主模型一边适应错误的上下文，一边承受不稳定的选择，训练容易出现损失抬升甚至崩溃。

这四步是根据论文给出的训练顺序、离散 top-k 和 detached 梯度路径做出的**文章解释**，不是论文中一句逐字的“直接训练必然崩溃”。论文真正报告的做法是先用 dense warm-up 初始化 indexer，再打开稀疏选择。

### 3.2 阶段一：Dense Warm-up，让 indexer 先学会模仿教师

论文从已经扩展到 128K 上下文的 DeepSeek-V3.1-Terminus checkpoint（训练过程中保存的模型参数快照）出发。第一阶段保留稠密注意力，冻结除 Lightning Indexer 以外的所有模型参数。

对第 $t$ 个 query，先把主注意力在所有 head 上的分数相加，再沿序列维度做 L1 归一化，得到教师分布 $p_{t,:}$。L1 归一化的白话是：把每个位置的非负分数除以所有位置分数之和，使整行加起来等于 1。

让 indexer 的分布接近教师分布，用 KL 散度训练：

$$
\mathcal L^I=\sum_t D_{\mathrm{KL}}\left(p_{t,:}\ \middle\|\ \operatorname{Softmax}(I_{t,:})\right)。
$$

直觉是左边 $p_{t,:}$ 是“稠密老师认为每个位置该得多少注意力”，右边是 indexer 根据 $I_{t,:}$ 给出的概率分布；损失就是让两张分布图尽量重合。

KL 散度逐项写作：

$$
D_{\mathrm{KL}}(p\|q)=\sum_s p_s\log\frac{p_s}{q_s}。
$$

- $p_s$ 是教师在位置 $s$ 上的目标概率；
- $q_s$ 是 indexer Softmax 后的概率；
- $p_s=0$ 的位置不贡献这一项；
- $q_s$ 越接近 $p_s$，KL 越小。

数值走一遍：若教师分布 $p=(0.75,0.25)$，indexer 分布 $q=(0.5,0.5)$，则：

$$
D_{\mathrm{KL}}(p\|q)=0.75\log(1.5)+0.25\log(0.5)\approx0.131\ \text{nat}。
$$

这个数值是文章算例，不是论文实验指标。论文的 warm-up 设置是：学习率 $10^{-3}$，训练 1000 steps，每步 16 条、每条 128K token，共报告约 2.1B tokens。按 $128K=128\times1024$ 验算：

$$
1000\times16\times(128\times1024)=2\,097\,152\,000\approx2.1\text{B}。
$$

### 3.3 阶段二：Sparse Training，让全模型适应选择模式

第二阶段才引入 fine-grained token selection。主模型与 indexer 都训练，但 indexer 的输入从主计算图中 detach，也就是切断从 indexer 输入回到主模型的梯度。

选中集合仍然是：

$$
\mathcal S_t=\left\{s\ \middle|\ I_{t,s}\in\operatorname{Top\mbox{-}k}(I_{t,:})\right\}。
$$

论文把 indexer 的 KL 对齐限制在已选集合上：

$$
\mathcal L^I=\sum_t D_{\mathrm{KL}}\left(p_{t,\mathcal S_t}\ \middle\|\ \operatorname{Softmax}(I_{t,\mathcal S_t})\right)。
$$

这里 $p_{t,\mathcal S_t}$ 表示只看选中位置的教师分布。为了把它作为 KL 的概率输入，理解时应把教师分布限制到 $\mathcal S_t$ 内并做集合内归一化；论文公式沿用这个简写，但没有在此处展开归一化实现。

这一阶段有两条互不混淆的训练路径：

- **Indexer 路径**：只用 $\mathcal L^I$ 更新 Lightning Indexer；
- **主模型路径**：只用语言模型损失更新主模型；
- **选择路径**：top-k 决定主注意力读取哪些 $\mathbf c_s$，但不把一个模糊的语言模型梯度硬传回离散选择器。

论文报告的 sparse training 设置是：学习率 $7.3\times10^{-6}$，每个 query 选择 2048 个 KV token，训练 15000 steps，每步 480 条、每条 128K token，共 943.7B tokens。按 $128K=128\times1024$ 验算：

$$
15000\times480\times(128\times1024)=943\,718\,400\,000\approx943.7\text{B}。
$$

### 3.4 detached indexer 与 STE：稳定性和上限怎么取舍？

先看为什么 top-k 让梯度麻烦。设分数是 $z=(0.9,0.8,0.1)$，$k=1$ 时选中第 1 项。把第 1 项从 0.9 改成 0.81，选择仍是第 1 项，前向输出没有变化；把第 2 项改成 0.95，选择突然跳到第 2 项。也就是说，top-k 在大多数小变化区间内像一个常数函数，跨过排序边界时又发生跳变。

- **Detached indexer**：前向照常 top-k；反向不让主模型的语言模型梯度穿过选择器。它牺牲“主模型直接告诉 indexer 哪次选错了”的路径，换取稳定、可拆开的两个优化目标。
- **STE**：Straight-Through Estimator，前向仍做离散 top-k，反向却用一个近似导数代替真实的 0 或跳变。它让端到端优化有机会，但这个梯度是有偏的，可能把并不存在的连续方向当成真实改进方向。

课程幻灯片把两者的取舍总结为：

| 维度 | Detached indexer | End-to-end / STE 类方案 |
|---|---|---|
| 能否感知 indexer 造成的错误 | 不能直接感知 | 可以 |
| 目标是否统一 | 否，indexer 用 KL，主模型用语言模型损失 | 理论上可以用统一语言模型损失 |
| 训练稳定性 | 高；离散梯度被隔离 | 低；离散梯度或 STE 可能不稳定 |
| 性能上限 | 受 indexer 质量限制 | 理论上更高，但依赖可靠的离散梯度 |

> 💡 **回顾：MoE 路由为什么是同一类难题**  
> MoE（Mixture of Experts，混合专家）先用 gate 给专家打分，再用 top-k 把一个 token 发给少数专家；若专家输出是 $E_i(x)$、路由权重是 $\alpha_i$，一个简化的输出写成 $y=\sum_{i\in\operatorname{Top\mbox{-}k}}\alpha_iE_i(x)$。top-k 一旦把路径变成离散选择，语言模型损失同样很难直接告诉 gate“换另一个专家”。站内 [3.12 参数扩 1000 倍但计算不变：MoE 的诞生（Shazeer 2017 Sparsely-Gated MoE 精读）](/AIInfraGuide/prerequisites/模块一-前置知识/transformer/312-moe-sparsely-gated-moe论文精读) 解释了 gate、noisy top-k、负载均衡和专家通信；本文只借它回顾离散路由的训练难题，DSA 的 indexer 与 MLA 细节在本文内独立讲完。

因此 DSA 的 detached 选择不是“忘了做端到端训练”，而是一个有意识的权衡：**先接受 indexer 作为瓶颈，换取可控的训练稳定性。**

## 4. 工程落地：prefill、decode 与 FlashAttention

### 4.1 为什么主要是 decode 获益？

**Prefill 更像一次大矩阵计算，decode 更像每一步都去历史仓库取货。**

- **Prefill**：整段输入同时进入模型，多个 query 可以组成规则的大矩阵。短上下文时，完整稠密 kernel 的硬件利用率可能比“先索引、再不规则 gather”更好。
- **Decode**：每一步通常只生成一个新 token。这个 query 的计算量很小，却要访问从开头到当前末尾的全部历史 latent KV；当 $L$ 变长时，跳过未入选条目的 Value 读取更有价值。

本文的部署默认分工是：**prefill 仍优先走稠密或等价的高吞吐路径，decode 才走 indexer + top-k + 稀疏主注意力。** 这不是说 DSA 在数学上不能处理 prefill。论文 §2.3 明确说明：对短序列 prefilling，作者专门实现了 masked MHA 模式来模拟 DSA，在短上下文条件下可以获得更高效率。因此，Figure 3 的 prefill 曲线不能被误读成“所有 prefill 都使用和 decode 完全相同的稀疏 kernel”。

### 4.2 DSA 和 FlashAttention：一条改模型，一条改读法

> 💡 **回顾：FlashAttention 是什么**  
> FlashAttention 是精确的稠密注意力实现：它不改变 $L\times L$ 的数学配对，而是把 Q、K、V 切成小块，用片上高速存储和 Online Softmax 减少显存往返，并避免把完整的 $L\times L$ 分数矩阵长期写回显存。站内 [第 6 章 Attention 算子](/AIInfraGuide/cuda/模块二-cuda编程与算子优化/第6章-attention算子) 汇总了 FlashAttention V1、V2、V3 的 IO 优化与硬件递进；它讲的是“稠密计算怎样搬得更少”，本文讲的是“DSA 怎样少算一部分位置”，两者不是同一个优化层次。

| 路线 | 是否改变模型注意力模式 | 是否减少数学上的位置对 | 主要省什么 | 主要代价 |
|---|---|---|---|---|
| **FlashAttention V1–V3** | 否，仍是精确稠密注意力 | 否，仍是 $L^2$ | 显存读写、分数矩阵物化和 kernel 调度 | 需要按硬件设计 tile、规约和流水线 |
| **DSA** | 是，训练后模型依赖动态 top-k | 是，主注意力从 $L$ 变为 $k$ | 主注意力的 Value 读取与相关性计算 | 仍要跑 indexer，且有 top-k、稀疏 gather 和训练适配 |

📌 **关键点**：FlashAttention 是“同样的问题，搬运得更聪明”；DSA 是“让主注意力少处理一些问题”。前者通常可以作为普通 Attention 的 kernel 替换，后者绑定模型结构和训练配方；工程上甚至可以把 DSA 选择出的稀疏块交给专门的稀疏 kernel，但不能把两者的收益数字直接相加。

这篇文章也把站内 Attention 线从“FlashAttention V1–V3 的精确稠密 IO 优化”补到“DSA 的模型原生稀疏选择”：读者现在可以沿着“减少显存搬运”和“减少参与计算的 token”两条路线分别判断瓶颈。

### 4.3 代价账：DSA 不是把所有复杂度都抹掉

把收益和代价放在同一张账上：

- **换来的东西**：主注意力每个 query 只处理 $k$ 个 latent KV，长上下文 decode 的 Value 读取和主注意力计算减少。
- **付出的东西**：indexer 仍要给全部历史位置打分；top-k 需要排序或选择；选中后是稀疏 gather，不一定像稠密矩阵乘法那样规则。
- **质量上的约束**：indexer 选错位置会直接改变主模型看到的上下文，所以需要 dense warm-up 和 sparse training，不能只在推理引擎里临时加一个 top-k 开关。
- **模型绑定**：DSA 是 DeepSeek-V3.2 的模型原生结构。把一个普通 MHA 模型直接接上同名开关，不会自动得到训练过的 indexer 和匹配的 latent KV。

落成一句话的选型规则：

- **瓶颈是普通模型的显存读写**：先考虑 FlashAttention 一族，它不改模型输出定义。
- **瓶颈是 MLA 模型长上下文 decode 的主注意力计算**：考虑 DSA，先确认 checkpoint、indexer、top-k kernel 和训练配方是一套。
- **瓶颈是 KV Cache 容量本身**：DSA 不能替代 MLA、GQA、量化或分页缓存，因为它没有把持久 latent KV 的 $O(Ld_{\mathrm{lat}})$ 宽度再变小。

### 4.4 TRT-LLM 的开关应该放在哪里理解？

站内 [12.5 并行、量化与高级特性 §8 稀疏注意力](/AIInfraGuide/inference/模块四-推理优化/第12章-tensorrt推理引擎/125-并行量化与高级特性#8-稀疏注意力长上下文的三条省力路线) 列出了 TensorRT-LLM 中 RocketKV、DSA、Skip Softmax Attention（BLASST）三条稀疏路线，并说明 DSA 通过 `index_topk` 保留指定数量的 KV 条目；它讲的是部署时有哪些开关、各路线是否模型原生以及缓存/计算取舍，本文则负责解释论文中的 indexer、训练和复杂度来源。

因此，看到 `index_topk=2048` 时要同时问三个问题：

1. 当前 checkpoint 是否真的包含 DSA indexer 和 MLA latent KV；
2. 当前 backend 是否实现了与训练时一致的 top-k、mask 和 sparse attention；
3. 目标负载是长上下文 decode，还是短 prompt prefill、缓存容量或普通稠密模型。

只打开一个参数而不核对这三件事，得到的可能只是一个名称相同、数据流不同的配置。

### 5.2 Figure 3 的“加速”为什么要谨慎说？

论文 §2.3 说 Figure 3 的成本来自部署在 H800 GPU 集群上的实际服务 benchmark，并以每张 GPU 每小时 2 美元的租赁价格估算。图的横轴是 token position，纵轴是每百万 token 的成本；它比较的是 DeepSeek-V3.1-Terminus 与 DeepSeek-V3.2，而不是一个脱离模型、硬件、服务实现的纯 Attention kernel 微基准。

所以可以说：

- **论文实测口径**：长上下文服务中，DSA 版本的成本曲线明显低于 MLA 基线；
- **图上读数**：在 128K decode 端点约为 2.15 美元对 0.25 美元/百万 token，约 8.6 倍成本差；
- **不能推出**：每个模型、每张 GPU、每个 batch、每个短上下文请求都能获得 8.6 倍延迟加速。

这也是为什么本文把“加速”拆成“主注意力位置对减少”“服务成本下降”“端到端延迟”三个词：它们相关，但不是同一个测量量。

## 📝 总结

1. **先分清两笔账**：MQA、GQA、MLA 主要减少 KV Cache 的头数或表示宽度；它们仍然让每个 query 面对稠密的 $L\times L$ 位置关系。
2. **DSA 的核心动作**：在 MLA latent KV 之上，用小 head、低维 q/k、FP8 的 Lightning Indexer 给历史位置打分，top-k 选出 $S_t$，主注意力只读取 $\{\mathbf c_s\mid s\in S_t\}$。
3. **复杂度要带限定**：主注意力从 $O(L^2)$ 变成 $O(Lk)$，但 indexer 仍是全历史打分；DSA 减少的是主注意力读取与计算，不是持久 KV Cache 宽度。
4. **训练顺序不是装饰**：先用稠密主注意力和 KL 分布对齐初始化 indexer，再打开 top-k，并用 detached 的两条损失路径分别训练 indexer 与主模型。
5. **工程选择看瓶颈**：FlashAttention 让稠密注意力搬得更少，DSA 让主注意力少看一些 token；prefill 与 decode、缓存容量与计算时间，必须分开测量。
